# Velexis Guidebook — content and code contract (binding for every change to the guidebook)

The guidebook is a static, highly interactive HTML site that lives in its own folder, `guidebook/` at the repository
root.
Its reader is the owner, who will walk through every application to find bugs (UI bugs, wrong data, DB fixes). So
every page must answer: what is this, how do I use it, what should happen, where is the code, which tables change.

Principles: concise but thorough; accurate to the CODE at the commit named in `site.json` (`a68a8cd8`; code beats
docs when they disagree; say so); modular (one concern per file, content separate from code, adding an app = adding a
folder); no secrets (development seed passwords that are already committed in the repo may be quoted, marked
"development only"); placeholder hosts only (`*.example.com`, `localhost` for local development).

## 1. Folder layout

```
guidebook/
  index.html                 shell: loads vendor libs (CDN, pinned, SRI), assets/css, assets/js/**, dist/content.js
  README.md                  how to open, update, build, test; folder map; how to add an app/term/diagram
  SCHEMA.md                  this contract
  assets/css/guide.css       all styles; CSS custom properties; light + dark themes; responsive (>= 360 px)
  assets/js/core/*.js        classic scripts (NO ES modules for local files: the site must work from file://)
  assets/js/views/*.js       one file per view, registered with VG.views.register(...)
  assets/js/widgets/*.js     one file per diagram type, registered with VG.widgets.register(...)
  content/site.json          title, tagline, repoBase, nav order, app order, version/date
  content/pages/*.md         system-level pages (overview, getting-started, concepts, ...)
  content/apps/<appId>/app.json            facts card (see §3)
  content/apps/<appId>/usage.md            usage guide (see §4)
  content/apps/<appId>/architecture.md     architecture guide (see §5)
  content/apps/<appId>/diagrams/<id>.json  diagrams referenced from that app's markdown (see §6)
  content/journeys/<id>.json               cross-app end-to-end walkthroughs (see §7)
  content/glossary/*.json                  glossary (see §8; usually terms.json)
  content/taxonomy/taxonomy.json           taxonomy tree (see §9; one file)
  content/ontology/*.json                  ontology (see §10; usually ontology.json)
  content/graph/*.json                     extra knowledge-graph triples (see §11; usually relations.json)
  content/issues/*.json                    known issues: verified bugs, the owner's backlog (see §14)
  content/system/topology.json             home map and System 3D (see §13; one file)
  dist/content.js            GENERATED by tools/build.mjs: `window.VG_CONTENT = {...}`; committed so file:// works
  tools/build.mjs            zero-dependency Node 24 script: reads content/, validates, writes dist/content.js
  tools/serve.mjs            zero-dependency static server (optional; `node guidebook/tools/serve.mjs` → http://127.0.0.1:4173)
  tools/guidebook.test.mjs   node:test: build is reproducible, dist is up to date, every reference resolves
```

App ids (folder names, fixed): `platform-api` (platform/backend), `portal` (platform/frontend), `platform-admin`
(platform/admin), `ota-api` (ota/backend), `ota-admin` (ota/admin), `storefront` (ota/frontend), `sdk` (ota/sdk),
`packages` (packages/* and tools/*), `deploy` (deploy/*, the single VM, Caddy, systemd, backups, monitoring).
`tools` is not a folder: `site.json` maps it to `packages` (`"appAliases": { "tools": "packages" }`). The builder and
the site resolve an alias wherever an app id is accepted: `[[app:tools]]`, `#/app/tools/...`, journey and step apps,
term, taxonomy and individual apps, `dependsOn` / `talksTo`, diagram and topology nodes, relations and known issues.

Folders merged by the builder: every `*.json` in `content/glossary`, `content/ontology`, `content/graph` and
`content/issues` is read in name order and merged (ids must stay unique across files). `taxonomy/taxonomy.json` and
`system/topology.json` are single files.

Repository root: `tools/build.mjs` checks every repo path (`repo:` links, `repoPath`, `docs`, `adrs`, screen and
journey-step `code`, glossary `see`, issue `where`, `files` and `newFiles`) against the repository. Without `--repo`
it uses the guidebook's parent folder (`guidebook/` at the repository root), else its grandparent, whichever holds
`pnpm-workspace.yaml`. `--repo <dir>` names the root (an error when it has no `pnpm-workspace.yaml`); `--repo none`
turns the check off. Without a root the paths are not checked and one warning says so. The bundle is the same with or
without the root (`stats.repoPaths` counts the paths, checked or not).

## 2. Markdown dialect (rendered with marked + DOMPurify)

Every `.md` starts with front matter (only `key: value` scalars and `key: [a, b]` lists):

```
---
id: usage            (pages: unique page id; apps: usage | architecture)
title: Portal — usage guide
summary: One sentence shown in cards and search results.
order: 10            (pages only: nav order)
---
```

Extensions (the renderer implements them; writers use them):
- `[[term-id]]` or `[[term-id|shown text]]` → glossary link with hover card. term-id = kebab-case id from §8.
- `[[app:portal]]`, `[[page:getting-started]]`, `[[journey:book-a-flight]]`, `[[diagram:portal/signup-flow]]` → internal links.
- `` `repo:platform/backend/src/auth/auth.controller.ts` `` (inline code starting with `repo:`) → link to the file
  (repoBase from site.json + path; `#L10` allowed). Use real paths only (check they exist).
- Fenced block ```` ```diagram ```` whose body is one diagram id (`signup-flow` = this app's diagram, or
  `ota-api/booking-states` = another app's) → embeds that interactive diagram.
- Fenced blocks ```` ```tip ````, ```` ```note ````, ```` ```warning ````, ```` ```bug-hunt ```` (things worth testing,
  likely edge cases) → styled callouts; their body is markdown.
- Fenced block ```` ```try ```` → a "try it" card: lines `url: …`, `login: …`, `password: …`, `command: …`, `expect: …`
  (each optional, any order; values are copyable).
- Tables, headings (`##` sections become the page's table of contents), code blocks as usual.

## 3. app.json

```json
{
  "id": "portal",
  "name": "Portal",
  "kind": "frontend | backend | worker | library | tooling | infrastructure",
  "product": "platform | ota | shared",
  "summary": "One sentence.",
  "audience": ["OTA owner", "..."],
  "repoPath": "platform/frontend",
  "package": "@velexis/platform-frontend",
  "stack": ["Next.js 15 App Router", "React 19", "..."],
  "local": { "url": "http://localhost:3000", "port": 3000, "command": "pnpm --filter @velexis/platform-frontend dev", "notes": "..." },
  "production": { "host": "platform.example.com" },
  "dependsOn": ["platform-api"],
  "talksTo": [{ "app": "platform-api", "how": "HTTPS, server side (BFF)" }],
  "data": ["platform.accounts", "..."],
  "docs": ["platform/docs/architecture.md", "..."],
  "adrs": ["docs/mvp/adr/0014-....md"],
  "roles": [{ "name": "OTA owner", "can": "..." }],
  "screens": [{ "route": "/sign-up", "title": "Sign up", "purpose": "...", "code": "platform/frontend/src/app/(public)/sign-up/page.tsx" }],
  "endpoints": [{ "method": "POST", "path": "/v1/...", "operationId": "...", "purpose": "..." }],
  "tags": ["..."]
}
```
`screens` for UIs (every route that exists), `endpoints` for APIs (group by tag; at least every operation a UI uses;
the full list where practical), both optional for libraries. Keep each string short.

## 4. usage.md (per app) — sections in this order (skip what does not apply)
1. `## What it is` — purpose, who uses it, where it sits (one `diagram` of its neighbours is welcome).
2. `## Before you start` — how to run it locally (exact commands), URL, seeded accounts (dev only), prerequisites
   (other apps that must run), a ```try``` card.
3. `## Tour` — every screen/area: route, what it shows, what to try, what should happen (tables are good).
4. `## How to …` — task walkthroughs (numbered steps; a `flow` diagram for the main ones), with expected results.
5. `## Roles and permissions` — who can do what; what a forbidden action should look like.
6. `## Bug-hunting checklist` — ```bug-hunt``` callouts: validations, edge cases, error states, money/time zones,
   tenancy isolation, emails (Mailpit), queues, what to check in the DB (`psql` queries on real table names).
7. `## Troubleshooting` — common failures and fixes.

## 5. architecture.md (per app) — sections in this order (skip what does not apply)
1. `## At a glance` — stack, entry points (main.ts, worker.ts, app dir), port, build/test commands.
2. `## Components` — modules/folders and their jobs (a `component` diagram).
3. `## Data` — tables/schemas it reads and writes (an `er` diagram), tenancy (platform schema vs tenant schemas,
   `tenantTx`), Redis keys, queues.
4. `## Key flows` — `sequence` diagrams of the important request paths.
5. `## Lifecycles` — `state` diagrams (e.g. OTA status, booking status, payment status) where they exist.
6. `## Integrations` — Stripe, Amadeus, SMTP, other apps; contracts (OpenAPI files).
7. `## Security` — authentication, sessions/tokens, CSRF, rate limits, secrets, PCI scope.
8. `## Configuration` — key environment variables (names, purpose; never values of secrets).
9. `## Testing` — unit, integration, e2e: where, how to run one.
10. `## Where to change things` — table: "to change X → look at `repo:...`". This is the bug-fixer's map.
11. `## Further reading` — repo docs and ADRs (`repo:` links).

## 6. Diagram JSON (content/apps/<appId>/diagrams/<id>.json); `id` = file name without .json
All: `{ "id", "type", "title", "caption" }` plus per type:
- `component`: `groups: [{id,label}]`, `nodes: [{id,label,group,kind:"ui|api|worker|db|cache|queue|external|lib|user|edge",detail,app?,term?}]`,
  `edges: [{from,to,label,kind:"sync|async|data"}]`
- `sequence`: `actors: [{id,label,kind}]`, `steps: [{from,to,label,kind:"call|return|async|self",note?}]`
- `state`: `states: [{id,label,kind:"initial|normal|final|error",detail?}]`, `transitions: [{from,to,label}]`
- `er`: `entities: [{id,label,schema:"platform|tenant|reference|redis",fields:[{name,type,key?:"pk|fk|uk"}]}]`,
  `relations: [{from,to,label,cardinality:"1-1|1-n|n-n"}]` (use real table and column names)
- `flow`: `steps: [{title, actor?, screen?, url?, body (markdown), expect? (markdown)}]` (an interactive stepper)
- `tree`: `root: {name, children:[...], term?, detail?}`
Node/actor/entity ids are local to the diagram. `detail` fields are short markdown shown on click.

## 7. Journey JSON (content/journeys/<id>.json)
`{ "id", "title", "summary", "apps": [appIds], "roles": [...], "duration": "15 min", "prerequisites": [md...],
   "steps": [{ "id", "app", "title", "url"?, "actions" (md), "expect" (md), "data"? (md: tables/emails/queues to check),
   "code"? ["repo paths"] }] }`
The site renders a checklist with per-step status (pass / bug / skipped) kept in localStorage, and a "copy bug
report" button that formats journey, step, expected and a blank "actual".

## 8. glossary/terms.json
`[{ "id": "tenant-schema", "term": "Tenant schema", "aliases": ["tenant_<key>"], "category": "<one of: product,
   travel, payments, identity, tenancy, data, api, security, operations, engineering, process>",
   "definition": "markdown, 1–3 sentences", "apps": [appIds], "related": [term ids], "see": ["repo path or page id"],
   "classOf": "ontology class id (optional)" }]`
Ids unique, kebab-case; every `related` id must exist. A `see` entry is a page id when such a page exists; otherwise
it is a repo path when it contains `/` or `.` (checked against the repository root); anything else is an error.

## 9. taxonomy/taxonomy.json
`{ "id": "velexis", "label": "Velexis", "children": [ { "id", "label", "description"?, "children"?: [...], "terms"?: [term ids], "apps"?: [appIds] } ] }`
A classification of the whole system (products → domains → capabilities → concepts). Every glossary term appears in
at least one node's `terms`.

## 10. ontology/ontology.json
`{ "classes": [{ "id": "Tenant", "label", "parent"?: class id, "description", "examples"?: [..] }],
   "properties": [{ "id": "ownsTenant", "label", "domain": class id, "range": class id, "cardinality"?: "1|0..1|0..n|1..n", "description", "inverse"?: property id }],
   "individuals": [{ "id", "label", "class": class id, "app"?: appId, "term"?: term id }],
   "assertions": [{ "subject": individual id, "property": property id, "object": individual id }] }`
Class ids PascalCase, property ids camelCase, individual ids kebab-case.

## 11. graph/relations.json
`[{ "from": "<kind>:<id>", "to": "<kind>:<id>", "label": "uses", "note"? }]` with kind ∈ app, term, class,
individual, page, journey, issue. tools/build.mjs assembles the knowledge graph from: apps (dependsOn/talksTo),
glossary (apps, related, classOf), ontology (subclass, property domain/range, assertions), journeys (apps), known
issues (app "affects", journey "seen in", terms "about") and these extra triples. The graph view starts with the Issue
chip off, and, in a graph of more than 600 nodes, the Individual chip off too; `#/graph?focus=issue:<id>` (or
`individual:<id>`) turns that kind on.

## 14. content/issues/*.json (known issues)
Each file is an array of issues; the builder merges every file (like the glossary). One issue:

```json
{
  "id": "KI-007",
  "title": "No not-found or error page: Next.js defaults without the portal shell",
  "app": "portal",
  "severity": "critical | high | medium | low",
  "kind": "bug | db | security | ux | docs | perf",
  "status": "confirmed | plausible",
  "where": ["platform/frontend/src/lib/tenant.ts:76-83", "tools/e2e/specs/portal-team.e2e.ts:256"],
  "summary": "markdown: what is wrong and why it matters",
  "reproduce": ["markdown: one step per entry"],
  "expected": "markdown",
  "actual": "markdown",
  "fix": "markdown: the change, concrete enough to become a task",
  "files": ["repo paths to change (no line numbers)"],
  "newFiles": ["repo paths to create (optional)"],
  "migration": false,
  "journey": "team-and-console-sso",
  "step": "remove",
  "terms": ["portal"]
}
```
- `id`: `KI-` and three or more digits, unique across files, never reused or renumbered (tasks refer to it). New issues
  take the next free number; the first list was numbered by severity, then app (site.json order).
- `app`: an app id or an alias of `site.json` (stored resolved). `journey` and `step` (optional; `step` needs
  `journey`) must exist; `terms` (optional) must be glossary ids.
- `where`: the evidence, repo paths with an optional `:line` or `:start-end`; `files`: what to change. With a repository
  root the builder checks that each path exists and each line is inside its file; a `newFiles` entry must not exist yet
  (a warning once it does: move it to `files`, or remove the fixed issue) and its folder must exist.
- `migration`: true only when the fix needs a database migration (a schema or data change shipped as a migration).
- Markdown fields use the dialect of §2 (`[[term]]` links count as backlinks; `#/…` links are checked).
- Plain English, short sentences; development credentials only when committed, marked "development only";
  placeholder hosts only. Errors name the file and the issue id (`issues/issues.json:KI-007: unknown app "x"`).
- The bundle carries `issues` (sorted by id), stats (`issues`, `issuesBySeverity`, `issuesByKind`, `issuesByStatus`,
  `issuesByApp`), one search entry per issue (kind `issue`) and graph nodes `issue:<id>`. Views: `#/issues` (filters
  `app`, `severity`, `kind`, `status`, comma-separated values; `q`, `journey`, `step`, `sort`, `open`) and
  `#/issue/<id>`; the app tabs, the journey steps and the glossary link to them.
