# `@velexis/api-types`

The API contract package of Velexis ([ADR-0006](../../docs/mvp/adr/0006-contract-first-openapi.md)). It holds the TypeScript types generated from the two OpenAPI documents, the operations index used by the parity tests, the contracts of the cross-backend queue messages and cache invalidation events with their validators and shared fixtures, and the Redocly lint of the documents. The documents are the source of truth; this package never defines a request or response shape by hand.

Related: [`packages/README.md`](../README.md#velexisapi-types) (public API sketch), [`ota/backend/openapi/README.md`](../../ota/backend/openapi/README.md) (how to change the OTA document), [`AGENTS.md` §6](../../AGENTS.md#6-contract-first) (contract first), [`tech-stack.md`](../../docs/mvp/tech-stack.md) §2.

## What is generated, and from where

Generated files are committed, start with `// Generated by scripts/generate.mjs — do not edit`, and are deterministic. CI runs the generator again and fails on any diff. Nothing under `src/generated/` is edited by hand: change the document, then regenerate.

| Import | Source | Generator | Output |
|---|---|---|---|
| `@velexis/api-types` (OTA: `paths`, `components`, `operations`, `$defs`, `webhooks`) | [`ota/backend/openapi/velexis-ota-booking-api.openapi.yaml`](../../ota/backend/openapi/velexis-ota-booking-api.openapi.yaml) | `openapi-typescript` 7 | `src/generated/ota.ts`, re-exported by `src/index.ts` |
| `@velexis/api-types/platform` (the same names) | `platform/backend/openapi/velexis-platform-api.openapi.yaml` (created by the platform plan in M1) | `openapi-typescript` 7; an empty placeholder until the document exists | `src/generated/platform.ts`, re-exported by `src/platform.ts` |
| `@velexis/api-types/operations` | both documents | `scripts/generate.mjs` (`yaml` 2): `operationId`, method, path, `x-sdk-method`, `x-scope`, tags, `x-internal`, `x-milestone`, `x-edge-only`, `x-permission` | `src/generated/operations.ts` (entries and their `ApiOperation` type), re-exported by `src/operations.ts` |
| `@velexis/api-types/jobs` | hand-written in `src/jobs/` | none: queue names, types, JSON Schemas and Ajv validators of the queue messages and invalidation events ([ADR-0009](../../docs/mvp/adr/0009-background-jobs-bullmq.md)) | — |
| `@velexis/api-types/fixtures/jobs/*.json` | hand-written in `fixtures/jobs/` | none: one valid message per file, shared by both backends' tests | — |

The SDK contract in [`docs/velexis-sdk/sdk/src/`](../../docs/velexis-sdk/sdk/src/) imports `@velexis/api-types` by that name, which is why the package is not called `@velexis/contracts`:

```ts
import type { paths, components, operations } from "@velexis/api-types"; // OTA booking API
import type { components as PlatformComponents } from "@velexis/api-types/platform";
import { otaOperations, platformOperations, type OtaOperationId } from "@velexis/api-types/operations";
import { JOB_ENVELOPE_SCHEMA, jobMessageSchema, type JobEnvelope } from "@velexis/api-types/jobs";

type Money = components["schemas"]["Money"]; // a misspelt schema name does not compile
type Booking = paths["/v1/bookings/{bookingId}"]["get"]; // the same type as operations["getBooking"]
```

Like the other packages, it builds with `tsc -b` to `dist/` (CommonJS and `.d.ts`), and the `exports` map lists `.`, `./platform`, `./operations` and `./jobs`. Apps import the built package; build it (`pnpm build`, or `pnpm --filter @velexis/api-types build`) before typechecking a consumer. The type modules compile to empty files and the operations index is plain data. Only `./jobs` has runtime dependencies: `validateJob` and `validateInvalidation` compile the schemas with `ajv` and `ajv-formats`, which are therefore `dependencies` ([Dependencies](#dependencies)).

```bash
REDOCLY_TELEMETRY=off REDOCLY_SUPPRESS_UPDATE_NOTICE=true \

```

## `contracts:lint`

`node scripts/contracts-lint.mjs [--config <redocly.yaml>]` is step 2 of the contract workflow ([ADR-0006](../../docs/mvp/adr/0006-contract-first-openapi.md), Workflow): run it after every change to a document, before `pnpm contracts:generate`.

1. It reads the `apis` of [`redocly.yaml`](redocly.yaml): `ota` and `platform`, with their document paths relative to that file.
2. Every document that exists is linted, in one Redocly CLI run, with the rules of `redocly.yaml` and the `stylish` output (one line per problem: `line:column severity rule message`).
3. The **platform** document does not exist until the platform plan creates it in M1 (PBE-005). Until then the script prints `contracts:lint: skipped "platform": … does not exist yet; the platform plan creates it in M1 (ADR-0006).` and goes on. Once the file exists it is linted with no change here. Any other missing document (the OTA one) fails the run.
4. It exits 1 on any lint **error**, on a `redocly.yaml` that Redocly rejects (`--lint-config error`, so a misspelt rule name fails instead of being ignored), and when a `.redocly.lint-ignore.yaml` sits next to the config. Warnings are printed and do not fail the run.
5. Redocly CLI 1.x would otherwise send usage telemetry and check the npm registry for a newer version. The script sets `REDOCLY_TELEMETRY=off` and `REDOCLY_SUPPRESS_UPDATE_NOTICE=true` for the Redocly process, and `redocly.yaml` also says `telemetry: off`, so a lint never calls the network.

`--config` lints another copy of the repository layout (`<root>/packages/api-types/redocly.yaml` with the documents at their repository paths); the tests use it to lint broken copies without touching the real documents.

### The rules

[`redocly.yaml`](redocly.yaml) extends Redocly's `recommended` ruleset and sets:

| Rule | Severity | Why |
|---|---|---|
| `operation-operationId-unique` | error | Route parity, the operations index and the SDK route table are keyed by `operationId` |
| `no-unused-components` | warn | The documents keep shared schemas that no operation references yet |

The vendor extensions (`x-sdk-method`, `x-scope`, `x-amadeus`, the table extensions, `x-error-codes`, `x-error-catalogue`, `x-tagGroups`, `x-examples` and the others listed in [`ota/backend/openapi/README.md`](../../ota/backend/openapi/README.md) §2, plus the planned `x-internal`, `x-edge-only`, `x-sensitive`, `x-milestone`, `x-permission` and `x-sdk-exclude`) are allowed: OpenAPI 3.1 permits `x-*` keys wherever they are used, and the `struct` rule of `recommended` accepts them. No rule may reject them.

The copied OTA document lints with **0 errors and 10 warnings**: nine `no-unused-components` (six `Amadeus*` schemas carried over from [`docs/amadeus-api/`](../../docs/amadeus-api/): the four error shapes, `AmadeusFlightFilters` and `AmadeusFlightOfferPricingIn`; plus `TravelerFieldErrorCode`, `ConsoleApiKeyScope` and `ConsoleBookingTimeoutDetails`) and one `no-server-example.com` (the `http://localhost:4000` server). Fix a warning in the document when a task touches that part anyway; never silence it.

A problem is fixed in the document. Tightening a rule is a normal change; relaxing one, skipping one (`--skip-rule`) or adding an ignore file needs an ADR first ([`AGENTS.md` §7](../../AGENTS.md#7-tests-are-never-weakened)).

### Tests

[`src/contracts-lint.test.ts`](src/contracts-lint.test.ts) runs the script as a child process:

- `[X-007 AC1]` the OTA document of the repository lints with zero errors, and no problem concerns an `x-*` extension;
- `[X-007 AC2]` without a platform document the lint passes and prints the skip notice;
- `[X-007 AC3]` a copy of the OTA document whose second operation repeats the first `operationId` fails with `operation-operationId-unique`;
- a platform document is linted once it exists, and its errors fail the run; a missing OTA document, an ignore file, a misspelt rule in the config, a config without APIs and an unknown option fail it too.

Apart from AC1, the documents live in a scratch copy of the repository layout with a verbatim copy of `redocly.yaml`, in the system temporary folder, removed after the run. The two tests on the full OTA document take about five seconds each.

AC1 reads the documents outside this package, so `turbo.json` gives this package's `test` task its own inputs (`@velexis/api-types#test`): the generic ones plus both `openapi/` folders. A changed document therefore reruns these tests in `pnpm test` (locally and in CI, which restores the Turborepo cache) instead of replaying a cached pass.

## `contracts:generate`

`node scripts/generate.mjs [--config <redocly.yaml>] [--out <dir>]` is step 3 of the contract workflow ([ADR-0006](../../docs/mvp/adr/0006-contract-first-openapi.md), Workflow).

1. It reads the `ota` and `platform` documents from the `apis` of [`redocly.yaml`](redocly.yaml), the same file `contracts:lint` reads, so both commands always see the same documents.
2. It parses each existing document with `yaml` and builds the operations index (below). It fails, and writes nothing, on an operation without `operationId`, an `operationId` used twice in one document, a path item `$ref`, `tags` that are not a list of strings, an `x-internal` or `x-edge-only` that is not a boolean, an `x-sdk-method`, `x-scope` or `x-permission` that is not a non-empty string, or an `x-milestone` other than `M0` … `M6` and `deferred`. Only a missing key counts as absent: a key without a value (`x-internal:`, `x-edge-only:` or `tags:`, YAML `null`) fails too, so an internal or edge-only operation is never indexed as public by accident.
3. It runs `openapi-typescript` 7 through its Node API (`openapiTS` and `astToString`, default options) on the OTA document and writes `src/generated/ota.ts`.
4. The **platform** document does not exist until the platform plan creates it in M1 (PBE-005). Until then the script prints `contracts:generate: "platform": … does not exist yet; the platform plan creates it in M1 (ADR-0006). Writing the empty placeholder.` and writes `src/generated/platform.ts` with the names `openapi-typescript` writes, all empty: `interface paths {}`, `interface components {}`, `interface operations {}`, and `webhooks` and `$defs` as `Record<string, never>`. Once the document exists, the next run replaces the placeholder with its types; nothing else changes. A missing OTA document fails the run.
5. It writes `src/generated/operations.ts`, and rewrites a file only when its content changed (`wrote` or `unchanged` per file).

Every generated file starts with `// Generated by scripts/generate.mjs — do not edit` and a `// Source:` line with the document's repository path. The output is **deterministic**: no timestamps, no absolute paths, operations in document order, and the same `openapi-typescript` and TypeScript versions (exact pins). Prettier and ESLint skip `src/generated/` ([`.prettierignore`](../../.prettierignore), [`eslint.config.mjs`](../../eslint.config.mjs)), so the committed files are byte for byte the generator's output.

`--config` generates from another copy of the repository layout (`<root>/packages/api-types/redocly.yaml` with the documents at their repository paths) and `--out` writes elsewhere than `src/generated/`; the tests use both, so they never touch the committed files.

Why the generated OTA types differ from the SDK contract's [`api-types.d.ts`](../../docs/velexis-sdk/sdk/src/api-types.d.ts): that file was generated by an earlier `openapi-typescript` release that did not copy `example` values into the JSDoc. The types are the same; the tests compare schema names, never the files.

## The operations index (`@velexis/api-types/operations`)

```ts
import { otaOperations, platformOperations, type ApiOperation } from "@velexis/api-types/operations";

otaOperations[0];
// { operationId: "getStorefront", method: "get", path: "/v1/storefront", sdkMethod: "storefront.get",
//   scope: "both", tags: ["Storefront"], internal: false, milestone: "M2", edgeOnly: false, permission: null }
```

- `otaOperations` and `platformOperations` are frozen arrays (entries and tags frozen too) of `ApiOperation`: `operationId`, `method` (lower case, as in `paths`), `path` (the path template), `sdkMethod` (`x-sdk-method` or `null`), `scope` (`x-scope` or `null`), `tags`, `internal` (`x-internal: true`), `milestone` (`x-milestone`: `"M0"` … `"M6"`, `"deferred"`, or `null`), `edgeOnly` (`x-edge-only: true`) and `permission` (`x-permission` or `null`). The vendor extensions are described in the OTA document's `info.description` ([`ota/docs/api-changes.md`](../../ota/docs/api-changes.md) §1).
- Entries follow the document: paths in document order, and per path the methods in the order `get`, `put`, `post`, `delete`, `options`, `head`, `patch`, `trace`.
- `operationId` is typed: `OtaOperationId` is `keyof operations` of the OTA types, `PlatformOperationId` the same for the platform types (`never` until the document exists). A misspelt id in a route decorator or a pending-operations list does not compile.
- Route-parity tests compare it with the bound routes, SDK-parity tests and the SDK route table with the SDK methods ([ADR-0006](../../docs/mvp/adr/0006-contract-first-openapi.md), Checks in CI); the OTA backend's pending-operations list follows `milestone`, and its scope guard reads `scope`, `edgeOnly` and `permission`.
- The fields come from one table in the generator, `INDEX_FIELDS` (name, TypeScript type, JSDoc, how the value is read). The generator writes both the entries and the `ApiOperation` interface from it, so a new field is one row there and nothing else: OBE-009 added `milestone`, `edgeOnly` and `permission` that way. The tests match entries by subset, so new fields do not break them.

## The job envelope (`@velexis/api-types/jobs`)

Every message on the cross-backend queues (`ota-tenant-ops` platform → OTA, `platform-tenant-events` OTA → platform) has the same envelope ([ADR-0009](../../docs/mvp/adr/0009-background-jobs-bullmq.md) item 3, [PADR-0001](../../platform/docs/adr/0001-tenant-provisioning-orchestration.md) item 9, [platform architecture §6.1](../../platform/docs/architecture.md)):

| Field | Type | JSON Schema |
|---|---|---|
| `v` | `number` | integer ≥ 1; the contract version, `JOB_CONTRACT_VERSION` = `1` today |
| `name` | `TName` (`` `${string}.${string}` ``) | dotted lower case, `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$`, for example `tenant.provision` |
| `jobId` | `string \| null` | `job_` + ULID, the `platform.provisioning_jobs.id`; `null` only for the deploy fan-out reports `tenant.migrated` and `tenant.migration_failed` |
| `tenantId` | `string` | `ten_` + ULID |
| `requestedAt` | `string` | ISO 8601 in UTC as `Date.prototype.toISOString` writes it (`format: date-time` plus a `Z` pattern) |
| `requestId` | `string` | `^[A-Za-z0-9._-]{8,128}$`, the valid `X-Request-Id` of `@velexis/logger` |
| `payload` | `TPayload` | an object; each message defines its own, with ids and small parameters only (ADR-0009 item 10) |

- `JobEnvelope<TName, TPayload>` is the TypeScript type; a message that always answers a job narrows `jobId` with `& { readonly jobId: string }`.
- `JOB_ENVELOPE_SCHEMA` is the JSON Schema (draft 2020-12, `additionalProperties: false`) of any message: the envelope fields, `jobId` nullable, any object payload.
- `jobMessageSchema({ name, payload?, version?, nullableJobId?, description? })` builds the schema of one concrete message: `name` and `v` become constants, `jobId` is non-null unless `nullableJobId`, and `payload` must be a closed object schema (`type: "object"`, `additionalProperties: false`, else it throws), so no stray field such as a secret or a token can travel. The default payload is `EMPTY_JOB_PAYLOAD_SCHEMA`.
- All schemas are deep-frozen. Compile them with `Ajv2020` from `ajv/dist/2020` and `ajv-formats` (for `date-time`), as ADR-0006 sets Ajv up everywhere.

The concrete messages, the queue names and the validators below are defined by the platform plan (PBE-004); the OTA plan consumes them and extends them only backward compatibly for one release ([PADR-0016](../../platform/docs/adr/0016-contract-rollout-per-milestone-and-route-parity.md) item 3, [AGENTS.md §6](../../AGENTS.md#6-contract-first)).

## Queues (`@velexis/api-types/jobs`, `src/jobs/queues.ts`)

```ts
import { BULLMQ_PREFIX, OTA_TENANT_OPS, PLATFORM_TENANT_EVENTS, PLATFORM_QUEUES, OTA_QUEUES,
         bullmqJobId, parseBullmqJobId } from "@velexis/api-types/jobs";

new Queue(OTA_TENANT_OPS, { connection, prefix: BULLMQ_PREFIX });            // keys vx:ota-tenant-ops:…
await queue.add(message.name, message, { jobId: bullmqJobId(job.id, attempt) }); // "job_01HZX…-2"
parseBullmqJobId("job_01HZX-2");                                               // { jobId: "job_01HZX", attempt: 2 }
```

| Export | Value | Source |
|---|---|---|
| `BULLMQ_PREFIX` | `vx` | [ADR-0009](../../docs/mvp/adr/0009-background-jobs-bullmq.md) item 1 |
| `OTA_TENANT_OPS` | `ota-tenant-ops` (platform → OTA worker) | ADR-0009 item 3 |
| `PLATFORM_TENANT_EVENTS` | `platform-tenant-events` (OTA worker → platform) | ADR-0009 item 3 |
| `PLATFORM_QUEUES` | the seven queues the platform worker consumes: `platform-tenant-events`, `platform-emails`, `platform-stripe-events`, `platform-domains`, `platform-connections`, `platform-settlements`, `platform-maintenance` | [platform architecture §5](../../platform/docs/architecture.md#5-worker-queues-and-schedules) |
| `OTA_QUEUES` | the eight queues the OTA worker consumes: `ota-tenant-ops` (produced by the platform), then the OTA's own `ota-stripe-events`, `ota-payments`, `ota-bookings`, `ota-ticketing`, `ota-notifications`, `ota-documents`, `ota-maintenance` (OBE-002; their concurrency and job defaults are in `ota/backend/src/common/queues/queue-names.ts`) | ADR-0009 item 4, [OTA architecture §6](../../ota/docs/architecture.md#6-workers-queues-and-schedulers) |
| `bullmqJobId(jobId, attempt)` | `<jobId>-<attempt>`: one BullMQ job per dispatch attempt; throws a `TypeError` on a job id that is not letters, digits and `_`, or an attempt that is not a positive integer | [PADR-0001](../../platform/docs/adr/0001-tenant-provisioning-orchestration.md) item 3 |
| `parseBullmqJobId(id)` | `{ jobId, attempt }` of an id written by `bullmqJobId`, otherwise `null` (stale attempts, reconciler) | PADR-0001 items 5 and 6 |

Every queue belongs to the backend whose worker consumes it and is named after it (`<owner>-<topic>`, ADR-0009 item 4), so each name is in exactly one of the two lists. Together they hold the eight queues of platform architecture §5 and the OTA's internal queues: `ota-tenant-ops` is in `OTA_QUEUES` although the platform produces it, because the OTA worker consumes it and the admin queue view shows `ota-*` queues read-only (PBE-031).

## `tenant.*` messages (`src/jobs/tenant-ops.ts`, `src/jobs/tenant-events.ts`)

Every message is the [envelope](#the-job-envelope-velexisapi-typesjobs) with `v: 1` and its own `payload` ([platform architecture §6.1](../../platform/docs/architecture.md#61-queue-messages)). Each has a type, a JSON Schema built with `jobMessageSchema` (name and version pinned, every object closed with `additionalProperties: false`, deep-frozen) and an entry in `TENANT_JOB_SCHEMAS`.

| Message | Queue | `jobId` | Payload | Type / schema |
|---|---|---|---|---|
| `tenant.provision` | `ota-tenant-ops` | job | `{}` | `TenantProvisionJob` / `tenantProvisionJobSchema` |
| `tenant.migrate` | `ota-tenant-ops` | job | `{targetVersion?}` (a migration version) | `TenantMigrateJob` / `tenantMigrateJobSchema` |
| `tenant.suspend` | `ota-tenant-ops` | job | `{reason}`: `billing`, `abuse`, `request` or `admin` ([PADR-0014](../../platform/docs/adr/0014-tenant-suspension-and-resume.md)) | `TenantSuspendJob` / `tenantSuspendJobSchema` |
| `tenant.resume` | `ota-tenant-ops` | job | `{}` | `TenantResumeJob` / `tenantResumeJobSchema` |
| `tenant.provisioned` | `platform-tenant-events` | job | `{schemaName, schemaVersion, migrations[], steps[]}` | `TenantProvisionedEvent` / `tenantProvisionedEventSchema` |
| `tenant.provision_failed` | `platform-tenant-events` | job | `{error, retryable, steps[]}` | `TenantProvisionFailedEvent` / `tenantProvisionFailedEventSchema` |
| `tenant.migrated` | `platform-tenant-events` | job or `null` | `{schemaVersion, migrations[]}` | `TenantMigratedEvent` / `tenantMigratedEventSchema` |
| `tenant.migration_failed` | `platform-tenant-events` | job or `null` | `{version, error, retryable?}` | `TenantMigrationFailedEvent` / `tenantMigrationFailedEventSchema` |
| `tenant.suspended` | `platform-tenant-events` | job | `{}` | `TenantSuspendedEvent` / `tenantSuspendedEventSchema` |
| `tenant.resumed` | `platform-tenant-events` | job | `{}` | `TenantResumedEvent` / `tenantResumedEventSchema` |

The parts of the payloads:

| Part | Fields | Rules |
|---|---|---|
| migration version (`targetVersion`, `schemaVersion`, `version`) | — | `TENANT_MIGRATION_VERSION_PATTERN`, the CHECK of `tenant_schema_migrations.version`: `0001_baseline` |
| `schemaName` | — | `TENANT_SCHEMA_NAME_PATTERN`, the pattern of `assertTenantSchema` in `@velexis/db`: `tenant_acme` |
| `migrations[]` (`TenantMigrationRecord`) | `version`, `checksum`, `phase`, `appliedAt`, `durationMs` | The schema's **full ledger** in apply order, at least one row ([OADR-0007](../../ota/docs/adr/0007-tenant-migration-runner-and-provisioning-worker.md) item 5); `checksum` is lower-case SHA-256 hex; `phase` is `expand`, `migrate` or `contract` (tenants have no repeatable files); `appliedAt` is UTC; `durationMs` is an integer ≥ 0, or `null` when the ledger row has no `execution_ms` |
| `steps[]` (`ProvisioningStepRecord`) | `step`, `status`, `startedAt`, `finishedAt`, `error?` | The OTA worker's steps of this run: snake-case names (`OTA_PROVISIONING_STEPS`: `create_schema`, `run_migrations`, `seed_defaults`, [PADR-0001](../../platform/docs/adr/0001-tenant-provisioning-orchestration.md) item 1); `status` is `succeeded`, `failed` or `skipped`; UTC times |
| `error` (`TenantJobError`) | `code`, `message` | `code` is upper case (`LOCK_TIMEOUT`, `CHECKSUM_MISMATCH`, `TENANT_NOT_PROVISIONING`) or a SQLSTATE (`55P03`); `message` has 1 to 1,000 characters and never holds values, secrets, SQL parameters or connection strings |
| `retryable` | — | `true`: the platform may dispatch another attempt with backoff ([PADR-0001](../../platform/docs/adr/0001-tenant-provisioning-orchestration.md) item 4). Required on `tenant.provision_failed`; optional on `tenant.migration_failed`, where absent counts as `false` |
| `version` of `tenant.migration_failed` | — | The failing (or first changed) migration, or `null` when no file was at fault, as in the fan-out report of `@velexis/db` |

`TenantOpsJob` and `TenantEvent` are the unions of each queue and narrow on `name`; `TenantJobMessage` is both; `TENANT_OPS_JOB_NAMES`, `TENANT_EVENT_NAMES`, `TENANT_OPS_JOB_SCHEMAS` and `TENANT_EVENT_SCHEMAS` list them in the order of architecture §6.1. A message that answers a job (`TenantJobEnvelope`) has a non-null `jobId`; only the fan-out reports (`TenantReportEnvelope`) allow `null`.

## Invalidation events (`src/jobs/invalidation.ts`)

The platform publishes `{ v: 1, type, …ids }` on the Redis channel `INVALIDATION_CHANNEL` (`vx:invalidate`) after the commit of every change to a row the OTA backend caches ([platform architecture §6.3](../../platform/docs/architecture.md#63-cache-invalidation-vxinvalidate)). No other field travels.

| `type` | Fields | Rules |
|---|---|---|
| `tenant` | `id` | `ten_` + ULID |
| `domain` | `hostname` | lower case, labels of 1–63 characters of `a-z`, `0-9` and inner `-` (punycode allowed), at least two labels, no trailing dot, at most 253 characters, not an IP address ([PADR-0004](../../platform/docs/adr/0004-custom-domain-verification.md) item 1) |
| `api_key` | `prefix` | `pk`, `sk` or `hk`, `test` or `live`, and 6 characters: `pk_live_3fA9x2` ([PADR-0005](../../platform/docs/adr/0005-api-key-format-and-hashing.md)) |
| `connection` | `tenantId` | `ten_` + ULID |
| `membership` | `accountId`, `tenantId` | `acc_` + ULID, `ten_` + ULID |
| `account` | `accountId` | `acc_` + ULID |
| `amadeus_account` | `id` | `ama_` + ULID |
| `plan` | `code` | the plan code CHECK: `early_access` |

`InvalidationEvent` is the union and narrows on `type`; `INVALIDATION_TYPES` lists the types, `INVALIDATION_EVENT_SCHEMAS` has one closed schema per type, and `INVALIDATION_EVENT_SCHEMA` is the union (`oneOf`) for consumers that compile it themselves.

## Validation (`src/jobs/validate.ts`)

```ts
import { validateJob, validateInvalidation, isTenantJobName, MessageValidationError } from "@velexis/api-types/jobs";

const message = validateJob("tenant.provision", data);  // TenantProvisionJob, or throws
const any = validateJob(job.name, job.data);            // TenantJobMessage (switch on message.name)
redis.publish(INVALIDATION_CHANNEL, JSON.stringify(validateInvalidation({ v: 1, type: "tenant", id })));
```

- `validateJob(name, data)` checks `data` against the schema of `name` and returns it typed (`TenantJobMessageMap[name]`, or `TenantJobMessage` for a `string` name). `validateInvalidation(event)` does the same for an invalidation event, against the schema of its `type`.
- Both throw a `MessageValidationError` (`subject`: the message name or `vx:invalidate`; `issues`: `{path, keyword, message}` with a JSON Pointer per failing value). Messages and issues name paths and rules only, never values (Ajv runs without `verbose`, and stray property or message names are shortened to 64 characters), so the error can be logged without the payload. An unknown name is refused the same way.
- One Ajv 2020 instance in strict mode with the `date-time` format of `ajv-formats` compiles every schema once, on the first call; modules that only import the names and schemas never compile anything.
- Producers validate before `queue.add` or `publish`, consumers when they take the message. An invalid message is a bug of the other side and is not retried: the OTA worker turns the error into BullMQ's `UnrecoverableError` (OBE-002), the platform consumer fails the job (PBE plan).
- `isTenantJobName(name)` and `isInvalidationType(type)` are the type guards behind them.

## Fixtures (`fixtures/jobs/`)

One valid message per file, used by the tests of this package and by both backends' tests (the platform's fake OTA worker of [PADR-0017](../../platform/docs/adr/0017-platform-test-doubles-and-end-to-end-harness.md), the OTA consumer and producer tests). They are published through the `exports` map and the `files` list:

```ts
import provision from "@velexis/api-types/fixtures/jobs/tenant-provision.json";
const job = validateJob("tenant.provision", provision);
```

| File | Message |
|---|---|
| `tenant-provision.json` | `tenant.provision` for `ten_01M4T9E68084G7ZWYRD6Z1RV0W`, job `job_01M4T9HVE0355QAKGD2AVSQWH2` |
| `tenant-provisioned.json` | its answer: `tenant_acme` at `0001_baseline` (the real checksum of `ota/backend/migrations/tenant/0001_baseline.sql`) after the three OTA steps |
| `tenant-provision-failed.json` | a retryable `LOCK_TIMEOUT` in `run_migrations` |
| `tenant-migrated-fanout.json` | a deploy fan-out report: `tenant.migrated` with `jobId: null` |

The fixtures hold made-up ids and no secrets. A fixture is changed only together with its schema, backward compatibly for one release.

## Tests of X-008

[`src/api-types.test.ts`](src/api-types.test.ts) runs the generator as a child process, into scratch folders in the system temporary folder (removed after the run), and checks the types with the TypeScript compiler API:

- `[X-008 AC1]` two runs of the generator give byte-identical files, equal to the committed `src/generated/` files, with the header first and no timestamp or local path;
- `[X-008 AC2]` every one of the 96 operations of the frozen contract ([`docs/velexis-sdk/openapi/`](../../docs/velexis-sdk/openapi/velexis-ota-booking-api.openapi.yaml)) is in `otaOperations` with its method, path and `x-sdk-method`, and every operation without `x-internal` has an `sdkMethod` (operations that the working document marks `x-sdk-exclude`, plain URLs such as file downloads, are exempt, [`ota/docs/api-changes.md`](../../ota/docs/api-changes.md) §1). The index may grow; the test never counts it exactly;
- `[X-008 AC3]` every schema name of the SDK contract's generated [`api-types.d.ts`](../../docs/velexis-sdk/sdk/src/api-types.d.ts) is a key of `components["schemas"]`. It is a subset check, never equality, so spec-first tasks that add schemas do not touch it;
- `[X-008 AC4]` `components["schemas"]["Money"]` compiles and `components["schemas"]["Mony"]` does not: a `// @ts-expect-error` in the test (checked by `tsc` in `typecheck` and `build`) and the same two snippets compiled in the test itself (`TS2339`);
- the SDK contract's [`shared.d.ts`](../../docs/velexis-sdk/sdk/src/shared.d.ts) compiles with `@velexis/api-types` resolved to this package; `paths`, `operations` and the index agree; the platform placeholder and a real platform document (in a scratch copy) give the expected files, which compile, and the expected index (the generated module is run after TypeScript strips its types); `milestone`, `edgeOnly` and `permission` are read from `x-milestone`, `x-edge-only` and `x-permission` (OBE-009), with `null`, `false` and `null` when absent, and match the working document entry by entry; generation fails on the problems listed above; the index is frozen and typed;
- the job envelope validates with Ajv 2020 and `ajv-formats`, refuses missing and extra fields, wrong ids, non-UTC times and list payloads, and `jobMessageSchema` pins the name and version, closes the payload and refuses open payload schemas.

The generator tests on the full OTA document take about three seconds per run.
