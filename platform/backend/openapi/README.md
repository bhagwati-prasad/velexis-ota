# Platform API contract (`platform/backend/openapi/`)

This folder holds the OpenAPI 3.1 document of the Velexis platform API, `velexis-platform-api.openapi.yaml`. It is the **source of truth** for every request and response shape of the platform backend, the portal and the platform admin ([ADR-0006](../../../docs/mvp/adr/0006-contract-first-openapi.md), [PADR-0009](../../docs/adr/0009-platform-api-surface-and-authentication.md)). This page says where its operations come from, which conventions and `x-` extensions it uses, how to change it and how to regenerate what is built from it. Read it, with [`AGENTS.md` §6](../../../AGENTS.md#6-contract-first), before any task that edits the document.

Related: [`../../docs/api-inventory.md`](../../docs/api-inventory.md), [`../../docs/api-inventory-resources.md`](../../docs/api-inventory-resources.md) and [`../../docs/api-inventory-admin.md`](../../docs/api-inventory-admin.md) (the inventory), [PADR-0016](../../docs/adr/0016-contract-rollout-per-milestone-and-route-parity.md) (slices and route parity), [`packages/api-types/README.md`](../../../packages/api-types/README.md) (`contracts:lint`, `contracts:generate`, the operations index), [`packages/errors/README.md`](../../../packages/errors/README.md) (the error catalogue), [`ota/backend/openapi/README.md`](../../../ota/backend/openapi/README.md) (the OTA document, whose conventions this one shares).

## 1. What is here

| File | Role |
|---|---|
| `velexis-platform-api.openapi.yaml` | The contract, OpenAPI 3.1 YAML. `info.version` `1.0.0`; operations are only added, slice by slice (§2). |
| `README.md` | This page. |

Only the YAML is the contract. When a tool needs JSON, generate it into a scratch location (`redocly bundle platform --ext json`, see [`packages/api-types/README.md`](../../../packages/api-types/README.md#commands)); it is never committed.

Keep the file name and location: [`packages/api-types/redocly.yaml`](../../../packages/api-types/redocly.yaml) (lint and types), the generator of `@velexis/errors`, the response checks of `@velexis/testing`, the Turborepo inputs in [`turbo.json`](../../../turbo.json) and the backend's Ajv loader (PBE-008) all read it from here.

## 2. Where the operations come from

Every operation comes from the platform API inventory, with its `operationId`, method and path unchanged. The inventory's columns map to the document like this:

| Inventory | Document |
|---|---|
| Operation, Method and path | `operationId`, the path item and its method |
| Auth `public` / `portal*` / `portal` (with roles) / `admin` / `internal` / `webhook` | `x-scope`: `public` / `portal_unverified` / `portal` / `platform_admin` / `internal` / `webhook`, and the security scheme (§3) |
| `MFA↑`, `Idem`, `F:<switch>`, admin **reason** | `x-mfa-step-up: true`, `x-idempotent: true`, `x-feature: <switch>`, `x-reason-required: true` |
| Request → response | `requestBody` and `responses`, with named component schemas |
| Tables | `x-platform-tables` (Redis keys are named in the description) |
| Errors | `x-error-codes` and one error response per status, with an example per code (§5) |

The document grows in **milestone slices**, each written before the implementation tasks of its milestone ([PADR-0016](../../docs/adr/0016-contract-rollout-per-milestone-and-route-parity.md) item 1). Until a route is implemented, its operation is listed in `platform/backend/test/contract/pending-operations.ts` with the implementing task (PBE-008 creates the list and the route parity test).

| Slice | Task | Operations | State |
|---|---|---|---|
| M1 identity, plans, internal | PBE-005 | Auth (api-inventory §4, 11), account (§5, 9), `listPlans` (§6), `tlsAsk`, `healthLive`, `healthReady` (admin §9): 24 | Done |
| M1 tenants, team, keys, reads | PBE-006 | Tenants (api-inventory §7 without `goLive`, 9), team (§8 without `createConsoleToken`, 9), API keys (api-inventory-resources §1, 5), `listDomains`, `listAmadeusConnections`, `listPaymentConnections`, `getSubscription`: 27 | Done |
| M1 admin, part 1 | PBE-007 | Admin auth and dashboard (api-inventory-admin §2, 7), tenants, provisioning jobs and queues (§3, 14): 21 | Done |
| M1 admin, part 2 | PBE-066 | The M1 rows of api-inventory-admin §4 (plans and subscriptions, 6), §5 (Amadeus accounts and offices, 9) and §7 (accounts, platform admins and audit, 11): 26 | Done |
| M3–M4 | PBE-037 | `updatePaymentConnection` (api-inventory-resources §4), `createConsoleToken` (api-inventory §8), `updateAmadeusConnection` (api-inventory-resources §3): 3 | Done |
| M5 portal | PBE-041 | `goLive` (api-inventory §7) and the M5 rows of api-inventory-resources §2 (custom domains, 4), §3 (live Amadeus request and own credentials, 3), §4 (Stripe Connect, API keys and Velexis payments, 4), §5 (payout account and settlements, 5) and §6 (Checkout, Customer Portal and invoices, 3): 20 | Done |
| M5 admin and webhooks | PBE-042 | The M5 rows of api-inventory-admin §4 (Stripe billing admin, 5), §5 (the office release, 1), §6 (settlements and payout accounts, 12, with `adminDownloadSettlementLines` of PADR-0016 item 4), §7 (domains, 3) and the two Stripe receivers of §8, and the M5 Stripe ids of `adminUpdatePlan`: 23 | Done |

Notes on the PBE-005 slice:

- `healthLive` is `public` (the uptime monitor reaches it through Caddy) and `healthReady` and `tlsAsk` are `internal`, as the inventory says; PADR-0009 item 1 groups all of `/health/*` with the internal surface. All three carry `x-internal: true` and the tag `Internal`, because none belongs to the portal or admin surface.
- `tlsAsk`'s `domain` parameter has no schema constraint and is not required: a missing or malformed host must answer `404` before any lookup ([PADR-0004](../../docs/adr/0004-custom-domain-verification.md) item 6), never `400`.
- The health answers are the ones `HealthService` gives since PBE-001; `HealthReady.queues` (the oldest waiting job per platform queue, api-inventory-admin §9) is optional until the queues exist.
- `resendVerification` sends a new link and leaves the earlier unexpired links valid, as [PADR-0008](../../docs/adr/0008-email-verification-and-mfa-policy.md) item 3 decides. Step 4 of PBE-013 in the plan says the older tokens are consumed; the ADR wins.
- Passwords are bounded only in length (1–256): the password rules answer `422 PASSWORD_TOO_WEAK` from the service, so a short password must pass the schema (PBE-013).

Notes on the PBE-006 slice:

- **Conditional step-up.** `createApiKey` and `rollApiKey` need a step-up only for a live secret key, and `updateMember` only when it grants `owner` (the inventory's "live secret keys MFA↑" and "granting owner: MFA↑"). `x-mfa-step-up: true` would put `RecentMfaGuard` on every call, so these operations do not carry it: the service checks the case, and the operations list `REAUTH_REQUIRED` and `MFA_REQUIRED` in their errors.
- **Roles** of `portal: owner, admin` rows are not an extension: each handler declares them with `@TenantRoles(...tenantRolesOf("<operationId>"))` from `memberships/tenant-roles.ts` (PADR-0009 item 5), which `TenantRoleGuard` enforces, and each operation's description names them. Non-members get `404 NOT_FOUND`, members with another role `403 FORBIDDEN` (PBE-017).
- `createTenant` already has its M5 shape: `planCode` and `billingInterval` in the request, `checkoutUrl` (always present, `null` before M5) and the optional `checkoutError` in the answer, with an example of each case, so the Ajv example check covers the M5 answers too. It is the only idempotent operation of the slice and also answers `503 SERVICE_UNAVAILABLE` while the idempotency store is down (PBE-009). A malformed key answers `400`; `409 TENANT_KEY_UNAVAILABLE` is for a reserved or used key, as the error catalogue says.
- `checkTenantKey` accepts any key of 1–64 characters, because a key that breaks the rules answers `200` with `reason: invalid`, not `400`.
- `Tenant` has `billingNotice` (`tenants.billing_notice`) in addition to the inventory's fields, because the portal dashboard shows the billing banner to every member (PFE-010) and only owners and finance members may call `getSubscription`. api-inventory §7 lists it.
- `updateApiKey`, `rollApiKey` and `revokeApiKey` answer `409 TENANT_NOT_ACTIVE` too, as `createApiKey` does: [PADR-0014](../../docs/adr/0014-tenant-suspension-and-resume.md) item 5 makes a suspended OTA's keys read-only. api-inventory-resources §1 lists it.
- **Keys shown once.** `revealInitialKeys`, `createApiKey` and `rollApiKey` answer the full key in `key` (schema `ApiKeySecret`) with `NoStore`. The generic secret check of the contract test cannot key on the name `key` (the OTA key of `Tenant` has the same name), so it follows references to `ApiKeySecret` instead, and the slice test also names these three operations.
- **API key scopes** are strings with a light pattern, not an enum: the service validates them against the generated OTA `ConsoleApiKeyScope` and `StaffPermission` types (PADR-0005 item 6), and the contract test checks that every value of both OTA enums matches the pattern.
- Lists that stay short answer `{data}` only, as the inventory says: the caller's OTAs, members and invitations (bounded by the staff seats), API keys, domains and connections. Cursor pagination starts with the admin lists (PBE-007).
- `AmadeusConnection.ticketingDefaults` has the closed shape of the baseline comment, `{ticketingAgreement: {option, delay}, automatedProcess, issue}` with every property optional (an empty object until set), and a `monitoredQueues` item is `{officeId, queueId, category}`. The M4 update (PBE-037) writes them with the same schemas and may only add optional properties.

Notes on the PBE-007 slice:

- **Admin sign-in.** `adminSignIn` always answers an `AdminMfaChallenge` (TOTP on every admin sign-in, PADR-0006 item 2), and an account that is not an active platform admin gets the same `401 INVALID_CREDENTIALS` as a wrong password. `adminVerifyMfa`, `adminRefresh` and `adminStepUp` answer `AdminSession`: the tokens and `admin` (`AdminMe`). Challenges and refresh families never cross the portal and admin surfaces. Only these three sign-in steps are `public` under `/v1/admin/`; every other admin operation is `platform_admin` with the `adminBearer` scheme.
- **`features` in `adminGetMe`.** `AdminMe` (also inside `AdminSession`) carries the `MilestoneFeatures` of `getMe`, because the admin cannot call the portal-scoped `getMe` and the backend is the only source of the switches (PADR-0015 item 3). api-inventory-admin §2 notes the addition.
- **The admin guard.** A token of an account that is no longer an active platform admin answers `401 UNAUTHENTICATED`, like a portal token (`AdminUnauthenticated`, described on `adminBearer` and in api-inventory-admin §1); the admin operations have no `403` for it.
- **Reasons and step-ups.** The four **reason** operations (`adminSuspendTenant`, `adminResumeTenant`, `adminSetConnectionStatus`, `adminCancelProvisioningJob`) carry `x-reason-required: true` and a required body with `reason` (`AdminReason`, 5–500 characters). No operation of §2 and §3 is marked MFA↑, so the slice has no `x-mfa-step-up`; `adminStepUp` is the step-up itself. `adminSuspendTenant` takes `abuse`, `request` or `admin`: `billing` is set by billing sync only (PADR-0014 item 1).
- **Conflicts** name their cause in `details.reason`: `not_active` (suspend), `not_suspended` and `subscription_not_active` (resume), `migrate_job_active` and `schema_missing` (migrate), `not_disabled`, `no_office` (an Amadeus connection without an office) and `deauthorized` (a payment connection deauthorised in Stripe) (connection status), `not_queued` (cancel); `adminRetryQueueJob` answers `403 FORBIDDEN` with `details.reason = ota_queue`. PBE-030 and PBE-031 answer these values.
- **Dashboard.** The M5 counters are always present and `null` while their switch is off: `domainsPending` (`custom_domains`), `settlementsToReview` (`settlements`), `stripeEventsFailed` (`stripe_billing` or `own_stripe`), `subscriptionsPastDue` (`stripe_billing`). `jobsFailedByQueue` is keyed by the names of `PLATFORM_QUEUES`; its counts come from BullMQ, so the dashboard answers `503 SERVICE_UNAVAILABLE` while Redis is down, as the queue operations do.
- **Tenant detail.** `adminGetTenant` reuses the masked portal shapes (`Member`, `Invitation`, `Subscription`, `AmadeusConnection`, `PaymentConnection`, `Domain`) with `AdminTenant` (the portal `Tenant` without `myRole`, plus `suspendedAt` and the internal `notes` of `tenants.metadata.notes`), `AdminProvisioningJob` (at most 20) and `AuditEntry` (at most 50). `AuditEntry` is also the item of `adminListAudit` (PBE-066); its `id` is a decimal string. `adminSetConnectionStatus` answers `AdminConnection`, a `oneOf` of the two masked connection shapes.
- **Jobs and queues.** `adminMigrateTenant` takes an optional body (`required: false`, as the OTA document does for optional bodies); `targetVersion` has the `TENANT_MIGRATION_VERSION_PATTERN` of `@velexis/api-types/jobs`. `AdminProvisioningJobDetail.result` and `payload` are open objects that never hold a ciphertext; `bullmqState` is a BullMQ state, `unknown` when BullMQ no longer holds the attempt and `null` before the first dispatch. The three queue operations read Redis only and answer `503 SERVICE_UNAVAILABLE` while it is down. `QueueName` is a pattern (`<owner>-<topic>`), not an enum: an unknown queue of that form answers `404`, any other value `400 VALIDATION_FAILED`. `TenantMigrationVersion`, the `suspensionReason` of `adminSuspendTenant` (without `billing`), `ProvisioningJobKind` and `QueueJobId` follow `@velexis/api-types/jobs`, and the contract test compares them.
- **Pagination.** `adminListTenants` and `adminListProvisioningJobs` are the first cursor-paginated lists (`Cursor`, `Limit`, `{data, page: Page}`); `adminListFailedQueueJobs` takes `limit` only and `adminListQueues` neither, as the inventory says.
- **Tables.** Every admin action that changes state writes `platform_audit_log` (api-inventory-admin §1), so `x-platform-tables` lists it on every writing operation of §3, also where the inventory's Tables cell names only the changed tables. Of the sign-in steps of §2, `adminSignIn` and `adminVerifyMfa` audit, as the inventory says; `adminRefresh`, `adminStepUp` and `adminSignOut` change only the admin's own session rows and, like the portal's `refreshSession`, `stepUp` and `signOut`, list no audit table. The queue reads list no table.

Notes on the PBE-066 slice:

- **Scope and tags.** All 26 operations are `platform_admin` with `adminBearer`, under the tags `Admin billing` (plans and subscriptions), `Admin Amadeus`, `Admin accounts` (accounts and platform admins) and `Admin audit`. With PBE-007 they make the 47 M1 admin operations; the M5 rows of the same sections follow in PBE-042.
- **Reasons.** The six **reason** operations (`adminUpdateManualSubscription`, `adminRetireAmadeusOffice`, `adminDisableAccount`, `adminEnableAccount`, `adminResetAccountMfa`, `adminGrantAdmin`) carry `x-reason-required: true` and a required `reason` (`AdminReason`) in a required body. `adminUpdateManualSubscription` also needs at least one change (`minProperties: 2`, because a top-level `anyOf` of `required` lists would not be a closed body). `adminRevokeAdmin` is a `DELETE` without a body: the inventory's `?reason=` is an optional query parameter with the `AdminReason` schema, since its row is not marked **reason** and PADR-0006 item 5 does not list revocations; `adminUnlockAccount` takes no reason either, as the inventory and PADR-0006 say (scope.md PF-87 reads "reason required" for the whole group).
- **Step-ups.** `adminCreateAmadeusAccount`, `adminResetAccountMfa`, `adminGrantAdmin` and `adminRevokeAdmin` carry `x-mfa-step-up: true` (PADR-0006 item 4) and answer `AdminStepUpUnauthorized` (`401` with `UNAUTHENTICATED`, `TOKEN_EXPIRED` or `REAUTH_REQUIRED`). `adminUpdateAmadeusAccount` needs a step-up only when `clientSecret`, `clientId` or `baseUrl` changes (PADR-0006 item 4, rotating the shared credentials): the host counts because the verification job and the OTA backend send the stored secret to it, so without a step-up a stolen admin session could point the account at another host and receive the secret. The inventory row reads "MFA↑ when the secret, client id or base URL changes" since the PBE-066 review (it read "when the secret changes"). Like the conditional step-ups of PBE-006, the service checks these cases, the operation lists `REAUTH_REQUIRED` and is not marked. No admin operation answers `403 MFA_REQUIRED`: every platform admin has MFA, and admins cannot turn it off (PADR-0006 item 2).
- **Plans.** `AdminPlan` is the public `Plan` (the same property schemas) plus `currency`, `isPublic`, `isActive`, `sortOrder`, `settlementFeeBps`, the three Stripe ids, `priceWarnings`, `tenantCount`, `version`, `createdAt` and `updatedAt`. The Stripe ids are always present, `null` until linked, and `priceWarnings` (`{field, expected, actual}`, the shape of `adminCheckPlanPrices`) stays empty until then, so the answer does not change in M5. The M1 `UpdatePlanRequest` has no Stripe id and `adminUpdatePlan` no `502 PROVIDER_ERROR`: PBE-042 adds both, as the task says. Prices in requests are `PlanPrice` (a `Money` with a non-negative amount and at most two decimals); the service checks that their currency is the plan's. `isActive: false` retires a plan. `adminListPlans` is a short list without pagination, so each plan carries the `version` that `adminUpdatePlan` needs in `If-Match`. Unlike the other versioned tables, `platform.plans` has no `version` column; how PBE-033 provides it (a column in migration `0003`, or a value derived from `updated_at`) was left open for that task. PBE-033 derives it from `updated_at`: the instant in epoch milliseconds (so `version` equals `Date.parse(updatedAt)`), which every write of a plan raises by at least one ([`../README.md`](../README.md) §4, "Admin plans and manual subscriptions"); the document is unchanged.
- **Subscriptions.** `AdminSubscription` names its OTA and carries the Stripe customer and subscription ids (references, never secrets; `null` on manual rows). `adminGetSubscription` adds the subscription's invoices and the OTA's Stripe events (at most 50 each, both empty before M5) as `AdminInvoice` and `AdminStripeEvent`, the item shapes PBE-042 reuses for `adminListInvoices` and `adminListStripeEvents`. `adminUpdateManualSubscription` answers `409 CONFLICT` with `details.reason` `stripe_billed` or `current_exists`, and `422 UNPROCESSABLE` (`plan_not_active`) for a plan code that names no active plan; plans that are not public are allowed.
- **Amadeus.** `AdminAmadeusAccount` never holds the client secret or its ciphertext; `clientSecret` exists only in the create and update bodies (`AmadeusClientSecret`, `writeOnly`). `baseUrl` is an `https` URL or the loopback stub (`http://127.0.0.1:<port>`), as the CHECK of `amadeus_accounts` allows. `adminVerifyAmadeusAccount` answers `202` without a body and `503 SERVICE_UNAVAILABLE` while Redis is down, because the job is its whole effect. Office ids in `adminAddAmadeusOffices` accept lower case and repeats (the service upper-cases them and lists each repeat and each id the pool already holds in `skipped`, one entry per skipped request entry, in request order), so the schema has no `uniqueItems`. `{officeRowId}` is the `amo_` pool entry, never the 9-character office id. `adminAssignAmadeusOffice` answers its two `409`s in one response: `AMADEUS_OFFICE_UNAVAILABLE` (the office is not `available`) and `CONFLICT` (`tenant_credentials`, `office_already_assigned`).
- **Accounts and admins.** `AdminAccount` has no password hash, MFA secret, recovery code or token. `adminGetAccount` answers `activeSessions` as a count (PBE-032) and `memberships` as the portal's `AccountMembership`. Conflicts name their cause in `details.reason`: `not_enabled` (disable an account already `disabled` or `deleted`), `not_disabled` (enable), `mfa_not_enabled` (reset MFA), `already_admin` (grant); `adminGrantAdmin` answers `422 UNPROCESSABLE` with `account_not_active`, `email_not_verified` or `mfa_not_enabled`, and its `201` carries the new `PlatformAdmin`. `AdminSelfOrLastAdminForbidden` is the `403` of disable and revoke (`self`, `last_admin`); the `403` of `adminResetAccountMfa` is `platform_admin`.
- **Audit.** `adminListAudit` answers `AuditEntry` (PBE-007), whose `actorType` now references `AuditActorType`, the enum the `actorType` filter shares (same values). The filters are shared parameter components (`AuditTenantId` … `AuditTargetId`) used by both audit operations.
- **The CSV export.** `adminExportAudit` is the first operation whose body is not JSON: `200` answers `text/csv` (a `string` schema) with one header row (`id`, `createdAt`, then the other `AuditEntry` properties, `details` as redacted JSON), RFC 4180 quoting, an empty cell for `null`, and a leading `'` on cells that start with `=`, `+`, `-`, `@`, a tab or a carriage return (the OWASP rule against CSV injection). It documents `Content-Disposition` and `Cache-Control` with `NoStoreExport` (`no-store`, because the file holds e-mail and IP addresses, not a secret). Its filters are those of `adminListAudit` without `cursor` and `limit`, and `from` and `to` are required, so the one-year limit is checked on every call. The response checker of `@velexis/testing` reads JSON only and refuses a CSV body ("check its body another way"), so the integration tests check the file themselves.
- **Tables.** As in PBE-007, every operation that changes state lists `platform_audit_log`, and so do `adminVerifyAmadeusAccount` (it audits the request) and `adminExportAudit` (a sensitive read, PADR-0006 Audit item 2).

Notes on the PBE-037 slice:

- **Scope.** The three operations are `portal` with `portalBearer`, under the tags `Team` (`createConsoleToken`) and `Connections` (the two updates). None carries `x-mfa-step-up`, `x-idempotent` or `x-feature`: the inventory marks none of them, and no switch of PADR-0015 covers M3 or M4.
- **The console token.** `createConsoleToken` takes no body and answers `201 ConsoleToken` (`portalToken`, `expiresAt`, `consoleSsoUrl`) with `NoStore`, so the token is never cached nor kept for a replay; it is not idempotent. `PortalToken` is `ptk_` and exactly 43 base62 characters (PADR-0007 item 1), within the OTA contract's `ConsolePortalTokenSignIn.portalToken` pattern (`ptk_` and 24–64), which the contract test checks. `consoleSsoUrl` is a `uri` without an `https` pattern, because `PUBLIC_OTA_ADMIN_URL` is `http://localhost:3002` in development. Any active member may ask, so there is no `FORBIDDEN`. `403 MFA_REQUIRED` is the MFA policy of live OTAs (PADR-0008), not a step-up, so the operation answers no `REAUTH_REQUIRED`; its `403` names `EMAIL_NOT_VERIFIED` and `MFA_REQUIRED`. `409 TENANT_NOT_ACTIVE` carries `details.status` and, for a suspended OTA, `details.suspensionReason` (PBE-039 step 1). The token lives only in Redis, so the operation answers `503 SERVICE_UNAVAILABLE` while Redis is down, as the failure handling of [the SSO flow](../../docs/flows/team-and-ota-admin-sso.md#failure-handling) says (the inventory row does not list it, like the other Redis-only operations above). The Redis key `ptk:<sha256>` is named in the description; `x-platform-tables` lists `accounts`, `tenant_memberships`, `tenants` and `platform_audit_log`.
- **The connection updates.** `{environment}` is the shared path parameter `ConnectionEnvironment` (the `Environment` enum); an environment without a connection answers `404 NOT_FOUND`. Both take `If-Match`, answer `200` with `ETag` and the masked connection that `listAmadeusConnections` or `listPaymentConnections` answers, and `412 PRECONDITION_FAILED`. Only owners and admins write (`403 FORBIDDEN`). Both also answer `409 TENANT_NOT_ACTIVE`, because [PADR-0014](../../docs/adr/0014-tenant-suspension-and-resume.md) item 5 makes a suspended OTA's connections read-only, as for the API key writes of PBE-006; api-inventory-resources §3 and §4 list it now, and `NOT_FOUND` for `updatePaymentConnection`. `x-platform-tables` lists `credential_submissions`, because the answer carries `pendingSubmission`.
- **The statement descriptor suffix.** `StatementDescriptorSuffix` holds the rules of PBE-038 in the schema: 2–22 characters, only ASCII letters, digits and spaces, starting with a letter or a digit and with at least one letter (`^(?=[0-9 ]*[A-Za-z])[A-Za-z0-9][A-Za-z0-9 ]*$`); Stripe's forbidden characters `<`, `>`, `\`, `'`, `"` and `*` fall outside that set. The minimum of 2 and the leading letter or digit come from the CHECK of migration `0002` (`^[A-Za-z0-9][A-Za-z0-9 .&-]{1,21}$`), so every accepted value can be stored. The CHECK and the answer's pattern also allow `.`, `&` and `-`, which PBE-038 excludes: the request is narrower than the answer, and a stored value is answered unchanged. So the schema already answers `400 VALIDATION_FAILED` for `ACME*TRAVEL` and for 23 characters (PBE-038's acceptance); PBE-038's `descriptor.ts` and PFE-016's Zod schema apply the same rules.
- **The Amadeus settings.** `UpdateAmadeusConnectionRequest` has the inventory's five optional fields, at least one (`minProperties: 1`, like the other PATCH bodies); a field that is sent replaces the stored value. The office defaults are non-null `AmadeusOfficeId`s, because PF-53 keeps them within the connection's offices. `ticketingDefaults` and the items of `monitoredQueues` reuse the schemas of `AmadeusConnection` (PBE-006 note above). `monitoredQueues` takes at most 20 distinct queues (`maxItems`, `uniqueItems`), because each costs one Amadeus Queue List call per 15-minute poll of the OTA worker; the answer's list stays unbounded. A queue's `queueId` is 0–99 and its `category` 0–254 (FIX-W32-PLATFORM, lead decision (2) of 2026-10-28, which [PADR-0016](../../docs/adr/0016-contract-rollout-per-milestone-and-route-parity.md) item 1 records as the approved narrowing): the bounds of every `queueId` parameter of the OTA document's Queue List reads, outside which the OTA poller skips a stored queue as invalid (`parseMonitoredQueues`), so the request validation answers `400 VALIDATION_FAILED` at `/monitoredQueues/<n>/queueId` instead. `updateAmadeusConnection` is the only operation that writes monitored queues (bound since PBE-040); the contract test, the validation interceptor's test and its integration test (`test/integration/connections/amadeus-settings.int.test.ts`) run its body through the request validation. The service checks that every office id of the body is one of `officeIds` (`400 VALIDATION_FAILED`): the three defaults (PBE-040 step 1), and also the `officeId` of each `ticketingDefaults.automatedProcess` entry and each monitored queue, because the office isolation of [ADR-0012](../../../docs/mvp/adr/0012-amadeus-account-model.md) lets the OTA backend act on the shared Velexis account only for the OTA's own offices, queue offices included.

Notes on the PBE-041 slice:

- **Scope, tags and marks.** All 20 operations are `portal` with `portalBearer`, under the tags `Tenants` (`goLive`), `Domains`, `Connections`, `Billing` and the new `Settlements` (payout account and statements). `x-feature` and `x-mfa-step-up` follow the inventory's `F:` and MFA↑ exactly. ## 3. Conventions

The same as the OTA document ([`conventions.md` §1 and §6](../../../docs/mvp/conventions.md), [PADR-0009](../../docs/adr/0009-platform-api-surface-and-authentication.md) item 6), and stated in the document's `info.description`:

- JSON in camelCase; ids are prefixed ULIDs (`acc_`, `ten_`, `stf_`, …, pattern `^<prefix>_[0-9A-HJKMNP-TV-Z]{26}$`); money is the `Money` schema of the OTA document (`amount` a decimal string); times are ISO 8601 UTC with `Z`.
- Lists: the `Cursor` and `Limit` parameters (default 50, maximum 200) and `{data, page: Page}`. A list that is never long (`listSessions`, `listPlans`) answers `{data}` only, as the inventory says.
- Versioned resources answer `ETag: "<version>"` (component header `ETag`); their PATCH takes the `IfMatch` parameter and answers `412 PRECONDITION_FAILED` when it is stale.
- `x-idempotent: true` operations take the `IdempotencyKey` parameter (required); a replay within 24 hours answers the stored response.
- **Secrets.** A 2xx answer that carries a secret (access, refresh, MFA challenge or portal tokens, the TOTP secret, recovery codes, a key shown once, revealed bank details) documents the header `Cache-Control` with the component `NoStore` (`const: no-store`). Such answers are never cached and never stored for an idempotent replay. The health answers use `NoStoreHealth`, which says the same without meaning a secret. A secret in a request (a password, a client secret, a Stripe key, a bank identifier, an OAuth code or state) is a `writeOnly` schema, and no answer reaches one (PBE-041); the payout account reveal answers the bank identifiers with readable schemas of its own (PBE-042).
- Every response documents `X-Request-Id`. Request bodies are closed (`additionalProperties: false`, also in every `oneOf` branch), except the Stripe events of the two webhook receivers, which Stripe extends without notice (PBE-042). Response schemas are closed too, so the response checks of the integration tests catch a field that should not be there (a hash, a ciphertext).
- **Security schemes.** `portalBearer` (audience `portal`) on `portal_unverified` and `portal` operations, `adminBearer` (audience `platform_admin`) on `platform_admin` ones, and `security: []` on `public`, `internal` and `webhook` operations, whose checks are not bearer tokens.
- The end-user headers `X-Velexis-End-User-IP`, `X-Velexis-End-User-Agent` and `X-Velexis-Bff-Key` ([PADR-0019](../../docs/adr/0019-end-user-ip-forwarding-from-the-portal-and-admin.md)) are handled by the request context for every operation and are described in `info.description`, not repeated as parameters.
- **Bodies are JSON**, except the CSV export of the audit log (`adminExportAudit`, `text/csv`, PBE-066), which documents `Content-Disposition` and `Cache-Control: no-store` (`NoStoreExport`, personal data), and the lines of a settlement statement (`downloadSettlementLines`, `text/csv`, PBE-041, and the admin's `adminDownloadSettlementLines`, PBE-042, both with `NoStoreStatement`).
- **The error envelope** is the OTA document's `ErrorResponse`, `Error` and `FieldError` (the same properties, types and patterns) without the console-only `supplier` field, which the platform never sends, and closed.

## 5. The error catalogue

`x-error-catalogue` lists every code of [api-inventory §3](../../docs/api-inventory.md#3-error-catalogue) (52 codes) with its status and a default message that is safe to show and never echoes a submitted value. `pnpm contracts:generate` turns it into `PlatformErrorCode`, `PLATFORM_ERROR_CODES` and the platform entries of `ERROR_CATALOGUE` in `@velexis/errors`.

- A code that both documents list must have the **same HTTP status** in both, or the generator of `@velexis/errors` fails (conventions §6). For such a shared code `ERROR_CATALOGUE` keeps the OTA entry, so the default `AppError` message is the OTA description; the platform backend passes its own message where the OTA wording does not fit.
- A new code is added here and to api-inventory §3 in the task that first answers it.
- An operation answers each error status with one response whose examples name its codes (component examples named after the code, such as `#/components/examples/NOT_FOUND`). Only `VALIDATION_FAILED` examples carry `fieldErrors`; a code with field errors must be in `FIELD_ERROR_CODES` of `@velexis/errors`, whose test compares the list with the examples of both documents.

## 6. Changing the document

1. **Edit the document.** Take the operation from the inventory (§2) and follow §3 to §5. Additive changes only, unless an ADR approves a breaking one (the rules of [`ota/backend/openapi/README.md` §4](../../../ota/backend/openapi/README.md#4-additive-changes-only) apply here too).
2. **`pnpm contracts:lint`** until it reports zero errors (§7).
3. **`pnpm contracts:generate`**, then commit the document with `packages/api-types/src/generated/platform.ts`, `packages/api-types/src/generated/operations.ts` and `packages/errors/src/generated/catalogue.ts`. A second run must give no diff; CI runs it again and fails on one.
4. **`pnpm --filter @velexis/platform-backend test`** runs the contract test below.
5. Add the new operations to `platform/backend/test/contract/pending-operations.ts` (from PBE-008) with their implementing task, and a row to the change log (§8).
