# Platform backend (`@velexis/platform-backend`)

This is the NestJS 11 control-plane backend of Velexis: the API that the portal and the platform admin call from their servers, the Stripe webhook receivers, Caddy's TLS `ask` endpoint, and a worker process for queues and schedules. This page is the component specification: folder tree, modules, environment variables, jobs, commands, the OpenAPI document and tests. Design and decisions are in [`../docs/`](../docs/README.md); start with [`../docs/architecture.md`](../docs/architecture.md).

Related: [`../docs/api-inventory.md`](../docs/api-inventory.md) (endpoints), [`../docs/data-model.md`](../docs/data-model.md) (schema), [`.env.example`](.env.example), [MVP tech stack](../../docs/mvp/tech-stack.md#platform-backend-platformbackend-velexisplatform-backend), [conventions](../../docs/mvp/conventions.md#2-nestjs-backends).

## 1. At a glance

| Item | Value |
|---|---|
| Runtime | Node.js 22, TypeScript 5.6 strict, CommonJS output |
| Framework | NestJS 11 (Express 5), `nestjs-pino`, `nestjs-cls`, `@nestjs/bullmq`, `@nestjs/throttler` |
| Data | PostgreSQL 16 schemas `platform` and `reference` through `@velexis/db` (Kysely), role `velexis_platform_app` |
| Processes | API `dist/main.js` on `127.0.0.1:3100`; worker `dist/worker.js` with health on `127.0.0.1:3101`; CLI `dist/cli.js` |
| Public host | `https://api.platform.example.com` (Caddy); `/internal/*` blocked publicly |
| Contract | `openapi/velexis-platform-api.openapi.yaml` (created in M1 from the [API inventory](../docs/api-inventory.md)) |
| systemd units | `velexis-platform-api.service`, `velexis-platform-worker.service` ([ADR-0007](../../docs/mvp/adr/0007-single-vm-without-docker.md)) |

There is no reference-data folder and no reference loader in this package. The vendored datasets and their loader live in `tools/reference-data` (`@velexis/reference-data`) and run through `pnpm db:seed:reference` with this backend's database role ([ADR-0024](../../docs/mvp/adr/0024-reference-data-sources-and-loader.md)). The backend owns the `reference` migrations and only reads the tables.

Each module follows [`conventions.md` §2](../../docs/mvp/conventions.md#layout-one-module-per-bounded-context): thin controllers bound to an `operationId`, services owning transactions, Kysely repositories, gateways for external calls, processors for jobs. The module list, layers and responsibilities are in [`../docs/architecture.md`](../docs/architecture.md) §2.

## 3. Environment variables

Loaded and validated by `src/config.ts` (`@velexis/config`); the process refuses to start on a missing or invalid value. On the VM both processes read `/etc/velexis/platform-backend.env` (template [`deploy/env/platform-backend.env.example`](../../deploy/env/platform-backend.env.example)); the worker also reads the optional overlay `/etc/velexis/platform-worker.env`, which only overrides values for the worker. Locally they come from `.env.local` based on [`.env.example`](.env.example). "New" marks variables this document adds to the [configuration matrix](../../docs/mvp/architecture.md#6-configuration-matrix); the task that first reads one adds it to the matrix, the root `.env.example` and `deploy/env/` ([`conventions.md` §8](../../docs/mvp/conventions.md#8-configuration)).

The queues are opened by `QueuesModule` (PBE-009): BullMQ prefix `vx`, the process's BullMQ connection of `RedisModule`, and the defaults of ADR-0009 (`attempts: 5`, exponential backoff from 30 s, failed jobs kept 30 days, completed ones 1 day). A processor uses `@Processor(PLATFORM_QUEUE.<topic>, platformWorkerOptions(…))` for the concurrency of [`../docs/architecture.md`](../docs/architecture.md) §5. The worker only consumes; the API only produces.

The schedules of architecture §5 are declared in `src/common/queues/scheduler.registry.ts` (`PLATFORM_SCHEDULES`, cron patterns in UTC). When the worker starts, `JobSchedulerRegistry` upserts one BullMQ job scheduler per schedule on `platform-maintenance` (scheduler id = job name, e.g. `provisioning.reconcile`, empty payload), in the background so the worker starts while Redis is down. A schedule of a milestone switch that is off ([PADR-0015](../docs/adr/0015-milestone-feature-switches.md): `FEATURE_CUSTOM_DOMAINS`, `FEATURE_STRIPE_BILLING` or `FEATURE_OWN_STRIPE`, `FEATURE_SETTLEMENTS`; a variable the configuration does not define counts as off) is not registered, and any other scheduler found on the queue is removed, so turning a switch off stops its schedules at the next worker start. The log line `scheduler.registered` lists what was registered, skipped and removed.

BullMQ hands any job of a queue to any worker of that queue, whatever its name, so the schedules share one consumer: `MaintenanceProcessor` (`src/common/queues/maintenance.processor.ts`, PBE-021, concurrency 1), registered by WorkerModule. A module adds the work of a schedule with an injectable class marked `@MaintenanceJob("<schedule id>")` that implements `run(job)`, provided in its `forWorker()` module; the processor finds the handlers among the worker's providers when it takes its first job. A decorator for an id that is not in `PLATFORM_SCHEDULES`, or two handlers of one schedule, is a programming error. A job whose schedule has no handler yet completes without doing anything (one `maintenance.no_handler` warning per name and process); a handler that throws fails the job (`maintenance.job_failed`) and BullMQ tries it again with the defaults of ADR-0009. Never add a second `@Processor` on `platform-maintenance`.

The e-mail processor has one scheduler of its own, on its own queue (PADR-0013 item 2): `email.sweep` on `platform-emails`, every minute (`every: 60000`, first run at worker start), registered by `EmailSweepScheduler` (log `email.sweep_registered`). It is not in `PLATFORM_SCHEDULES`, so `JobSchedulerRegistry` never removes it. The credential submissions have one the same way (FIX-W38-PLATFORM, lead decision (2f) of 2026-10-31): `credentials.sweep` on `platform-connections`, every 5 minutes (`every: 300000`, first run at worker start), registered by `CredentialsSweepScheduler` (log `credentials.sweep_registered`) whatever the switches say, so a submission made while a switch was on still loses its secrets after it is turned off (Credential submissions below).

### E-mail outbox (PBE-011, [PADR-0013](../docs/adr/0013-platform-email-outbox.md))

- **Queue.** A module that sends e-mail imports `NotificationsModule` and calls `OutboxService.queue(trx, {templateKey, to, accountId?, tenantId?, data, secretData?, idempotencyKey?})` inside its own `runInTransaction(platformDb, …)`: one `email_outbox` row (`pending`), and after the commit the job `email.send {emailId}` (job id = e-mail id, nothing else in the payload, ADR-0009). `queueOpsAlert(trx, {title, message, tenantId?, idempotencyKey?})` sends `ops.alert` to `OPS_ALERT_EMAIL`. `portalLink(path, query)` and `adminLink(path, query)` build links on `PUBLIC_PORTAL_URL` and `PUBLIC_PLATFORM_ADMIN_URL`.
- **Checks in the caller's transaction** (a bad call rolls the business change back): a known template key; `to` one plain address (the OpenAPI `email` format, no display name, comment or second address); `data` and `secretData` exactly the template's allow-list (`templates.ts`), strings of at most 4000 characters; every link variable (`…Url`) starting with one of the two public URLs (PADR-0013 item 7).
- **Secrets.** `secretData` (links with tokens) is envelope-encrypted into `secret_payload_ciphertext` with the associated data `platform.email_outbox.secret_payload_ciphertext:<id>` (`EnvelopeService` of `common/crypto.provider.ts`, the KEKs of `MASTER_KEY_DIR`). It is never stored in clear, logged or queued (`secretData` is on the redaction list of `@velexis/logger`), and the update that makes a row `sent` or `failed` erases it and sets `secrets_purged_at`.
- **Idempotency.** With an `idempotencyKey`, the e-mail id is derived from the template, the lower-cased recipient and the key (`eml_` and 26 Crockford base32 characters of a SHA-256), so the same e-mail is queued once, also from two concurrent transactions (`INSERT … ON CONFLICT (id) DO NOTHING`); `queue` then answers `{emailId, queued: false}`. The key holds as long as the row exists (sent rows are deleted after 30 days, `purge.daily`).
- **Redis down at the commit** never fails the caller: the enqueue gives up after 2 seconds (`email.enqueue_timeout`, `email.enqueue_failed`), and the sweep enqueues the row.
- **Send** (`email.processor.ts`, worker only, concurrency 4): claim the row (`pending`, or a `sending` row whose worker stopped, becomes `sending`, `attempts + 1`; a missing or final row is skipped), decrypt, check the allow-list again, render the subject, HTML and text (Handlebars in strict mode, HTML-escaped HTML part, one-line subject), send through SMTP (`mailer.gateway.ts`: Nodemailer, no pooling, 10-second connection and greeting timeouts, 30-second socket timeout, no file or URL access, the recipient also as the SMTP envelope, Message-ID `<eml_…@sender domain>`), then mark it `sent` with `sent_at` and `provider_message_id` (the Message-ID) and erase the ciphertext in one update. An SMTP failure puts the row back to `pending` with `last_error` (the SMTP error code, reply code and command only, never the server's text) and BullMQ retries (5 attempts, backoff from 30 s); the last attempt marks it `failed` and erases the ciphertext. An e-mail that can never be sent (unknown template, variables outside the allow-list, a ciphertext that does not decrypt for its row, an invalid recipient) fails at once (`UnrecoverableError`).
- **Sweep** (`email.sweep`, every minute): `pending` rows older than 2 minutes and `sending` rows unchanged for 10 minutes whose BullMQ job is missing or finished get a new `email.send` job (log `email.sweep` with the count).
- **Templates** (`src/notifications/templates/<key>.{subject,html,txt}.hbs`, English): `auth.verify_email`, `auth.account_exists`, `auth.password_reset`, `auth.password_changed`, `auth.mfa_changed`, `team.invitation`, `tenant.welcome`, `tenant.provisioning_failed`, `tenant.suspended`, `tenant.resumed`, `ops.alert`; M5 adds `payouts.reviewed` (PBE-058), `settlement.paid` (PBE-060), `connection.stripe_disconnected` (PBE-056), `domain.verified` and `domain.failed` (PBE-050; `domain.failed` also for three failed daily re-checks, with its `failure` sentence, PBE-051), `domain.removed` (PBE-051), `billing.payment_failed` (PBE-046), `billing.trial_ending` (PBE-047) and `billing.trial_ended` (FIX-W41-PLATFORM). They are logic-less (text and `{{variable}}` only: no helpers, blocks, partials or triple braces), name only their allow-list and the built-ins `portalUrl` and `adminUrl`, and are loaded and checked when the worker starts. The build copies the folder to `dist/notifications/templates`; Prettier ignores `*.hbs` (their whitespace is the text part's content). A new template adds its key and allow-list to `EMAIL_TEMPLATES` and its three files, and `templates.test.ts` renders it with sample data.
- **Logs** carry the e-mail id, the template, the attempt and the SMTP error code (`email.sent`, `email.send_failed`, `email.render_failed`, `email.skipped`, `email.sweep`), never the recipient, a variable or the message.

### API keys (PBE-021, [PADR-0005](../docs/adr/0005-api-key-format-and-hashing.md))

- **Generator** (`src/api-keys/api-key-generator.ts`): `<pk|sk>_<test|live>_` + 40 base62 characters from the CSPRNG (rejection sampling, so each character is uniform), the first 14 characters as the unique `prefix`, `last4`, and `key_hash = hex(HMAC-SHA-256(pepper, key))` with the pepper of `API_KEY_PEPPER_FILE` (read once at start-up). `ApiKeyGenerator.issue(trx, …)` inserts with `ON CONFLICT DO NOTHING` and makes a new key on a collision, at most three times (then `500 INTERNAL_ERROR`). `issueInitialTestKeys(trx, tenantId)` issues the `pk_test` key without origins and the `sk_test` key scoped `storefront` of a new OTA (names `Initial test key (…)`, no creator, `api_key.created` audited by the system) and returns the full keys once, for the provisioning post-step of PBE-022.
- **Rules** (`src/api-keys/api-key-rules.ts`): origins only on publishable keys, exact as a browser sends them (`https`, or `http://localhost:<port>` and `http://127.0.0.1:<port>` on test keys; lower case, no default port, path, trailing slash, user info or wildcard; at most 20); scopes only on secret keys, from the OTA contract's `ConsoleApiKeyScope` and `StaffPermission` (lists checked at compile time against the generated OTA types and in `api-key-rules.test.ts` against the OTA document): no scopes (absent or empty) means `["storefront"]`, `storefront` stands alone, `console:automation` needs at least one permission and permissions need it. A broken rule answers `400 VALIDATION_FAILED` with field errors (`wildcard`, `origin`, `insecureOrigin`, `notCanonical`, `maxItems`, `notAllowed`, `unknownScope`, `scopeCombination`; `past` for an `expiresAt` that is not in the future).
- **Endpoints** (owners and admins): `listApiKeys` (newest first; `environment`, `includeRevoked`), `createApiKey`, `updateApiKey` (name, origins), `rollApiKey` (`expireOldIn` `now`, `1h`, `24h`, `7d`; the old key's expiry is never moved later than one it has) and `revokeApiKey`. Writes need an `active` OTA (`409 TENANT_NOT_ACTIVE`); a revoked key answers `409 CONFLICT` (`details.reason = "revoked"`); `live` keys, created or rolled, need the live switch (`FEATURE_LIVE_SWITCH`, PBE-061: `403 FEATURE_DISABLED` with `details.feature = live_switch`, checked by the service because test keys need no switch, before any other rule of a creation and as soon as a rolled key is found, always before the step-up) and a live OTA (`422 LIVE_MODE_NOT_ENABLED`), and a live secret key, created or rolled, a TOTP step-up (`assertRecentMfa`; the account's MFA state is read before the transaction opens, so a request never waits for a second pool connection while it holds one). Keys that are neither revoked nor expired count against `plans.limits.apiKeys` (`422 PLAN_LIMIT_REACHED` with `details.limit` and `details.used`; a roll that keeps the old key working needs room for both, while a roll with `now` replaces a working key one for one and needs none, so an OTA over its limit after a downgrade can still replace a leaked key); creations and rolls of one OTA are serialised by a transaction-level advisory lock. The answers of create and roll carry the full key once with `Cache-Control: no-store` (never stored for a replay, never logged); the row holds only the prefix, `last4` and the HMAC. Audit rows `api_key.created`, `api_key.updated`, `api_key.rolled` and `api_key.revoked` hold the prefix, kind, environment and scopes (and the changed name or origins, the new prefix and the expiry), never the key. Update, roll and revoke publish `vx:invalidate {type: "api_key", prefix}` after the commit.
- **Usage flush** (`api_keys.flush_usage`, every 5 minutes, `src/api-keys/usage-flush.processor.ts`): for every key not revoked or expired more than a day ago, in pages of 500 ids, `GETDEL apikey:used:<keyId>` (written by the OTA backend as `{at, ip}`, `at` an ISO date-time or epoch milliseconds) and one `UPDATE` per page of `last_used_at` and `last_used_ip`, which never moves the last use back. An `ip` that is not an address is stored as `null`; a counter that is not `{at, ip}` is dropped (`api_keys.usage_discarded`, with the key id only). Log `api_keys.usage_flushed` with the counts.

### Invitations (PBE-026, [team flow §A](../docs/flows/team-and-ota-admin-sso.md#a-invitations))

- **Create** (`createInvitation`, owners and admins): only owners invite owners or admins (`403 FORBIDDEN`); an address that belongs to a member who is not removed answers `409 ALREADY_MEMBER`, one with a pending invitation `409 INVITATION_PENDING` (letter case ignored, as the unique index `tenant_invitations_pending_uq` on `lower(email)`); `active` members plus `pending` invitations must stay below `plans.limits.staffSeats` (`422 PLAN_LIMIT_REACHED` with `details.limit` and `details.used`; a plan without the limit allows none). Creations of one OTA are serialised by a transaction-level advisory lock. The row holds the SHA-256 of a 256-bit token (`iv_` + 43 base64url characters) and `expires_at = now + 7 days`; the e-mail `team.invitation` carries the link `PUBLIC_PORTAL_URL/invitations/accept?token=…` as the outbox's encrypted secret data, never in an answer, a log or an audit row. Audit `invitation.created` with the address and role.
- **List, resend, revoke** (owners and admins, within the role matrix for the invited role): `listInvitations` shows the `pending` ones, newest first; `resendInvitation` gives a pending invitation a new token and 7 more days from now and queues the e-mail again (the old link stops working at once; audit `invitation.resent`); `revokeInvitation` sets it `revoked` (audit `invitation.revoked`). Both answer `409 CONFLICT` (`details.reason = "not_pending"`) for an invitation that is not pending.
- **Look up and accept** (`lookupInvitation` public, 20 per end-user IP per hour; `acceptInvitation` for a verified portal account): the invitation must be `pending`, unexpired and of an OTA members can see, else `400 INVITATION_INVALID` (one answer for every reason). Acceptance re-reads the account, because the access token does not carry its state (a disabled or deleted account answers `401 UNAUTHENTICATED`, one not verified `403 EMAIL_NOT_VERIFIED`), needs its verified address to equal the invited one, letter case ignored (`403 INVITATION_EMAIL_MISMATCH`), and locks the invitation row first, so one link accepted twice gives one membership. In one transaction it inserts the membership with the invited role and inviter, or makes a `removed` one active again (same `stf_` id; `409 ALREADY_MEMBER` for an active or suspended member), sets the invitation `accepted`, and audits `membership.created`; after the commit it publishes `vx:invalidate {type: "membership", accountId, tenantId}`.
- **Expiry** is decided at use; `invitations.expire` (hourly at minute 5, `src/memberships/invitations-expire.scheduler.ts`, provided by `MembershipsModule.forWorker()`) sets the `pending` invitations past `expires_at` `expired`, in batches of 500 per transaction (rows another transaction holds are skipped), with one `invitation.expired` audit row of the system each, and logs `invitations.expired` with the count. Until then an invitation past its expiry is still pending: listed, holding its seat and address, and it can be resent or revoked.

### Console token (PBE-039, [team flow §C](../docs/flows/team-and-ota-admin-sso.md#c-open-console-m4), [PADR-0007](../docs/adr/0007-portal-to-ota-admin-sso-token.md))

- **Who** (`createConsoleToken`, `POST /v1/tenants/{tenantId}/console-token`, `ConsoleTokenController` of `src/memberships/members.controller.ts` over `console-token.service.ts`): every active member, 30 per account per minute (`consoleToken` of `throttler.config.ts`, `429 RATE_LIMITED` with `Retry-After`). A fresh read of the membership with its account and tenant (`MembershipsRepository.findConsoleTokenState`) then refuses, in this order, an account that no longer holds a session (`401 UNAUTHENTICATED`), an unverified one (`403 EMAIL_NOT_VERIFIED`), a membership gone since the guard's read (`404`), a tenant that is not `active` (`409 TENANT_NOT_ACTIVE` with `details.status` and, when suspended, `details.suspensionReason`), and a live OTA (`storefront_environment = 'live'`) for an account without MFA (`403 MFA_REQUIRED`, PADR-0008; no step-up needed).
- **Token**: `ptk_` + 43 base62 characters from the CSPRNG (rejection sampling, 256 bits). `SET ptk:<sha256 hex> <json> EX 60 NX` (`redisKeys.portalToken`, `setKeyIfAbsent`) with `{v: 1, accountId, tenantId, membershipId, role, mfa, issuedAt, requestId}`, the value the OTA backend takes with `GETDEL`. Redis first: while it refuses the write the answer is `503 SERVICE_UNAVAILABLE` and nothing else is written. Then the audit row `console.token_issued` (target the membership, details `role`, `mfa`, `expiresAt`, never the token or its digest); if it fails, the key is deleted again (`console_token.discard_failed` when that fails too), so no usable token lacks its audit row.
- **Answer**: `201 {portalToken, expiresAt, consoleSsoUrl}` with `Cache-Control: no-store` (also on the service's refusals; a guard's refusal before the handler carries no token either), `consoleSsoUrl` = `PUBLIC_OTA_ADMIN_URL` with `/sso`. The token is never logged (no line names it; a Redis error is reduced to its name and message, since an ioredis reply error lists the command's arguments), never in the idempotency store (the operation is not idempotent, and `no-store` answers are never stored) and in no other Redis key or value.

### Credential submissions (PBE-052, [PADR-0010](../docs/adr/0010-credential-submission-and-verification.md), [Amadeus flow §D](../docs/flows/amadeus-connection.md#d-ota-owned-credentials-m5), [Stripe payments flow §D](../docs/flows/stripe-payments-account.md#d-api-keys-m5))

- **What it is.** The framework that own Amadeus credentials (PBE-053) and own Stripe API keys (PBE-057) share: the credentials wait in `platform.credential_submissions` while a worker job verifies them, so a typo never breaks a working connection. `src/common/credentials/`: `CredentialSubmissionsModule` (static, with `CredentialSubmissionsService` for the modules whose operations submit; `forApi()` adds the read route, AppModule; `forWorker()` is the verification and the registry of verifiers, imported by SupplierConnectionsModule's worker part, whose `VerificationProcessor` is the one processor of `platform-connections`, and by every worker module that registers a verifier). `forWorker()` answers the static `CredentialSubmissionsWorkerModule` class itself, never a new `{ module: … }` object: Nest 11 tells dynamic modules apart by object reference, so a DynamicModule built per call would give each importer its own registry, and a verifier registered from PBE-057's module would never reach the processor.
- **Submit** (`CredentialSubmissionsService.submit(trx, {tenantId, kind, environment, publicData, secrets, submittedBy})`, in the operation's `runInTransaction`, after its own checks): takes the slot's advisory lock (tenant, kind, environment), so two submissions at the same time run one after the other; marks the open submission of the slot `superseded` with both secrets erased and `finished_at`; inserts the new one `pending` with each secret envelope-encrypted (associated data `platform.credential_submissions.secret_ciphertext:<id>` and `…webhook_secret_ciphertext:<id>`; the webhook secret is required for `stripe_api_keys` and refused for `amadeus`) and the non-secret fields in `public_data` (a field named like a secret is refused); writes the kind's audit row (`amadeus.credentials_submitted`, `payments.api_keys_submitted`: the public fields, the superseded id, never a secret); after the commit enqueues `credentials.verify {submissionId}` (job id = submission id). A call that can never give a submission throws `InvalidCredentialSubmissionError` and rolls the operation back. Redis down does not fail the committed request (`credentials.enqueue_failed`, `credentials.enqueue_timeout`): the submission stays `pending`, and a new one supersedes it.
- **Verify** (`CredentialsVerifyProcessor`, 5 attempts, backoff from 30 s): the submission becomes `verifying` with `attempts + 1` (a `pending` one, or one a crash or an earlier attempt left `verifying`: a retry always finds it; a final or missing one is skipped). The secrets are decrypted and handed, outside any transaction, to the `check` of the verifier registered for the kind (`CredentialVerifiers.register(kind, verifier)`, once per kind; PBE-053 and PBE-057 register theirs): `verified`, `rejected` with a stable code and a sanitised message (final at once), or `unavailable` (retried, the submission stays `verifying` without an error; the last attempt fails it with `PROVIDER_UNAVAILABLE` and the provider's message). An attempt that cannot complete otherwise (no verifier for the kind, a secret that does not decrypt, a `check` or `apply` that throws, an answer that breaks the contract) is retried the same way, then fails with `PROVIDER_UNAVAILABLE`, so no submission keeps its secrets past its last attempt. Then one transaction, with the submission locked and still `verifying` (else nothing is written: a newer submission superseded it, or the sweep below failed it; the job's result then names the status the submission has, `superseded` or `failed`): the verifier's `apply(trx, …)` switches the connection (or throws `CredentialRejection` to fail the submission, its writes rolled back); the submission becomes `applied` or `failed` (`error_code`, `error_message`) with both secret columns erased in the same UPDATE (the CHECK `credential_submissions_secret_purge_ck` refuses anything else) and `finished_at`; the kind's audit row (`…credentials_applied` / `…_rejected`, `payments.api_keys_applied` / `…_rejected`; actor `system`, label `credentials.verify`; `apply` adds what it changed); and the submitter's e-mail `connection.credentials_applied` or `connection.credentials_failed` (PADR-0013 item 5; the credentials, environment, reason and a link to the portal's Amadeus or payments page) while the account is active and still a member of the OTA (idempotency key `credentials:<submissionId>`).
- **Switches** (FIX-W39-PLATFORM, lead decision (2b) of 2026-11-02; `SUBMISSION_FEATURES`): the worker applies a kind only while its milestone switch is on (`amadeus`: `FEATURE_OWN_AMADEUS`, `stripe_api_keys`: `FEATURE_OWN_STRIPE`; the worker's FeatureSwitches). An attempt of a switched-off kind fails the submission at its start, before anything is decrypted or a provider is asked (`CredentialsVerifyProcessor.process`): `failed` with `FEATURE_DISABLED` and a fixed message, both secret columns erased, the kind's `*_rejected` audit row (`details.reason = feature_disabled`, `details.feature`) and the submitter's `connection.credentials_failed` e-mail, in the attempt's final transaction with its status guard. The sweep below fails a `pending` submission of a switched-off kind the same way (`failSwitchedOff`, label `credentials.sweep`) instead of queueing it again; a `verifying` one past the hour is failed with `PROVIDER_UNAVAILABLE` whatever the switch says.
- **Sweep** (`credentials.sweep`, every 5 minutes on `platform-connections`, `src/common/credentials/credentials-sweep.ts`; FIX-W38-PLATFORM, lead decision (2f) of 2026-10-31): a submission `pending` for more than 10 minutes (`updated_at`; its enqueue was lost, or its job ended before an attempt started) gets `credentials.verify` again with the submission id as the job id: a job of the id that still waits, is delayed or runs is left to finish, so two sweeps never queue one twice, and a finished one is removed first (BullMQ ignores an add whose job id it keeps). A submission `verifying` for more than 1 hour (`updated_at`, which every attempt's first step sets; the five attempts and their backoff take minutes) lost its job and fails (`CredentialsVerifyProcessor.failStuck`): `failed` with `PROVIDER_UNAVAILABLE` and the fixed message, both secret columns erased, the kind's `*_rejected` audit row (actor `system`, label `credentials.sweep`, `details.reason = verification_timeout`) and the submitter's `connection.credentials_failed` e-mail, in one transaction with the row locked and a status guard (still `verifying`, no attempt started since the cut-off): a job that finishes at the same time commits first and the sweep writes nothing, or finds the row `failed` in its final transaction and writes nothing itself (`credentials.verify_superseded`, its result `{submissionId, status: "failed"}`). At most 100 submissions of each kind per run; nothing is decrypted, and the log lines (`credentials.sweep_requeued`, `credentials.sweep_failed`, `credentials.sweep`) carry ids, the tenant, kind, environment, error code and counts.
- **No secret leaves the worker's memory.** The job data is the submission id, the result the id and the status, the errors BullMQ keeps are fixed texts, the log lines (`credentials.submitted`, `credentials.verify_started`, `credentials.verify_retry`, `credentials.applied`, `credentials.failed`, `credentials.verify_superseded`, `credentials.verify_skipped`) carry ids, kind, environment, attempt, outcome and error code; a verifier's error is logged by its name and its message with every secret of the submission replaced by `[secret]`, as the stored `error_message` is.
- **Read** (`getCredentialSubmission`, `GET /v1/tenants/{tenantId}/credential-submissions/{submissionId}`, owners and admins): status, error code and message, `createdAt`, `finishedAt`; never a secret, a ciphertext or the public fields; a submission of another OTA answers `404 NOT_FOUND`. Not audited (a read without personal data).
- **`pendingSubmission`** (FIX-W39-PLATFORM, lead decision (2k) of 2026-11-02; `src/common/credentials/pending-submissions.ts`): every answer that carries a connection shows the latest submission of the connection's kind and environment while it is `pending` or `verifying`, or after it `failed` (`{id, status, errorCode}`), and `null` otherwise. One query (`CredentialSubmissionsService.pendingByEnvironment(tenantId, kind, db?)` over `CredentialSubmissionsRepository.latestByEnvironment`, on the pool or the answer's transaction) and one mapper (`toPendingSubmission`, `pendingSubmissionOf`) serve `toAmadeusConnection` and `toPaymentConnection`, which take the pending submissions as an argument: `listAmadeusConnections`, `updateAmadeusConnection`, `requestLiveAmadeus`, `listPaymentConnections`, `updatePaymentConnection`, `useVelexisPayments`, `completeStripeConnect`, `adminGetTenant`, `adminSetConnectionStatus` and `adminAssignAmadeusOffice`.
- **Tests**: `src/common/credentials/credentials-sweep.test.ts` (the sweep's cut-offs by the Clock, a job queued again once with the submission id as its id and never over one that will still run, a finished job replaced, `failStuck`'s writes and its status guard, the scheduler, the log lines) and `test/integration/connections/credential-submissions.int.test.ts` (the worker graph's registry is a test registry of the file, `TestVerifierRegistry`, which keeps the test verifier and sets aside the real verifiers that PBE-053 and PBE-057 register in the worker graph, FIX-W38-PLATFORM; a test verifier registered for both kinds from a module of its own that imports `forWorker()`, as PBE-053 and PBE-057 do: supersede of a `pending` and of a `verifying` submission with its secrets erased and its answer never applied; two submissions at the same time; the secrets bound to their column and row; applied and failed with both columns null, audited, the submitter e-mailed through Mailpit, nobody when the submitter left; an unavailable provider retried to `PROVIDER_UNAVAILABLE`; no verifier for the kind, a secret that does not decrypt and an answer outside the contract retried to `PROVIDER_UNAVAILABLE` with both columns null; a crash in `check` or in `apply` retried; a row a crash left `verifying` completed; a `CredentialRejection` from `apply` rolled back; the read for each role; the sweep (FIX-W38-PLATFORM): the worker's job scheduler, a lost `pending` job queued again once and applied, a submission left `verifying` failed with both columns null, audited and e-mailed, a `credentials.sweep` job run by the queue's processor, a job that commits first and a sweep that commits first; and after every test no secret in any log line at `trace`, any Redis value or any audit, outbox or submission row).

### Velexis Amadeus accounts and office pool (PBE-020, [Amadeus flow §A](../docs/flows/amadeus-connection.md#a-velexis-shared-account-and-office-pool-platform-admin-m1), [PADR-0012](../docs/adr/0012-amadeus-office-pool.md))

- **Routes** (`src/admin/admin-amadeus.controller.ts` over `AmadeusAccountsService` and `AmadeusOfficesService`, `x-scope: platform_admin`): every change writes its audit row with `actor_type = 'platform_admin'` in the transaction of the change, and publishes its invalidations after the commit.
- **Accounts.** One per environment (`409 CONFLICT`, `details.reason = environment_exists`). `adminCreateAmadeusAccount` needs a TOTP step-up (`x-mfa-step-up`); `adminUpdateAmadeusAccount` needs one only for a new client secret, client id or base URL (checked by the service: the job and the OTA backend send the stored secret to that host), with `If-Match` (`412 PRECONDITION_FAILED`). New credentials set the account `pending_verification` and queue the verification after the commit; `status: disabled` wins over them (no verification). A disabled account stays disabled until `adminVerifyAmadeusAccount`, which takes it to `pending_verification` first (the verification job leaves a disabled account alone, so a job queued before the disable, for example one waiting for a retry, never undoes it). - **Verification** (`amadeus_account.verify {amadeusAccountId}` on `platform-connections`, `verification.processor.ts`; `amadeus-oauth.gateway.ts`): the worker decrypts the secret and posts `grant_type=client_credentials` to `{baseUrl}/v1/security/oauth2/token` (10-second timeout, redirects never followed, at most 64 KiB of the answer read, the token discarded). A token makes the account `active` with `last_verified_at` (audit `amadeus_account.verified`, actor `system`); a refusal (4xx other than 408 and 429, a 2xx without a token, a redirect, a secret that does not decrypt) makes it `invalid_credentials` at once with a short `last_error` such as `HTTP 401 invalid_client (Amadeus code 38187)`: the HTTP status, the OAuth error code and the Amadeus error code, never the body (audit `amadeus_account.verification_failed`). A job that finds the account `disabled` sends nothing and ends `superseded`. The result is written only when the host, client id, secret and status are still those the job tested (an update queues its own verification), and a changed status publishes the `amadeus_account` invalidation. The job data is the account id; its result the id and the status; log lines (`amadeus_account.verified`, `amadeus_account.verification_failed`, `amadeus_account.verify_superseded`) the id, environment, outcome, attempt and short error.

Retirement and assignment publish `amadeus_account` (an office status changed).
- **Pool level** (`amadeus.pool_level`, daily at 06:55 UTC, `pool-level.scheduler.ts`): for each account that is not `disabled`, fewer than 3 `available` offices queue an `ops.alert` e-mail to `OPS_ALERT_EMAIL`, once per environment and UTC day (outbox idempotency key `amadeus.pool_level:<environment>:<date>`); log `amadeus.pool_level` with the counts.

### Provisioning post-steps (PBE-022, [provisioning flow §3](../docs/flows/provisioning.md#3-platform-post-steps-platform-worker-platform-tenant-events-consumer), [PADR-0001](../docs/adr/0001-tenant-provisioning-orchestration.md))

The attempt comes from the event's BullMQ id `<jobId>-<attempt>`. A step that throws rolls back; the runner appends `{step, status: "failed", error: {code, message}}` and the job's `error` (the SQLSTATE or the error's code, never its message) and fails the BullMQ job (`provisioning.post_step_failed`), which BullMQ tries again with the producer's options; the next try resumes at the failed step.
- **Steps** (`src/provisioning/post-steps/*.step.ts`): `record_migrations` upserts the event's ledger into `tenant_schema_migrations` (`applied`, checksum, phase, duration, the job as `runner_id` of a version not mirrored before) and sets `tenants.schema_version`. `assign_amadeus_office` takes the tenant's connection lock of `test`, then the oldest `available` office of the Velexis test account with `FOR UPDATE SKIP LOCKED` (concurrent provisionings get different offices and never wait for each other), assigns it and inserts the `velexis` connection (`office_ids = {office}`, default, queuing and owner office, `active`; else the tenant key; else none), `ON CONFLICT (tenant_id, provider, environment) DO NOTHING`. `issue_api_keys` issues `pk_test` and `sk_test` with `ApiKeyGenerator.issueInitialTestKeys` (unless `result.apiKeyIds` exists) and envelope-encrypts the two raw keys, as the `InitialKeys` answer of the reveal, into `reveal_ciphertext` (associated data `platform.provisioning_jobs.reveal_ciphertext:<jobId>`); the raw keys are never stored in clear, logged or queued. `activate` sets the tenant `active` (from `provisioning` only; `activated_at`, `version + 1`) and the job `succeeded` (`finished_at`, no lease, no error) and audits `tenant.activated` as `system`. `notify` queues `tenant.welcome` to every active owner (idempotency key = job id, so one e-mail per owner and job) and publishes the `tenant` and `connection` invalidations after its commit.

### Provisioning failures, reconciler and the setup page (PBE-023, [provisioning flow §4 and "Failure handling"](../docs/flows/provisioning.md#failure-handling), [PADR-0001](../docs/adr/0001-tenant-provisioning-orchestration.md) items 4, 6 and 7)

- **Failure handler** (`src/provisioning/failure-handler.ts`, worker): the one way a failed attempt of any job kind ends, in one transaction that locks the job's row and acts only while it is `running` at the failed attempt (so a late event, a second reconciler run or a dispatch meanwhile never count an attempt twice). A retryable failure with `attempt < max_attempts` (5) puts the job back to `queued`, due at `now + 30 s × 2^attempt`, without a lease, with the error; otherwise the job is `failed` (`finished_at`). Only a `provision` job touches the tenant: `provisioning → failed` (conditional), and when that happened the audit row `tenant.provisioning_failed` (`system`), the e-mail `tenant.provisioning_failed` to every active owner (keyed by the job id) and the `tenant` invalidation. A `migrate`, `suspend` or `resume` job never changes `tenants.status`. Every job that fails for good queues one `ops.alert` (keyed `provisioning.failed:<jobId>`). The job's `error` is `<step> failed: <CODE>: <message>` (at most 1,000 characters). Logs: `provisioning.retry_scheduled`, `provisioning.job_failed`, `provisioning.failure_ignored`.
- **Its three callers.** The consumer of `platform-tenant-events` hands it `tenant.provision_failed` of the job's current attempt (retryable as the OTA worker says; the OTA worker's steps of the attempt are appended to the step log, so the setup page shows the failed step; `{outcome: "requeued" | "failed"}` is kept with the BullMQ job). When post-steps fail on the event's **last** BullMQ try (`isLastTry`: `attemptsMade + 1 >= opts.attempts`), the consumer fails the job with the step's name first (not retryable; a retry runs the post-steps again). The reconciler hands it lost attempts (below).
- **Reconciler** (`provisioning.reconcile`, every 5 minutes, `src/provisioning/reconciler.scheduler.ts`): first the `running` jobs whose lease has ended (`locked_until <= now`, at most 100 per run; a job inside its lease is never touched). For each, BullMQ is asked about `<jobId>-<attempt>` on `ota-tenant-ops` (the message) and then on `platform-tenant-events` (the answer; the OTA worker adds it before its message finishes, so asking in this order never misses it): while either is `waiting`, `active`, `delayed`, `prioritized` or `waiting-children`, the lease is extended by 15 minutes and `locked_by = 'reconciler'`; a lease that ends again with that mark means the job stayed `running` across two leases, and ops get one `ops.alert` per attempt (keyed `provisioning.reconcile.stuck:<jobId>:<attempt>`). Otherwise (the message is missing, or failed or completed without an answer the platform acted on) the attempt is lost: a retryable failure (`ATTEMPT_LOST`) through the failure handler, whatever the kind. A dispatch clears `locked_by`. Then the `queued` jobs that are due and have a message, oldest first (at most 1,000 per run), are dispatched when `checkDispatch` says their gate is open. One request id per run; a job that throws is logged (`provisioning.reconcile_failed`) and left for the next run; the run logs `provisioning.reconciled` with counts.
- **Purge** (`provisioning.purge_reveals`, hourly at minute 35, `src/provisioning/purge-reveals.scheduler.ts`): one UPDATE erases `reveal_ciphertext` and its KEK id of every job that finished 24 hours ago or more and was never revealed (`provisioning.reveals_purged` with the count). The keys stay valid; only the one copy that could still be shown goes.
- **Portal routes** (`LifecycleController`, `ProvisioningModule.forApi()`): `getProvisioning` (any member) answers the tenant's status and its latest `provision` job (the active one, else the newest) with the step log in the schema's shape, attempts, the last error and `initialKeysAvailable` (a succeeded job whose unrevealed ciphertext is younger than 24 hours). `retryProvisioning` (owners) locks the tenant: only a `failed` one is retried (`409 PROVISIONING_NOT_RETRYABLE`, also when a `provision` job is active already); it goes back to `provisioning` (`version + 1`), a **new** `provision` job is queued (the failed ones stay as history), `provisioning_job.retried` is audited, and after the commit a `tenant` invalidation is published (the status changed, [architecture §6.3](../docs/architecture.md#63-cache-invalidation-vxinvalidate), as the admin's retry publishes it; FIX-W32-PLATFORM) and the job is dispatched as createTenant's is; the answer is `202 {job, checkoutUrl: null}` (with `FEATURE_STRIPE_BILLING` on, a tenant failed by an abandoned Checkout gets a new Checkout instead, PBE-044 below). `revealInitialKeys` (owners) locks the latest `provision` job; within 24 hours of a succeeded setup it decrypts the ciphertext (associated data `platform.provisioning_jobs.reveal_ciphertext:<jobId>`) and in the same update sets `revealed_at` and `revealed_by_account_id` and erases the ciphertext; `tenant.initial_keys_revealed` is audited with key ids and prefixes only. The answer carries `Cache-Control: no-store` and is never stored for a replay. After the reveal, or from 24 hours after `finished_at` (purged or not), `410 KEYS_ALREADY_REVEALED`; before the setup has issued its keys, `404 NOT_FOUND`.
- **Repositories.** `ProvisioningJobsRepository` gained the locked read of the failure handler and the reconciler, `requeue`, `markFailed`, the lease reads and extension, the dispatch candidates, the progress reads and the reveal writes; `TenantsRepository` gained `failProvisioning` (`provisioning → failed`) and `reopenFailed` (`failed → provisioning`), both conditional with `version + 1`.

### Platform admin sign-in and bootstrap (PBE-028, [PADR-0006](../docs/adr/0006-platform-admin-access-and-audit.md), [admin flow §A](../docs/flows/platform-admin-operations.md#a-access))

- **Sign-in** (`src/admin/admin-auth.controller.ts` over `AdminAuthService`). `adminSignIn` runs the portal's password step (`SignInService.verifyPassword`: the same lockout and failure count, the same Argon2id work for an unknown address; a wrong password is audited as `admin.sign_in_failed`). - **Sessions.** Admin access tokens have `aud = platform_admin`, `ev = true`, `amr = ["pwd","otp"]` and `mfa_at`. `adminRefresh` rotates only admin families (a portal refresh token answers `REFRESH_TOKEN_INVALID` and changes nothing, as the portal's `refreshSession` does for admin tokens); a reused token revokes the family; each refresh token lives 2 idle hours and never past the family's end, so no admin session outlives 12 hours; an account that is no longer an active admin with MFA cannot refresh. `adminStepUp` takes a fresh TOTP code (`MfaService.verifyStepUpCode`) and rotates the caller's family with `mfa_verified_at` = now. `adminSignOut` revokes the caller's admin family of the presented token (`204` whatever it is). `adminGetMe` answers `{id, email, fullName, features}` (`featuresFor()`).
- **Bootstrap** (`src/admin/admin-cli.commands.ts`, run through `dist/cli.js`, §5). Each command loads the configuration and runs in a Nest application context of its own (`AdminCliModule`: `CommonModule.forCli()`, the audit, the outbox, the repositories of AuthModule); log lines go to stderr. `admin:grant` needs an `active` account with a verified address and MFA, sets `is_platform_admin` (`version + 1`) and writes one `admin.granted` row; an admin already is left as it is. `admin:reset-mfa` (platform admins only) writes `staffdeny:acct:<id>`, then turns MFA off, deletes the recovery codes, revokes every session family (`revoke_reason = 'admin'`), queues `auth.mfa_changed`, writes one `account.mfa_reset` row and publishes an `account` invalidation after the commit. Both rows have `actor_type = 'system'` and `actor_label = 'cli <command> by <operator>'`.

### Suspension, resume, migrate and connection status (PBE-030, [PADR-0014](../docs/adr/0014-tenant-suspension-and-resume.md), [provisioning flow §5](../docs/flows/provisioning.md#5-migrate-job), [admin flow §B](../docs/flows/platform-admin-operations.md#b-tenants), scope PF-82)

- **Routes** (`src/admin/admin-tenants.controller.ts` over ProvisioningModule's `SuspensionService` and `MigrateService`, `x-scope: platform_admin`). - **Suspend** (`adminSuspendTenant`, reason `abuse`, `request` or `admin`; `billing` is billing sync's only): one transaction locks the tenant; only an `active` one (`409 CONFLICT`, `details.reason = not_active`) becomes `suspended` with `suspended_at`, `suspension_reason` and `version + 1`; a `suspend` job (payload `{reason}`) is queued, `tenant.suspended` audited and the e-mail `tenant.suspended` queued to every active owner (keyed by the job id). A suspend or resume while the previous job of its kind still waits for its answer supersedes that job (`canceled`, error `SUPERSEDED: …`, named in the audit row), since `provisioning_jobs_active_uq` allows one active job of a kind; its late answer is then ignored.
- **The OTA worker's answers** (the consumer above): `tenant.suspended` and `tenant.resumed` of the job's current attempt mark the job `succeeded`, whatever the tenant's status is now (PADR-0014 item 7). A changed version or a finished job writes one `tenant.migrated` row (`system`). `tenant.migration_failed` of a job goes to the failure handler (retryable as the OTA worker says, absent counting as not retryable): back to `queued` with the backoff, or `failed` with an `ops.alert`, never the tenant's status. One of the fan-out (`jobId: null`) queues one `ops.alert` per tenant and deploy run (keyed `tenant.migration_failed:<tenantId>:<requestId>`) with one `tenant.migration_failed` audit row (`system`, label `deploy`).
- **Connection status** (`adminSetConnectionStatus`, reason): the Amadeus (`supplier_connections`) or payment (`payment_provider_connections`) connection of one environment, its row locked (`404` without one). `disabled` sets it `disabled` (`version + 1`); a disabled one stays as it is and nothing is written. `active` only on a `disabled` connection (`409 not_disabled`) that can work again: an Amadeus connection with an office (`no_office`), a payment connection not deauthorised in Stripe (`deauthorized`). A change writes `connection.status_changed` (status before and after, kind, environment, reason) and publishes `{type: "connection", tenantId}`. The answer is the portal's masked connection.
- **Repositories.** `TenantsRepository` gained `suspend` (`active → suspended`) and `resume` (`suspended → active`), both conditional with `version + 1`; `ProvisioningJobsRepository` `supersedeActive`; `SupplierConnectionsRepository` and `PaymentConnectionsRepository` `setStatus` (and the payment one `lockForTenant`), which never select or return the secrets' ciphertext columns; `SubscriptionsRepository.findShownForTenant` reads on the caller's transaction, so a resume checks the subscription under the tenant's row lock.

The stored account typed again changes nothing (FIX-W35-PLATFORM, lead decision (2i) of 2026-10-30): in the transaction the row is locked with its ciphertext (`lockWithDetailsForTenant`), and when the holder (trimmed), country, currency, scheme and `last4` match, the stored identifiers are decrypted in memory only (never logged) and compared with the typed ones after the save's normalisation; if they are the same, the answer is the current account as it is (`200`, the same version, status and review, so a verified account stays verified and a pending one keeps waiting), with no write, no audit row and no e-mail. A `rejected` account typed again is the exception (FIX-W36-PLATFORM, lead decision (2a) of 2026-10-30): the owner asks for a new review, so it is saved as a change (the next version back in `pending_review` with the review cleared, the audit row, and the `ops.alert`, which says the bank details are the ones reviewed before). A stored copy that cannot be decrypted is replaced as a change. The tenant may be in any state its members see.
- **Reveal** (`adminRevealPayoutAccount`, MFA step-up, a `reason` of 5–500 characters after trimming, else `400` on `/reason`; the validation interceptor trims it, as every admin reason, since FIX-W35-PLATFORM): one transaction reads the row `FOR SHARE`, decrypts it and writes `payout_account.revealed` with the trimmed reason (and the scheme and version, never a number); the identifiers are answered after the commit with `Cache-Control: no-store` (set before the service runs, so its own refusals, such as `404`, carry it too, while the request validation's `400` comes before the handler; the operation is not `x-idempotent`, so no idempotency record ever holds the answer).
- **Review** (`adminReviewPayoutAccount`, `If-Match`): `verified` (note cleared) or `rejected` with a note (a blank note answers `400` on `/note`); a stale version answers `412` (also after the owner changed the account). The review is written with `version + 1`, the reviewer and the time, audited as `payout_account.reviewed`, and every active owner is e-mailed `payouts.reviewed` (the outcome and a link to `/otas/<id>/payments/payout-account`; the note stays in the portal). A review the account already has writes, audits and e-mails nothing. No `vx:invalidate` event: the OTA backend never reads payout accounts.
- **Tests**: `src/settlements/iban.test.ts` (valid and invalid IBANs, every single-character change and adjacent-digit swap, the document's patterns) and `test/integration/settlements/payout-accounts.int.test.ts` (the routes, the field errors without the value, the ciphertext bound to the row, the stored account typed again against one changed field, the stored account typed again in each review status (only a rejected one goes back to review), the audit rows, the e-mails rendered by the worker's templates to the active owners only, and after every test no bank number or BIC in any log line at `trace`).

### Settlement drafts (PBE-059, [Stripe payments flow §F](../docs/flows/stripe-payments-account.md#f-settlements-velexis-mode-m5) items 1–3, [PADR-0003](../docs/adr/0003-settlement-of-velexis-collected-payments.md) items 2–8, scope PF-63 AC1)

- **The job** `settlement.generate {periodStart, tenantId?, requestId?}` on `platform-settlements` (`src/settlements/settlements.processor.ts`, worker only, concurrency 1). `settlements.monthly` (`0 5 3 * *` UTC, registered while `FEATURE_SETTLEMENTS` is on; `settlements-monthly.scheduler.ts`) queues it for the previous calendar month; `adminGenerateSettlements` (`POST /v1/admin/settlements/generate`, AdminSettlementsController over `SettlementJobs`) for a month that has ended at the Clock's now (else `400 VALIDATION_FAILED`, `period_not_closed` on `/periodStart`), optionally for one tenant (`404 NOT_FOUND` for an unknown one), answering `202` before the job runs, `503 SERVICE_UNAVAILABLE` when Redis does not take the job within 2 s; the audit row `settlement.generation_requested` is written once the job is queued. No job id is set: a second job for a month rebuilds the same drafts. A failure BullMQ can mend (Stripe unreachable, 429 or 5xx, the database) is retried with the defaults of ADR-0009; another job name, invalid data, no `STRIPE_SECRET_KEY`, a Stripe 4xx or data the statements cannot hold end the attempts at once. Failures are logged as `settlement.generate_failed` with a code and a short message, never a Stripe payload; a run logs `settlement.generated` with its counts.
- **Stripe** (`settlement-generator.ts`, `collectTransactions`): the month's balance transactions of the Velexis account (`created` in `[periodStart, periodEnd)`, `limit` 100, `starting_after`, `expand: ["data.source"]`), listed once for all tenants; GET calls only (`balanceTransactions.list`, `charges.retrieve`, `paymentIntents.retrieve` of `StripeApi`). The `reporting_category` decides: `charge`, `refund`, `refund_failure` (a positive refund line), `dispute` and `dispute_reversal` are settled, nothing else. The categories of Velexis's own money (`UNSETTLED_CATEGORIES`: payouts, Stripe's own fees and their tax, transfers, top-ups, Connect and reserve movements, contributions) are skipped silently; any other category is skipped with one `settlement.unknown_category` warning line per transaction, its type and id only (FIX-W36-PLATFORM, lead decision (2g), [PADR-0003](../docs/adr/0003-settlement-of-velexis-collected-payments.md) item 3 note), counted as `unknownCategory`. The tenant is `metadata.velexis_tenant_id` of the charge, else of its PaymentIntent; a refund or dispute resolves through its charge (each charge and PaymentIntent retrieved at most once per run). Without a tenant, or with a tenant the platform does not know, a transaction is skipped. No transaction is open during a Stripe call.
- **Drafts** (one transaction per tenant, environment and balance currency; `settlements.repository.ts`): `live` statements with `APP_ENV=production`, `test` ones elsewhere (PADR-0003 item 1). The statement of the key that is not `void` is locked (`FOR UPDATE`) or created as a draft (`ON CONFLICT … DO NOTHING` on `settlements_period_uq`); an `approved`, `paid` or `carried_forward` one is never touched. A draft is rebuilt from scratch: its lines are deleted (manual adjustments too, as the contract of `adminAddSettlementAdjustment` says), one line per balance transaction is inserted with `ON CONFLICT (balance_transaction_id) DO NOTHING` (a transaction on another statement is skipped), and one `carry_forward` line adds the net of the earlier `carried_forward` statements of the same tenant, environment and currency whose `carried_to_id` is still null and that no earlier open draft absorbs already (the earliest later open draft absorbs a balance, PADR-0003 item 7 and its note of 2026-10-30, so two open drafts never count it twice; once that draft is voided, the next one takes it over). The totals come from `settlement-formula.ts` (decimal.js, half-even): gross, refunds, disputes (disputed amounts and dispute fees minus reinstated amounts), Stripe's processing fees (never a dispute fee again: PADR-0003 item 5 note of 2026-10-30), the Velexis fee `round_half_even(fee_bps × max(gross − refunds, 0) / 10 000)` with `fee_bps` copied from the tenant's plan, adjustments and net, so `settlements_net_ck` holds. A rebuilt draft gets `version + 1` and an audit row `settlement.generated` (actor `system`, label `settlement.generate`, the job's request id). Existing drafts of the month are rebuilt even when no transaction names them any more; a tenant and currency whose only open item is a carried-forward balance that the month's draft would absorb (no statement of the month yet) gets a draft holding just that `carry_forward` line (`carryForwardKeys`, counted as `carryForwardOnly`; FIX-W36-PLATFORM, lead decision (2g)), while balances that sum to zero open none.

### Stripe Connect account events (PBE-056, [Stripe payments flow §C](../docs/flows/stripe-payments-account.md#c-connect-standard-m5) item 5, [PADR-0011](../docs/adr/0011-stripe-connect-standard-and-api-key-connections.md) items 3 and 4, scope PF-61 AC2)

- **Receiver** (`receiveStripeConnectAccountEvent`, `POST /webhooks/stripe/connect-accounts`, `PaymentConnectionsModule.forApi()`, `src/payment-connections/connect-webhook.controller.ts`): the inbox handling of the billing receiver (below) with `StripeSignatureGuard("connect_accounts")` on `STRIPE_CONNECT_WEBHOOK_SECRET` and the inbox endpoint `connect_accounts` (the CHECK's spelling; the URL's is `connect-accounts`). The open `StripeConnectAccountEvent` schema requires `account`, so a body that is not a Connect event answers `400 VALIDATION_FAILED` on `/account`; the row keeps the connected `acct_…` in `stripe_events.account`. Stripe is never called here, and the events are stored whatever `FEATURE_OWN_STRIPE` says (the processor ends them `ignored` while it is off).
- **Handler** (`ConnectAccountEventsHandler`, `src/payment-connections/connect-account-events.handler.ts`, `PaymentConnectionsModule.forWorker()`, `@HandlesStripeEvents("connect_accounts", ["account.updated", "account.application.deauthorized"])`, run by the one `platform-stripe-events` processor). It works on the `connect_standard` connections whose `account_reference` is the event's `account` (`connectRowsOfAccount`, `lockConnectRowsOfAccount`: `test` before `live`; since FIX-W40-PLATFORM, lead decision (2d) of 2026-11-03, both events lock them with `lockAccountRows`, which re-lists them once the locks are held, so a live copy go-live committed while the lock waited is locked and handled by the same event: `account.updated` sees the rows changed and re-fetches for both, a deauthorisation disables the copy too); an account no such connection holds (none at all, or only an `api_keys` connection) ends `ignored` with `UNKNOWN_ACCOUNT`, and Stripe is not called.
- **`account.updated`**: re-fetch the account (`stripe.accounts.retrieve(acct_…)`, never the payload), then one transaction refreshes every connection of it: `capabilities` (`chargesEnabled`, `payoutsEnabled`, `detailsSubmitted`) and, for a `pending` or `active` connection, `status` (`active` with charges enabled, `pending` otherwise), `version + 1`, one `payments.connect_status_changed` audit row per changed connection (actor `system`, label `stripe.connect_events`; status and capabilities before and after, the environment, the account and the event) and `{type: "connection", tenantId}` after the commit. A connection Stripe confirms is not written. A deauthorised connection (`disabled` with `disconnected_at`) is skipped, and when every connection is one Stripe is not asked (`ACCOUNT_DISCONNECTED`, `ignored`); a connection a platform admin disabled (`disabled` without `disconnected_at`) gets the capabilities and stays `disabled`. A 403 or 404 of Stripe for the account (Velexis's access is gone) ends `ignored` (`ACCOUNT_UNREACHABLE`); any other Stripe error fails the attempt as the processor records failures (retried for a network error, a rate limit or a 5xx). Two rules keep an older answer from outliving a newer one, with no transaction or lock held during the Stripe call: the connections' ids and versions are read before the re-fetch and compared on the locked rows, and when any changed meanwhile (another event of the account, the owner, an admin) nothing is written and the account is re-fetched (`stripe_connect.account_changed_during_refresh`); and a refresh that wrote is followed by another re-fetch after its commit, because a re-fetch that confirms the connections leaves no trace in their versions, so another event's older answer could otherwise commit after it. The event ends when a re-fetch made after the last write confirms the connections (`stripe_connect.account_confirmed`); a changing event therefore asks Stripe twice. An event that wrote and then finds the connections deauthorised, gone or out of Stripe's reach ends `processed`, not `ignored`. After 4 re-fetches without that confirmation it fails with the retryable `CONNECTION_BUSY`.
- **`account.application.deauthorized`**: one transaction locks the connections and sets each `status = 'disabled'` and `disconnected_at` (`version + 1`; the mode stays `connect_standard` and the account reference stays: no fallback to Velexis mode), one `payments.connect_disconnected` audit row per connection, the e-mail `connection.stripe_disconnected` (PADR-0013 item 5: name, OTA name and key, link to `/otas/<id>/payments`) once to every active owner (idempotency key `stripe_disconnected:<tenantId>:<eventId>`; none while the OTA is deleted or being deprovisioned), and the `connection` invalidation after the commit. Stripe is not called. A connection connected again after the event (`connected_at` in a later second than the event's `created`) is kept, whatever its status, and an event that finds only such connections (besides connections deauthorised already) writes nothing and ends `ignored` (`STALE_EVENT`, logged `stripe_connect.deauthorization_stale`); this stale rule is checked first, so a deauthorisation older than a connection a platform admin disabled after a reconnect ends `ignored` with `STALE_EVENT` too, like the other stale events (FIX-W38-PLATFORM, lead decision (2b) of 2026-10-31, second batch; it ended `processed` with nothing written before), while an event that audits an admin-disabled connection it concerns ends `processed`; a connection a platform admin disabled is kept as it is, so the admin's disable still holds against the OTA's reconnect (`stripe_connect.deauthorized_admin_disabled`), and gets one audit row per event, `payments.connect_deauthorized_while_disabled` (actor `system`, label `stripe.connect_events`; `details`: environment, `acct_…`, event id and type, the status it keeps; no `before` or `after`), with its status, `disconnected_at` and version unchanged, no e-mail and no invalidation (FIX-W37-PLATFORM, lead decision (2k) of 2026-10-31; a re-run of the same event finds its row through `AuditService.hasEventEntry` and writes none, and a deauthorisation older than the connection's `connected_at`, which revoked an earlier connection, writes none either). A plan no longer available or a Stripe failure logs `billing.checkout_failed` and answers `checkoutUrl: null`. A tenant on a manual trial is retried and dispatched as before M5.

### Billing events: re-fetch and status rules (PBE-045, [billing flow §D and §E](../docs/flows/subscription-billing.md#d-processing-worker-platform-stripe-events-concurrency-2), [PADR-0002](../docs/adr/0002-stripe-billing-integration.md) items 1, 5, 6 and 7, [PADR-0014](../docs/adr/0014-tenant-suspension-and-resume.md), scope PF-73 AC1 and PF-74)

- **Handlers** (`src/billing/sync/handlers/`, `@HandlesStripeEvents("billing", …)`, providers of `BillingSyncModule.forWorker()`, which imports the one `ProvisioningModule.forWorker()` object for the dispatcher and `SuspensionService`): each re-fetches its object from Stripe before any transaction (`checkout.sessions.retrieve(id)`, then `subscriptions.retrieve(id)` under the subscription's lock below), never reading the payload, then runs one transaction that locks the tenant's row first (billing's lock order below). A duplicate or reordered event writes Stripe's current state again: the row's `version` moves only when something changed (`provider_synced_at` records every re-fetch).
- **The subscription's lock** (FIX-W30-PLATFORM, lead decision (2) of 2026-10-26, [PADR-0002](../docs/adr/0002-stripe-billing-integration.md) item 5 revision of 2026-10-26; `src/billing/sync/subscription-lock.ts`, `SubscriptionSyncLock`): the worker runs two events at a time, so two events of one subscription whose re-fetches overlapped could commit the older answer after the newer one. Both handlers therefore re-fetch and write a Stripe subscription inside `SubscriptionSyncLock.run(<sub_…>)`: the Redis lock `vx:stripe:sub:<sub_…>:lock` (15 s TTL, a random token) is taken before the re-fetch (the Checkout's handler takes it once the session named the subscription), renewed every 5 s while the handler runs, confirmed in the transaction just before its commit (`SUBSCRIPTION_LOCK_LOST`, retryable, rolls the write back when it is no longer this event's) and released after the work that follows the commit. Another event of the subscription tries again every 100 ms (`billing.sync_lock_waiting`, once) and gives up after 30 s with the retryable `SUBSCRIPTION_BUSY` (`billing.sync_lock_busy`), which BullMQ runs again later; it then re-fetches after the first one's commit, so the row ends in Stripe's newest state whichever event Stripe answered first. Lost or failed renewals log `billing.sync_lock_lost` and `billing.sync_lock_renew_failed`; a failed release `billing.sync_lock_release_failed` (the lock expires on its own).
- **Lock order of billing** ([billing flow §D](../docs/flows/subscription-billing.md#d-processing-worker-platform-stripe-events-concurrency-2)): the subscription's Redis lock (billing sync only, before any transaction), then the tenant's row (`FOR UPDATE`), then the OTA's `billing_customers` row (a completed Checkout), then its subscription rows (the one the event or the admin edits, then the OTA's other current rows in id order), then what the status rules' suspend or resume locks ([PADR-0014](../docs/adr/0014-tenant-suspension-and-resume.md)). The admin's manual edit (PBE-033) keeps it since FIX-W30-PLATFORM: it locks the tenant's row before the subscription's. The Checkout's start (PBE-044) keeps it since FIX-W31-PLATFORM (lead decision (2) of 2026-10-27, [PADR-0002](../docs/adr/0002-stripe-billing-integration.md) item 5 revision of 2026-10-27): its transaction locks the tenant's row before it writes the pending row and the audit row (whose foreign key takes a `KEY SHARE` lock on the tenant's row), so it never deadlocks with a completed Checkout of the same pending row. It locks the row in a billing repository, as the billing reads join `tenants`, because BillingModule may not import TenantsModule (architecture §2.2). PBE-046's invoice handler takes the lock of the invoice's subscription too (the same revision; see below).
- **`checkout.session.completed`** (`checkout-session-completed.handler.ts`): `ignored` unless `mode: subscription`, `complete` and a known OTA in `client_reference_id`; `failed` for good (`TENANT_MISMATCH`, `NO_SUBSCRIPTION`, `INVALID_CUSTOMER`, `CUSTOMER_CONFLICT`) when the session does not fit together. Stores the session's Customer in `billing_customers` (insert, or this Customer, `livemode` and the collected e-mail), finds the row by `provider_subscription_id`, else by `metadata.velexis_subscription_id`, else inserts one, cancelling the OTA's manual or unpaid `incomplete` row first in the same transaction (another current Stripe subscription: `SUBSCRIPTION_CONFLICT`), and copies the subscription with the shared update path below. A `provisioning` OTA has its `queued` provision job dispatched after the commit, once: a repeat finds it `running`. Lead decision (5) of 2026-10-24: a `failed` OTA whose shown subscription is now this Checkout's, `trialing` or `active`, goes back to `provisioning` with a new `queued` provision job (the active one if any), `provisioning_job.retried` audited (actor `system`, `billing.sync`) and dispatched after the commit, as `retryProvisioning` does.
- **`customer.subscription.created`, `…updated`, `…deleted`** (`subscription-changed.handler.ts`): the row by `provider_subscription_id`, else the pre-inserted row of `metadata.velexis_subscription_id`; none is `ignored` (`UNKNOWN_SUBSCRIPTION`; the Checkout's event writes it). A subscription whose `metadata.velexis_tenant_id` names another OTA than its row, or whose Customer `billing_customers` stores for another OTA, fails for good (`TENANT_MISMATCH`, `CUSTOMER_CONFLICT`) and writes nothing. `syncInTransaction` is the update path both handlers share (and PBE-048's resync): the price's plan (`price-to-plan.ts`: the one item's price linked as `stripe_price_id_month` or `_year` of any plan; unlinked or linked twice is `UNKNOWN_PRICE`, several items `UNSUPPORTED_SUBSCRIPTION`, both final), the state (status, Customer, ids, price, plan, interval, the item's period, trial end, `cancel_at_period_end`, `canceled_at`, the Session), the status rules, the dispatch of the `queued` provision job of a `provisioning` OTA whose subscription is now `trialing` or `active`, and one `subscription.updated` audit row (actor `system`, `billing.sync`, request id = the event id) with the changed fields and the tenant's plan and banner before and after.
- **Status rules** (`status-rules.ts`, `billingEffects` and `BillingStatusRules`): on the tenant's shown subscription (current, else latest; nothing for a manual one): `trialing`/`active` clear `billing_notice` and resume a `billing` suspension; `past_due`/`paused` set `billing_notice = 'past_due'`; `canceled`/`unpaid`/`incomplete_expired` suspend an `active` OTA with reason `billing`; `tenants.plan_code` follows the plan. A new plan or banner bumps the tenant's `version` and publishes `tenant` after the commit; a suspend or resume goes through `SuspensionService.suspendInTransaction` / `resumeInTransaction` in the event's transaction (job, `tenant.suspended`/`tenant.resumed` audit row, the owners' e-mail, invalidation), its job dispatched after the commit (`dispatchQuietly`). Never an `abuse`, `request` or `admin` suspension.
- Log lines `billing.subscription_synced` (ids, statuses, whether it changed) and `billing.failed_tenant_redispatched`; never an e-mail address or a payload.

### Admin billing of M5: Stripe prices, resync, invoices and the Stripe inbox (PBE-048, [billing flow §A and §D](../docs/flows/subscription-billing.md#a-plans-and-prices-admin), [PADR-0002](../docs/adr/0002-stripe-billing-integration.md) items 2, 4 and 5, scope PF-88 and PF-89)

## 7. OpenAPI document

- Location: `openapi/velexis-platform-api.openapi.yaml` (OpenAPI 3.1), as [ADR-0006](../../docs/mvp/adr/0006-contract-first-openapi.md) names it. The first M1 backend task (PBE-005) created it from [`../docs/api-inventory.md`](../docs/api-inventory.md) and its two companion parts, with the error catalogue, `x-scope` on every operation and `x-internal: true` on webhooks and internal endpoints. [`openapi/README.md`](openapi/README.md) explains its slices, conventions, extensions and contract test, and how to change it.
- Every endpoint change starts in the document; `pnpm contracts:generate` updates the types; controllers bind to `operationId`s with `@OpenApiOperation("signUp")`; the route parity test fails on drift.
- **Runtime validation** (PBE-008). The API reads the document from `openapi/` next to `dist/` (the package ships it) once per process. At start-up `OpenApiValidationInterceptor` compiles Ajv 2020 validators (with `ajv-formats`, strict for unknown keywords) for the path, query and header parameters and the JSON body of every bound operation; an `operationId` that the document lacks stops the start. A request that fails answers `400 VALIDATION_FAILED` with `fieldErrors[]` of `{path, code, message}`: `path` is a JSON pointer into the body (`/email`, `""` for the body itself) or `/<in>/<name>` for a parameter (`/query/limit`, `/path/tenantId`, `/header/Idempotency-Key`), `code` the failed rule, and `message` never contains the submitted value. Unknown body properties fail (request bodies are closed); undocumented query parameters are ignored. Handlers read the coerced parameters (with their defaults) through `@Validated("query")`. Every admin reason (the document's `AdminReason`, in a body or as `adminRevokeAdmin`'s query parameter) is trimmed before its 5–500 characters are counted (`TRIMMED_SCHEMAS`, FIX-W35-PLATFORM, lead decision (2j) of 2026-10-30): a reason of only spaces answers `400 VALIDATION_FAILED` (`minLength` on `/reason` or `/query/reason`), and the handler, so the audit row and any stored reason, gets the trimmed value; a body that can hold one is validated and handed on as a copy, so the request itself is never changed. Responses are validated in the integration tests only.
- **Route parity** (PADR-0016 item 2). [`test/contract/route-parity.contract.test.ts`](test/contract/route-parity.contract.test.ts) walks the API's module graph and fails when a route has no `@OpenApiOperation`, binds an operation the document lacks or with another method or path, when two routes bind one operation, or when an operation is neither bound nor listed in [`test/contract/pending-operations.ts`](test/contract/pending-operations.ts), or both. Each pending entry names the plan task that implements it; that task removes the entry when it binds the route.
- Queue message contracts are not in this document: they live in `@velexis/api-types/jobs` ([`../docs/architecture.md`](../docs/architecture.md) §6.1).

## 9. Operations

- Health: `GET /health/live`, `GET /health/ready` on both processes: the API on `127.0.0.1:3100`, the worker's small `node:http` server on `127.0.0.1:3101` (any other path there answers the `404 NOT_FOUND` error envelope). Both answers carry `Cache-Control: no-store`, and `/health/*` writes no request log line.
  - `live` answers `200 {"status":"ok"}` while the process serves requests; it checks nothing else.
  - `ready` runs `SELECT 1` on a `createPool` pool (role `velexis_platform_app`) and `PING` on Redis in parallel, each within 2 seconds, and answers `200 {"status":"ok","checks":{"postgres":"ok","redis":"ok"}}`, or `503` with `"status":"unavailable"` and `"down"` for each dependency that failed. The cause is never answered: it is logged as `health.dependency_down` (warn, with the `dependency`, the `err` and the request's `requestId`). The worker's answer also lists its queues (FIX-W46-PLATFORM, lead decision (11d) of 2026-11-06; `src/health/queue-age.ts`), in the shape and with the rules of the OTA worker's (OBE-025): `"queues": {"platform-tenant-events": {"waiting": 0, "oldestWaitingSeconds": null, "failedLastHour": 0}, …}`, every queue of `PLATFORM_QUEUES`, where `waiting` counts the wait list, a paused queue's list, the prioritized jobs and the delayed jobs that are due, `oldestWaitingSeconds` is the longest wait among them (`null` when none waits) and `failedLastHour` the jobs whose last attempt failed in the hour before the Clock's time, read with about 2·log2(n) reads of BullMQ's failed set. They are read on a Redis connection of their own (`platform-worker-health-queues`: no offline queue, every command given up after 1 s) through read-only `Queue` objects, in parallel with the probes and within 1 s; when Redis refuses or does not answer them in time the answer has no `queues` (unknown, never "no job waits") and `health.queues_unknown` is logged (warn, with `part`, `status` and the `err` of a refusal). Old or failed jobs never make the worker unready: the on-VM check (`deploy/scripts/healthcheck.sh`, X-030) reads `failedLastHour` and `oldestWaitingSeconds` of both workers and decides. The API's answer has no `queues`; the admin's queue counts are `adminListQueues` (PBE-031).
- Start-up: an invalid configuration logs one `fatal` line `config.invalid` whose `ConfigError` names every variable (never a value) and exits `1`; so does a failure to build the module graph or bind the port (`api.start_failed`, `worker.start_failed`).
- Logs: pino JSON to journald with the standard fields and the redaction list of [ADR-0016](../../docs/mvp/adr/0016-observability.md) plus the platform additions in [`../docs/architecture.md`](../docs/architecture.md) §8 (`x-velexis-bff-key` since PBE-008, the other keys and the `code` and `state` of an `mfa` or `oauth` body since PBE-010; see [`packages/logger/README.md`](../../packages/logger/README.md#the-redaction-list)). Nest's own lines (start-up) go through the same logger, and every line written inside a request carries its `requestId`. `configureApiApp` flushes Nest's start-up buffer as soon as the logger is in place, so these lines are written also when `listen()` fails or a request test only runs `init()`.
- Errors: every error answer is the envelope of `@velexis/errors` with the `requestId` (also in `X-Request-Id`). `ErrorFilter` answers Nest's own HTTP exceptions (an unknown route, a guard's `401`) with the generic code of their status and never their message, and uses the platform document's message for a code both catalogues list. An unknown error answers `500 INTERNAL_ERROR` and is logged as `http.unhandled_error` (error, with `err` and its stack, never in the body); an `AppError` of 5xx is logged as `http.server_error` with its `code`.
- Authentication (PBE-012, [`../docs/architecture.md`](../docs/architecture.md) §3.1): `TokenService` (`src/auth/token.service.ts`) signs EdDSA access tokens with the Ed25519 key of `JWT_PRIVATE_KEY_FILE`, read once at start-up (a missing key, one readable by group or others, or one that is not Ed25519 stops the process), and verifies a token with the key its `kid` names: that key, or during a rotation the previous key's public half of the optional `JWT_PREVIOUS_PUBLIC_KEY_FILE` (FIX-W48-PLATFORM, lead decision (15f) of 2026-11-11; ADR-0010: the old key stays valid for one token lifetime; `src/auth/jwt-keys.ts` and `config.ts` refuse a private key, a key that is not Ed25519 and the current key's public half at start-up; every other `kid` is `401 UNAUTHENTICATED`): 15 minutes, `iss` `https://api.platform.example.com`, `aud` `portal` or `platform_admin`, `kid` the key's JWK thumbprint, claims `sub`, `typ`, `sid`, `ev`, `amr` and `mfa_at`. The global guards of `API_GUARDS` (`src/common/auth/`) act on the policy of the handler's operation (`OperationPolicies`: `x-scope` from the operations index, `x-mfa-step-up` and `x-feature` from the document; an unknown scope or switch stops the start), in this order, between the rate-limit guards of PBE-009 (`RateLimitGuard` first, `AccountRateLimitGuard` right after `AdminAuthGuard`; see Rate limits below):
  - `InternalOnlyGuard` (`internal`): a loopback peer and no `X-Forwarded-For`, else `404 NOT_FOUND`;
  - `PortalAuthGuard` (`portal_unverified`, `portal`): a token of audience `portal` (`401 UNAUTHENTICATED`, `401 TOKEN_EXPIRED`) whose account is still `active`, `locked` or `pending_verification`, read from `platform.accounts` on every request (a missing, erased, `disabled` or `deleted` account answers `401 UNAUTHENTICATED` at once; PBE-067, lead decision (5a) of 2026-11-05); `portal` also needs `ev`, else `403 EMAIL_NOT_VERIFIED`;
  - `AdminAuthGuard` (`platform_admin`): a token of audience `platform_admin` whose account is still an `active` platform admin, read from `platform.accounts` on every request, else `401 UNAUTHENTICATED`;
  - `MfaEnrolmentGuard` (`portal`; right after `AccountRateLimitGuard`, before `TenantRoleGuard`; PBE-071, [PADR-0008](../docs/adr/0008-email-verification-and-mfa-policy.md) revision of 2026-11-05): an account without MFA (the flag `PortalAuthGuard` read for the request, so an account with MFA costs no further query) that holds an active `owner` or `admin` membership of a live OTA in a status members see (`MfaEnrolmentLookup`, which the global `MembershipsModule` provides with `MembershipsRepository.holdsMfaMandatoryRole`: one indexed query, no cache) answers `403 MFA_REQUIRED` with `details.reason = enrolment_required` on every `portal` operation, reads and its other OTAs' included, until it turns MFA on; `portal_unverified` (`getMe`, `updateMe`, the MFA set-up and enabling, sessions, sign-out, `listTenants`) stays open. `getMe`, `updateMe` and every `PortalSession` answer the same rule in `Account.mfaEnrolmentRequired`;
  - `TenantRoleGuard` (`@TenantRoles(…)`, PBE-017): see Tenant routes in §8;
  - `FeatureGuard` (`x-feature`, `@Feature(…)`): `403 FEATURE_DISABLED` with `details.feature` while the switch is off, before any step-up is asked for (FIX-W38-PLATFORM, lead decision (2i) of 2026-10-31: it ran after `RecentMfaGuard` before);
  - `RecentMfaGuard` (`x-mfa-step-up`, `@RequireRecentMfa()`): `403 MFA_REQUIRED` for an account without MFA (read from the database), `401 REAUTH_REQUIRED` when the token's `mfa_at` is missing or older than 15 minutes; services with a conditional step-up call `assertRecentMfa`.

  The verified claims stay on the request (`@AccessToken()`), the account becomes the context's actor (`account` or `platform_admin`), and `public` operations need nothing. A handler without `@OpenApiOperation` has no policy; the route parity test keeps such handlers out of the API. `featuresFor()` builds the `features` object of `getMe` and `adminGetMe`.
- Request pipeline (PBE-008, [`../docs/architecture.md`](../docs/architecture.md) §3): `helmet` and `cookie-parser`, pino-http (request id and request line), the JSON body parser (100 KB; 1 MB and the raw body on `/webhooks/*`; a body that cannot be read answers `400 VALIDATION_FAILED` without quoting it), the request context (`nestjs-cls`: `requestId`, `ip`, `userAgent`, `actor`), the end user of PADR-0019 (`X-Velexis-End-User-IP` and `X-Velexis-End-User-Agent` believed only from loopback, without `X-Forwarded-For` and with `X-Velexis-Bff-Key` equal to `PLATFORM_BFF_KEY` in constant time; a believed request without a valid IP answers `400`; a key sent but not believed is logged as `request_context.bff_key_ignored` with the reason only), then the guards above, the validation interceptor, the handler and the error filter. Services read the IP and user agent from `RequestContext`, never `req.ip`.
- Redis (PBE-009, [`../docs/architecture.md`](../docs/architecture.md) §6.4): every key and its TTL come from `src/common/redis/redis-keys.ts`, and only its helpers (`setKey`, `setKeyIfAbsent`, `incrementInWindow`, `setKeyIfHigher` (PBE-015), `extendKeyIfValue` to renew a held lock (FIX-W29-PLATFORM), and `deleteKeyIfValue` to release a lock; the locks are the idempotency lock and, since FIX-W30-PLATFORM, the subscription lock of billing sync) write one, always with the TTL (`noeviction`); a source scan in `redis-keys.test.ts` fails on a key written by hand or a Redis write elsewhere in `src/`. Each process holds one command client (fails fast while Redis is down) and one BullMQ connection; a lost connection is logged once per outage as `redis.connection_error`, never with the URL.
- Cache invalidation (PBE-009, §6.3): a service opens its transaction with `runInTransaction(platformDb, fn)` and calls `InvalidationPublisher.publishAfterCommit(trx, event)` inside it; the events (validated with `validateInvalidation`) go to `vx:invalidate` once COMMIT succeeded, each distinct event once, and are dropped on a rollback. Both calls refuse (`NotInTransactionError`) a transaction that `runInTransaction` did not open or whose function has returned. `afterCommit(trx, work)` is the same hook for other work, such as enqueueing a job. A Redis failure while publishing is logged as `invalidation.publish_failed` and never fails the request (the OTA's 60 s TTL bounds the delay). The API listens to the channel too, for the cache of the TLS `ask` (PBE-027, §4).
- Idempotency (PBE-009, §3 step 10): operations with `x-idempotent: true` require `Idempotency-Key`; the record `vx:idem:<accountId>:<key>` holds the request fingerprint (operation, validated path, query and body) and the 2xx answer for 24 hours. The same key and body replay the status and body without running the handler; another body answers `409 IDEMPOTENCY_KEY_REUSED`; a concurrent duplicate waits on the lock `vx:idem:<accountId>:<key>:lock` (10 s TTL) and gets the same answer, or `503 SERVICE_UNAVAILABLE` when the first request still runs after the duplicate's 10-second wait. The holder renews the lock every 3 s with its own token (`extendKeyIfValue`) until its answer is stored, so a handler that waits on Stripe for longer than 10 s keeps it, and never renews a lock it lost (`idempotency.lock_lost`; a Redis error of a renewal is `idempotency.lock_renew_failed` and the next renewal tries again) (FIX-W29-PLATFORM, [PADR-0002](../docs/adr/0002-stripe-billing-integration.md) revision of 2026-10-24); errors and `Cache-Control: no-store` answers are never stored; Redis down answers `503 SERVICE_UNAVAILABLE` before the handler runs.
- Rate limits (PBE-009, [`../docs/api-inventory.md`](../docs/api-inventory.md) §2): one named throttler of `@nestjs/throttler` per limit of the inventory's table (`RATE_LIMITS` in `src/common/http/throttler.config.ts`), applied by the route's operation (`OPERATION_RATE_LIMITS`; every other authenticated request counts against `authenticated`, 300 per account per minute). Fixed windows in Redis (`rl:<throttler>:<sha256 of the tracker>`), so no IP or e-mail address is stored in clear. The per-IP tracker is the end user's IP of the request context (PADR-0019), never `req.ip`; an IPv6 address counts for its /64, as `@nestjs/throttler`'s own tracker does. Over the limit: `429 RATE_LIMITED` with `Retry-After` (seconds to the end of the window), and no `X-RateLimit-*` headers. `RateLimitGuard` counts the `ip`, `email` and `domain` limits before the auth guards; `AccountRateLimitGuard` counts the per-account limits after them. While Redis is down the specific limits answer `503 SERVICE_UNAVAILABLE` and `authenticated` lets the request through, logged as `throttler.store_unavailable`.
- Sign-up and e-mail verification (PBE-013, [`../docs/flows/signup-and-create-ota.md`](../docs/flows/signup-and-create-ota.md) steps 1 to 3, [PADR-0008](../docs/adr/0008-email-verification-and-mfa-policy.md)): `AuthModule` (`src/auth/`) binds `signUp`, `verifyEmail` and `resendVerification`.
  - Passwords (`PasswordPolicy`, [ADR-0008](../../docs/mvp/adr/0008-identity-accounts-customers-sessions.md) and its revisions of 2026-11-10 and 2026-11-11, PCI DSS 8.3.6): every portal account's password needs at least 12 characters (code points) with at least one letter (`\p{L}`) and one digit (`\p{Nd}`), and must not be in `breached-passwords.txt` (lower-cased, compared lower-cased, read once when the module is built; checked first, lead decision (16b)), else `422 PASSWORD_TOO_WEAK` with the rule's message and a field error on `/password` (or `/newPassword`) that never quotes it: `password_rule` (the length, the letter or the digit) or `breached`; stored as Argon2id (`argon2`, m = 19 MiB, t = 2, p = 1). The build copies the list to `dist/auth/`. The rule is the same at `signUp` (an invited person signs up first), `changePassword` and `confirmPasswordReset` (lead decision (15e) of 2026-11-11, FIX-W48-PLATFORM, which replaced FIX-W47-PLATFORM's rule of platform admins and the owners and admins of OTAs, whose field code `privileged_rule` became `password_rule`, and the 10-character rule with its `too_short`). A password in use is never checked again; accepting an invitation and `admin:grant` set no password, and `dev:seed`'s platform admin gets a password that meets the rule.
  - The breached-password list (PBE-073, lead decision (17b) of 2026-11-11, ADR-0008's note of that day): the entries that meet the rule of a public list of about a million breached passwords, SecLists `Passwords/Common-Credentials/xato-net-10-million-passwords-1000000.txt` (MIT licence) at commit `c23b603128ed21e46164a0afd357f0c242135f41` (999 999 lines, SHA-256 `424a3e03a17df0a2bc2b3ca749d81b04e79d59cb7aeec8876a5a3f308d0caf51`). `scripts/breached-passwords.mjs --source` (§5) built it on 2026-11-12 from a copy fetched by hand: 28 968 lines meet the rule, 28 897 entries once lower-cased and unique, sorted by code point, 421 156 bytes, SHA-256 `df67d6b895d1c029308223dd82298bbde1b2f776fd9ae5d5b9ac3bbe17e31faf`; regenerating from the pinned source gives the same bytes, and `--check` checks the committed file offline in CI (through `password-policy.test.ts`). Nothing downloads it at build or deploy time, and it is never edited by hand. It replaced the SecLists top-10 000 list (`10k-most-common.txt`, 73 026 bytes), none of whose entries meets the rule: the file adds 348 130 bytes (about 340 KiB; 213 436 bytes against 37 956 with `gzip -9n`) to the repository, `dist/` and each release, and the set takes 1.91 MiB of the API's heap instead of 0.62 MiB (about 1.3 MiB more; `node --expose-gc`, `heapUsed` after a full collection, around the parse of `parseBreachedPasswords`). Every entry meets the rule, so a short common password such as `QwertyUiop`, which the old list named `breached`, is refused as `password_rule`. No password that `dev:seed`, the e2e arrangements, the test builders or [`deploy/demo-deployment.html`](../../deploy/demo-deployment.html) choose is on the list (`dev:seed` and the e2e harness draw random ones; checked on 2026-11-12 against every string of the repository). The OTA backend keeps its own copy of the top-10 000 list for customer passwords ([`ota/backend/README.md`](../../ota/backend/README.md)).
  - `signUp` checks and hashes the password for every request, so a known and an unknown address cost the same, and answers the same `202 {"status":"verification_sent"}` either way. A new address (trimmed, compared lower-cased) gets an account in `pending_verification` with `terms_accepted_at` and `terms_version`, a verification token (`vt_`, 256 bits, 24 hours) and the e-mail `auth.verify_email` linking to `PUBLIC_PORTAL_URL/verify-email?token=…`, and the audit row `account.signed_up`. A known address gets only `auth.account_exists`, sent to the account's own address, whose reset link (`/reset-password?token=…`) is a `password_reset` token of 1 hour, as the template and PADR-0013 item 5 say; an erased (`deleted`) account gets nothing. Two sign-ups racing for one address make one account (`ON CONFLICT` on `lower(email)`).
  - `verifyEmail` uses up an unused, unexpired token (the Clock's time) of a `pending_verification` account whose address is still the token's: the account becomes `active` with `email_verified_at`, its other open verification links are used up too, and `account.email_verified` is audited. Anything else answers `400 VERIFICATION_TOKEN_INVALID`, without saying why. The account is locked before its token is used up, so two of its links opened at the same time give one `200` and one `400`, never a deadlock.
  - `resendVerification` answers `202` without a body whatever the address; an unverified account gets a new link, and earlier links that have not expired keep working (PADR-0008 item 3).
  - Only the SHA-256 of a token is stored (`account_tokens`, with the end user's IP); the links travel only as the outbox's encrypted secret data. The rate limits are the operations' throttlers: 5 sign-ups per IP per hour, 3 resends per address and 10 per IP per hour (`429 RATE_LIMITED`).
- Sign-in and sessions (PBE-014, [`../docs/flows/signup-and-create-ota.md`](../docs/flows/signup-and-create-ota.md) step 4, [PADR-0009](../docs/adr/0009-platform-api-surface-and-authentication.md) item 4, [PADR-0007](../docs/adr/0007-portal-to-ota-admin-sso-token.md) item 6): `AuthModule` binds `signIn`, `refreshSession`, `signOut` and `signOutEverywhere`.
  - `signIn` (`SignInService`, 10 per end-user IP per minute) checks the lockout first: a future `locked_until` answers `423 ACCOUNT_LOCKED` with `Retry-After` (the seconds left) before the password is looked at. Then one Argon2id verification, against the account's hash or, for an unknown address, an erased account or one without a password, against a dummy hash of the same parameters made when the module starts: a wrong address and a wrong password give the same `401 INVALID_CREDENTIALS` (the same body apart from the request id) after the same Argon2id work; only the failure count of an existing account adds one short transaction. A wrong password counts one more consecutive failure (`auth.sign_in_failed`); the fifth locks the account for 15 minutes (`auth.locked`) and answers `423` at once. The count goes on until a sign-in succeeds or an admin unlocks the account, so after a lockout each further failure locks again. Only after a correct password does a disabled account answer `403 ACCOUNT_DISABLED`. The counters are changed in one statement each and only while the account is not locked out; they leave `version` (the profile's `ETag`) alone.
  - Success clears the count and the lockout. Without MFA it sets `last_login_at`, starts a portal refresh family, audits `auth.sign_in` (target the family) and answers the `PortalSession`; an unverified account gets a token with `ev = false`. With MFA it answers `{mfaRequired: true, mfaChallengeToken, expiresIn: 300}`: the challenge is `mfach:<sha256(token)>` in Redis for 5 minutes, `{v, audience, accountId, issuedAt, maxAttempts: 5}` (`MfaChallengeStore`); `verifyMfa` (PBE-015) completes it with `SignInService.startSession`.
  - Refresh families (`SessionsService`, `account_sessions`): one row per refresh token generation; the family id is the `asn_…` id of its first row and the access token's `sid`. A portal family lives 30 days (`family_expires_at`), each refresh token 7 days idle and never past the family's end; the row keeps the SHA-256 of the opaque token (`rt_…`, 256 bits), the end user's user agent and IP of the sign-in, and `mfa_verified_at`. The answer is `{accessToken, accessTokenExpiresAt, refreshToken, refreshTokenExpiresAt, account}` with `Cache-Control: no-store`; `account` is the `Account` of `getMe` (memberships of visible OTAs, the six switches). The access token copies `mfa_at` from `mfa_verified_at` (`amr` `["pwd","otp"]`).
  - `refreshSession` rotates on use: the presented row is marked `rotated_at`/`replaced_by_id` and the next generation is written. A token that was rotated already revokes the whole family (`revoke_reason = 'rotation_reuse'`, committed before the `401 REFRESH_TOKEN_REUSED` answer, logged as `auth.refresh_token_reused` with the ids only), so the newest token fails too. An unknown, revoked or expired token, a family past its end, an admin family or an account that may no longer hold a session answers `401 REFRESH_TOKEN_INVALID` and changes nothing. Every change of a family takes the account's `FOR KEY SHARE` lock, then the lock of the family's first row, then the token's row, so two refreshes with one token run one after the other (the second is a reuse) and a revocation never misses a generation being written.
  - `signOut` (`portal_unverified`) revokes the family of the presented refresh token when it is a portal family of the caller (`logout`); anything else changes nothing, and the answer is `204` either way. `signOutEverywhere` writes `staffdeny:acct:<accountId>` = now in epoch milliseconds for 30 days first (the OTA backend revokes the account's staff sessions created before it), then, holding the account's `FOR UPDATE` lock, revokes every family of the account (portal and admin), audits `auth.signed_out_everywhere` and publishes an `account` invalidation after the commit. If Redis cannot take the cut-off nothing is revoked and the call fails.
- MFA (PBE-015, [PADR-0008](../docs/adr/0008-email-verification-and-mfa-policy.md) "MFA", scope PF-04): `AccountsModule` (`src/accounts/`) binds `startMfaSetup`, `enableMfa`, `disableMfa` and `regenerateRecoveryCodes`; `AuthController` binds `verifyMfa` and `stepUp`, whose work `MfaService` does through the abstract `MfaVerification` (`src/auth/mfa-challenge.store.ts`) that the global `AccountsModule` provides, so `AuthModule` never imports it (`AccountsModule` imports `AuthModule` for the account repository, the challenges, the sign-in and the sessions).
  - TOTP: `otplib`, SHA-1, 6 digits, 30-second steps, ±1 step, at the `Clock`'s time. Each code works once per account: the step of every accepted code (set-up, sign-in, step-up) goes to `mfastep:<accountId>` (90 s) with `setKeyIfHigher`, and a code of that step or an earlier one answers `MFA_CODE_INVALID`.
  - `startMfaSetup` (`portal_unverified`): a 160-bit secret, envelope-encrypted with the associated data `redis.mfasetup.totp_secret:<accountId>` (`CiphertextPlace` with `schema: "redis"`) into `mfasetup:<accountId>` for 10 minutes with its start time (the `Clock` ends it too), replacing an earlier one; answers `{secret, otpauthUrl, expiresIn: 600}` with `Cache-Control: no-store`; `409 MFA_ALREADY_ENABLED` while MFA is on. `enableMfa`: a valid code moves the secret into `accounts.mfa_secret_ciphertext` (associated data `platform.accounts.mfa_secret_ciphertext:<id>`), sets `mfa_enabled`, `mfa_enabled_at` and `version + 1`, replaces the recovery codes, queues `auth.mfa_changed`, audits `account.mfa_enabled` and publishes an `account` invalidation in one transaction, then deletes the pending secret (a Redis failure there is logged as `mfa.setup_cleanup_failed` and the codes are still answered: MFA is on, so the set-up can no longer be used); the ten codes are answered once (`no-store`). A missing, expired or used set-up answers `400 MFA_SETUP_EXPIRED`.
  - Recovery codes (`account_recovery_codes`): 16 Crockford base32 characters (80 bits) shown as `XXXX-XXXX-XXXX-XXXX`, typed in any case with or without dashes and spaces (O reads 0, I and L read 1), stored as the SHA-256 of the 16 normalised characters, used up with one `UPDATE … WHERE used_at IS NULL`.
  - `verifyMfa` (`public`): the `mfach:<sha256>` challenge of `signIn` (portal audience, 5 minutes by Redis's TTL and the `Clock`); unknown or ended answers `401 MFA_CHALLENGE_INVALID`. Each attempt counts against the account's `mfa` limit (10 per 10 minutes, the bucket the `stepUp` guard counts too; `429 RATE_LIMITED` with `Retry-After`, `503` while Redis cannot count) and against the challenge (`mfach:<sha256>:attempts`, one atomic increment each): a wrong code answers `401 MFA_CODE_INVALID` and is audited `auth.sign_in_failed` (`reason: invalid_mfa_code`, the method and the attempt, never the code); the fifth ends the challenge. A TOTP code or an unused recovery code (used up first, audited `auth.recovery_code_used` with the codes left) ends the challenge (only the call that deletes it continues) and starts the family with `mfa_verified_at` = now (`SignInService.startSession`, audit `auth.sign_in` with `mfa: true`). An account that may no longer sign in or lost MFA ends the challenge.
  - `stepUp` (`portal`): `403 MFA_REQUIRED` without MFA, `401 MFA_CODE_INVALID` for a wrong or used code; a valid TOTP code rotates the current generation of the token's family (`SessionsService.stepUp`, the locks of a refresh) with `mfa_verified_at` = now and answers the new `PortalSession` (`mfa_at` now, a new refresh token replacing the current one, `no-store`). A revoked or ended family answers `401 UNAUTHENTICATED`.
  - `disableMfa` and `regenerateRecoveryCodes` (`portal`, `x-mfa-step-up`: `RecentMfaGuard` answers `403 MFA_REQUIRED` or `401 REAUTH_REQUIRED` first): a platform admin cannot turn MFA off (`403 FORBIDDEN`, `details.reason = "platform_admin"`), and neither can an active owner or admin of a live OTA (`409 CONFLICT`, `details.reason = "mfa_mandatory"`, read through `MfaEnrolmentLookup` in the transaction that holds the account's lock; nothing is written; PBE-071). Disabling clears the secret, its key id, `mfa_enabled_at` and every recovery code (`version + 1`), audits `account.mfa_disabled` and publishes an `account` invalidation; regenerating replaces the ten codes (answered once, `no-store`) and audits `account.recovery_codes_regenerated`. Both queue `auth.mfa_changed` (PADR-0008 item 6).
  - The TOTP secret, the codes and the recovery codes are never logged, audited, queued or stored in clear (the integration test scans every log line, audit row, outbox row and Redis value).
- Password reset, account and sessions (PBE-016, [`../docs/scope.md`](../docs/scope.md) PF-05 to PF-07, [`../docs/api-inventory.md`](../docs/api-inventory.md) §4 and §5, [PADR-0007](../docs/adr/0007-portal-to-ota-admin-sso-token.md) item 6): `AuthModule` binds `requestPasswordReset` and `confirmPasswordReset` (`PasswordResetService`); `AccountsModule` (`src/accounts/`, `AccountsService`) binds `getMe`, `updateMe`, `changePassword`, `listSessions` and `revokeSession`.

Older links that have not expired keep working until one is used. Its throttlers are those of the resend (3 per address and 10 per IP per hour, shared by the two operations).
  - `confirmPasswordReset` checks the token first (unknown, used or expired, or an account that can no longer hold a session or no longer has the token's address: `400 PASSWORD_RESET_TOKEN_INVALID`), then the password rule (`422 PASSWORD_TOO_WEAK` on `/newPassword`, the link stays usable). The links of `auth.account_exists` are reset tokens too, so an unverified account may use one; the reset does not verify its address.
  - `changePassword` (`portal`) checks the current password (`422 CURRENT_PASSWORD_INCORRECT` on `/currentPassword`), then the rules for the new one. `PasswordResetService` does it, since `AuthModule` owns the credentials.
  - A new password, reset or changed, writes `staffdeny:acct:<accountId>` = now (epoch ms, 30 days) first, then in one transaction holding the account's `FOR UPDATE` lock stores the Argon2id hash with `password_changed_at`, revokes every family of the account, portal and admin (`password_change`; a change keeps the caller's family, the access token's `sid`), queues `auth.password_changed`, audits `account.password_reset` or `account.password_changed` (`revokedFamilies`, `staffDenyFrom`) and publishes an `account` invalidation after the commit. A reset also uses up the account's other reset links. The password is hashed before the transaction opens.
  - `getMe` (`portal_unverified`) answers the `Account` of a `PortalSession` (active memberships of visible OTAs with key, name, status and role; the six switches of `featuresFor()`) with its version in `ETag`. `updateMe` takes `If-Match` (`412 PRECONDITION_FAILED` when stale), trims the name (blank: `400` on `/fullName`), checks the time zone against `reference.time_zones` (`400` on `/timeZone`), writes only the fields that change with `version + 1` and one `account.updated` audit row, and answers the account with its new `ETag`. An account that may no longer hold a session gets `401 UNAUTHENTICATED`.
  - `listSessions` (`portal_unverified`) lists the active families of the account (a current generation that is neither rotated, revoked nor expired, in a family that has not ended), portal and admin, newest sign-in first, with the sign-in's user agent and IP, the last refresh and `current` for the caller's family. `revokeSession` revokes one of them (`logout`, audit `auth.session_revoked`), so its refresh token fails at once; a revoked, unknown or another account's family answers `404 NOT_FOUND`.

- Provisioning dispatch (PBE-019, [`../docs/flows/provisioning.md`](../docs/flows/provisioning.md) §1, [PADR-0001](../docs/adr/0001-tenant-provisioning-orchestration.md) items 2 to 4): `ProvisioningDispatcher.dispatch(jobId, {requestId?})` (`src/provisioning/dispatcher.ts`, in the static ProvisioningModule for the API and the worker) is the one dispatch of every job kind with a message (`provision`, `migrate`, `suspend`, `resume`). In one short transaction it locks the job's row and reads its tenant and current subscription; a job that is not `queued`, not due (`scheduled_at` after the Clock's now), of another kind, or a `provision` job whose gate is closed (the tenant must be `provisioning` and its current subscription `trialing`, `active` or manual) changes nothing (`provisioning.not_dispatched` with the reason). Otherwise the conditional update `queued → running`, `attempt + 1`, `step = 'dispatch'`, `started_at = coalesce(started_at, now)`, `locked_until = now + 15 min`, and the message `{v: 1, name, jobId, tenantId, requestedAt, requestId, payload}` (`payload` is the job's `payload` column), checked with `validateJob`, so an invalid one rolls the update back. After the commit it is added to `ota-tenant-ops` with the BullMQ id `<jobId>-<attempt>`, `attempts: 3` and an exponential backoff from 30 s; two dispatches of one job give one `running` row and one BullMQ job. A Redis error or no answer within 2 s is logged (`provisioning.enqueue_failed`, `provisioning.enqueue_timeout`) and never fails the caller: the job stays `running` until the reconciler (PBE-023) finds its lease ended. Integration tests answer the messages with the fake OTA worker of [`test/support/`](test/support/README.md).
- Audit (PBE-010, [PADR-0006](../docs/adr/0006-platform-admin-access-and-audit.md)): a module that changes state imports `AuditModule` and calls `AuditService.record(trx, {actorType, actorAccountId?, action, targetType, targetId, tenantId?, before?, after?, details?})` in its own transaction, so the `platform_audit_log` row commits and rolls back with the change. `action` and `targetType` are names of [`src/audit/audit-actions.ts`](src/audit/audit-actions.ts), where a new action is added first. The service takes the request id, the end user's IP and user agent from `RequestContext` (outside a request, a job passes its `requestId`; IP and user agent stay empty), snapshots the actor's e-mail and the tenant key unless given, and stores `details` as `{…details, before, after}`, each passed through `redactPayload` of `@velexis/logger`. The table is append-only for `velexis_platform_app` (migration 0002).
