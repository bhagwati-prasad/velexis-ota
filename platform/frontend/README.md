# Portal (`@velexis/platform-frontend`)

This is the Velexis portal at `platform.example.com`: the Next.js 15 App Router app where people sign up, create and pay for an OTA, manage API keys, domains, Amadeus and Stripe connections, team and billing, and open the OTA admin. It is a backend-for-frontend: every call to the platform API happens on the server, and tokens live only in httpOnly cookies. This page is the component specification: route map, components, data fetching, auth cookies, configuration and tests.

Related: [`../docs/scope.md`](../docs/scope.md) (features and roles), [`../docs/api-inventory.md`](../docs/api-inventory.md), [flows](../docs/README.md#flows), [ADR-0014](../../docs/mvp/adr/0014-frontend-stack-nextjs-tailwind.md), [`conventions.md` §3](../../docs/mvp/conventions.md#3-nextjs-apps-portal-platform-admin-ota-admin), [`.env.example`](.env.example).

## 2. Route map

Route groups: `(marketing)` public pages, `(auth)` sign-in flows, `(app)` signed-in shell. "Role" is the minimum membership role from [`../docs/scope.md`](../docs/scope.md) §1.2; the backend enforces it again.

### Public

| Route | Purpose | API | M |
|---|---|---|---|
| `/` | Marketing landing (static content, call to action) | — | M1 |
| `/pricing` | Public plans with limits; "Start" links to sign-up with the plan preselected | `listPlans` | M1 |
| `/legal/terms`, `/legal/privacy` | Static legal pages (versioned terms label used at sign-up) | — | M1 |

How the public pages behave (PFE-004; scope §2.2, PF-70):

- **`(marketing)/layout.tsx`** puts a header (home link, "Pricing", "Sign in", "Get started" → `/sign-up`) and a footer (terms of service, privacy notice) around each public page; each page renders its own `<main id="main-content" tabIndex={-1}>` with exactly one `h1`. The text lives in `lib/strings.ts` (`MARKETING_STRINGS`, `LANDING_STRINGS`, `PRICING_STRINGS`, `LEGAL_STRINGS`).
- **`/`** is static: what Velexis does, the three steps from sign-up to the first booking, what every OTA gets, and the calls to action to `/sign-up` and `/pricing`. No API call.
- **`/pricing`** calls `listPlans` on the server for every request and shows the plans it answers, in its order (`sort_order`), and nothing else: name, description, the monthly and the annual price with `Money` ("Monthly billing only" without an annual price), the free trial in days, the limits (team members, API keys, custom domains, live or test mode only), and "Start", a link to `/sign-up?plan=<code>` whose accessible name includes the plan's name. `listPlans` is public, so the call carries no access token, even for a signed-in visitor; it carries the end-user headers of PADR-0019, so the API's rate limit counts the visitor. A failed call shows the portal's message for its code (never the API's text) with a link to sign up; an empty list says no plan is open. Whether Checkout is available (`checkoutAvailable`) does not change the page: "Start" always leads to sign-up, which does not read `plan` yet, and the plan is chosen again in the create-OTA wizard.
- **`/legal/terms`** and **`/legal/privacy`** hold placeholder text, marked as such in a note, under "Version `termsVersion`" of `lib/terms.ts`: the value sign-up sends, so the pages and the acceptance the API stores name the same text. Change `termsVersion` (at most 32 characters) whenever either text changes in substance.

How sign-up and verification behave (PFE-005; [flow](../docs/flows/signup-and-create-ota.md) steps 1–3, PADR-0008):

- **`/sign-up`** (`sign-up-form.tsx`, action `signUp` in `actions.ts`). Zod checks the form on the server first: a full name (trimmed, at most 200 characters, counted in UTF-16 units as the field's `maxLength` counts them), an e-mail address (trimmed, at most 254), a password of 10 to 256 characters (counted in Unicode code points, as the API counts them) and the terms checkbox. The action then calls `signUp` with `acceptTerms: true` and `termsVersion` of `lib/terms.ts`. The API's field errors are mapped by JSON pointer to the form's own messages (`PASSWORD_TOO_WEAK` with `too_short` or `breached` lands on the password field), `RATE_LIMITED` and other failures show above the form, and `202` redirects to `/sign-up/check-email`. A refused submission keeps the name, the address and the checkbox, never the password.
- **`/sign-up/check-email`** reads the same for a new and an already registered address and asks for the address to send a new link to (the portal keeps no copy of it). **`/verify-pending`** shows a signed-in, unverified account its own address, a "send a new link" button for it and "Sign out"; a visitor without a session types the address. Both use `resendVerificationLink` (`verify-pending/actions.ts`): the confirmation never says whether the address has an account, and `RATE_LIMITED` shows the 3-links-per-hour message.
- **`/verify-email?token=…`** (`verify-email/route.ts`) calls `verifyEmail` on the server without a bearer token and answers `303` to a URL without the token, with `Referrer-Policy: no-referrer` and `Cache-Control: no-store`: `/sign-in?verified=1` without a session; for a signed-in account it first renews the session through the single-flight `refresh()` (the old access token still says `ev: false`, which the middleware would send back to `/verify-pending`) and continues to `/dashboard`. An expired, used, unknown or malformed token goes to `/verify-pending?error=token`, a rate limit or an unavailable API to `/verify-pending?error=unavailable`. Redirects use `PUBLIC_PORTAL_URL`. Only `GET` consumes the token: `HEAD` answers `204` with the same two headers and never calls the API, because Next.js would otherwise answer `HEAD` by running `GET`, and link checkers and mail scanners send `HEAD` to the links they find.
- An account verified in another tab or browser keeps an access token with `ev: false` until it is renewed: `/verify-pending` then shows "Your e-mail address is verified" with a "Continue" button (`continueAfterVerification`), which refreshes the session and goes to `/dashboard`.

How sign-in, MFA, password reset and sign-out behave (PFE-006; PF-03, PF-04 AC2, PF-05). Each page has its client form next to it (`sign-in-form.tsx`, `mfa/mfa-form.tsx`, `forgot-password-form.tsx`, `reset-password-form.tsx`) and its server action in `actions.ts`. `signIn`, `verifyMfa`, `requestPasswordReset` and `confirmPasswordReset` are public operations: the actions call them without a bearer token, even when an older session cookie is there, but with the end-user headers of PADR-0019, so the API's lock-out and per-IP limits count the person. Passwords, codes and tokens are never returned in an action's state, logged or kept.

- **`/sign-in`** (`signIn`). Zod checks the address (trimmed, at most 254 characters) and that a password was typed (at most 256 code points; the password rules apply when a password is chosen, not when it is used). `next` comes from the query, is kept only when `safeNextPath()` accepts it (so `next=https://evil.example/x` and `next=//evil.example` lead to `/dashboard`), travels in a hidden field, and is checked again by the action. A `PortalSession` becomes the two session cookies and the browser continues to `next`, or to `/dashboard` (`/verify-pending` for an unverified account). An `MfaChallenge` goes into `__Host-vxp_mfa` (`SameSite=Strict`, its `expiresIn`, at most 5 minutes) with `next` in `__Host-vxp_next`, and the browser continues to `/sign-in/mfa`; no session cookie is written yet. `INVALID_CREDENTIALS` and `ACCOUNT_DISABLED` show the portal's messages; `ACCOUNT_LOCKED` shows the wait of its `Retry-After` ("try again in 14 minutes"; seconds under a minute, minutes rounded up; the general message without the header) [PF-03 AC2]; `RATE_LIMITED` says the network made too many attempts. A refused submission keeps the address, never the password. The page shows one notice from the query: `verified=1` (from `/verify-email`), `reset=1` (a new password), `signedOut=1` (from `/sign-out`) or `mfa=expired` (an alert). It never sends a visitor with a session cookie away, because only the API can say whether that session still works.
- **`/sign-in/mfa`** (`verifyMfa`). Without a challenge cookie the page and the action send the visitor to `/sign-in?mfa=expired` (with the stored `next`). The form asks for the 6-digit code of the authenticator app; "Use a recovery code instead" swaps the field for a recovery-code field (and back) and moves the focus to it, and the hidden field `method` tells the action which one was sent [PF-04 AC2]. The action checks the format first (6 digits, spaces dropped; a recovery code of 16 to 24 letters, digits, dashes and spaces, any case), then sends `{mfaChallengeToken, code}` or `{mfaChallengeToken, recoveryCode}`. Success stores the session, deletes `__Host-vxp_mfa` and `__Host-vxp_next`, and continues to `next` or `/dashboard`. `MFA_CODE_INVALID` shows at the field and keeps the challenge; `MFA_CHALLENGE_INVALID` (expired, unknown, or five wrong codes) deletes both cookies and goes back to `/sign-in?mfa=expired&next=…`; `RATE_LIMITED` shows the wait of `Retry-After`.
- **`/forgot-password`** (`requestPasswordReset`). The same confirmation for every address, because the API answers `202` for every address [PF-05 AC1]; `RATE_LIMITED` (3 links per address or 10 calls per IP an hour, for any address) shows the 3-per-hour message.
- **`/reset-password`** (`confirmPasswordReset`). The link `/reset-password?token=…` never reaches the page: `middleware.ts` answers `GET` and `HEAD` of it itself. It sets `__Host-vxp_reset` (httpOnly, `SameSite=Strict`, 15 minutes) from the first `token` (an empty or over-long token, more than 512 characters, deletes an older cookie instead) and answers `200` with a small page without script that refreshes at once to `/reset-password` (other query parameters kept, HTML-escaped), with a "Continue" link for a browser that does not follow refreshes, `Referrer-Policy: no-referrer` (header and `<meta>`) and `Cache-Control: no-store` [PF-05 AC1]. The refresh replaces the token URL in the history. It is not a `303`: a browser sends a `SameSite=Strict` cookie only with a navigation the portal itself started, and a redirect keeps the start of the navigation it continues, so after a `303` a link clicked in web mail (a navigation started by another site) reached the page without the cookie it had just set and showed "Open the link from your e-mail" (checked in Chrome 147: the refresh carries the cookie, the `303` does not). Pages cannot set cookies in Next.js, which is why the middleware does it (`TOKEN_LINKS`, which also holds `/invitations/accept`, PFE-012). With the cookie the page shows the new-password form (one field, 10 to 256 code points, `autocomplete="new-password"`), whose action reads the token from the cookie on the server; without it the page asks to open the link again or to request a new one. `204` deletes the reset cookie and this browser's session cookies (the API revoked every session, PF-05 AC2) and goes to `/sign-in?reset=1`; `PASSWORD_TOO_WEAK` shows at the field and keeps the token; `PASSWORD_RESET_TOKEN_INVALID` deletes the cookie and offers a new link.
- **`/sign-out`** (route handler, `POST` only; Next.js answers other methods with `405`). The "Sign out" forms of the shell and of `/verify-pending` are plain form posts, and a route handler does not get the Origin check of server actions, so it checks `Origin` itself: anything but the origin of `PUBLIC_PORTAL_URL` (a foreign origin, `null`, none) answers `403` and changes nothing. Otherwise it calls `signOut` with the session's bearer token and refresh token (the middleware has renewed an expired access token first), deletes the session cookies (and a pending MFA challenge and return path) whatever the API answered, and answers `303` to `/sign-in?signedOut=1` with `Cache-Control: no-store`.

How invitation acceptance behaves (PFE-012; [flow](../docs/flows/team-and-ota-admin-sso.md) §A steps 2–3 and "Failure handling", PF-20 AC3):

- **The link** `/invitations/accept?token=…` never reaches the page: `middleware.ts` moves the token into `__Host-vxp_invite` (httpOnly, `SameSite=Strict`, 15 minutes) and answers the same refresh page as for `/reset-password?token=…` (`TOKEN_LINKS`; other query parameters kept, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`), so the URL loses its token after the first request and the token is never in the history, a `Referer` or the rendered page. An empty or over-long token deletes an older invitation cookie.
- **`/invitations/accept`** (`invitations/accept/page.tsx`, a server component) reads the cookie on the server. Without it the page asks to open the link from the e-mail again. With it the page calls `lookupInvitation` (public: no bearer token, the end-user headers, so its 20 lookups per IP and hour count the visitor) and shows "Join <OTA>", who invited, the role, the invited address and the link's expiry; an unknown, used, revoked or expired token (`INVITATION_INVALID`, or a refused shape) shows that the invitation cannot be used and asks the inviter to send it again; other failures show the portal's message for their code.
- **A visitor without a session** (no access token cookie, or `getMe` says the session ended) gets "Sign in to accept" (`/sign-in?next=/invitations/accept&email=<invited address>`) and "Create an account" (`/sign-up?email=…&next=…`). Both pages prefill the address (`prefillEmail()` of `lib/session.ts`: trimmed, at most 254 characters, no control character) and keep `next` (sign-in for the return, sign-up on its "Sign in" link); after the e-mail verification of a new account the person signs in and opens the invitation link again (the page says so), because `/verify-email` continues to `/sign-in?verified=1` without a return path.
- **A signed-in visitor** sees "You are signed in as <address>" and "Accept the invitation", a plain form post to the `acceptInvitation` action (`invitations/accept/actions.ts`), which reads the token from the cookie and calls `acceptInvitation` with the session. `200` deletes the cookie and continues to the OTA's dashboard `/otas/<tenantId>`. A refusal returns to `/invitations/accept?error=<code>` (the code only, never the token; the page ignores a value that is not a catalogue code): `INVITATION_INVALID` (and a refused token shape) also deletes the cookie; `UNAUTHENTICATED` and `TOKEN_EXPIRED` go to sign-in with `next` back here instead.
- **Another address** (PF-20 AC3): when `getMe` names an address other than the invited one (letter case ignored, as the API compares them), or `acceptInvitation` answered `INVITATION_EMAIL_MISMATCH`, the page shows no "Accept" but "This invitation was sent to <invited address>", the signed-in address, and "Sign out and sign in with the invited address": the `signOutForInvitation` action revokes the session as `/sign-out` does (`signOut` with the refresh token), deletes the session cookies (the invitation cookie stays) and continues to `/sign-in?next=/invitations/accept&email=<invited address>` (an address Zod does not accept is left out). Another address wins over an unverified one, because verifying an address that was not invited never lets the account accept. An unverified account with the invited address (`emailVerified` false, or `EMAIL_NOT_VERIFIED`) is asked to verify first, with the link to `/verify-pending`; `ALREADY_MEMBER` says so and links to `/dashboard`.

How the MFA enrolment gate behaves (PFE-030; scope PF-04 AC4, [PADR-0008](../docs/adr/0008-email-verification-and-mfa-policy.md) revision of 2026-11-05). The rule is the API's alone (PBE-071's `MfaEnrolmentGuard`): an active `owner` or `admin` of a live OTA without MFA. The portal never decides it itself; it reads `Account.mfaEnrolmentRequired` of `getMe` and the API's `403 MFA_REQUIRED` with `details.reason = enrolment_required`, and sends the browser to `/mfa-enrolment?next=<the page>` through `mfaEnrolmentPath()` of `lib/errors.ts`.

- **Where the gate meets the account.** The `(app)` layout reads `mfaEnrolmentRequired` of the `getMe` it already calls (after the unverified check) and redirects every page of the signed-in area there before the shell or the page renders; `next` is the page the request was for, which `middleware.ts` hands on in the request header `x-velexis-requested-page` (`REQUESTED_PAGE_HEADER` of `lib/session.ts`: the path and query of a request for the signed-in area or `/mfa-enrolment` when `safeNextPath()` accepts them, and `/invitations/accept` by its path alone, whose "Accept" calls the gated `acceptInvitation`, so an account that meets the gate there comes back to the invitation once enrolled; set or deleted on every request it passes on, so a value the browser sent never reaches a page; Next.js tells a layout nothing of the page it wraps). Everything else that calls the API meets the API's gate: `platformApi()` of `lib/api.ts` passes every refused call through `leaveForMfaEnrolment()` (`lib/errors.ts`), so a page, a server action or a `GET` route handler whose call answers `enrolment_required` leaves for the page with the same `next` (`redirect()`: a `303` from an action, a `307` from a page). This covers a page rendered inside the shell when the requirement starts mid-session (an OTA goes live while its admin browses: Next.js does not render the shared layout again then). The two route handlers with a client of their own answer their own `303`: the console launch to `/mfa-enrolment?next=/console?tenant=<id>`, Stripe Connect's callback to `/mfa-enrolment?next=<the payments page>?stripeConnect=unavailable` ("nothing changed, try again").
- **`/mfa-enrolment`** (`(auth)/mfa-enrolment/page.tsx`, outside the shell: one `<main>`, no navigation) says why (an owner or admin of a live OTA, real bookings and payments, what a stolen password could do), runs the set-up of the security page (`MfaEnrolment` of `account/security/mfa-setup.tsx`: the QR code drawn from the server's geometry, the base32 secret in a `CopyField`, the confirming code, the ten recovery codes shown once in `SecretRevealPanel`) and then offers "Continue" to `next`, a plain link (a full page load, so the signed-in layout reads `getMe` afresh). Nothing more reaches the browser than on the security page: the page's own markup holds no secret, and the secret, the QR code and the codes come only in the answers of its actions and live in React state. `next` is kept only when `safeNextPath()` accepts it and it is not the enrolment page itself, otherwise `/dashboard`. "Sign out" (the plain form post to `/sign-out`) stays offered. An account that does not (or no longer) need the enrolment goes to `next` at once, one without a session to `/sign-in?next=/mfa-enrolment?next=…`, an unverified one to `/verify-pending`; a `getMe` that fails otherwise shows the portal's message in place of the set-up.
- **Its actions** (`(auth)/mfa-enrolment/actions.ts`): `beginEnrolment` (`startMfaSetup`) and `confirmEnrolment` (`enableMfa`), both `portal_unverified` operations the API's gate leaves open, with the security page's checks of the answers and the typed code, from the one module both pages import (`lib/mfa-checks.ts`, FIX-W46-PLATFORM, lead decision (11c)) (an answer that is not the document's shows the general error and nothing of it; a turned-on MFA whose answer has no recovery codes of the document's shape says, in an alert, to replace them on the security page, never "try again"). Unlike the security page's actions they revalidate nothing: rendering the page again would send an account that no longer needs the enrolment on to `next` before it has seen its recovery codes. `MFA_ALREADY_ENABLED` (turned on in another tab) offers "Continue"; an expired set-up offers "Start again"; an ended session signs in again and comes back to the enrolment with its `next`.

How the dashboard and the create-OTA wizard behave (PFE-008; [flow](../docs/flows/signup-and-create-ota.md) steps 5–7 and failure handling, PF-10):

- **`/dashboard`** (`dashboard/page.tsx`) calls `getMe`, `listTenants` and, for the plans' names, `listPlans` on the server. Each OTA of `listTenants` (oldest first) shows its name, linked to its overview (to its set-up page while it is `provisioning` or `failed`), its status (`StatusBadge`), "Test mode" while the storefront is in test, the key, the plan's name (its code when `listPlans` does not know it or fails), the caller's role, the storefront link `https://<key>.<STOREFRONT_BASE_DOMAIN>/` and "Open console" (`OpenConsoleButton`, PFE-017, below). "Create an OTA" shows only when `getMe` says the address is verified: an unverified account gets a link to `/verify-pending` instead (the `(app)` layout already sends it there, but layouts and pages render side by side, so the page does not rely on it), and a failed `getMe` hides the button. A failed `listTenants` shows the portal's message for its code; an empty list explains how to start, or how to join someone else's OTA. `listPlans` is public and carries no access token.
- **`/otas/new`** (`otas/new/page.tsx`, a server component) loads `getMe` (the M5 switch and the account's time zone; an ended session goes to `/sign-in?next=/otas/new`, an unverified account to `/verify-pending`) and `listPlans` (public, no access token), builds the option lists on the server so the server's markup and the browser's hydration agree, and makes the wizard's one `Idempotency-Key` with `randomUUID()`: a new one each time the page opens. Countries are the ISO 3166-1 codes and currencies the active ISO 4217 codes of the reference data the API checks against (`tools/reference-data`; the test keeps both lists equal to it), named with `Intl.DisplayNames`; time zones are the IANA zones of `Intl`, `UTC` and the account's own zone, which is preselected.
- **`Wizard`** (`wizard.tsx`, client) is one form in three steps, so the final submit sends every field: *OTA details* (name; key, prefilled from the name — letters and digits, lower case, accents dropped, 30 at most — until the person types a key of their own; country, default currency and time zone as selects), *Plan* (`PlanPicker`) and *Review* (every value, the storefront address, "Change" for each earlier step). "Continue" (or Enter) checks the fields of its step in the browser and shows the problems in `FormErrorSummary` (it takes the focus) and at the fields; otherwise the next step's heading takes the focus. "Back" keeps every value.
- **`KeyAvailabilityField`** (`key-availability-field.tsx`) shows the address the key gets (`<key>.<STOREFRONT_BASE_DOMAIN>`) as the person types, and its availability in a live region read with the field: a key that breaks `^[a-z][a-z0-9]{2,29}$` is reported at once without a call; otherwise, once typing pauses for 400 ms, the server action `checkKeyAvailability` calls `checkTenantKey` (with the session and the end-user headers) and the field says available, taken or reserved, or that the key could not be checked (rate limit, API down; `createTenant` checks it again). Only the answer for the key still in the field counts. A taken or reserved key keeps "Continue" on step 1 [PF-10 AC1], and so does a key `createTenant` refused. A message at the key (from "Continue" or a refused submit) goes as soon as the key changes, so the field shows the live check of the new key.
- **`PlanPicker`** (`plan-picker.tsx`): before M5 (`getMe.features.stripeBilling` off) only `early_access`, preselected, with a note that every new OTA starts on it [PF-10 AC3]; when `listPlans` fails the step says so and the wizard still sends `early_access`, which is what the API uses before M5 anyway. With the switch on (PFE-020, PF-71; the page passes `stripeBilling` to the wizard) it offers every public plan `listPlans` answers, in its order, under the "Annual billing" switch (a checkbox with the `switch` role, off for monthly; the hidden field `billingInterval` sends `month` or `year`, so the form always has one): each plan shows its price for the interval (the annual price, or "Monthly billing only"), its free trial and its limits, and a plan without a Stripe price for the interval (`checkoutAvailable`) is shown disabled with the reason in its name (the error summary's link leads to the first plan that can be chosen, because a disabled radio button cannot take the focus). A note says Stripe's payment page opens after the review. A chosen plan that the new interval cannot bill is no longer chosen, so "Continue" asks for one; the page's default plan is kept only when it can be billed monthly.
- **`createOta`** (`actions.ts`) checks every field again with Zod, then calls `createTenant` with the hidden `idempotencyKey` as `Idempotency-Key` (a submission without a valid key is refused without a call). Every submit of one wizard sends the same key — React runs queued submits one after the other, and the API answers a repeat with the stored `202` — so a double click or a retry after a lost answer creates one OTA [PF-10 AC2]. `202` redirects to `/otas/<id>/setup`. `TENANT_KEY_UNAVAILABLE` (taken since the check, or reserved) returns to step 1 with the message at the key, and "Continue" does not take that key again; `VALIDATION_FAILED` puts the portal's message at each field of its `fieldErrors` and opens the step of the first; `PLAN_NOT_AVAILABLE` goes to the plan; `UNPROCESSABLE` with `details.reason = "tenant_limit"` stays on the review with the limit message, naming `details.limit` when the API sent it [PF-10 AC4]; `UNAUTHENTICATED` goes to sign-in, `EMAIL_NOT_VERIFIED` to `/verify-pending`; anything else shows the portal's message for its code.
- **From M5** (PFE-020; [flow](../docs/flows/signup-and-create-ota.md) step 7 and "Failure handling"): the request also carries `billingInterval` (before M5 the form has no such field and the request no such property, as in M1 [PFE-020 AC3]), the review names the billing, price and free trial and says Stripe's page opens next, and the submit reads "Create OTA and continue to payment". `202` with a `checkoutUrl` is a `redirect()` to exactly that URL, Stripe Checkout (§5, external navigations; PF-71 AC1): the portal follows it only when it is an absolute `https:` URL without credentials and never builds one. Without a URL (Stripe failed after the OTA was created: `checkoutUrl: null` and `checkoutError`) the browser goes to `/otas/<id>/setup?payment=<code>` (the `checkoutError` code when it is one of the catalogue, otherwise `PROVIDER_ERROR`; an answer whose URL cannot be followed gives `INTERNAL_ERROR`), where "Continue to payment" waits.

How the set-up page behaves (PFE-009; [flow](../docs/flows/provisioning.md) §4 and "Failure handling", PF-11):

- **`/otas/[tenantId]/setup`** (`setup/page.tsx`, a server component) reads `getTenant` (the name for the `h1`, `primaryHost` for the storefront link `https://<primaryHost>/`, and `myRole`) and the progress (`getSetupProgress`, below) side by side. An id that is not a `ten_` ULID, or `NOT_FOUND` (no membership), renders the not-found page; an ended session goes to `/sign-in?next=/otas/<id>/setup`, an unverified account to `/verify-pending`; any other failure shows the portal's message for its code. In the app the OTA layout (PFE-010, below) loads the OTA first and answers these cases itself, so an ended session returns to the OTA's overview (`/sign-in?next=/otas/<id>`); the page still calls `getTenant` on its own, a second call per request until it reads the layout's cached `loadTenant`. The page never calls `revealInitialKeys`: the keys come only from an owner's click.
- **`setup/actions.ts`** holds three server actions, each checking the OTA id first and calling the API with the session and the end-user headers: `getSetupProgress` (`getProvisioning`, any member), `retrySetup` (`retryProvisioning`, owners; a `checkoutUrl` of M5 is a `redirect()` to Stripe) and `revealSetupKeys` (`revealInitialKeys`, owners; the publishable key first). The progress they return is `getProvisioning` without the job's `error` text and the steps' error messages, which stay on the server (§5: raw API messages are never shown); `hasError` only says that an attempt failed.
- **`ProvisioningProgress`** (`components/provisioning-progress.tsx`, client) gets the page's progress and the three actions bound to the OTA. It reads the progress every 2 seconds (`SETUP_POLL_INTERVAL_MS`), one call at a time, and stops for good at a final state: the OTA `active`, `failed` or `suspended`, or its job `failed` or `canceled` [PF-11 AC1]. `RATE_LIMITED` (after its `Retry-After`, at most a minute), `SERVICE_UNAVAILABLE` and `INTERNAL_ERROR` keep polling with a note; any other failure (`NOT_FOUND` after a removal) stops it with the portal's message. When an action ends with `redirect()` (an ended session), Next.js rejects the call with that redirect: the component throws it again while rendering, so the router's redirect boundary takes the page to sign-in, as for a form's action, and polling stops. A summary in a live region says where the set-up stands ("4 of 9 steps done", a retried attempt waiting for its next try, ready, failed). The steps list shows each step once with its latest outcome, because the job's step log only grows (a failed attempt, each try of a post-step and every new attempt append their steps again): the finished steps with `StatusBadge` (`jobStep`), then the step in progress (a step whose last try failed runs again while an attempt runs) and the ones still waiting; after a failure, the step it stopped at and "Not run" for the rest, including a step an earlier attempt failed at further on.
- **Active:** "Your OTA is ready", the storefront link and the OTA dashboard link. Owners get "Reveal the test keys" while `initialKeysAvailable` is true: the keys show in `SecretRevealPanel` from React state only and the button goes; `KEYS_ALREADY_REVEALED` (or a page that opens after the reveal or the 24 hours) shows the portal's explanation with a link to the API keys page [PF-11 AC3]. Other roles read that an owner can reveal them.
- **Failed:** the step it stopped at, the attempts made, that Velexis is on it, and the job id as the reference for support. Owners of a `failed` OTA get "Retry the set-up" (other roles a note that only an owner can retry) [PF-11 AC2]: the answer's new job replaces the progress and polling starts again. `PROVISIONING_NOT_RETRYABLE` keeps its message in view and reads the progress once (another owner may have retried); other refusals show their message under the button. A retry whose answer carries a `checkoutUrl` (M5) is a `redirect()` to it when it is an `https:` URL.

How the set-up page handles the payment of an OTA created from M5 (PFE-020; [flow](../docs/flows/signup-and-create-ota.md) steps 7–8 and "Failure handling", [billing flow](../docs/flows/subscription-billing.md) §B and §H, PF-71):

- **Which OTAs wait for a payment.** Only the subscription tells, and only owners and finance members may read it (`getSubscription`, `viewBilling`), so the page reads it for them, and only when the progress leaves the question open: a `provisioning` OTA whose job never went out (`queued`, attempt 0: the dispatch gate stays closed while the subscription is `incomplete`), or a `failed` OTA whose job was `canceled` (the abandoned-Checkout job). An `incomplete` Stripe subscription means the OTA waits for its payment; an `incomplete_expired` one that its Checkout was abandoned. Anything else, a manual trial before M5, a subscription that cannot be read, and the roles that cannot read it, get the progress as in M1.
- **Waiting for the payment:** "Payment needed" with the plan and the billing interval, instead of the steps. Owners get "Continue to payment", a `CheckoutForm` (`setup/checkout-form.tsx`, a client component) that calls the server action `continueToPayment` (§7: never a native form post; the router follows its `redirect()` to Stripe as a top-level navigation), which calls `createCheckoutSession` with the plan and interval of the `incomplete` subscription and an `Idempotency-Key` made when the page rendered (a double click opens one Checkout; the next visit makes a new key, so a fresh Checkout once the last one expired after 24 hours), then `redirect()`s to the answer's URL [PFE-020 AC2]; finance members read that an owner continues. The page says that without a payment within 48 hours the set-up stops.
- **Back from Stripe** (`?checkout=success`, Checkout's `success_url`): the page does not offer a payment but follows the progress (`ProvisioningProgress`, polling every 2 s) under a status note that Stripe's confirmation can take a minute: the webhook, not the redirect, starts the set-up (PF-71 AC1). Since PFE-021 the same URL of an OTA that is not `provisioning` and has no test keys waiting for their reveal (an OTA failed by an abandoned Checkout and paid from the billing page, or an active OTA that chose a plan there) goes on to `/billing?checkout=success` for the roles that see billing, where the billing page confirms the payment (§2 `/billing`).
- **Abandoned:** "The payment was not completed", and for owners "Retry", a `CheckoutForm` that calls `retryPayment`: `retryProvisioning`, then a `redirect()` to the new Checkout URL of its answer; without one (Stripe failed, or the plan is no longer available) the page comes back with "Continue to payment" for the new `incomplete` subscription. Other roles read that an owner can retry.
- **A payment that did not leave for Stripe** comes back to the set-up page with `?payment=<code>`, a code of the catalogue (a form action has no state to return), and the page shows the portal's words for it: Stripe not reached (`PROVIDER_ERROR`, `SERVICE_UNAVAILABLE`, `INTERNAL_ERROR`), already paid (`CONFLICT`, a status message), a plan no longer available (`PLAN_NOT_AVAILABLE`, with a link to the billing page for the roles that see it), a retry someone else made (`PROVISIONING_NOT_RETRYABLE`), an expired form, or the message of any other code. A value that is not a code of the catalogue is ignored. An ended session signs in again and comes back to the set-up page.

How the OTA dashboard, its checklist and its settings behave (PFE-010; PF-12, PF-13, [PADR-0018](../docs/adr/0018-onboarding-checklist-computation.md), [PADR-0014](../docs/adr/0014-tenant-suspension-and-resume.md) item 5):

- **`otas/[tenantId]/layout.tsx`** loads the OTA once per request with `getTenant` (`requireTenant` of `lib/tenant.ts`) and passes it down: `loadTenant` is a React `cache()`, so a page below that asks for the same OTA in the same request reads the layout's answer and makes no second call. An id that is no OTA id (`ten_` + ULID) makes no call, and it and `NOT_FOUND` (an OTA the caller is no member of: the API never says whether it exists) render the not-found page (`notFound()`); `UNAUTHENTICATED` and `TOKEN_EXPIRED` go to `/sign-in?next=/otas/<id>` (the OTA's overview: the layout redirects before any page below it, and Next.js never tells a layout which page it wraps), `EMAIL_NOT_VERIFIED` to `/verify-pending`; any other failure (rate limit, API unavailable) shows the portal's message for its code in place of the page, under one `h1`, and the page renders nothing for it.
- **`/otas/[tenantId]`** (`page.tsx`, every member) shows the OTA's name (the page's `h1`) with its status (`StatusBadge`; the OTA's notices, `TenantBanner`, sit above every page of the OTA since PFE-021, below), a notice with the link to the set-up page while the OTA is `provisioning` or `failed`, the storefront link `https://<primaryHost>/`, the key, the caller's role and the default currency, "Edit the OTA profile" for owners and admins only, and `OnboardingChecklist` from `getOnboarding` (called next to the tenant's load, with the session). A failed `getOnboarding` shows the portal's message for its code in place of the checklist; the rest of the page stays. "Open console" (`OpenConsoleButton`, every role) sits next to "Edit the OTA profile", and `?console=<problem>` shows why a launch was refused (`ConsoleLaunchNotice`, PFE-017, below).
- **`OnboardingChecklist`** (`components/onboarding-checklist.tsx`, a server component) lists every item `getOnboarding` answers, in its order (the account items are the caller's; M5 items only while their switch is on), each with its `label` as a link to its `href` and its state in words ("Done" or "To do", never the icon alone), the count of done items, and a line when all are done. Done items stay listed: the checklist is computed on every request and the portal stores nothing about it (PADR-0018). `checklistLink()` links only a portal path (one leading `/`, no backslash or control character) or an `https:` URL without credentials (the storefront of `storefront_open`); any other `href` renders as text [PF-12 AC1].
- **`/otas/[tenantId]/settings`** (`settings/page.tsx`, owner and admin): any other role gets the not-allowed page (`NotAllowed`: the role in words, who can change it, the way back to the overview); the navigation has no entry for those roles and the API refuses `updateTenant` with `403` all the same [PF-13 AC1]. **`SettingsForm`** (`settings-form.tsx`, client) edits the name, the legal name, the support e-mail, the country (the reference countries of `lib/reference-options.ts`) and the time zone (the server's IANA zones and the OTA's own); the key and the default currency are shown read-only, because the API never changes them. The fields are controlled and, once the page has hydrated, `onSubmit` posts the form's data in a transition, so React's reset of an action form never puts the old values back; the form's `action` is the same server action, so a form posted before the page hydrated still goes to `saveOtaProfile` as a `POST` (Next.js renders its answer, with what was sent in the fields) and never puts the fields in a `GET` query string. While the OTA is not `active` the fields and the button are disabled, with the reason for `provisioning`, `suspended` or `failed` (PADR-0014 item 5; the API answers `TENANT_NOT_ACTIVE` then).
- **`saveOtaProfile`** (`settings/actions.ts`) checks the form again with Zod (a trimmed name of 1 to 100 code points, a legal name of at most 200, an e-mail address of at most 254, both optional, where an empty field sends `null` and clears the value; a country `^[A-Z]{2}$`; a time zone of the document's pattern) and the hidden `tenantId` and `version` (a submission without them is refused without a call), then calls `updateTenant` with `If-Match: "<version>"`, the version the page was rendered with. `200` shows "The profile is saved." with the saved profile and its new version, so the next save carries it, and revalidates `/otas/<id>` (layout), so the shell and the overview show the new name. `PRECONDITION_FAILED` (someone else saved in the meantime) keeps what was typed and the old version and offers "Reload the page"; `VALIDATION_FAILED` puts the portal's message at each field of its `fieldErrors` (`/header/If-Match` and other paths outside the form read as an expired form); `TENANT_NOT_ACTIVE`, `FORBIDDEN`, `NOT_FOUND` and `RATE_LIMITED` have their own messages; `UNAUTHENTICATED` goes to sign-in and back to the settings, `EMAIL_NOT_VERIFIED` to `/verify-pending`; anything else shows the portal's message for its code.

How the API keys page behaves (PFE-011; [flow](../docs/flows/api-keys.md), [PADR-0005](../docs/adr/0005-api-key-format-and-hashing.md) items 4–8, PF-30):

- **`/otas/[tenantId]/api-keys`** (`api-keys/page.tsx`, owner and admin): any other role gets the not-allowed page without a key call (the navigation has no entry for it; the API answers `403` all the same). The tenant comes from the layout's `getTenant`; the page then calls `listApiKeys` with `includeRevoked=true` (revoked keys stay listed: the audit log refers to them). An ended session goes to sign-in and back to `/otas/<id>/api-keys`, an unverified account to `/verify-pending`, `NOT_FOUND` to the not-found page; another failure shows the portal's message in place of the list, and the create form stays. One tab per environment: the "Test keys" tab, and the "Live keys" tab once the OTA is live (PFE-026, M5: `environmentsOf` in the page reads `storefrontEnvironment` of `getTenant`; the table, the form and the actions take the environment). The live tab stays for a live OTA whatever the live switch says, so its live keys can still be revoked; creating or rolling one with the switch off is the API's `FEATURE_DISABLED`, which the form shows. Creating a live secret key asks for a step-up [PF-30 AC6]: the API answers `REAUTH_REQUIRED`, `createKey` answers `stepUp` and the form's `useStepUpAction` opens `StepUpDialog` and sends the same form again after the code. Each tab lists its keys (`ApiKeysTable`) and holds the create form (`CreateKeyForm`). The page decides each key's state once per request (`revoked`; `expired` once `expiresAt` has passed; else `active`), so the server's and the browser's markup agree. While the OTA is not `active` the form and the row actions are disabled with the reason (PADR-0014 item 5; the API answers `TENANT_NOT_ACTIVE` then). **The page never has a full key:** a key exists only in the answer of the create or roll action, rendered by a client component from React state (§5), so a reload never shows it again.
- **`ApiKeysTable`** (`api-keys/keys-table.tsx`, client; `DataTable` with its columns next to the page): name, kind, the key as `prefix…last4`, access (the origins of a publishable key, or "No browser origin" without any; the use of a secret key and its permissions), created (the date, and the creator's name or "at set-up" for the keys of the set-up), last used (`DateTime`, or "Never"; the list's intro says it can be 5 minutes behind) [PF-30 AC5], expiry (or "No expiry") and state (with the revocation time). Every key that is not revoked has "Edit", "Roll" and "Revoke", each named with the key for screen readers (`Roll Storefront (sk_test_Qw34Er…Df90)`): **Edit** opens a dialog with the name and, for a publishable key, `OriginsField` (`updateKey`); kind, environment and scopes are never editable. **Roll** opens a dialog with when the old key stops working (now, in 1 hour, in 24 hours (preselected) or in 7 days; `rollKey`, with a step-up when the API asks for one); the new key shows once in `SecretRevealPanel` above the list, with when the old key stops (or stopped) working, from `previous.expiresAt` of the answer [PF-30 AC4] ("stopped" after a roll with "now", and for a key whose expiry had already passed: the API never moves an expiry later, so an expired key keeps its own); "I have stored it" drops it from the table's state. **Revoke** goes through `ConfirmDialog` (`revokeKey`); until the list is renewed the row says "The key is revoked." and its actions are locked. A refusal shows the portal's message in its dialog or row (`CONFLICT`: revoked in the meantime; `TENANT_NOT_ACTIVE`; `PLAN_LIMIT_REACHED` of a roll that keeps the old key working).
- **`CreateKeyForm`** (`api-keys/create-key-form.tsx`, client): name (1 to 100 code points, trimmed), kind (secret, the default, or publishable), then `OriginsField` for a publishable key or `ScopePicker` for a secret key, and an optional expiry (none, or 7, 30 or 90 days or 1 year from the submission). As in the settings form the fields are controlled and `onSubmit` sends the form's data (React's form reset never empties them), and `action` keeps a form posted before hydration from going out as a `GET` (React replays it once the page has hydrated). `createKey` runs through `useStepUpAction` (a live secret key needs a TOTP step-up: PF-30 AC6, with PFE-026) and answers the new key once: `SecretRevealPanel` shows it with the shown-once warning, where the key shows in the list (`prefix…last4`) and the recommended set-ups of the flow (a storefront: a secret key scoped Storefront; a back office: Console with a staff token; each automation job: its own Console automation key with the fewest permissions; browser code: a publishable key with exact origins), and the form starts again, so a second click makes no second key [PF-30 AC1]. The key is never written to storage, cookies, the URL or the history.
- **`OriginsField`** (`components/origins-field.tsx`, controlled, no state of its own) has one input per origin (`allowedOrigins`, in order), each with its label, error and "Remove", and "Add an origin" while there are fewer than 20. `originProblem` holds the rules of PADR-0005 item 5 as the platform API's `api-key-rules.ts` checks them: an exact origin as a browser sends it (no wildcard, path, query, user info or trailing slash; lower case; no default port), `https` only, except `http://localhost:<port>` and `http://127.0.0.1:<port>` on test keys. The action drops empty rows, refuses more than 20 origins with the count's one message before it looks at any of them (FIX-W45-PLATFORM, lead decision (9c)), checks each origin and duplicates before any call, and puts the API's `/allowedOrigins/<n>` at the row it was typed in.
- **`ScopePicker`** (`components/scope-picker.tsx`, controlled): the use of a secret key as radio buttons (`storefront`, the default; `console`; `console:automation`), each with what it allows, and the `StaffPermission` checkboxes, disabled (neither checked nor sent) unless Console automation is chosen; the choice is kept while another use is selected. The values are the OTA contract's `ConsoleApiKeyScope` and `StaffPermission` of `@velexis/api-types` (one object per type, `satisfies Record<…, true>`, so the type check fails when the OTA document changes until the lists follow, and the test compares them with the document). `scopeProblem` holds the rules of PADR-0005 item 6: permissions only with `console:automation` (a forged submission that sends them anyway is refused without a call), `console:automation` needs at least one, `storefront` alone. The action sends `["console:automation", …permissions]` in the document's order [PF-30 AC2].
- **The actions** (`api-keys/actions.ts`): `createKey`, `updateKey`, `rollKey` and `revokeKey` check their hidden ids (`ten_` and `key_` ULIDs; a submission without them makes no call) and their fields first, call the API with the session and the end-user headers, map the API's field errors by JSON pointer to the form's own messages (`/name`, `/allowedOrigins/<n>`, `/allowedOrigins`, `/scopes`, `/expiresAt`; other paths, and `notAllowed` for a field the key's kind does not take, read as an expired form) [PF-30 AC2], and revalidate the page after a change. `PLAN_LIMIT_REACHED` names `details.limit` and `details.used`; `REAUTH_REQUIRED` answers `stepUp`; `UNAUTHENTICATED` and `TOKEN_EXPIRED` go to sign-in and back, `EMAIL_NOT_VERIFIED` to `/verify-pending`. The full key of a create or a roll leaves the server only in the action's answer, which Next.js sends with `Cache-Control: no-store`; it is never logged, stored, cached, or put in a cookie or a URL.

How the card statement suffix form behaves (PFE-016; [Stripe flow](../docs/flows/stripe-payments-account.md) §A item 3, PF-60, ADR-0011 Velexis mode):

- **Where.** On `/otas/[tenantId]/payments` each card of a `velexis`-mode connection (test, and live once the OTA is live) ends with the form (`payments/descriptor-form.tsx`, client, given to `ConnectionCard` as its children) for owners and admins (`manageConnections` of `lib/roles.ts`); finance members read the suffix in the card's details with a note that only owners and admins change it, and get no form [PFE-016 AC1]. Cards of the OTA's own Stripe account (M5) add nothing, because the OTA backend sends no suffix for them. Each form names its connection by the hidden `tenantId`, `environment` and `version` (the connection's, for `If-Match`), and its ids carry the environment, so two cards never share a field id.
- **The rules** (`payments/descriptor-rules.ts`, plain functions in a module without a directive, so the browser form and the `"use server"` action share them; the action's Zod schema applies them again, and Zod stays out of the browser bundle): the ends are trimmed (a stray space is neither refused nor sent; inner spaces stay as typed, as the API stores them), then the rules of the platform document's `StatementDescriptorSuffix` and of the API's `statementDescriptorSuffixProblems` (PBE-038), each with its own words: something typed; none of Stripe's forbidden characters `<` `>` `\` `'` `"` `*`; no other character than the letters A to Z, digits and spaces (no accents; nor `&`, `.` or `-`, which the column's `CHECK` would hold but the API refuses); 2 to 22 characters; at least one letter. The test compares the browser's and the action's verdicts with the document's `minLength`, `maxLength` and `pattern` over values around every rule.
- **In the browser.** A character the rules refuse shows at the field as it is typed (`aria-invalid`, `aria-describedby`); the other rules show once a submit was refused, because more typing can still fix a length. A submit checks every rule first and, while one is broken, shows it in the focused `FormErrorSummary` and sends nothing: `"ACME*TRAVEL"` never reaches the action or the API [PFE-016 AC1]. The form posts its data in a transition (fields controlled, as on the settings page); its `action` serves a form posted before hydration, which the action checks with the same rules.
- **The preview** (`statementLine`): the line a card statement shows, `VELEXIS* ACME TRAVEL` (the Velexis Stripe account's shortened descriptor, `STATEMENT_DESCRIPTOR_PREFIX`, then `* ` and the suffix in capital letters), at most 22 characters: a longer suffix is cut, with a note that up to 13 characters show in full. It is an `<output>` for the field, read by screen readers when it changes; it shows the length typed, and no line while the suffix is empty or breaks a rule. Banks print the line their own way; the preview says so.
- **`saveStatementDescriptor`** (`payments/actions.ts`) refuses a form without a valid OTA id, environment (`test`, `live`) or version without a call (an expired form), checks the suffix with Zod, then calls `updatePaymentConnection` with `If-Match: "<version>"`, the session and the end-user headers. `200` shows "saved" with the stored suffix and the new version, so the next save carries it, and revalidates the payments page, so the card's details show it. `PRECONDITION_FAILED` (someone else saved in the meantime) keeps what was typed and the old version and offers "Reload the page"; `VALIDATION_FAILED` with an error on `/statementDescriptorSuffix` shows the portal's message for its code at the field (`minLength`, `maxLength` and `pattern` of the request validation, the service's `forbiddenCharacter`, `characters`, `letter`, `start`; another code the general rule), never the API's text; any other path reads as an expired form; `TENANT_NOT_ACTIVE`, `FORBIDDEN` and `NOT_FOUND` ask for a reload, `RATE_LIMITED` to wait; `UNAUTHENTICATED` and `TOKEN_EXPIRED` go to sign-in and back to the payments page, `EMAIL_NOT_VERIFIED` to `/verify-pending`; anything else shows the portal's message for its code. While the OTA is not `active` the form is disabled with the reason (PADR-0014 item 5; the API answers `TENANT_NOT_ACTIVE` then). The operation needs no step-up.

The page itself never holds a secret. `?console=mfa_required&tenant=<id>`, where the "Open console" launch sends an account without MFA for a live OTA, adds the explanation above the sections with "Open the console again" (`/console?tenant=<id>`, PFE-017).
- **Password** (`password-form.tsx`, `changeAccountPassword`): the current password and a new one (`autocomplete` `current-password` and `new-password`); the form is a plain action form with uncontrolled fields, so React empties both after every answer and no password is kept in the page or the action's state. Zod checks that the current password was typed (at most 256 code points) and the new one's 10 to 256 code points; `CURRENT_PASSWORD_INCORRECT` shows at the current password, `PASSWORD_TOO_WEAK` at the new one (`too_short`, `breached`); `204` says that every other session was signed out (the API also ends the OTA admin sessions through `staffdeny:acct`) and revalidates the page, so the sessions list shrinks. `EMAIL_NOT_VERIFIED` goes to `/verify-pending`.
- **Two-factor authentication** (`mfa-setup.tsx`, client). Off: "Set up two-factor authentication" calls `beginMfaSetup` (`startMfaSetup`); the action turns the `otpauth://` URI into a QR code on the server with `lib/qr.ts` (the `qrcode` package, error correction level M, a 4-module quiet zone) and answers only the code's geometry (its size and one SVG path of the dark modules), the base32 secret and the expiry. `MfaSetup` draws the QR code as an inline `<svg role="img">` (no markup string, no `data:` URL, nothing for `dangerouslySetInnerHTML`, and the `qrcode` package stays out of the browser bundles), shows the secret in a `CopyField` for manual entry and the 10 minutes the set-up lasts, and asks for the code. `confirmMfaSetup` (`enableMfa`) checks it (6 digits, spaces dropped) and answers the ten recovery codes, which show once in `SecretRevealPanel`; the page is revalidated with MFA on, and a reload never shows the codes or the secret again [PF-04 AC1]. A wrong code (`MFA_CODE_INVALID`) shows at the field and keeps the set-up; `MFA_SETUP_EXPIRED` drops it and offers "Start again"; "Cancel the set-up" drops it without a call (the pending secret expires on its own). On: the date MFA was turned on, "Replace the recovery codes" and "Turn off two-factor authentication", each after a `ConfirmDialog` and through `useStepUpAction`: `replaceRecoveryCodes` (`regenerateRecoveryCodes`) and `turnOffMfa` (`disableMfa`) answer `stepUp` on `REAUTH_REQUIRED`, `StepUpDialog` takes a TOTP code, and the same action runs again with the stepped-up session [PF-04 AC3]; a cancelled step-up says that nothing changed. The new codes show once in a panel of their own. A platform admin gets no "Turn off" and reads that admins keep MFA on (the API refuses with `FORBIDDEN`, `platform_admin`); so does an owner or admin of a live OTA ([PADR-0008](../docs/adr/0008-email-verification-and-mfa-policy.md) revision of 2026-11-05), which the page knows without a contract change from `listTenants`: it lists the OTAs of the account's active memberships in the statuses members see with the role and `storefrontEnvironment`, the very rows of the API's rule, so an `owner` or `admin` entry with `live` hides "Turn off" and says that such an account keeps MFA on (FIX-W46-PLATFORM, lead decision (11c)). When that list cannot be read, or the OTA went live after the page was rendered, "Turn off" stays and the API's `409 CONFLICT` with `details.reason = mfa_mandatory` shows the same words, not the general conflict message; `MFA_ALREADY_ENABLED` and `MFA_REQUIRED` (changed in another tab) offer a reload. An answer that is not the document's (a URI that is no `otpauth://totp/` URI, codes of another shape) shows the general error and nothing of it; the checks of the answers and of the typed code are `lib/mfa-checks.ts`, which the enrolment page's actions use too.
- **Sessions** (`sessions-table.tsx`, client): `SessionsTable` lists every active session of `listSessions` (portal and platform admin, newest sign-in first) with the device in words from its user agent ("Safari on macOS", `deviceOf`; "Unknown device" otherwise, the full user agent as the cell's title), where it signs in to, the IP address ("Unknown" without one), the sign-in time and the last use ("Not since signing in" before the first refresh), in the account's time zone. This browser's session (`current`) is marked "This browser" and has no "Revoke": it ends with "Sign out". "Revoke" asks in a `ConfirmDialog` and calls `revokeAccountSession` (`revokeSession`); the row goes at once and the page is revalidated [PF-06 AC1]; `NOT_FOUND` (ended in the meantime) drops the row too, other refusals keep it with a reload link. **`SignOutEverywhere`** asks in a `ConfirmDialog` and calls `signOutEverywhere`: `204` deletes the session cookies (and a pending MFA challenge and return path) and continues to `/sign-in?signedOut=1` [PF-06 AC2]; a refusal keeps the session and shows the portal's message.
- The TOTP secret, the QR code and the recovery codes leave the server only in an action's answer (Next.js sends it with `Cache-Control: no-store`) and live in React state only; they are never logged, stored, cached, or written to storage, cookies, the URL or the history (§5).

How "Open console" behaves (PFE-017; [flow](../docs/flows/team-and-ota-admin-sso.md) §C, [PADR-0007](../docs/adr/0007-portal-to-ota-admin-sso-token.md) points 4 and 5, PF-22):

- **`OpenConsoleButton`** (`components/open-console-button.tsx`, no client code) is a small `<form method="post">` to `/otas/<id>/console/launch` with one submit button and no field, never a link: a prefetch, a crawler or an image cannot mint a token, and it works before the page hydrates. It shows on the OTA dashboard (every role: scope §1.2 "Open console") and on each OTA of `/dashboard` and `/console`, where the button's name for screen readers ends with the OTA ("Open console for Acme Travel"). It shows for an OTA in any status: the API decides, and the launch explains a refusal.
- **The launch** (`otas/[tenantId]/console/launch/route.ts`): `POST` checks `Origin` against `PUBLIC_PORTAL_URL` (a foreign, `http:`, `null` or missing one answers `403` without a call), refuses a path without a `ten_` id (`404`), and calls `createConsoleToken` with the session's access token (the middleware has renewed it) and the end-user headers. `201` answers the hand-off page: one form `POST <consoleSsoUrl>` (`application/x-www-form-urlencoded`) with the hidden `portalToken`, a visible "Continue" button, and a script carrying the request's nonce that submits the form while the page loads (so the page is replaced in the history and "Back" from the OTA admin returns to the portal page). The token is only in that form body: never in a URL, a header, a cookie, a log line or a redirect. An answer whose `consoleSsoUrl` is not at the origin of `PUBLIC_OTA_ADMIN_URL` (or has credentials, a query or a fragment), or whose token is not of the document's pattern, is never rendered. Headers: `Cache-Control: no-store`, `Referrer-Policy: strict-origin` (also as `<meta name="referrer">`), and a Content-Security-Policy whose `form-action` is the origin of `PUBLIC_OTA_ADMIN_URL` alone (§7). `strict-origin`, not `no-referrer`: under `no-referrer` browsers send `Origin: null` with this cross-origin post and the OTA admin's `/sso` refuses it (OADR-0018 point 2); `strict-origin` sends `Origin: https://platform.example.com` and a `Referer` of the origin alone, never the launch path or the token (lead decision of 2026-10-23). Checked with Chromium 147 against the built portal and a stand-in `/sso` (PFE-017 review): the post carried the portal's origin as `Origin`, the origin and `/` as `Referer`, and only `portalToken` in the body, with JavaScript and with "Continue" alone; the same page rewritten to `no-referrer` posted `Origin: null`.
- **Refusals** answer `303`, `no-store`: `TENANT_NOT_ACTIVE` goes to `/otas/<id>?console=<details.status>` (`provisioning`, `failed`, `suspended` with `&reason=<details.suspensionReason>`, or `not_active`); `MFA_REQUIRED` to `/account/security?console=mfa_required&tenant=<id>`; `RATE_LIMITED` to `/otas/<id>?console=rate_limited`; an unavailable API and anything else to `?console=unavailable`; `UNAUTHENTICATED` and `TOKEN_EXPIRED` to `/sign-in?next=/console?tenant=<id>` (a sign-in cannot come back to a `POST`); `EMAIL_NOT_VERIFIED` to `/verify-pending`; `NOT_FOUND` (no membership of that OTA) and `VALIDATION_FAILED` (an id the API does not accept) to `/console?tenant=<id>`. `GET` mints nothing and answers `303` to `/console?tenant=<id>` (the middleware's sign-in redirect lands there for a launch without a session).
- **`ConsoleLaunchNotice`** (same module) says why: the problem's message and, for a suspension, its reason (PADR-0014); for a billing suspension the billing link for the roles that see billing (owners and finance) and whom to ask for the others; for `mfa_required` "Open the console again" to `/console?tenant=<id>`. `consoleProblemOf` reads only the problems and reasons the portal knows, so a crafted URL can only show one of the portal's own messages.
- **`/console`** (`console/page.tsx`, any signed-in account; the middleware sends a visitor without a session to sign-in and back) calls `listTenants` and lists the account's OTAs with their status, the caller's role and an "Open console" button each. `?tenant=<id>` pre-selects that OTA: it comes first, is marked "Selected" (`aria-current`) and its button is the primary one. With exactly one OTA the page shows that one, with a single button, selected unless `tenant` named another OTA; with none it explains how to get one. A `tenant` the account is not (or no longer) a member of gets a note, and the account's OTAs stay listed, none of them selected. An ended session goes to sign-in and back to the same `/console?tenant=<id>`; another failure shows the portal's message.

How the shared components behave (PFE-003; `src/components/`):

- **Shell.** `(app)/layout.tsx` calls `getMe` once per request and renders `AppShell` (a server component): the sidebar with `OtaSwitcher` and `SideNav`, a header with the account and a "Sign out" form posting to `/sign-out`, the toaster, and the page inside `<main id="main-content">` (pages inside the shell render no `<main>` of their own). `getMe` answering `UNAUTHENTICATED` or `TOKEN_EXPIRED` redirects to `/sign-in`, an unverified account to `/verify-pending`, and an account whose `getMe` says `mfaEnrolmentRequired` to `/mfa-enrolment?next=<the page>` (PFE-030, §2 Auth); any other failure shows the message of its code instead of the shell. Only the memberships and the switches reach the browser components.
- **Navigation.** `lib/roles.ts` holds the matrix of [scope §1.2](../docs/scope.md) (`PORTAL_ACTIONS`, `can(role, action)`) and the entries of an OTA with the action each needs: overview and domains for every member; API keys, team (team management) and settings for owners and admins; Amadeus and payments (the connection settings) for owners, admins and finance; billing for owners and finance; payout account and settlements for owners and finance while `features.settlements` is on; go-live for owners while `features.liveSwitch` is on. `SideNav` reads the OTA from the path (`/otas/<tenantId>/…`) and marks the current page with `aria-current="page"`; outside an OTA it shows the account entries only. `OtaSwitcher` lists every membership (set-up page while an OTA is `provisioning` or `failed`), "All OTAs" and "Create an OTA".

Suspended and `past_due` are alerts, the others status messages. Since PFE-021 the OTA layout (`otas/[tenantId]/layout.tsx`) renders it above every page of the OTA, so a `past_due` OTA shows its banner on every OTA page [PF-74 AC1]; the dashboard renders no banner of its own. The `trial_ending` words hold before and after the trial's end ("Your trial is ending", "Choose a plan to keep your OTA running", lead decision (2k) of 2026-11-04: the notice stays after the end until a plan replaces the trial or the OTA is suspended); for owners and finance members the layout also reads the trial's end (`trialEndForBanner` of `lib/tenant.ts`: `getSubscription` only while the notice is `trial_ending`, one call with the billing page of the same request), and the notice adds the days left ("The trial ends in 5 days.", "within a day" for the last hours) only while that end is known and still ahead. The other roles, a subscription that cannot be read and a past end get no number.
- **`StatusBadge kind status`** names each status in words with a tone; the kinds and statuses are typed from the platform document (settlements from [`data-model.md`](../docs/data-model.md) until M5), and a status the portal does not know yet still renders.
- **Step-up.** An action whose API call answers `REAUTH_REQUIRED` returns `{ stepUp: true }` in its state (`StepUpRequired` of `(app)/step-up-actions.ts`). The form uses `useStepUpAction(action, initialState)` instead of `useActionState` and renders the returned `stepUpDialog` next to its `<form action={dispatch}>`: the dialog asks for the TOTP code, the `stepUp` action calls `POST /v1/auth/step-up` and stores the new session in the cookies, and the original action runs again with the same `FormData`, now with the new access token. A wrong code stays in the dialog with the message at the field; cancelling keeps the state.
- **Shown once.** `SecretRevealPanel` renders the values an action returned with `CopyField`s and the warning that they cannot be shown again; "I have stored it" removes them from the page (`onDismiss` lets the caller drop its copy). The values live in React state only; the fields have no `name` (a form never submits them) and no autocomplete, and copying writes to the clipboard on request only.
- **Forms.** `FormField` (server or client) renders a visible label, an optional hint and the error, both linked to the control with `aria-describedby`, and `aria-invalid` on error; its control id is `fieldId(name)` unless given, and a render prop takes other controls (select, textarea). `FormErrorSummary` takes the focus when it gets a new errors array and links each entry to its field.
- **`ConfirmDialog`** is an alert dialog (focus on "Cancel", Escape cancels, no close on an outside click) that calls `onConfirm` and closes. **`DataTable`** is the shadcn data table on TanStack Table with a caption (visually hidden by default), `scope="col"` headers and an empty message; its columns live in a client module next to the page.
- **`Money`** formats the decimal string of `{ amount, currency }` with `Intl.NumberFormat` (the string goes to `Intl` as it is, never through a float; every digit of the amount is kept), **`DateTime`** an ISO instant with `Intl.DateTimeFormat` in an explicit time zone (UTC by default) inside `<time dateTime>`; both use the portal's `en` locale, so the server and the browser render the same text.

## 5. Data fetching and mutations

- **Reads** happen in server components through `lib/api.ts`, with `cache: "no-store"`. `otas/[tenantId]/layout.tsx` loads the tenant and the caller's role once per request and passes them down: a page reads it with `requireTenant(tenantId)` of `lib/tenant.ts`, whose `loadTenant` is a React `cache()`, so the layout and the page share one `getTenant` call (PFE-010). A page decides with `can(tenant.myRole, …)` whether to render itself or `NotAllowed`.
- **Mutations** are server actions (`actions.ts` next to the page): validate with Zod, call the API, map `fieldErrors` to the form, return state for `useActionState`, then `revalidatePath` or `redirect`. Actions that answer `REAUTH_REQUIRED` return a `stepUp` state (`{ stepUp: true }`); the `StepUpDialog` of `useStepUpAction` calls the `stepUp` action and re-submits (§4).
- **Secrets shown once** (API keys, initial keys, recovery codes, MFA set-up secret) are returned by the action and rendered by a client component in memory only; they are never put in cookies, URLs, `localStorage` or the Next.js cache.
- **Polling** (setup page, credential submissions, the billing page's Checkout confirmation) uses a client component that calls a server action every 2 seconds and stops at a final state.
- **Errors** map codes to messages in `lib/errors.ts`; `error.tsx` per area; raw messages from the API are never shown.
- **External navigations** (Checkout, Customer Portal, Connect authorise URL) are `redirect()` calls in server actions with URLs returned by the API, never assembled in the browser. The Checkout hand-offs of the create-OTA wizard, the set-up page (PFE-020) and the billing page (PFE-021, also its Customer Portal) follow the answer's URL only when it is an absolute `https:` URL without credentials, exactly as answered (Stripe's Checkout URLs carry a fragment the page needs); anything else comes back to the set-up page instead.
- **The API client** (`lib/api.ts`, `server-only`). `platformApi()` returns the client for the request being rendered: `openapi-fetch` typed by `@velexis/api-types/platform`, base URL `PLATFORM_API_URL`, `Authorization: Bearer` from `__Host-vxp_at` (none without a session), the request's `X-Request-Id` when it is valid (Caddy sets one on every request; `middleware.ts` creates one in development), `cache: "no-store"`, and `redirect: "manual"` so the bearer token never follows a redirect. `createPlatformApi({ baseUrl, bffKey, requestHeaders, accessToken? })` builds the same client from explicit values; `middleware.ts` uses it for the refresh. Every method (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`) takes the path and options of `openapi-fetch` (a caller's `baseUrl`, `fetch`, `Request`, `cache` and `redirect` are dropped, so the token only ever goes to `PLATFORM_API_URL` and nothing is cached) and answers `{ data }` or `{ error }`, never throws: `error` is `{ code, status, fieldErrors, details, requestId?, retryAfterSeconds? }`, where `code` is always a code of the platform catalogue (an answer without a valid envelope becomes `SERVICE_UNAVAILABLE` for 502, 503 and 504 or an unreachable API, and `INTERNAL_ERROR` otherwise). The API's `message` and the `message` of each field error are dropped on purpose, so a page can only show the portal's own text. One answer of `platformApi()` does not come back: the API's MFA enrolment gate (`403 MFA_REQUIRED`, `details.reason = enrolment_required`) sends the browser to `/mfa-enrolment` with the page of the request as `next` (`leaveForMfaEnrolment` of `lib/errors.ts`, PFE-030, §2 Auth); `createPlatformApi()` itself never redirects (the middleware's refresh, and the route handlers that answer their own `303`).

  ```ts
  const api = await platformApi();
  const me = await api.GET("/v1/me");                   // typed by the platform document
  if (me.error) return { message: errorMessage(me.error) };
  const updated = await api.PATCH("/v1/me", { body: { fullName }, params: { header: { "If-Match": etag } } });
  ```
- **End-user IP and user agent.** The API's per-IP rate limits and audit rows need the visitor's address, not the portal server's. `lib/api.ts` sends on every call, including the refresh in `middleware.ts`: `X-Velexis-End-User-IP` (the right-most `X-Forwarded-For` entry, which Caddy sets; `127.0.0.1` when there is none in development), `X-Velexis-End-User-Agent` (the browser's `User-Agent`, at most 512 characters) and `X-Velexis-Bff-Key` (`PLATFORM_BFF_KEY`). A browser-supplied left-most `X-Forwarded-For` entry is never used ([PADR-0019](../docs/adr/0019-end-user-ip-forwarding-from-the-portal-and-admin.md)). The headers are set after the caller's own headers, so a caller cannot replace them. The address is passed on as Caddy wrote it; the API answers a malformed one with `400 VALIDATION_FAILED`, so a proxy misconfiguration shows at once.

## 6. Auth cookies and session

| Cookie | Content | Lifetime | Flags |
|---|---|---|---|
| `__Host-vxp_at` | Platform access token (JWT) | 15 minutes | `HttpOnly; Secure; SameSite=Lax; Path=/` |
| `__Host-vxp_rt` | Refresh token | Until the family's absolute expiry (30 days) | same |
| `__Host-vxp_mfa` | MFA challenge token during sign-in | 5 minutes | same, `SameSite=Strict` |
| `__Host-vxp_reset`, `__Host-vxp_invite` | Reset or invitation token moved out of the URL | 15 minutes | same, `SameSite=Strict` |
| `__Host-vxp_next` | Validated relative return path | 15 minutes | same |
| `__Host-vxp_connect` | The id of the OTA whose Stripe Connect an owner or admin started (not a secret), for the callback's way back (PFE-024) | 1 hour (the OAuth state lasts 10 minutes) | same: `Lax`, because Stripe sends the browser back with a top-level navigation from its own site |

`lib/session.ts` (`server-only`) owns the names and attributes. `sessionCookies(session)` gives both session cookies of a `PortalSession`, each living as long as its token (`accessTokenExpiresAt`, at most 15 minutes; `refreshTokenExpiresAt`, the refresh token's idle expiry and never after the family's 30 days); `mfaChallengeCookie`, `passwordResetCookie`, `invitationCookie`, `nextPathCookie` and `stripeConnectCookie` give the flow cookies; `writeCookies(sink, writes)` writes them to `cookies()` (actions, route handlers) or `NextResponse#cookies` (middleware), and `setSession()` / `clearSession()` do it for the session in one call. Cookies are deleted by `clearedCookie(name)`: an empty value with the same attributes and `Max-Age=0`, because a browser ignores a `__Host-` deletion without `Secure` (which `cookies().delete()` would send).

- `middleware.ts` refreshes an access token that is missing, unreadable or expires within 30 seconds before rendering, when a refresh token is there. It reads `exp` and `ev` from the token without checking the signature (the API checks it on every call; a forged cookie gets no further than pages whose calls answer 401). The new tokens are set on the response **and** replace the old ones in the request's own `Cookie` header, so the page rendered for that request already uses them; an expired access token is never passed on to a page.
- Refresh is **single-flighted** inside the one portal process (`refresh()`, an in-memory map keyed by the SHA-256 of the refresh token): every request that presents the same refresh token while the call is pending, or within 10 seconds after it succeeded or failed for good, gets the same outcome without a second call, so parallel requests never present a rotated token twice and trip reuse detection. The middleware runs in the Node.js runtime (`export const config = { runtime: "nodejs" }`), in the portal process itself, which is what makes the map shared by all requests.
- `REFRESH_TOKEN_INVALID`, `REFRESH_TOKEN_REUSED`, `VALIDATION_FAILED` and `UNAUTHENTICATED` end the session: both cookies are deleted. A failure that may pass (rate limit, API unavailable) keeps the cookies and is not remembered, so the next request tries again; the request itself continues without a session.
- Unauthenticated requests for the `(app)` area (`/dashboard`, `/otas`, `/console`, `/account` and below) get `303` to `PUBLIC_PORTAL_URL/sign-in?next=<path and query>`; an account whose token says `ev: false` gets `303` to `/verify-pending`. Other paths (public pages, the `(auth)` pages, route handlers outside `(app)`) pass with or without a session.
- **Tokens in links move into cookies before anything renders.** `middleware.ts` answers `GET /reset-password?token=…` and `GET /invitations/accept?token=…` itself, with the token in `__Host-vxp_reset` or `__Host-vxp_invite` and a page without script whose declarative refresh (`<meta http-equiv="refresh">`) takes the browser to the same page without the token (`tokenLinkRedirect`, `TOKEN_LINKS`), because a page cannot set cookies in Next.js; the page and its action read the cookie on the server (PFE-006, PF-05 AC1; PFE-012 for invitations). A `303` would not do: the `SameSite=Strict` cookie would not be sent with a redirect that continues a navigation another site started (a link in web mail), while the refresh is a navigation the portal starts.
- **`next` is a relative path only.** `safeNextPath()` keeps a value only when it starts with a single `/`, has no backslash or control character, is at most 2 048 characters long, and resolves to the portal's own origin; `https://evil.example/x`, `//evil.example`, `/\evil.example` and the like are dropped. The path the URL parser makes of it (dot segments resolved) must pass the same test again: `/.//evil.example`, `/a/..//evil.example`, `/%2e//evil.example` and `/%2E%2E//evil.example` normalise to the protocol-relative `//evil.example` and are dropped too (FIX-W26-SECURITY). The middleware applies it to the `next` it writes and to the page it hands on in `x-velexis-requested-page` (the signed-in area and `/mfa-enrolment` only, and `/invitations/accept` without its query, PFE-030), `nextPathCookie()` to the value it stores, the sign-in pages to the value they redirect to, and the `(app)` layout and `/mfa-enrolment` to the MFA enrolment's `next`.
- Server actions rely on Next.js's Origin check; route handlers that change state check `Origin` against `PUBLIC_PORTAL_URL` explicitly.
- No `NEXT_PUBLIC_` variable holds a key or token. Client components never import `lib/api.ts` or `lib/session.ts`.

## 7. Security headers

Set in `next.config` `headers()` and middleware: CSP with a per-request nonce (`script-src 'self' 'nonce-…'`, `connect-src 'self'`, `img-src 'self' data:`, `form-action 'self'` plus the origin of `PUBLIC_OTA_ADMIN_URL` (`https://admin.ota.example.com` in production; the hand-off page of "Open console" allows that origin alone), `frame-ancestors 'none'`, `base-uri 'self'`, `object-src 'none'`), `Referrer-Policy: strict-origin-when-cross-origin` (`no-referrer` on token pages, `strict-origin` on the "Open console" hand-off page), `X-Content-Type-Options: nosniff`, `Permissions-Policy` minimal. Stripe pages are reached by navigation, never framed.

The policy of `lib/csp.ts`, set by `middleware.ts` on every response it handles (pages, server actions, route handlers, redirects) with a fresh 128-bit nonce:

```text
default-src 'self'; script-src 'self' 'nonce-<nonce>'; style-src 'self' 'unsafe-inline'; img-src 'self' data:;
font-src 'self'; connect-src 'self'; form-action 'self' <origin of PUBLIC_OTA_ADMIN_URL>; frame-ancestors 'none';
base-uri 'self'; object-src 'none'
```

- The middleware also puts the policy and the nonce (`x-nonce`) on the request headers; Next.js reads the nonce from there and adds it to every script it renders. A server component that renders its own `<script>` reads `x-nonce` from `headers()`.
- **Every page is rendered per request** (`export const dynamic = "force-dynamic"` in the root layout): a prerendered page would keep inline scripts without the nonce, and the policy would block them.
- `'unsafe-eval'` is added to `script-src` only when `APP_ENV=development`, because `next dev` evaluates modules with `eval`. Inline styles are allowed (`style` attributes of components such as Radix); inline scripts never are.
- **Stripe Connect** (PFE-024) needs no Stripe origin in the policy: "Connect Stripe" posts only to the portal's own server action (`form-action 'self'`; the form runs through `useStepUpAction`, so React replays a submit made before hydration instead of posting natively), and `connectStripe` ends with `redirect()` to the authorize URL the API answered, which the router follows as a top-level navigation (`location`), and no directive of the policy restricts top-level navigation. Stripe's page is never framed (`frame-ancestors 'none'` covers the portal; the portal frames nothing). Stripe's return is a `GET` of `/connect/stripe/callback`, whose only answers are redirects.
- **Stripe Checkout** (PFE-020) needs no Stripe origin in the policy either. The wizard's submit and the set-up page's "Continue to payment" and "Retry" post only to the portal's own server actions, and those end with `redirect()` to the Checkout URL the API answered, which the router follows as a top-level navigation (`location`): no directive of the policy restricts top-level navigation. They are never native form posts, whose `303` to Stripe `form-action 'self'` would block: the wizard's form has no action of its own (its submit handler calls `useActionState`'s dispatch once hydrated), and the set-up page's forms are `CheckoutForm`s (`setup/checkout-form.tsx`), whose action is a function of a client component that calls the server action, so React replays a submit made before hydration instead of posting it. A server action passed straight to `<form action>` would render a form the browser posts natively before hydration.
- **The "Open console" hand-off page** (`/otas/<id>/console/launch`, PFE-017): the middleware gives that path the same policy with `form-action <origin of PUBLIC_OTA_ADMIN_URL>` alone (`lib/csp.ts` `handOff`, `isHandOffPath`), because Next.js keeps the middleware's response header over a route handler's; the route handler reads the nonce from `x-nonce` for its one script and sets the same policy itself.

| Header | Value | Where |
|---|---|---|
| `X-Content-Type-Options` | `nosniff` | `next.config.ts`, every response (PFE-001) |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | `next.config.ts`, every response (PFE-001); token pages override it with `no-referrer` |
| `Referrer-Policy` | `no-referrer` | `next.config.ts` `TOKEN_PAGES` (`/verify-email`, PFE-005), a later rule that replaces the one above, and the route handler itself. The rule is needed: Next.js sets the configured headers on the response before a route handler runs and keeps them over the handler's own value of the same header |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), payment=(), usb=(), browsing-topics=()` | `next.config.ts`, every response (PFE-001) |
| `Referrer-Policy` | `no-referrer`, with `Cache-Control: no-store` | the refresh page of `middleware.ts` that moves the token of `/reset-password?token=…` (PFE-006) or `/invitations/accept?token=…` (PFE-012) into its cookie, also as `<meta name="referrer">`; the middleware's value replaces the configured one. The page behind it carries no token and keeps the default: a page served with `no-referrer` would make the browser send `Origin: null` with its form posts |
| `Referrer-Policy` | `strict-origin`, with `Cache-Control: no-store` | `next.config.ts` `HAND_OFF_PAGES` (`/otas/:tenantId/console/launch`, PFE-017), a later rule that replaces the default, and the route handler itself (also as `<meta name="referrer">`). Not `no-referrer`: the page's form posts to the OTA admin, whose `/sso` needs `Origin` = `PUBLIC_PORTAL_URL`, and under `no-referrer` browsers send `Origin: null` ([PADR-0007](../docs/adr/0007-portal-to-ota-admin-sso-token.md) point 4, revised 2026-10-23) |
| `Content-Security-Policy` | nonce-based, as above | `middleware.ts` with `lib/csp.ts` (PFE-002); the hand-off page's `form-action` is the OTA admin's origin alone (PFE-017) |

`X-Powered-By` is switched off (`poweredByHeader: false`). Caddy adds `Strict-Transport-Security` and `X-Frame-Options: DENY` on the public host ([`deploy/caddy/Caddyfile`](../../deploy/caddy/Caddyfile)).

- `getConfig()` validates the process environment on first use and caches the frozen result. Outside production it first fills unset variables from `platform/frontend/.env.local`, then from the root `.env.local` (`loadDevEnvFiles`), so the root file made from the root `.env.example` is enough for `pnpm dev`.
- Call it inside request handling (route handlers, server components, server actions), never at module scope: `next build` imports modules without the runtime environment. An invalid environment therefore fails the first request that needs it, and `/health/ready` is such a request, so `deploy.sh` does not take a release live with a broken `/etc/velexis/platform-frontend.env`. The error is a `ConfigError` that names each variable and the reason, never a value.
- `parseConfig(source)` validates a plain object; the unit tests use it.
- **No browser-exposed variables.** No `NEXT_PUBLIC_` variable exists and `next.config.ts` has no `env` block, so nothing is inlined into client bundles; `src/lib/config.test.ts` fails if either appears.
