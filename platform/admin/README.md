# Platform admin (`@velexis/platform-admin`)

This is the Velexis staff console at `admin.platform.example.com`: a Next.js 15 App Router app for platform admins to run the fleet: tenants and their lifecycle, provisioning jobs and queues, plans and Stripe prices, subscriptions, invoices and Stripe events, the shared Amadeus account and office pool, settlements and payout accounts, domains, accounts, platform admins and the audit log. Like the portal it is a backend-for-frontend: it calls the platform API's `/v1/admin` surface from server code only, with an admin token in httpOnly cookies. This page is the component specification.

Related: [`../docs/flows/platform-admin-operations.md`](../docs/flows/platform-admin-operations.md), [`../docs/api-inventory-admin.md`](../docs/api-inventory-admin.md), [PADR-0006](../docs/adr/0006-platform-admin-access-and-audit.md), [ADR-0014](../../docs/mvp/adr/0014-frontend-stack-nextjs-tailwind.md), [`.env.example`](.env.example).

## 1. At a glance

| Item | Value |
|---|---|
| Stack | Next.js 15 App Router, React 19, TypeScript strict, Tailwind CSS 4, shadcn/ui, `@tanstack/react-table`, Zod (forms only) |
| API client | `openapi-fetch` typed by `@velexis/api-types/platform`, `src/lib/api.ts` (`server-only`), admin operations only |
| Port | `127.0.0.1:3001`, unit `velexis-platform-admin.service`, `standalone` output |

| Access | Accounts with `is_platform_admin = true` and MFA; TOTP on every sign-in; 12-hour sessions |

Health ([ADR-0016](../../docs/mvp/adr/0016-observability.md)), both `GET` with `Cache-Control: no-store` and the static headers of §4 (`X-Robots-Tag: noindex` included):

- `/health/live` answers `200 {"status":"ok"}` while the process serves requests. It checks no dependency.
- `/health/ready` calls `PLATFORM_API_URL/health/live` and answers `200 {"status":"ok","checks":{"platformApi":"ok"}}` when it answers 2xx within 2 seconds, otherwise `503` with `"status":"unavailable"` and `"platformApi":"down"` (refused, error status, redirect or timeout; the cause is not exposed). It also reads the configuration, so an invalid environment answers `500` and the `ConfigError` in the journal names the variable. `deploy.sh` polls `ready` on port 3001 after every restart.

## 4. Data fetching, actions and session

- Server components read through `lib/api.ts` with `cache: "no-store"`; lists use URL search params for filters and the cursor, so pages are linkable.
- Every mutation is a server action that validates with Zod, sends `If-Match` where the resource is versioned, passes the reason when required, and handles `REAUTH_REQUIRED` with `StepUpDialog` (TOTP → `adminStepUp` → retry).
- Revealed payout details come back from a server action and render in memory only; the panel hides them after 60 seconds and offers no copy-to-clipboard of the full value in logs or URLs.
- **Signed-in shell (PAD-003).** `(app)/layout.tsx` calls `adminGetMe` once per request and renders `AdminShell`: the navigation of every area of §2, grouped (overview; OTAs; plans and billing; Amadeus; payments; people and audit), the signed-in admin's name and e-mail address, "Sign out" (a plain `POST /sign-out`), and a badge of `APP_ENV` (production in red, so nobody takes it for a test system). The page renders inside `<main id="main-content">`; pages in the shell render no `<main>` of their own. The M5 areas show only while a milestone switch of `features` is on ([PADR-0015](../docs/adr/0015-milestone-feature-switches.md) item 3): `/invoices` with `stripeBilling`, `/stripe-events` with `stripeBilling` or `ownStripe`, `/settlements` with `settlements`, `/domains` with `customDomains`. `UNAUTHENTICATED` and `TOKEN_EXPIRED` from `adminGetMe` go to `/sign-in`; any other failure shows the admin's message for its code and a "Sign out" button instead of the shell. The shell gets the name, the e-mail address, the switches and `APP_ENV`, never a token.
- **Lists (PAD-003).** `FilterBar` keeps every filter in the URL's search params: a select applies at once, the search (and a date field, `YYYY-MM-DD`, added for the audit period in PAD-009) applies on submit, the other filters and parameters stay, the cursor goes (a new filter starts on the first page), and "Clear filters" links to the unfiltered list; without JavaScript it is a plain GET form with the other parameters as hidden fields, which also sends the empty ones ("Any", an empty search), so pages treat an empty parameter as no filter. A search field takes the `maxLength` of its parameter (254 by default, the `q` of `adminListTenants` and `adminListAccounts`, so a whole owner e-mail address fits). `DataTable` (TanStack Table, the API sorts) renders the rows of the server component and, given the answer's `page`, links "Next page" (`cursor=<nextCursor>`) and, on a later page, "First page", keeping the filters. `listHref()` builds those URLs; it lives in a client module, so server components pass `page` instead of calling it.
- **Reason and step-up (PAD-003).** `ReasonDialog` asks for the mandatory reason of a **reason** action: 5 to 500 characters after trimming, counted in code points as `AdminReason`'s `minLength` and `maxLength` count them; anything else is refused at the field and nothing runs. It calls `onConfirm` with its form's `FormData` (the trimmed `reason` plus any fields passed as children, such as the suspension reason type). A server action that gets `REAUTH_REQUIRED` returns `{ …state, stepUp: true }`; `useStepUpAction` then opens `StepUpDialog`, `stepUp` (`(app)/step-up-actions.ts`) sends the TOTP code to `adminStepUp` and stores the new `AdminSession` in `__Host-vxa_at` and `__Host-vxa_rt`, and the original action runs again with the same `FormData` (the same reason). A wrong code stays in the dialog at the field; cancelling runs nothing. `ConfirmDialog` confirms actions that need no reason.
- **Shared components (PAD-003).** `StatusBadge` names every status of the platform document in words (`lib/strings.ts` `STATUS_LABELS`; colour is never the only signal). `JsonView` shows id-only payloads and audit details as indented JSON in a focusable, scrollable region (React escapes it). `MaskedValue` shows the masked shapes the API answers (`prefix`, dots, `last4`; "IBAN ending in 7947" for screen readers) and never takes a full value. `RevealPanel` shows revealed details in React state only, counts down, clears them after 60 seconds or on "Hide now" and calls `onHide` so the caller drops its copy; a new reveal (a new array) shows again; it has no copy button, no form field and writes no storage, cookie or URL. `Money` formats decimal strings with `Intl` without a float; `DateTime` formats instants in an explicit zone (UTC by default). Both are copies of the portal's.
- **Dashboard (PAD-004).** `/` calls `adminGetDashboard` and shows every M1 counter as a link to the list it counts, filtered in the URL: the OTAs of each status (`/tenants?status=<status>`), the tenant jobs that failed in the last 24 hours (`/provisioning-jobs?status=failed`, every failed job newest first: that list has no time filter), the failed BullMQ jobs of each platform queue (`/queues/<queue>`) and, per environment with a Velexis Amadeus account, the available and assigned offices of the pool (`/amadeus/offices?environment=<env>&status=available|assigned`). Below 3 available offices the environment shows a warning in words (PADR-0012); without any account the page links to `/amadeus/accounts`. The M5 counters (always `null` in M1) and the live office requests, which `AdminDashboard` has no counter for until PBE-054, arrive with PAD-014. While Redis is down the API answers `503 SERVICE_UNAVAILABLE`, and the page shows its message instead of the counters. Like the layout, every page of the console sends `UNAUTHENTICATED` and `TOKEN_EXPIRED` to `/sign-in`.
- **Provisioning jobs (PAD-006, PF-83).** `/provisioning-jobs` validates its URL as `/tenants` does (`status` of `ProvisioningJobStatus`, `kind` of `ProvisioningJobKind`, `tenantId` of `TenantId`, `cursor` of at most 512 characters; an empty parameter is no filter; a repeated or invalid one, or a `VALIDATION_FAILED` answer, shows a notice with a link to the whole list and calls nothing more) and calls `adminListProvisioningJobs` with exactly those filters. `FilterBar` writes the status and the kind into the URL and keeps `tenantId`, which the jobs tab of a tenant links ("All jobs of this OTA"): the list then says it shows one OTA, links the OTA and links the same filters for every OTA. The rows (newest first) link the job and its OTA and show kind, status, step, attempts, last error and the three times; the columns live in a client module (`job-table.tsx`) that gets only those fields. `/provisioning-jobs/[jobId]` renders the not-found page for a value that is no job id (without a call) and for `NOT_FOUND`, and otherwise shows `adminGetProvisioningJob`: the OTA, kind, status, current or last step, attempts, last error, the scheduled time (the retry backoff), first dispatch and end, the lease (`lockedUntil`, only while running), the BullMQ state of the current attempt and its BullMQ job (`<jobId>-<attempt>` on `ota-tenant-ops`, linking that queue), the step log (each finished step with its status, times and error code and message), and the input and result in `JsonView` (ids and options only; the API never answers a ciphertext). The actions (`job-actions.tsx`, server actions in `actions.ts`) are offered only in the states the API allows them: **Retry** on a `failed` job behind `ConfirmDialog` (a failed set-up says that the OTA goes back to "Setting up"), answered with the **new** job, linked, while the failed one stays as history; **Cancel job** on a `queued` one behind `ReasonDialog` ("Keep the job" closes it), after which the job is `canceled`. A `running`, `succeeded` or `canceled` job offers neither. Each action checks the job id (and the reason, 5–500 code points after trimming) before it calls the API, so made-up fields send nothing; a success revalidates the job's page, the new job's page, the list and the OTA's page; `PROVISIONING_NOT_RETRYABLE` (`not_failed`, `tenant_not_failed`, `job_active`) and `CONFLICT` (`not_queued`) are worded by their `details.reason`; `REAUTH_REQUIRED` opens `StepUpDialog` and runs the action again with the same form data, and an ended session goes to `/sign-in?next=/provisioning-jobs/<id>`. The component gets the job's id, kind and status only.
- **Queues (PAD-006, PF-84).** `/queues` shows `adminListQueues` in two tables: the platform queues, whose failed jobs can be retried here, and the OTA queues (`ota-tenant-ops` included), view only. Each row links `/queues/<queue>` and shows the waiting, active, delayed and failed jobs and the age of the oldest waiting one in words ("4 seconds", "2 hours 3 minutes", "None waiting"). While the API cannot read Redis it answers `SERVICE_UNAVAILABLE`, and the page says that the queues cannot be read right now. `/queues/[queue]` renders the not-found page for a value that is no `QueueName` (without a call) and for `NOT_FOUND`, and otherwise lists `adminListFailedQueueJobs` (the 50 most recent failures): id, name, failure reason, attempts made, failure time and the id-only data in `JsonView`; a failed dispatch attempt of `ota-tenant-ops` (`<jobId>-<attempt>`) links its provisioning job, which can be retried on its page. The owner is the name's prefix (`<owner>-<topic>`, ADR-0009 item 4): a `platform-` queue gives each failed job **Retry** (`ConfirmDialog`, a button named after the job) and `adminRetryQueueJob` moves it back to waiting; an `ota-` queue shows its failures with no retry button and no action column, and the server action `retryQueueJob` refuses an OTA queue without calling the API (which would answer `403 FORBIDDEN`, `ota_queue`). The outcome of the last retry stays above the table while the revalidated page (the queue and `/queues`) drops the retried job; `NOT_FOUND` (retried by someone else, or removed by BullMQ), `FORBIDDEN` and `SERVICE_UNAVAILABLE` are worded for the admin. The list component (`failed-jobs.tsx`) gets only the documented fields of each job.
- **Plans (PAD-008; subscription-billing flow §A).** `/plans` shows `adminListPlans` (every plan, public or not and active or retired, in the pricing page's order; the list is short, so it is a server table and only what it shows reaches the browser): name (linking `/plans/<code>`) and code, **Active** or **Retired**, whether the portal's pricing page offers it (**On the pricing page** when public and active, as `listPlans` answers them, PF-70; **Not public**; **Retired, not offered**), the monthly and yearly prices (`Money`, decimal strings), the free trial, the limits in words, the OTAs on the plan (linking `/tenants?planCode=<code>`) and the Stripe link state with the number of price warnings (M5). The page links the portal's pricing page (`PUBLIC_PORTAL_URL/pricing`). **New plan** opens the form of `plan-form.tsx`: code, name, description, currency, the monthly and the optional yearly price (in the plan's currency), trial days, the limits as four structured fields (staff seats, API keys, custom domains, "may go live"), the features as rows of a flag name and an on/off switch (add and remove rows; never raw JSON), "Public" (not preselected, so a new plan never reaches the pricing page by accident), the order and the settlement fee in basis points. `createPlan` checks every field as `CreatePlanRequest` does (code and flag-name patterns, lengths in code points, amounts `^[0-9]{1,10}(\.[0-9]{1,2})?$` kept as strings, whole numbers in their ranges, at most 50 distinct flags; empty rows ignored) before it calls `adminCreatePlan`, so a form with a problem sends nothing and shows each problem at its field with the focus on the first; a taken code (`409`, `code_taken`) and the API's field errors (an unknown currency, a price in another currency) show at their fields too. A created plan is active at once: the form closes and says whether the pricing page now offers it, with links to the plan and, for a public one, to the pricing page; the revalidated list shows it. `/plans/[planCode]` renders the not-found page for a value that is no plan code (without a call) and for a code the list does not have (the API has no read of one plan), and otherwise shows the plan's fields, its Stripe product and prices, whether Checkout can start per interval, and the price warnings of the last comparison (M5). **Edit the plan** is the same form without the code and the currency; `updatePlan` sends every editable field (`annualPrice: null` when the yearly price is emptied) with the version the values come from in `If-Match` (`"<version>"`), and the API stores what changed and tells both backends to reload the plan when its limits or features changed. A save shows "The plan is saved" and the next save sends the new version; a stale version (`412`) keeps what was typed and asks to reload the page with a link that reloads it fully. When the page comes back with a newer version (after "Retire plan") the form takes the new values unless the admin typed something, which then keeps its old version and is refused as stale instead of overwriting the newer plan. **Retire plan** (`ConfirmDialog`) sends `isActive: false` with `If-Match`: the plan leaves the pricing page, the create-OTA wizard and the manual subscription form, and its OTAs keep it; a retired plan offers **Make the plan active again**. An ended session goes to `/sign-in?next=/plans/<code>`; `REAUTH_REQUIRED` opens `StepUpDialog` and runs the action again. The forms get only the fields they show.
- **Subscriptions (PAD-008; subscription-billing flow §G, PF-75).** `/subscriptions` validates its URL as `/tenants` does (`status` of `SubscriptionStatus`, `provider` of `BillingProvider`, `planCode` of `PlanCode`, `cursor` of at most 512 characters; an empty parameter is no filter; a repeated or invalid one, or a `VALIDATION_FAILED` answer, shows a notice with a link to the whole list and calls nothing more), calls `adminListSubscriptions` with exactly those filters and `adminListPlans` for the plan filter (retired plans marked), and lists every subscription row, newest first: the id (linking `/subscriptions/<id>`), the OTA (linking its page), the plan, the status, who bills it and how often, the end of the trial and of the current period, and the creation time. The columns live in a client module (`subscription-table.tsx`) that gets only those fields. `/subscriptions/[subscriptionId]` renders the not-found page for a value that is no subscription id (without a call) and for `NOT_FOUND`, and otherwise shows `adminGetSubscription`: the OTA, plan, status, billing, interval, trial end, periods, cancellation, the Stripe customer and subscription ids (references, never secrets), the invoices (number, status, period, total, amount due, issue and payment time, the Stripe-hosted page and PDF, linked only when they are `https:` URLs) and the Stripe events of the OTA (both empty before M5). A **manual** subscription has **Edit the manual subscription** (`manual-subscription-form.tsx`; the page then loads the active plans, and a failed list still renders the page with the current plan only): the plan (active plans; ones that are not public too), the day the trial ends (a date in UTC; the time of day of the current end stays, so `2027-01-12T08:20:11Z` moves to `2027-02-12T08:20:11Z`) and the status ("Trial" or "Canceled"). **Save changes…** is enabled once something changed and opens `ReasonDialog`, which lists the changes; only the changed fields are sent, with the reason and the version in `If-Match`. The outcome shows the saved plan, trial end and status, and the subscription's page, the list and the OTA's page are revalidated. `422 plan_not_active` shows at the plan, `409 current_exists` at the status, `409 stripe_billed` and a stale version (`412`) ask to reload. A **Stripe-billed** subscription has no edit form at all, only a note that Stripe owns it (the Customer Portal and Stripe's webhooks change it; "Resync" comes in M5); the server action would get `409 stripe_billed` from the API. `updateManualSubscription` checks the id, the version, each change and the reason (5–500 code points after trimming) before it calls the API, so made-up fields send nothing.
- **Tenants (PAD-004, PF-81).** `/tenants` validates its URL (`q` of at most 254 code points after trimming, `status` of `TenantStatus`, `planCode` of `PlanCode`, `cursor` of at most 512 characters; an empty parameter is no filter, and a repeated or invalid one shows a notice with a link to the whole list instead of an unfiltered list and calls nothing; a `VALIDATION_FAILED` answer, such as for a stale cursor, shows the same notice), then calls `adminListTenants` with exactly those filters and `adminListPlans` for the plan filter (every plan, retired ones marked; the list still shows without the plans, and the URL's plan stays selectable). `FilterBar` writes the search (part of the key, the name or an owner's whole e-mail address), the status and the plan into the URL and `DataTable` links the next page with them, so every search is a link another admin can open. Each row links to `/tenants/<id>`; the owner column says "No active owner" for `null`. The columns render links and badges, so they live in a client module (`tenant-table.tsx`); the page hands it only the fields the table shows, since Next.js sends a client component's props to the browser whether it renders them or not.
- **Tenant detail (PAD-004, PF-81).** `/tenants/[tenantId]` renders the not-found page for a value that is no tenant id (without a call) and for `NOT_FOUND`, and otherwise shows the answer of one `adminGetTenant` call in seven tabs: overview (the OTA's fields, the suspension reason and time, the internal notes), members and invitations (members link to `/accounts/<accountId>`), subscription and invoices (the subscription, and a link to `/subscriptions/<id>`, whose page lists the invoices and Stripe events; a manual trial has none), connections, domains, provisioning jobs (the last 20, each linking to its job page, and "All jobs of this OTA") and audit (the last 50 rows with their redacted details in `JsonView`, and "Full audit log of this OTA"). The panels are server components that render only the fields they name, and only their output reaches `TenantTabs` (`tabs.tsx`, Radix tabs), so a property the API might add never reaches the browser. The connections are masked on the server: the Stripe account, the publishable key and the client id of own Amadeus credentials show their prefix and last four characters only (`MaskedValue`); the API answers no secret, ciphertext, hash or token. The open tab is in the URL (`?tab=audit`, none for the overview): a link opens that tab, and switching replaces the history entry without asking the API again. The actions are in the next item.
- **Tenant actions (PAD-005, PF-82).** Client forms of `/tenants/[tenantId]` with the server actions of `actions.ts`; each action checks its fields with Zod (ids by their patterns, a reason of 5–500 code points after trimming as `AdminReason` counts it) before it calls the API, so made-up fields send nothing, and every success revalidates the page, so its header, tabs and buttons follow the new state. An ended session goes to `/sign-in?next=/tenants/<id>`; `REAUTH_REQUIRED` opens `StepUpDialog` and runs the action again with the same form data; other failures show the admin's message for the code or for the `CONFLICT`'s `details.reason`, never the API's text. The forms get only the fields they show (ids, names, statuses, the version, the notes and legal name the page already shows, the office ids of the pool).
  - *Actions* (above the tabs, on every tab): **Suspend** on an `active` OTA and **Resume** on a `suspended` one, each behind `ReasonDialog`; suspending also asks for the kind (`abuse`, `request` or `admin`, "Velexis decision" preselected; `billing` is billing sync's), and resuming a billing suspension says that it needs a subscription in trial or active. The outcome shows the OTA's new status and the `suspend` or `resume` job (id linking to `/provisioning-jobs/<id>`, kind, status, step). An OTA in set-up or failed offers neither. **Migrate** (`ConfirmDialog`, optional target version checked as `TenantMigrationVersion`; empty migrates to the latest) shows the `migrate` job; without a schema there is nothing to migrate.
  - *Overview*: **Edit notes and legal name** opens a form with both; it sends the version the page was rendered with in `If-Match` (`"<version>"`), and an empty field clears the value (`null`). A stale version (`412 PRECONDITION_FAILED`) keeps what was typed and asks to reload the page with a link that reloads it fully; a save closes the form and the next edit sends the saved version.
  - *Connections*: **Disable connection** or **Enable connection** on every Amadeus and payment card (`ReasonDialog`; the button names its connection), showing the new status. On a `velexis` Amadeus connection that waits for an office (`pending_verification` without one, because the pool was empty at provisioning) the card has **Assign office**: the page then loads the environment's available offices (`adminListAmadeusOffices`, `status=available`, up to 200, oldest first; only then, and a failed list still renders the page), the admin picks one, and `adminAssignAmadeusOffice` makes the connection `active`. The form shows the office and the new status, and the revalidated card shows the active connection with its office. No office available links to the pool page.
- **Amadeus accounts (PAD-007, PF-90).** `/amadeus/accounts` shows `adminListAmadeusAccounts` in one section per environment (test, then live; one Velexis account each, ADR-0012): name, verification state (`StatusBadge`: not verified, active, invalid credentials, disabled), host, the client id masked on the server (its last four characters; `MaskedValue`), "Stored encrypted, never shown" for the secret (the API never answers it), last verification, last error (HTTP status and Amadeus code only), creation, and the pool by status, each count linking to `/amadeus/offices?environment=<env>&status=<status>`, with the dashboard's warning below 3 available offices. An environment without an account offers **Set up the … account** (`account-form.tsx`): name, host (the environment's Amadeus host offered: `https://test.travel.api.amadeus.com`, `https://travel.api.amadeus.com`), client id and client secret; `adminCreateAmadeusAccount` is `x-mfa-step-up`, so the first save answers `REAUTH_REQUIRED`, `StepUpDialog` asks for a TOTP code and the same form data goes again; the account then shows `pending_verification`. An account offers **Verify now** (**Verify and enable** on a disabled one, which the API takes to `pending_verification` first; `503` when Redis does not take the job is worded), **Edit details** (name and host as they are, client id empty, which keeps it; a new host or client id needs the step-up), **Rotate secret** (a new secret only, step-up) and **Disable account** (`ConfirmDialog`; every OTA on the shared account of that environment loses Amadeus access). Each update sends the version the page was rendered with in `If-Match` (`"<version>"`); `412` asks to reload with a full-reload link. While an account is `pending_verification`, its actions call `router.refresh()` every 5 seconds for at most two minutes (and for half a minute after a verification of an account whose status stays), so the page shows `active` or `invalid_credentials` once the job ran. The secret fields are password fields with `autocomplete="new-password"` (browsers ignore `off` on a password field and would fill in the admin's saved console password) that are never pre-filled and are emptied after every answer but a step-up request; the secret goes from the field to the server action and on to the API in the request body only: no state, message or field error holds it, and the server actions never log. Field problems (Zod, as the API counts them: name 1–100, host `https` or the loopback stub, at most 300, client id without white space, at most 200, secret 1–512 after trimming) and the API's field errors show at their fields; `CONFLICT` (`environment_exists`) and the other codes are worded for the admin. A step-up request is the previous state with `stepUp: true`, so after an earlier save it still reads `done`: the forms treat it as no answer, so the form stays open and nothing says saved until the code is given (a cancelled step-up saved nothing). The props of the forms are the account's id, environment, status, version, name, host and the client id's last four characters.
- **Office pool (PAD-007, PF-90).** `/amadeus/offices` validates its URL as the other lists do (`environment` of `Environment`, `status` of `AmadeusOfficeStatus`, `cursor` of at most 512 characters; an empty parameter is no filter, a repeated or invalid one, or a `VALIDATION_FAILED` answer, shows a notice with a link to the whole pool and asks for no list) and calls `adminListAmadeusOffices` with exactly those filters, oldest first; `FilterBar` keeps both in the URL (the dashboard links `?environment=…&status=…`) and `DataTable` pages with the cursor. The rows (`office-table.tsx`, only the fields it shows) show the office id, environment, status (and since when a `releasing` office is releasing), the OTA of an `assigned` or `releasing` office (linking `/tenants/<id>`), when it was assigned, the notes and when it was added. **Add offices** (`add-offices-form.tsx`, above the list) picks the account (`adminListAmadeusAccounts`; the one of the environment filter first), takes one office id per line (trimmed, empty lines dropped, 9 letters or digits, at most 500; lines that are none are named by their number, never repeated) and optional notes for all of them, and shows the answer of `adminAddAmadeusOffices`: the created offices and the skipped ids (already in the pool, or repeated in the list); a success empties the list. Without an account it links `/amadeus/accounts`. An `available` office offers **Assign** (a dialog: the OTA's key, looked up with `adminListTenants` `q=<key>` (pages of 200, newest first, following the cursor for at most five pages: `q` also matches part of other keys, names and owners' e-mail addresses, so the OTA itself may come after many newer ones; beyond 1,000 such OTAs the field asks for the tenant id) and taken only on an exact key match, or its tenant id as it is; `adminAssignAmadeusOffice` makes the OTA's `velexis` connection of that environment `active`, and the outcome shows the office, the OTA (linked) and the connection's status) and **Retire** (`ReasonDialog`; `CONFLICT` `not_available` is worded); every office offers **Edit notes** (a dialog with the notes as they are, `If-Match` with the office's version; empty clears them; `412` keeps the text and links a full reload of the same list). A success revalidates the pool, `/amadeus/accounts` and `/` (an assignment also the OTA's page); as on the accounts page, a step-up request after an earlier success is no answer (the list and the dialogs stay, no earlier outcome shows); an ended session goes to `/sign-in?next=/amadeus/offices`. **Release** (reason and confirmation) comes with PAD-014 (M5).
- **Accounts (PAD-009, PF-87).** `/accounts` validates its URL as `/tenants` does (`q` of at most 254 code points after trimming, `status` of `AccountStatus`, `cursor` of at most 512 characters; an empty parameter is no filter, a repeated or invalid one, or a `VALIDATION_FAILED` answer, shows a notice with a link to every account and calls nothing) and calls `adminListAccounts` with exactly those filters, newest first; `FilterBar` keeps the search (part of the e-mail address or the name) and the status in the URL and `DataTable` pages with the cursor. The rows (`account-table.tsx`, only the fields it shows) link `/accounts/<id>` and show the e-mail address, status, two-factor, platform admin, last sign-in and creation. `/accounts/[accountId]` renders the not-found page for a value that is no account id (without a call) and for `NOT_FOUND`, and otherwise shows one `adminGetAccount` call: the account's fields (the API answers no password hash, MFA secret, recovery code or token), the number of active sessions (portal and admin sign-ins neither signed out nor expired; the API answers a count only), the active memberships (each linking its OTA, with the OTA's status and the role) and the last 50 audit rows (the shared `AuditTable` with the redacted details in `JsonView`), with links to `/audit?actorAccountId=<id>` (everything the account did) and `/audit?targetType=account&targetId=<id>` (everything done to it). The tenant page's members link here.
- **Account actions (PAD-009, PF-87).** `account-actions.tsx` with the server actions of `actions.ts`; each asks for exactly what its operation of the platform document requires (`x-reason-required`, `x-mfa-step-up`; `accounts.test.tsx` reads both from the document): **Unlock** (`ConfirmDialog`, no reason, no step-up) while the account is `locked` or has a lockout or failed sign-ins to clear; **Disable** (`ReasonDialog`) on an account that is not disabled or deleted, and never on the admin's own account, which the page knows from `adminGetMe` (a note says why; the API refuses `self` and the last active platform admin, `last_admin`, with `FORBIDDEN`); **Enable** (`ReasonDialog`) on a disabled account; **Reset two-factor** (`ReasonDialog`, then the step-up: the API answers `REAUTH_REQUIRED`, `StepUpDialog` asks for a TOTP code and the same reason goes again) on an account with two-factor authentication that is not a platform admin (a note says that another admin revokes the rights first, or the developer runs `admin:reset-mfa`; PADR-0006 item 6). A deleted account offers nothing. Each action checks the account id and the reason (5–500 code points after trimming) before it calls the API; a success shows the new status and revalidates the page and the list; `FORBIDDEN` (`self`, `last_admin`, `platform_admin`), `CONFLICT` (`not_enabled`, `not_disabled`, `mfa_not_enabled`), `NOT_FOUND` and `RATE_LIMITED` are worded for the admin; an ended session goes to `/sign-in?next=/accounts/<id>`. The component gets the account's id, name, status, two-factor and admin flags, whether there is a lockout and whether it is the admin's own account.
- **Platform admins (PAD-009, PF-86).** `/admins` calls `adminListAdmins` (by name, not paginated) and `adminGetMe` and shows each admin's name (linking the account), e-mail address, two-factor and last sign-in, with **Revoke** per row (`ConfirmDialog`, no reason: PADR-0006 item 5 asks for none; then the step-up). On the admin's own row ("You") and on the last admin's the button is disabled, with a note it is described by: revoking oneself is not offered (the API refuses `self` and `last_admin` with `FORBIDDEN`, worded too, since the list has no status and a disabled second admin still leaves the signed-in admin the last active one). **Grant admin rights** opens `ReasonDialog` with the account's e-mail address (checked as `EmailAddress` before the call) and a reason; `adminGrantAdmin` asks for the step-up, and the same address and reason go again. `NOT_FOUND` (no account), `CONFLICT` (`already_admin`) and `UNPROCESSABLE` (`account_not_active`, `email_not_verified`, `mfa_not_enabled`) are worded, and so is a `VALIDATION_FAILED` on `/email` (the API's `format: email` has the last word on the address); a success revalidates `/admins` and the account's page. If either call of the page fails, it shows the failure instead of the list. The component gets the fields the table shows and each row's rule (`allowed`, `self`, `last_admin`).
- **Audit log (PAD-009, PF-85).** `/audit` keeps every filter in the URL (`audit-filters.ts`, shared with the export): the OTA (`tenantId`) and the acting account (`actorAccountId`) by id, the actor type, the action and the target kind as selects of the backend's own lists (`AUDIT_ACTIONS` and `AUDIT_TARGET_TYPES` of `platform/backend/src/audit/audit-actions.ts`, copied in their order; `accounts.test.tsx` fails when they differ, PADR-0006 Audit item 6; a valid value of the URL that is not in the list is added to the select), the target id, and the period as two UTC days, `from` and `to` (date fields; the last day included). The page validates them as the API does (a repeated or invalid parameter, or a first day after the last, shows a notice with a link to the whole log and calls nothing) and calls `adminListAudit` with the days as the API's instants (`from` at `00:00:00Z`, `to` as the start of the next day, exclusive), newest first; `DataTable` pages with the cursor, keeping the filters. The rows (`AuditTable`, only the documented fields) show when, the OTA (linked), the actor (its kind, its e-mail snapshot linking the account), the action, the target (an account or an OTA linked), the request id, the IP address and browser, and the redacted details in `JsonView`. The tenant page's audit tab and the account page link here with their filters.
- **Audit export (PAD-009, PF-85).** The export panel of `/audit` links `/audit/export.csv` with the same filters (no cursor) once the period is set and spans at most one calendar year, as `adminExportAudit` requires; otherwise it says why. The link is a plain `<a>`, never `next/link`, whose prefetch would run the export (and write its `audit.exported` row) without a click. The route handler (`GET`) validates the same parameters, calls `adminExportAudit` with the admin's token through `lib/api.ts` (`parseAs: "stream"`) and answers the API's body as a stream, never buffered: `text/csv; charset=utf-8`, `Content-Disposition: attachment; filename="velexis-audit-<from>-<day after to>.csv"` (the API's name), `Cache-Control: no-store` (the file holds e-mail and IP addresses). A failure in the middle of the API's stream aborts the download, so a cut file is never complete. Filters the page would not link answer `400` with a plain-text explanation; API refusals answer their status with the admin's message (and `Retry-After` when there is one); an ended session goes to `/sign-in?next=/audit?<filters>`. `HEAD` answers `405` (`Allow: GET`): without its own handler Next.js would run `GET` for it and start an export, with its audit row, for an answer without a file.
- Cookies: `__Host-vxa_at` (admin access token, 15 minutes) and `__Host-vxa_rt` (refresh, 12-hour family), `HttpOnly; Secure; SameSite=Strict; Path=/`; `__Host-vxa_mfa` during sign-in. Middleware refreshes the access token (single-flighted in the process) and redirects to `/sign-in` without a session.
- **Sign-in (PAD-002).** `/sign-in` sends e-mail and password to `adminSignIn` (no bearer token, the end-user headers below). Its answer is always an MFA challenge, which goes into `__Host-vxa_mfa` (at most 5 minutes) before the browser continues to `/sign-in/mfa`; the password step never writes a session cookie, and an answer that is not a challenge is refused (`INTERNAL_ERROR`). `/sign-in/mfa` sends the challenge with a TOTP code or one recovery code to `adminVerifyMfa`, and only its `AdminSession` becomes `__Host-vxa_at` and `__Host-vxa_rt`, so the TOTP step happens on **every** sign-in (PF-80). Without a challenge cookie, and on `MFA_CHALLENGE_INVALID`, the admin goes back to `/sign-in?mfa=expired`. `MFA_REQUIRED` (a platform admin without MFA) explains that MFA is turned on in the portal and links to `PUBLIC_PORTAL_URL/account/security`; `ACCOUNT_LOCKED` and `RATE_LIMITED` show the wait of `Retry-After`. A forgotten password is reset in the portal (`PUBLIC_PORTAL_URL/forgot-password`): it is the same account.
- **Return path.** The middleware sends a request without a session to `/sign-in?next=<path and query>`; `next` travels in the query of `/sign-in/mfa` (no fourth cookie) and is used after the code step only when it is a relative path on the admin (`safeNextPath`: no absolute, protocol-relative or backslash URL, no control character, at most 2 048 characters; the path the URL parser makes of it is checked again, so dot segments that normalise to `//evil.example`, such as `/.//evil.example` or `/%2E%2E//evil.example`, are dropped; FIX-W26-SECURITY). Otherwise the admin lands on the dashboard `/`. Because every cookie is `SameSite=Strict`, a link to the admin opened from another site (a chat, a mail client) arrives without the session and asks to sign in again; `next` then brings the admin back to the page.
- **Middleware (PAD-002).** It runs on every request except `/_next/…`, `/favicon.ico` and `/health/…`, in the Node.js runtime (the single-flight map lives in the admin process). Deny by default: only the exact paths `/sign-in`, `/sign-in/mfa` and `/sign-out` work without a session; every other path, including one that does not exist yet (`/sign-in/other` too), answers `303` to `/sign-in`. An access token that is missing, unreadable, not of the `platform_admin` audience or within 30 seconds of its expiry is refreshed with `adminRefresh` (the same refresh token is sent once per 10 seconds however many requests present it; `REFRESH_TOKEN_INVALID`, `REFRESH_TOKEN_REUSED`, `VALIDATION_FAILED` and `UNAUTHENTICATED` delete both cookies, a rate limit or an unreachable API keeps them), and the new tokens replace the old ones in the request the page renders. The JWT signature is not checked here: the API checks it on every call.
- **Sign-out.** `POST /sign-out` answers `403` unless `Origin` is the origin of `PUBLIC_PLATFORM_ADMIN_URL`, then calls `adminSignOut` with the bearer token and the refresh token, deletes the cookies whatever the API answered, and answers `303` to `/sign-in?signedOut=1`. Other methods answer `405`.
- Portal sessions do not work here and admin sessions do not work in the portal: different cookies on different hosts and different token audiences ([PADR-0009](../docs/adr/0009-platform-api-surface-and-authentication.md)).
- Security headers as the portal, with `form-action 'self'` and `X-Robots-Tag: noindex`. The static ones are set in `next.config.ts` `headers()` for `/:path*`, so they reach every response: pages, route handlers (the health routes included), static assets and error pages.

  | Header | Value | Where |
  |---|---|---|
  | `X-Robots-Tag` | `noindex` | `next.config.ts`, every response (PAD-001); `middleware.ts` sets it on its own redirects too (PAD-002) |
  | `X-Content-Type-Options` | `nosniff` | `next.config.ts`, every response (PAD-001) |
  | `Referrer-Policy` | `same-origin`: admin URLs (tenant ids, filters) are not sent to other origins | `next.config.ts`, every response (PAD-001); see the Caddy note below |
  | `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), payment=(), usb=(), browsing-topics=()` | `next.config.ts`, every response (PAD-001), as the portal |
  | `Content-Security-Policy` | `default-src 'self'; script-src 'self' 'nonce-…'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'self'; object-src 'none'` with a new nonce per request; `script-src` also has `'unsafe-eval'` when `APP_ENV=development` (`next dev`). Every page is rendered per request (`export const dynamic = "force-dynamic"` in the root layout), as in the portal: a prerendered page would keep inline scripts without the nonce, and the policy would block them | `middleware.ts` (PAD-002), on pages and on its own redirects |

  `X-Powered-By` is switched off (`poweredByHeader: false`), and the root layout also renders `<meta name="robots" content="noindex, nofollow">`. Caddy adds `Strict-Transport-Security` and `X-Frame-Options: DENY` on the public host ([`deploy/caddy/Caddyfile`](../../deploy/caddy/Caddyfile)). Its shared `security_headers` snippet also sets `Referrer-Policy: strict-origin-when-cross-origin` (the value of [ADR-0014](../../docs/mvp/adr/0014-frontend-stack-nextjs-tailwind.md)), and Caddy's deferred header operations replace the app's `same-origin` with it on `admin.platform.example.com`; the stricter value only holds there once the Caddyfile's admin site stops overriding it.
- `lib/api.ts` (`server-only`) calls the admin surface `/v1/admin/…` only (the types refuse other paths, and a call of another path throws before anything is sent), with `cache: "no-store"`, no redirect following, the bearer token of `__Host-vxa_at` when there is one and the request id of the incoming request. A call answers `{ data }` or `{ error }` with the code of the platform catalogue, field errors, details and `Retry-After`, never the API's own message. It forwards the admin's IP and user agent on every call, as the portal does (`lib/end-user.ts`): `X-Velexis-End-User-IP` (right-most `X-Forwarded-For` entry set by Caddy, `127.0.0.1` without one), `X-Velexis-End-User-Agent` (at most 512 characters) and `X-Velexis-Bff-Key` (`PLATFORM_BFF_KEY`). Admin sign-in is throttled per admin IP, and admin audit rows record it ([PADR-0019](../docs/adr/0019-end-user-ip-forwarding-from-the-portal-and-admin.md)). The sign-in calls and the middleware's refresh carry them too.
- `lib/errors.ts` maps every code of the platform catalogue to the admin's own message (`lib/strings.ts`); `errors.test.ts` fails when the catalogue gains a code without one.

## 5. Configuration

See [`.env.example`](.env.example); on the VM `/etc/velexis/platform-admin.env` (template [`deploy/env/platform-admin.env.example`](../../deploy/env/platform-admin.env.example)): `APP_ENV`, `LOG_LEVEL`, `PORT` (3001), `HOSTNAME` (`127.0.0.1`), `PLATFORM_API_URL`, `PLATFORM_BFF_KEY` (shared with the API, PADR-0019), `PUBLIC_PLATFORM_ADMIN_URL`, `PUBLIC_PORTAL_URL` (link to enable MFA in the portal), `SENTRY_DSN`. All are read in server code through `@velexis/config`. On the VM the systemd unit sets `PORT` and `HOSTNAME`.

`src/lib/config.ts` (`import "server-only"`) declares the schema `ADMIN_CONFIG_SCHEMA`; later tasks add their entries there.

| Variable | Rule | Default |
|---|---|---|
| `APP_ENV` | `development`, `test` or `production` | required |
| `LOG_LEVEL` | a pino level (`fatal` … `trace`, `silent`) | `info` |
| `PORT` | 1–65535 | `3001` |
| `HOSTNAME` | host name or IP literal to bind | `127.0.0.1` |
| `PLATFORM_API_URL` | absolute `http:` or `https:` URL | required |
| `PLATFORM_BFF_KEY` | at least 32 characters of `[A-Za-z0-9_-]` (refuses the unsubstituted `@@PLATFORM_BFF_KEY@@`); the same value as the API and the portal | required |
| `PUBLIC_PLATFORM_ADMIN_URL`, `PUBLIC_PORTAL_URL` | absolute `http:` or `https:` URL; `https:` when `APP_ENV=production` | required |
| `SENTRY_DSN` | `https:` URL; unset or empty switches error tracking off | optional |

- `getConfig()` validates the process environment on first use and caches the frozen result. Outside production it first fills unset variables from `platform/admin/.env.local`, then from the root `.env.local` (`loadDevEnvFiles`), so the root file made from the root `.env.example` is enough for `pnpm dev`.
- Call it inside request handling (route handlers, server components, server actions), never at module scope: `next build` imports modules without the runtime environment. An invalid environment therefore fails the first request that needs it, and `/health/ready` is such a request, so `deploy.sh` does not take a release live with a broken `/etc/velexis/platform-admin.env`. The error is a `ConfigError` that names each variable and the reason, never a value.
- `parseConfig(source)` validates a plain object; the unit tests use it.
- **No browser-exposed variables.** No `NEXT_PUBLIC_` variable exists and `next.config.ts` has no `env` block, so nothing is inlined into client bundles; `src/lib/config.test.ts` fails if either appears.

**Health and headers without a browser.** After a build, `PORT=3001 APP_ENV=development PLATFORM_API_URL=http://127.0.0.1:3100 PLATFORM_BFF_KEY=dev_bff_key_change_me_0123456789abcdef PUBLIC_PLATFORM_ADMIN_URL=http://localhost:3001 PUBLIC_PORTAL_URL=http://localhost:3000 node .next/standalone/platform/admin/server.js` serves the standalone build (it sets `NODE_ENV=production`, so no `.env.local` is read), and `curl -i http://127.0.0.1:3001/health/live` shows `200` with `X-Robots-Tag: noindex`. The unit test `src/app/health/live/route.test.ts` checks the same headers by compiling the rules of `next.config.ts` with Next.js's own route matcher, for `/health/live` and other paths.

**Tests in Node.** `server-only` throws outside the `react-server` export condition, which only Next.js sets, so `vitest.config.ts` maps it to the package's own empty module. The `@/` alias matches `tsconfig.json`.

**Files outside this package.** The tests also read the root and portal `.env.example` files, the `deploy/` environment template and systemd unit of the admin, the platform OpenAPI document (`accounts.test.tsx` reads `x-reason-required` and `x-mfa-step-up` from it) and `platform/backend/src/audit/audit-actions.ts` (the backend's action and target lists the audit filters copy). [`turbo.json`](../../turbo.json) lists them as inputs of `@velexis/platform-admin#test`, so a change to any of them reruns the tests instead of replaying a cached pass (CI restores the Turborepo cache).

**postcss override.** Next.js 15 pins `postcss` 8.4.31, which has high-severity advisories. The root `package.json` overrides `next>postcss` to the patched version that Tailwind CSS already uses (the same override as the portal), so `pnpm audit --prod` stays clean. Remove the override once Next.js ships a patched `postcss`.

**Adding a shadcn/ui component.** From `platform/admin`, run the CLI pinned to the 2.x line of [`tech-stack.md`](../../docs/mvp/tech-stack.md), for example `pnpm dlx shadcn@2.10.0 add table`. `components.json` sends the copy to `src/components/ui/` with the `new-york` style, CSS variables and lucide icons, and `cn()` to `src/lib/utils.ts`. The CLI adds the component's dependencies with `^` ranges: make them exact in `package.json` before committing (`tools/ci/check-package-json.mjs` fails otherwise). The design tokens in `globals.css` are a copy of the portal's: change the portal, the platform admin and the OTA admin together ([ADR-0014](../../docs/mvp/adr/0014-frontend-stack-nextjs-tailwind.md)). Two copies differ from the registry as the portal's do since PFE-015, whose axe checks found the defects (FIX-W31-PLATFORM): `alert.tsx` gives the description of a destructive alert the full `text-destructive` (the registry's `text-destructive/90` measured 4.49:1 on white, under the 4.5:1 of WCAG AA), and `table.tsx` makes its scroll container focusable (`tabIndex={0}` with a focus ring), so a table wider than its column scrolls with the keyboard (axe `scrollable-region-focusable`, WCAG 2.1.1). `components.test.tsx` fails if either is reverted.

The `dev:seed` command of the backend creates a development admin and prints its TOTP set-up URI to the console (refused when `APP_ENV=production`). End-to-end tests create their own admin through test builders and compute TOTP codes from the secret they generated ([`../backend/README.md`](../backend/README.md)).
