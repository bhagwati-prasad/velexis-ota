# `@velexis/e2e`: the Playwright end-to-end harness

The end-to-end suite of Velexis ([ADR-0015](../../docs/mvp/adr/0015-testing-strategy.md) "End-to-end", [PADR-0017](../../platform/docs/adr/0017-platform-test-doubles-and-end-to-end-harness.md) item 3): Playwright journeys in `specs/**/*.e2e.ts` that drive the **built** apps in a real browser, against a stack that the harness starts itself on a fresh database, with Mailpit for e-mail, TOTP codes for MFA and axe for accessibility. Task PFE-014 created it with the `portal` and `platform-admin` projects; PFE-015 and PAD-010 add the platform M1 journeys, PAD-011 the storefront following a suspension, and PFE-019 the [console's single sign-on journey](#tests-of-pfe-019) (`specs/console-sso.e2e.ts`, project `portal`). The OTA plan adds its projects: `storefront` (OFE-008: the OTA API, the storefront previews and the demo OTA in the stack, the [storefront guards](#storefront-journeys) and the M2 search journey), the nightly `storefront-stripe` (OFE-017: the guest Stripe checkout journey with the [Stripe CLI forwarder](#stripe-journeys-of-the-storefront)) and `ota-admin` (OAD-016: the built OTA admin in the stack, the [single sign-on and bookings journey and the PNR import journey](#ota-admin-journeys), the gate of the platform's console journey PFE-019). OFE-018 adds the [airline-card journey](#the-airline-card-journey-of-the-storefront) with its card leak checks to `storefront`, and OAD-017 the OTA admin's [settings, roles and payments journeys](#tests-of-oad-017) (the payments journey in the nightly `storefront-stripe`).

- **Test-only.** Every dependency is a `devDependency`; nothing here is shipped or runs on the VM.
- **Not part of `pnpm test` or `pnpm test:int`.** The journeys run with `pnpm test:e2e`, nightly and on pull requests labelled `e2e` ([`.github/workflows/e2e.yml`](../../.github/workflows/e2e.yml)). `pnpm test` runs only the harness's own unit tests (`test/`).

## Run it

Once per machine: the local setup of [`docs/mvp/local-development.md`](../../docs/mvp/local-development.md) §2 (PostgreSQL 16 with the roles of `dev-setup.sh`, Redis, `.env.local`, `pnpm dev:keys`), Mailpit running (§4), and Playwright's Chromium:

```bash
pnpm --filter @velexis/e2e exec playwright install chromium     # add --with-deps on a bare Ubuntu: system libraries
```

Then build the apps and run the journeys:

```bash
pnpm --filter @velexis/platform-backend build && pnpm --filter @velexis/platform-frontend build \
  && pnpm --filter @velexis/platform-admin build                  # or `pnpm build`
pnpm test:e2e -- --project=portal --project=platform-admin specs/smoke.e2e.ts
E2E_WITH_OTA=1 pnpm test:e2e -- --project=portal                  # every portal journey, with the Amadeus stub, the OTA worker and API, the previews, the demo OTA
pnpm test:e2e -- --project=portal specs/portal-account-security.e2e.ts   # a journey that needs no OTA
pnpm exec turbo run build --filter=@velexis/ota-backend --filter=@velexis/ota-frontend   # for the storefront
E2E_WITH_OTA=1 pnpm test:e2e -- --project=storefront specs/storefront/search.e2e.ts      # the M2 search journey
pnpm --filter @velexis/ota-admin build                                                    # for the OTA admin (or `pnpm build`)
E2E_WITH_OTA=1 pnpm test:e2e -- --project=ota-admin                                       # the OTA admin's journeys
E2E_WITH_OTA=1 pnpm test:e2e -- --project=portal specs/console-sso.e2e.ts                 # "Open console" into the OTA admin (PFE-019; the OTA admin built too)
pnpm --filter @velexis/e2e exec playwright show-trace test-results/<test>/trace.zip   # after a failure
```

The portal journeys that need an active OTA (`portal-signup`, `portal-api-keys`, `portal-team`, and `console-sso`, which also needs the OTA API and the OTA admin) provision one on the OTA worker, so they need `E2E_WITH_OTA=1`; without it they fail at once with that message (never skipped). `pnpm test:e2e` is `pnpm --filter @velexis/e2e run test:e2e`: it builds the tooling the harness imports (`@velexis/testing`, `@velexis/reference-data`, `@velexis/amadeus-stub`, a no-op when they are built) and runs `playwright test` with the arguments after `--`. The script drops the `--` that pnpm forwards, because Playwright would take every argument after a `--` for a file filter and so ignore `--project`. It does **not** build the apps: the harness runs what is built, as the VM does, and says which build is missing. With `E2E_WITH_OTA=1` it also needs the OTA backend built with its packages, the storefront's production build and the OTA admin's standalone build: `pnpm exec turbo run build --filter=@velexis/ota-backend --filter=@velexis/ota-frontend --filter=@velexis/ota-admin` (or `pnpm build`).

One run at a time per machine: the stack listens on the fixed ports below, and the harness refuses to start when one is taken (a `pnpm dev`, another run).

A spec file belongs to a project by its name. `smoke.e2e.ts` is shared, so each of its tests carries the tag of its project (`PROJECT_TAGS` of [`support/fixtures.ts`](support/fixtures.ts)): `test("…", { tag: PROJECT_TAGS.portal }, …)`. A portal journey that needs Stripe over the network carries `PROJECT_TAGS.stripe` and so runs only in `portal-stripe`, a storefront journey that does only in `storefront-stripe` (`test.describe("…", { tag: PROJECT_TAGS.stripe }, …)`); no test is ever skipped with `.skip`, the project is simply not selected. A new project (the OTA plan's) adds its entry to `projects` in [`playwright.config.ts`](playwright.config.ts) with its own `testMatch` (for example `specs/storefront/**/*.e2e.ts`) and base URL.

Settings of every project: traces kept and screenshots taken for failed tests only, no video, no retries (a failure is a finding, [AGENTS.md](../../AGENTS.md) §7), `.only` refused when `CI` is set, files in parallel (2 workers in CI) and the tests of one file in order.

## The stack

[`support/stack.ts`](support/stack.ts) is Playwright's global setup. For each run it:

1. reads the harness settings (below), after the `.env.local` files of `tools/e2e` and the repository root;
2. checks that every app (and each seed's CLI) is built and that every port is free, and fails at once with the command to run when not;
3. empties the stack's Redis database (`E2E_REDIS_DB`), creates the database `velexis_e2e_<runId>` as `TEST_DATABASE_ADMIN_URL` the way [`bootstrap.sql`](../../deploy/postgres/bootstrap.sql) creates `velexis` (owner `velexis_migrator`, the database grants, [`schemas.sql`](../../deploy/postgres/schemas.sql)), then runs `pnpm db:migrate` and `pnpm db:seed:reference` against it (about 5 s);
4. with `E2E_STRIPE=1`, `E2E_WITH_OTA=1` and the OTA's Stripe test keys (OFE-017), starts the Stripe CLI forwarder and waits for its signing secret, which the OTA API gets ([below](#stripe-journeys-of-the-storefront)); then starts the built apps with `node` (the Next.js apps, the OTA admin among them with `E2E_WITH_OTA=1`, from their standalone `server.js`, with `.next/static` copied into the standalone tree as [`pack-release.sh`](../../deploy/scripts/pack-release.sh) does; the storefront with `vite preview` of its `dist/`);
5. waits until each answers `GET /health/ready` with `200` (at most 60 s each; the OTA admin's answers so once the OTA API is live); the Amadeus stub has no health route, so its Amadeus-style `404` on that path counts, and a storefront preview is ready when it serves its home page;
6. with `E2E_WITH_OTA=1`, runs the platform's `dev:seed` and then the OTA backend's from their built CLIs (about 2 s): the platform admin `admin@example.com`, the Velexis test Amadeus account (verified against the stub) and its twenty test offices, then the demo OTA `tenant_demo` ("Demo Travel", storefront `test`) on `demo.ota.example.com` with an Amadeus test connection, as in development ([`ota/backend/README.md`](../../ota/backend/README.md) §5). What they print on stdout (the admin's password and TOTP set-up URI, two API keys, each shown once) is discarded, never logged; their stderr goes to `test-results/stack/platform-dev-seed.log` and `ota-dev-seed.log`. Both are idempotent, so a journey that runs one again changes nothing.

Each preview is the one of [`ota/frontend/README.md`](../../ota/frontend/README.md) §11: the production build, the proxy of `/api/*` to the OTA API with the edge headers Caddy adds (`X-Velexis-Edge` with the development `VELEXIS_EDGE_SECRET`, `X-Velexis-Host` and `Origin` of its host), and the Caddyfile's headers, the CSP among them. The second one serves the host of the OTA `suspended`, which only the journey that needs a suspended OTA creates (`withSuspendedTenant` of [`support/ota.ts`](support/ota.ts)), so that no other journey ever sees the demo OTA suspended. The third one serves the host of the OTA `suspension` (`ADMIN_SUSPENSION_TENANT_KEY`), which only [`admin-suspension-storefront.e2e.ts`](specs/admin-suspension-storefront.e2e.ts) creates, through the portal API and the OTA worker, for the platform admin to suspend and resume ([below](#tests-of-pad-011)); the storefront guards count its origin among the storefront's own.

The teardown, also after Ctrl-C, stops every process and the forwarder (SIGTERM, SIGKILL after 10 s), drops the database and empties the Redis database. If the stack cannot start, it cleans up the same way and the run fails with the reason and the last lines of the process's output. A whole start takes 6 to 10 s locally, and 15 to 30 s with `E2E_WITH_OTA=1` (eleven processes and the two seeds).

**Environment of the apps.** Each process gets the values of the root `.env.example` and then of its own `.env.example` (the precedence of the `.env.local` files in development), and on top:

- `APP_ENV=test`, `LOG_LEVEL=info`, the stack's `REDIS_URL`, the harness's `SMTP_URL` and `MAILPIT_API_URL`;
- the stack database's DSN of the process's own role: `velexis_platform_app` for the platform API, worker and CLI, `velexis_ota_app` for the OTA API and worker, and `velexis_provisioner` (`DATABASE_PROVISIONER_URL`) for the OTA worker ([ADR-0004](../../docs/mvp/adr/0004-postgresql-schema-per-tenant.md)). The Next.js apps, the stub and the previews get no DSN, and no process gets `DATABASE_MIGRATOR_URL` or `TEST_DATABASE_ADMIN_URL`, even when the developer's shell exports them. The one exception is the OTA backend's `dev:seed`, a development command and no app: it gets the stack database's `velexis_migrator` DSN, as its development-only platform writes need, besides those of `velexis_ota_app` and `velexis_provisioner`;
- the ports above, and every public and internal URL on `127.0.0.1` (`PUBLIC_PORTAL_URL=http://127.0.0.1:3000`, `PUBLIC_PLATFORM_ADMIN_URL=http://127.0.0.1:3001`, `PLATFORM_API_URL`, `OTA_API_URL`, `AMADEUS_BASE_URL_TEST` and `_LIVE` on the stub, …), and `STOREFRONT_BASE_DOMAIN=ota.example.com`, so the OTA API, the seed and the previews agree on the storefront hosts. The browser reaches the apps on `127.0.0.1`, so links in e-mails and redirects must name that host: cookies of `localhost` are not sent to `127.0.0.1`;
- with `E2E_STRIPE=1`, the harness's `STRIPE_SECRET_KEY` and `STRIPE_BILLING_WEBHOOK_SECRET` for the platform backend instead of the dummies;
- with `E2E_STRIPE=1`, `E2E_WITH_OTA=1` and the OTA's keys, `STRIPE_SECRET_KEY_TEST` and `STRIPE_PUBLISHABLE_KEY_TEST` for the OTA API and worker, and `STRIPE_WEBHOOK_SECRET_VELEXIS_TEST` (the forwarder's signing secret) for the OTA API alone, instead of the dummies.

So a variable that a later task adds to an app's `.env.example` reaches the stack without a change here, and a developer's `.env.local` never changes what the apps see. These are the dummy development values of the `.env.example` files.

**Output.** Each process, `pnpm db:migrate` and `pnpm db:seed:reference` write to `test-results/stack/<name>.log` (redacted JSON lines of the apps; never a DSN), the Stripe CLI forwarder to `stripe-cli.log` (every `whsec_`, `sk_` and `rk_` value redacted). Playwright empties `test-results/` before each run, and CI uploads it on failure.

**After an interrupted run** (a killed terminal, not Ctrl-C), a database `velexis_e2e_*` may be left over. It is harmless; drop it when no run is active:

```bash
psql "$TEST_DATABASE_ADMIN_URL" -At -c "SELECT datname FROM pg_database WHERE datname LIKE 'velexis\_e2e\_%'"
psql "$TEST_DATABASE_ADMIN_URL" -c 'DROP DATABASE "velexis_e2e_…" WITH (FORCE)'
```

## Writing a journey

```ts
import { expectNoSeriousA11yViolations } from "../support/a11y";
import { expect, test } from "../support/fixtures";
import { uniqueEmail, waitForLink } from "../support/mailpit";
import { PORTAL_URL } from "../support/stack";

test("signs up and verifies the e-mail address [PFE-015 AC1]", async ({ page }) => {
  const email = uniqueEmail("signup");
  await page.goto("/sign-up");
  await expectNoSeriousA11yViolations(page);
  // …fill in the form…
  const link = await waitForLink({ to: email, subject: /verify/i, path: "/verify-email", origin: PORTAL_URL });
  await page.goto(link.href);
});
```

- Import `test` and `expect` from `support/fixtures.ts`. Name a test after the behaviour and end it with the criterion it proves (`[PFE-015 AC1]`, [conventions §10](../../docs/mvp/conventions.md#10-testing)).
- **Own data only.** Every journey creates its own accounts (`uniqueEmail`, `buildAccount()`) and reads only its own e-mail: spec files run in parallel, and other runs may share Mailpit. Never empty Mailpit or a table.
- **Accessibility:** call `expectNoSeriousA11yViolations(page)` on every page a journey visits, once the page shows what the journey came for. Wait for the page's title first (`await expect(page).toHaveTitle("Sign in · Velexis")`): Next.js 15 streams a page's metadata after its content, so right after a client-side navigation a page can be on screen a moment before its `<title>`, and axe would report `document-title`. The PFE-015 specs wrap both in `expectAccessible(page, title)`.
- **One journey, one file.** A journey whose steps build on each other is a file of tests in order (`test.describe.configure({ mode: "serial" })`, one browser context made in `beforeAll`): each step keeps Playwright's default 30-second budget, and a failed step stops the steps after it. One-time arrangements in `beforeAll` (an active OTA: about 2 s locally, PF-11 allows a minute) set their own budget there with `test.setTimeout`, commented; a test's own budget is never raised.
- **Middleware redirects name `localhost`.** Next.js writes the loopback host of a redirect made in `middleware.ts` (a signed-out visitor sent to `/sign-in?next=…`) as `localhost` (its `NextURL` turns `127.0.0.1` into `localhost`), and the browser's cookies of `127.0.0.1` are not sent there. Compare only the path and query of such a redirect (`page.waitForURL((url) => url.pathname + url.search === "/sign-in?next=%2Fdashboard")`) and come back to the stack's host before signing in. Redirects of route handlers and server actions keep `127.0.0.1`; on the VM the portal's domain is kept.
- **No sleeping.** Wait for what the page shows (`expect(locator).toBeVisible()`, `page.waitForURL`), for an e-mail (`waitForEmail`), or poll; never a fixed `waitForTimeout`. No `.only`, no `.skip`, no retries, no longer timeouts to get green ([AGENTS.md](../../AGENTS.md) §7).
- **Secrets:** tokens, passwords, MFA secrets and recovery codes stay in variables; never `console.log` them or put them in a test title.

- **The demo OTA** is shared by every storefront journey: it stays `active`, and a journey changes only its own data (its own searches, checkouts, customers). The third preview (`ADMIN_SUSPENSION_STOREFRONT_URL`) belongs to PAD-011's journey alone ([below](#tests-of-pad-011)).

- **The Amadeus stub** answers every search with the five offers of its fixture (Madrid to Paris), the destination `ZZZ` with none, and every upsell with the fare families BASIC, CLASSIC and FLEXIBLE ([`tools/amadeus-stub/README.md`](../amadeus-stub/README.md)). Dates are computed from today (a departure 40 days ahead), never fixed.

The setting stays on for the rest of the run: the one change of the demo OTA's own configuration a journey makes, and no journey depends on it being off.
- **End-user IPs.** A journey that pays sends an end-user IP of its own as `X-Forwarded-For` (`uniqueTestIp` of `support/fixtures.ts`), which the preview passes on and the OTA API takes as the client address (`TRUST_PROXY=loopback`, as behind Caddy), so its requests count against per-IP limits of their own (the airline-card completion: 5 a minute) whatever other journeys run meanwhile.
- **Provoking a guard on purpose** (the guard tests of `search.e2e.ts`): read `guards.problems`, expect `guards.verify()` to throw, then `guards.forget()`, so the test's own end is clean. ### The airline-card journey of the storefront

[`specs/storefront/checkout-airline-card.e2e.ts`](specs/storefront/checkout-airline-card.e2e.ts) (OFE-018, [`ota/frontend/README.md`](../../ota/frontend/README.md) §13 journey 3, [`checkout-airline-card.md`](../../ota/docs/flows/checkout-airline-card.md) §4 and §7) runs in `storefront` with the Amadeus stub; the airline charges the card through Amadeus, so it needs no Stripe:

```bash
E2E_WITH_OTA=1 pnpm test:e2e -- --project=storefront specs/storefront/checkout-airline-card.e2e.ts
```

- **Arrangement.** A `beforeAll` of the file turns the demo OTA's airline card on for its test storefront (`enableAirlineCard` of [`support/ota.ts`](support/ota.ts), shared with OFE-019's journeys: `tenantTx` as `velexis_ota_app`), then waits until storefront.get, asked through the preview as the edge, offers it: each poll deletes the demo OTA's `t:<tenantId>:test:sf:*` entries first, as the console's settings change does, so an entry another journey filled from the old row meanwhile goes too.
- **Three journeys**, each a file of steps in order on one browser context made in `beforeAll` with the storefront guards and the card leak checks installed before its first navigation, and its own end-user IP:
  - the success: price → guest checkout → "Card, charged by the airline" → the airline's notice and price → the test PAN `4111 1111 1111 1111` → the stub's VISA card fee of €1.20 and the airline's total → the confirmation with the ticket; then the payment in the demo OTA's `payments`: `captured` by the airline, with brand, BIN and last 4 and no expiry, the booking in net pricing. On the way: the same completion straight to the OTA API, without the edge credential, is refused (`401`); a page on `/checkout/pay-card.html` that opens the card page with `window.open` gets a handle that reports `closed` and reaches no document, and the opened page has no `window.opener` (`expectOpenerCutOff`); a validation error (a VISA number that fails the Luhn check) sends nothing, focuses the summary of the problems and repeats no card value on the page, and the leak checks then find nothing but the typed inputs themselves (so the input check reads the page's real inputs); a card typed and left behind (the page left for the payment step, then Back) is gone from the inputs;
  - the stub's declined test card `4000 0000 0000 0002` three times: `402 PAYMENT_DECLINED` twice ("The airline declined the card", the inputs emptied), then `403 PAYMENT_ATTEMPTS_EXCEEDED` ("Too many attempts"), each submit with an idempotency key of its own;
  - the airline's answer lost: the stub's `server-error` for the completion alone (through `X-Stub-Scenario`, as in OFE-017), so Flight Create Orders answers `500`, which the OTA cannot tell from a timeout: it answers `504 SUPPLIER_TIMEOUT` with the booking and keeps it `pending` for its reconciliation, the payment `processing`. The page opens the confirmation in pending mode; the browser sent one completion and the OTA one Flight Create Orders (`supplier_requests`). The stub's own `timeout` scenario holds its answer 30 s, longer than a step's 30-second budget, so the journey does not use it; the OTA handles both answers alike (OADR-0003 point 2).
- **The card leak checks** ([`support/card-leak-guards.ts`](support/card-leak-guards.ts)) run after each path of [OADR-0017](../../ota/docs/adr/0017-airline-card-form-isolation.md) point 8 (success, validation error, decline, attempt limit, the lost answer, leaving the page). The card number (also typed with spaces or encoded), its last 12 digits, the security code (as a value of its own) and the holder's name of every card the journey typed must not be in localStorage, sessionStorage, IndexedDB or `window.name`, a cookie (httpOnly ones included), the address or `history.state` of any document of the context, any address or state given to `history.pushState` and `replaceState`, any request (address, headers, and the body of every request but the completion's), or any answer of the OTA API (all but the security code, a 3-digit value that answers hold as flight numbers). The card inputs of the airline-card page it is on must be empty, and the airline-card page must have made no request to another origin. A left page cannot report its own inputs from `pagehide`: its COOP puts every navigation away from it into another browsing context group, from which Chromium no longer delivers the report, so the journey leaves the page and comes back instead. Problems name the place and the kind of value, never the value (`redactPlace`: a place whose own name holds a card value, such as a storage key or a path, is named without it). The spec's "the card leak checks" test provokes, on purpose in Chromium, a finding in localStorage, sessionStorage, IndexedDB, `window.name`, the page's address and `history.state`, an address and a state given to `history`, a request's address, header and body, an answer of the API (a `page.route` answer) and a cookie; the validation-error step above provokes the filled card inputs on the real airline-card page. A request of the airline-card page to another origin cannot be provoked there (its CSP refuses it first, and the storefront guards report it too), so [`test/card-leak-guards.test.ts`](test/card-leak-guards.test.ts) proves that check against a fake context. A green check therefore means something.
- **Card data** is the stub's test numbers and one number that fails the Luhn check, typed into the page's own inputs as a traveller would; the checks keep them in memory and never print them.

## OTA admin journeys

Specs in `specs/ota-admin/` run in the `ota-admin` project against the built OTA admin (base URL `OTA_ADMIN_URL`, `http://127.0.0.1:3002`, `E2E_WITH_OTA=1`), whose standalone server the stack starts next to the OTA API (OAD-016, [`ota/admin/README.md`](../../ota/admin/README.md) §12):

```bash
pnpm --filter @velexis/ota-admin build && \
  E2E_WITH_OTA=1 pnpm test:e2e -- --project=ota-admin specs/ota-admin/sso-bookings.e2e.ts specs/ota-admin/pnr-import.e2e.ts
```

- **Staff arrive as on the VM**: by the portal's single sign-on. `openConsoleFromPortal` of [`support/ota.ts`](support/ota.ts) opens the portal's page of the OTA in a context that holds the owner's portal session (`addSessionCookies(context, "portal", …)`), presses "Open console" and waits for `/bookings` of the OTA admin: the launch route mints the one-time portal token, its hand-off page posts it to the OTA admin's `/sso`, which sets the four httpOnly cookies of the staff session (`STAFF_COOKIES`: `__Host-vx_staff_at`, `__Host-vx_staff_rt`, `__Host-vx_env`, `__Host-vx_tenant`) and answers `303`. A journey's browser context takes the OTA admin as its base URL; the portal's pages are named by their whole address (`portalOtaPath`).
- **Each journey has its own OTA.** `newOwnerWithActiveOta(fullName, keyPrefix)` signs a new account up and in, creates its OTA through `createTenant` (a unique key) and waits until the OTA worker has set it up with its Amadeus test connection `active` on an office of the Velexis test pool (twenty offices from the platform's `dev:seed`, ten until the lead's decision (2f) of 2026-10-30; a whole run of the four projects takes twelve of them, the demo OTA's and one per journey's OTA (PFE-019's `console-sso` in the `portal` project and OAD-017's `settings-effects` and `roles` included; ten before OAD-017), besides one of the three test offices that `admin-amadeus-pool` adds, so a journey that needs no OTA of its own does not create one). The set-up passes over offices that another transaction holds, and [`admin-amadeus-pool.e2e.ts`](specs/admin-amadeus-pool.e2e.ts) holds every available one while its own OTA is set up ([below](#tests-of-pad-010)): an OTA set up in those seconds gets a connection that waits for an office. Then the helper waits until an available office is free of holds (a `SKIP LOCKED` read in a rolled-back transaction) and sets up another OTA, at most three; a pool without an available office fails at once. The owner is the OTA's staff `owner`. The demo OTA is no one's, so no journey opens its console; it serves as "another OTA" (its office: `activeAmadeusConnectionOf(await demoTenantId())`).
- **Bookings of the journey's OTA** are made in `beforeAll` through the OTA API as that OTA's storefront edge: `EdgeApi` sends what Caddy and the previews send in front of the storefront (the development `VELEXIS_EDGE_SECRET`, `X-Velexis-Host` and `Origin` of the OTA's host, the journey's end-user IP as `X-Forwarded-For`) and the CSRF double submit of the value storefront.get issued, because no preview serves a journey's own OTA. `bookAirlineCardTrip` books with the airline card (no Stripe) once `switchAirlineCardOn(schema)` turned the OTA's test switch on; `completionScenario: "ticketing-failed"` sends the stub's scenario with the completion alone, so the airline creates the order without its tickets and the booking waits in `manual_review` (its card payment `processing`: the airline charged nothing).
- **PNRs made outside Velexis**: `createStubOrder({ officeId, traveller, email, daysAhead })` books the stub's first offer straight at the stack's stub, as an agent's GDS terminal would (a token, a search, Flight Create Orders without issuing, the office as queuing and owner office, the flights moved to `daysAhead` days from today). The stub answers its by-reference read to every OTA; the OTA API's office isolation decides which may see it.
- **The OTA's midnight** (2026-10-30, lead decision (2g), FIX-W34-OTA). `sso-bookings` cancels a booking whose tickets it expects to be voided as "issued today", a minute or two after booking it. Booked in the last minutes of the OTA's day, the cancel step would run on the next day and meet tickets of yesterday. So its `beforeAll`, just before the bookings, reads the time zone that decides "today" from the stack (`bookingDayTimeZones`: `storefront_settings.time_zone`, which the API's cancellation reads and, since 2026-10-30 (lead decision (2a), FIX-W35-OTA), console.bookings.get answers as `cancellationMode` to the OTA admin's cancel dialog, which no longer reads the platform's zone of `console.auth.me`; provisioning seeds it from the OTA's platform zone, Europe/Oslo for the OTAs of `otaInput`, where it was `UTC` before) and, when it is within 3 minutes before midnight there, waits until 00:00:05 of the new day by polling the clock once a second (`waitPastMidnight`; `msUntilPastMidnight` is the pure rule, unit-tested with fixed instants in `test/ota.test.ts`). The hook's budget has `MIDNIGHT_WAIT_BUDGET_MS` (about 190 s) on top of its 120 s; no assertion changed.
- **Every page** of the OTA admin a journey visits passes axe once its title (`<page> · Velexis OTA admin`) is in place, dialogs included, and its JavaScript reads no cookie (`scriptReadableCookieNames(page)` is empty; the names only, never the values). The portal's page of the OTA passes axe too, and so does its hand-off page: that page submits itself while it loads, before a check could run, so `sso-bookings` serves the captured page again without its one script, in a page of its own, and checks that markup.

## Troubleshooting

| Problem | Cause | Fix |
|---|---|---|
| `The end-to-end stack runs the built apps, and these are not built` | An app has no build output | The command the message names, or `pnpm build` |
| `port 3000 (portal) is in use` | `pnpm dev` or another run | Stop it; one run at a time per machine |
| `Executable doesn't exist at …/chromium_headless_shell-…` | Playwright's browser is not installed (or is of another Playwright version) | `pnpm --filter @velexis/e2e exec playwright install chromium`. Where `cdn.playwright.dev` is blocked, `PLAYWRIGHT_CHROMIUM_DOWNLOAD_HOST` can point at a mirror with the same `builds/cft/<version>/linux64/*.zip` layout (Chrome for Testing publishes the same zips) |
| `<process> exited with code 1 before it was ready` | The app failed at start; the message shows the end of its log | Read `test-results/stack/<process>.log`; a `ConfigError` names the variable |
| `ConfigError: TEST_DATABASE_ADMIN_URL …` | No `.env.local` and no environment | `cp .env.example .env.local` (local-development.md §2) |
| `MailpitError … ECONNREFUSED` | Mailpit is not running | `mailpit --smtp 127.0.0.1:1025 --listen 127.0.0.1:8025` |
| `Project(s) "storefront" not found` | The project exists only with `E2E_WITH_OTA=1` | `E2E_WITH_OTA=1 pnpm test:e2e -- --project=storefront` |
| `Project(s) "ota-admin" not found` | The project exists only with `E2E_WITH_OTA=1` | `E2E_WITH_OTA=1 pnpm test:e2e -- --project=ota-admin` |
| `3 OTAs were set up without an Amadeus test office` or `the Velexis test pool has an available office that no other journey holds` | The Velexis test pool had no available office when the journey's OTA was set up (its connection waits `pending_verification`) | A whole run of the four projects uses twelve of the twenty offices of the platform's `dev:seed` (the demo OTA's and one per journey's OTA, PFE-019's `console-sso` and OAD-017's `settings-effects` and `roles` included; the nightly `storefront-stripe` run, a stack of its own, takes one for OAD-017's `payments`); each journey that adds an OTA of its own with an office takes one more, and when they outgrow the pool, it grows in `DEV_SEED_OFFICE_IDS` (`platform/backend/src/dev/dev-seed.command.ts`; twenty since the lead's decision (2f) of 2026-10-30) |
| `Project(s) "storefront-stripe" not found` | The project exists only with `E2E_STRIPE=1` and `E2E_WITH_OTA=1` | Both, and the Stripe values of [Settings](#settings) |
| `checkout-stripe.e2e.ts pays in Stripe's test mode: run it with …` | `E2E_STRIPE=1` without the OTA's keys | Add `STRIPE_SECRET_KEY_TEST` and `STRIPE_PUBLISHABLE_KEY_TEST` (test mode) |
| `stripe listen could not start: the Stripe CLI was not found …` / `exited … before it was ready` | No Stripe CLI, or a key Stripe refuses (the log shows the CLI's redacted output) | Install the Stripe CLI 1.x or set `E2E_STRIPE_CLI`; check the test key |
| `port 4173 (storefront) is in use` | `pnpm --filter @velexis/ota-frontend preview`, or another run | Stop it; one run at a time per machine |
| `node ota/backend/dist/cli.js dev:seed exited with code 1` | The demo OTA could not be seeded; the message shows `test-results/stack/ota-dev-seed.log` (stderr only: the seeds' stdout, with the keys, is never kept) | Usually a missing `pnpm dev:keys` (the pepper file) or a build of the OTA backend older than its migrations |
