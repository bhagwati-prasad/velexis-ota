# ADR-0028: How work reaches main

**Status:** Accepted
**Date:** 2026-11-15
**Deciders:** The product owner, who approved the lead's decisions (23i), (23j), (23k), (23l), (24d), (24f) and (24g) on 2026-11-15 (recorded by FIX-W54-DOCS and FIX-W55-DOCS)
**Revisions:** 2026-11-16 (lead decision (25d) of 2026-11-16, approved by the owner; FIX-W56-PLAN): new item 7, how the integration branch takes in what landed on `main` once `main` is the default branch; the follow-ups and [conventions §11](../conventions.md#11-git-workflow) say the same. 2026-11-19 (lead decision (31j) of 2026-11-19, approved by the owner; FIX-W62-DOCS): item 4's protection also requires branches to be up to date before merging (dated note under item 4). 2026-11-20 (lead decisions (32b) and (32c) of 2026-11-20, approved by the owner; FIX-W63-DOCS): item 4's protection of `main` is set before the first merge and binds the developer too, and the integration branch gets a ruleset of its own that requires the checks without a pull request and keeps the developer's admin bypass (dated note under item 4). 2026-11-20 (lead decision (33h) of 2026-11-20, approved by the owner; FIX-W64-DOCS): item 4's note of the same day corrected in a second dated note under item 4: the reason for the integration branch's admin bypass (a pushed commit has no check results until after the push; the claim about `workflow_dispatch` checks is withdrawn), whom **Restrict deletions** and **Block force pushes** bind, the default-branch switch, **Ready for review** on the draft pull request into `main`, and what happens when GitHub refuses an integrator push. 2026-11-20 (lead decisions (34c) and (34f) of 2026-11-20, approved by the owner; FIX-W65-DOCS): item 4's second note of the same day corrected in a third dated note under item 4: the fallback when GitHub refuses an integrator push (the developer checks the bypass list's Repository admin entry; adding their own user is withdrawn, since GitHub's **Add bypass** dialog offers roles, teams and apps, not individual users) and the exact clicks of item 1's merge commit.

## Context

[ADR-0020](0020-ai-agent-development-workflow.md) (2026-10-12) chose one task per branch and pull request, each squash-merged into `main` by the developer, with `main` protected by green CI, **one approval**, **squash merging only** and **linear history**.

The work did not reach `main` that way. Tasks are handed out in **waves**: each task is done on its own branch `task/<ID>-<slug>`, reviewed (by a second agent where the [runbook](../runbooks/second-agent-review.md) asks for one), and squash-merged by the wave's integrator into the **integration branch** `claude/intelligent-bardeen-90hhu7`, one commit per task with its `Task:` footer. `main` has not received that branch yet.

Three facts make ADR-0020's merging and approval rules unworkable for that branch and for later waves:

- **One developer.** The developer is the only person with write access, and GitHub does not let a pull request's author approve it, so a required approval blocks every merge.
- **History matters.** Precondition P21 of the airline-card go-live ([`airline-card-go-live.md`](../../../ota/docs/runbooks/airline-card-go-live.md) §2) checks with `git merge-base --is-ancestor` that a release contains a given task commit. A squash (or a rebase) of the integration branch would replace every task commit with new ones, and the check would fail.
- **PCI change control.** Every change to the cardholder data environment needs a review record by someone other than its author (PCI DSS 6.2.3, 6.2.3.1, 6.5.1; [ADR-0027](0027-pci-scope-and-vm-controls.md)). The changes are written by agents.

ADR-0020's revision of 2026-11-15 (FIX-W54-DOCS) recorded decisions (23i) to (23k) in place. They replace what ADR-0020 chose rather than refine it, so they belong in an ADR of their own that supersedes those points ([ADR-0001](0001-record-architecture-decisions.md) item 4), together with (24d) and (24f) of the same day (lead decision (24g)).

## Decision

This ADR replaces ADR-0020's points on **merging** (squash merge, linear history) and on **approvals** (one approval). The rest of ADR-0020 stands.

1. **The first merge (23i).** The integration branch `claude/intelligent-bardeen-90hhu7` is merged into `main` once, with a **merge commit, never a squash or a rebase**, so every task commit with its `Task:` footer stays in `main`'s history.
2. **The developer's deep review comes first (23l).** Before that merge the developer does a deep review of X-037, X-038, X-039 and X-041 (SSH second factor, off-VM logs and their review, the WAF, the outbound allow-list). The recorded agent reviews do not replace it.
3. **`main` becomes the default branch, and later waves reach it as one pull request each (23j).** After the first merge `main` is the repository's default branch, so the nightly E2E schedule and Dependabot run on it. In every later wave each task keeps its own branch, which the integrator squash-merges into the integration branch with its `Task:` footer; the integration branch reaches `main` as **one pull request per wave**, which the developer reviews and merges with a **merge commit**.
4. **A single task's pull request is squash-merged (24f).** A task done outside a wave opens its own pull request from `task/<ID>-<slug>`, which the developer **squash-merges** ([conventions §11](../conventions.md#11-git-workflow)). `main`'s protection therefore allows both merge commits and squash merging, requires no linear history, blocks force pushes and requires the six checks **Plan lint**, **Deploy files**, **Build and test**, **Integration tests**, **VM check test** and **Integration tests on other hosts and ports** ([`tools/ci/README.md`](../../../tools/ci/README.md#human-steps-the-developer)).

   *Note (2026-11-19, lead decision (31j), approved by the owner, FIX-W62-DOCS):* the protection also turns on **Require branches to be up to date before merging**, on `main` and on the integration branch if it is protected too, so that each pull request, a Dependabot one above all, runs CI on the base it merges into: on 2026-11-19 the merges of Dependabot pull requests #47 and #48 broke the lockfile together (repaired by db7d3c3b). Until the protection exists, the developer merges Dependabot pull requests one at a time, each after a CI run on the current base ([`tools/ci/README.md`](../../../tools/ci/README.md#human-steps-the-developer)).

   *Note (2026-11-20, lead decisions (32b) and (32c), approved by the owner; FIX-W63-DOCS):* `main` is protected **before** the first merge (X-019 step 5's order: protect `main`, the developer's deep review of item 2, the merge of item 1, then `main` becomes the default branch), with the developer bound too, since only pull requests reach `main`: a ruleset with an empty bypass list, or a classic branch protection rule with "Do not allow bypassing the above settings". The integration branch `claude/intelligent-bardeen-90hhu7` gets one ruleset of its own, set by the developer, that requires the six checks and up-to-date branches, restricts deletions and blocks force pushes but requires no pull request, with the Repository admin role allowed to bypass it always, because the wave integrator pushes each wave's squash merges to it directly under the developer's account and checks from `workflow_dispatch` runs never satisfy a required check; the bypass is never used to merge a Dependabot pull request, and the ruleset is disabled, not deleted, once `main` is the default branch ([`tools/ci/README.md`](../../../tools/ci/README.md#human-steps-the-developer), "Protect `main`" and "Protect the integration branch").

   *Note (2026-11-20, lead decision (33h), approved by the owner; FIX-W64-DOCS):* corrects the note above. The integration branch's ruleset keeps the Repository admin bypass because each squash commit the integrator pushes has no check results until after the push (`ci.yml` runs on that branch only when dispatched), so a rule that requires the checks refuses the push for anyone not on the bypass list; the claim that checks from `workflow_dispatch` runs never satisfy a required check is withdrawn (it was not verified, and it is not the reason). **Restrict deletions** and **Block force pushes** are ticked explicitly on both branches, not relied on as defaults (in a classic branch protection rule on `main`, **Allow force pushes** and **Allow deletions** stay off); on the integration branch, with the bypass, they bind only actors outside the bypass list, so not the developer or the integrator pushing as the developer (agents still never force-push or delete a branch, [AGENTS.md](../../../AGENTS.md) §4). Switching the default branch is not affected by the integration branch's ruleset, which targets that branch by name; the ruleset is disabled, not deleted, once `main` is the default branch, because from then on Dependabot targets `main`. The integrator's pull request into `main` for item 1's merge is a draft, so the developer clicks **Ready for review** before **Merge pull request** → **Create a merge commit**. A stale Dependabot pull request is refreshed with its **Update branch** button first, or with an `@dependabot rebase` comment when no agent has pushed to it. If GitHub refuses an integrator push after the ruleset exists, the integrator stops and reports it, and the developer adds their own user to the ruleset's bypass list ([`tools/ci/README.md`](../../../tools/ci/README.md#human-steps-the-developer), "Protect `main`", "Protect the integration branch" and "Merge the integration branch into `main` once").

   *Note (2026-11-20, lead decisions (34c) and (34f), approved by the owner; FIX-W65-DOCS):* corrects the note above in two points. (34c) Its fallback, that the developer adds their own user to the ruleset's bypass list, is withdrawn: GitHub's **Add bypass** dialog offers roles, teams and apps, not individual users, and the owner of a personal repository already holds the Repository admin role that the bypass list allows with **Always allow**. If GitHub refuses an integrator push after the ruleset exists, the integrator stops and reports GitHub's exact message, never working around the rule; the developer checks that the bypass list holds Repository admin set to **Always allow** (not **For pull requests only**) and corrects it if not; if it does, the developer sends GitHub's message to the lead, who decides. (34f) For item 1's merge, after **Ready for review** the developer opens the merge button's menu (the arrow beside it; the button may read **Squash and merge**), chooses **Create a merge commit**, clicks **Merge pull request**, then **Confirm merge**; a squash would lose the task commits and break P21's ancestry check (`git merge-base --is-ancestor`) ([`tools/ci/README.md`](../../../tools/ci/README.md#human-steps-the-developer), "Protect the integration branch" and "Merge the integration branch into `main` once", corrected in place).
5. **Approvals and the review record (23k).** `main` requires **0 approvals** while the developer is the only person with write access. The review record of a pull request into `main` is then: the six required checks green, the second-agent review comment where the runbook asks for one (X-036), and the developer's merge. The author (an agent) is never the reviewer (the developer). Once a second person with write access joins, `main` requires **1 approval**, from someone other than the pull request's author.
6. **Who may merge what (24d).** Agents never merge into `main` and never merge a pull request. Only the wave integrator squash-merges task branches into the integration branch. Only the developer merges into `main`: a wave's pull request with a merge commit, a single task's pull request with a squash. Agents never push to `main` ([CLAUDE.md](../../../CLAUDE.md) rule 2, [AGENTS.md](../../../AGENTS.md) §4 item 9).
7. **What landed on `main` reaches the integration branch by a merge (25d, 2026-11-16).** Once `main` is the default branch, pull requests can land on `main` between waves, for example Dependabot's, which the developer **squash-merges** on `main`. At the start of a wave the integrator takes them in by merging `main` into the integration branch **with a merge commit, never by a rebase**, so the task commits and their `Task:` footers keep their hashes and stay reachable for P21's ancestry check.

## Consequences

### Positive

- **P21's ancestry check works as written:** every task commit stays reachable from `main` and from the releases built from it.
- **The PCI change-control record is explicit.** A wave pull request's review record is the six required checks, the second-agent review comment where the runbook asks for one, and the developer's merge, and the author is never the reviewer. The PCI pack says so for 6.2.3, 6.2.3.1 and 6.5.1 ([`responsibility-matrix.md`](../../../ota/docs/pci/responsibility-matrix.md) row 6, [`data-flow.md`](../../../ota/docs/pci/data-flow.md) §3, [`script-inventory.md`](../../../ota/docs/pci/script-inventory.md) §3, the 6.2.3.1 row of the [pack's calendar](../../../ota/docs/pci/README.md#3-calendar)).
- **The pull request template says which merge applies** ([`.github/pull_request_template.md`](../../../.github/pull_request_template.md) line 3): a wave's pull request is merged with a merge commit, a single task's is squash-merged.
- One review per wave instead of one per task keeps the developer's review time where it was planned.

### Negative

- `main`'s history is no longer linear. `git log --first-parent main` shows one commit per wave and per single-task pull request; the task commits are on the second parent.
- A wave's pull request is large. The developer reviews it task by task, through the task commits, the second-agent reviews and the checks.
- With 0 approvals GitHub shows no approval on a merged pull request; the review record lives in the checks, the review comment and the merge, and an assessor is pointed at it by the PCI pack.
- Two merge methods are allowed, so the developer picks the right one for each pull request.

### Follow-ups

- Human steps of X-019 (step 5) and [`tools/ci/README.md`](../../../tools/ci/README.md#human-steps-the-developer): protect `main` as item 4 says, do the deep review of item 2, merge the integration branch once with a merge commit, make `main` the default branch, and record the settings in the pull request.
- When a second person with write access joins, set the required approvals to 1 (item 5).
- From the first wave after `main` becomes the default branch, the integrator merges `main` into the integration branch at the start of each wave (item 7).

## Alternatives considered

- **Squash the integration branch into `main`.** One commit for every task of the branch: the `Task:` footers and the per-task commits leave `main`'s history, and P21's ancestry check fails.
- **Rebase the integration branch onto `main`.** Linear history, but every task commit gets a new hash, so the commits that documents and P21 name are not in `main`.
- **One pull request into `main` per task of a wave** (ADR-0020 as written). Each needs its own CI run and a rebase on the previous one; the wave's integration and its end-to-end run happen once anyway.
- **Keep one required approval.** Impossible while the developer is the only writer: GitHub would block every merge, or every merge would need an administrator bypass, which leaves no better record.
- **Let agents merge when CI passes.** Rejected in ADR-0020 and still rejected: the developer's merge is part of the review record.
