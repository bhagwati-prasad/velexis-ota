# Velexis MVP conventions

This document sets the rules for how code is organised and written in every Velexis component. It covers:

- NestJS backends, Next.js apps, the vanilla storefront and the SDK;
- the error model, logging and redaction, and configuration;
- database migrations, testing, the git workflow, and the security checklist every pull request must pass.

It turns the [ADRs](adr/README.md) into day-to-day practice for the developer and the AI agents ([`AGENTS.md`](../../AGENTS.md)). When a rule here conflicts with [`decisions.md`](decisions.md) or an ADR, those win, and this file is fixed.

Related: [`architecture.md`](architecture.md), [`tech-stack.md`](tech-stack.md).

## 1. General

- **TypeScript strict** everywhere (`strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`). No `any` without an `// eslint-disable-next-line` comment that says why. The SDK and the storefront use JSDoc with `checkJs` (SDK) or plain JS (storefront).
- **Names:**
  - files `kebab-case.ts`;
  - classes `PascalCase`;
  - functions and variables `camelCase`;
  - constants `SCREAMING_SNAKE_CASE`;
  - database `snake_case`;
  - JSON `camelCase`.
- **Ids** are prefixed ULIDs (`bkg_…`, `ten_…`) generated by the application (db README §2.1). Never expose database sequence numbers.
- **Money** is `{ amount: "123.45", currency: "EUR" }`, a decimal string, with `decimal.js` arithmetic. Never `number`.
- **Time** is UTC `timestamptz` in the database and ISO 8601 with `Z` in the API. Local times appear only in views (`Intl.DateTimeFormat` with the tenant's or the airport's time zone).
- **Imports:** respect the dependency rules of [ADR-0002](adr/0002-monorepo-pnpm-turborepo.md) (`platform/*` ↛ `ota/*`, packages ↛ apps). Use workspace package names, never relative paths into another package.
- **No `process.env`** outside `@velexis/config` (ESLint `n/no-process-env`).
- **No dead code or commented-out code** in merged PRs. Use `TODO(<TASK-ID>)` only with a task id that exists in a plan.

## 2. NestJS backends

### Layout: one module per bounded context

```
<group>/backend/
  openapi/                 the API document (source of truth)
  migrations/              SQL migrations owned by this backend
  src/
    main.ts                HTTP entry point
    worker.ts              BullMQ workers and schedulers entry point
    app.module.ts          API module graph
    worker.module.ts       worker module graph
    common/                guards, interceptors, filters, decorators, Clock
    <context>/             one folder per bounded context (below)
    health/
  test/
    integration/<context>/*.int.test.ts
    contract/*.contract.test.ts
```

Suggested contexts (the component plans fix the final list):

| Backend | Contexts |
|---|---|
| Platform | `accounts` (sign-up, sign-in, MFA, sessions), `tenants` (create, memberships, invitations), `provisioning` (jobs, reconciler, tenant-events consumer), `billing` (plans, Stripe Billing, webhooks, invoices, settlements), `api-keys`, `domains` (verification, TLS `ask`), `connections` (Amadeus accounts and offices, payment providers), `reference` (loaders), `admin`, `audit`, `notifications` |
| OTA | `tenancy` (key, edge and service-credential resolution, tenant context), `identity` (customer auth, staff auth), `account`, `storefront`, `reference`, `shopping` (search, offers, upsell, pricing, availability), `checkout`, `payments` (gateways, webhooks), `bookings`, `console`, `amadeus` (client), `notifications`, `documents`, `settings` (markups, fees, storefront settings, templates), `provisioning` (`ota-tenant-ops` consumer, migration fan-out), `jobs` (schedulers) |

Inside a context:

```
bookings/
  bookings.module.ts
  bookings.controller.ts     HTTP only
  bookings.service.ts        application service (use cases)
  bookings.repository.ts     Kysely queries
  bookings.mapper.ts         rows <-> API schemas
  bookings.service.test.ts   unit tests
```

### Rules

- **Controllers are thin.** They bind the route to its OpenAPI operation with `@OpenApiOperation("listBookings")`, read the validated input, call **one** service method and return its result. No queries, no business rules, no `try/catch` for flow control.
- **Application services** own the use case and the transaction boundary:
  - open `tenantTx` or a platform transaction;
  - call repositories and gateways;
  - write audit and outbox rows in the same transaction;
  - enqueue jobs **after** commit.
  - Services never use `Request` or `Response` objects.
- **Repositories** take the transaction as their first argument, use Kysely only, return plain objects, and never open transactions. Tenant repositories never schema-qualify tables.
- **Types:** request and response bodies use the generated types (`components["schemas"]["Booking"]`, `paths[…]`) from `@velexis/api-types`. No hand-written DTO classes. Internal domain types live in `<context>.types.ts` when needed.
- **Validation:** the global OpenAPI validation interceptor (Ajv) has already validated path, query, headers and body before the controller runs ([ADR-0006](adr/0006-contract-first-openapi.md)). Business validation happens in services and throws `AppError`.
- **Authorisation:**
  - guards resolve the caller (key, edge, service credential, customer, staff or portal token) and check `x-scope`;
  - services check resource ownership (a customer's own booking) and staff permissions (`bookings:issue`).
- **Idempotency:** state-changing POSTs that call Amadeus or Stripe require `Idempotency-Key`. A shared interceptor stores and replays responses (`idempotency_keys` in the tenant, Redis for 24 h on the platform).
- **External calls** (Amadeus, Stripe, SMTP) happen only in infrastructure modules (`amadeus/`, `payments/` gateways, `notifications/`). Long external calls are never made while a database transaction is open, except the order-creation step that must be atomic with its record, as the contract describes.
- **Jobs:** processors live in the context that owns the work (`bookings/booking-sync.processor.ts`). Payloads are ids only ([ADR-0009](adr/0009-background-jobs-bullmq.md)). Processors are idempotent.
- **Time and randomness:** inject `Clock` and the id generator, so tests are deterministic.

## 3. Next.js apps (portal, platform admin, OTA admin)

```
<app>/src/
  app/
    (auth)/sign-in/page.tsx        route groups by area
    (app)/layout.tsx               signed-in shell
    (app)/bookings/page.tsx        server component: fetch + render
    (app)/bookings/[id]/actions.ts server actions ("use server")
    (app)/bookings/[id]/*-form.tsx client components ("use client") for interactivity only
    api/…/route.ts                 route handlers only where a URL is needed (SSO POST, file download)
  components/ui/                   shadcn/ui copies
  components/                      app components
  lib/api.ts                       API client, import "server-only"
  lib/session.ts                   cookie read/write, refresh, import "server-only"
  lib/errors.ts                    API error code -> user message
  middleware.ts                    auth redirects, token refresh
```

- **Server components by default.** Data is fetched on the server, through `lib/api.ts` (portal and platform admin) or the SDK (OTA admin).
- **Mutations are server actions.** They:
  - validate with Zod;
  - call the API;
  - map `fieldErrors` back to the form;
  - return a serialisable state for `useActionState`;
  - call `revalidatePath` or `redirect`.
- **No tokens in browser JS.** Tokens are only in `__Host-` httpOnly cookies set on the server. No `NEXT_PUBLIC_` variable holds a key, token or secret. Client components never import `lib/api.ts` or `lib/session.ts` (`server-only` enforces it).
- Pages that show personal or priced data use `cache: "no-store"` (the default in our client).
- Errors: `error.tsx` per area. Messages come from `lib/errors.ts`, keyed by error code, never from raw stack traces.
- UI: shadcn/ui components, Tailwind utility classes, design tokens in `app/globals.css` (`@theme`). Every form field has a visible label, and errors are linked with `aria-describedby`.

## 4. Vanilla storefront (`ota/frontend`)

```
ota/frontend/
  index.html, search.html, offer.html, checkout.html, confirmation.html,
  bookings.html, booking.html, lookup.html, account/*.html   one HTML file per page
  src/
    pages/<page>.js          one entry module per page (imported by its HTML file)
    lib/client.js            the single SDK client in cookie mode
    lib/dom.js               tiny helpers: $, render(template, data), on()
    lib/format.js            money, dates, durations with Intl
    lib/forms.js             form serialisation, field errors, submit state
    lib/i18n.js              UI strings (English in the MVP)
    styles/main.css          @import "tailwindcss"; @theme tokens; CSS variables for OTA branding
  vite.config.js             multi-page build (rollupOptions.input lists every HTML file)
```

- **ES modules, no framework, no global state library.** Each page module:
  - loads `storefront.get` once (cached in `sessionStorage` for 5 minutes);
  - applies branding;
  - renders with `<template>` elements cloned and filled with `textContent`.
- **Never use `innerHTML`** with data. ESLint `no-unsanitized` enforces it.
- **Progressive enhancement:**
  - the search form is a real `<form method="get" action="/search.html">`;
  - links are real links;
  - the base HTML is meaningful without JavaScript, and a `<noscript>` notice explains that booking needs JavaScript.
- **No inline scripts or styles**, so the CSP holds ([ADR-0018](adr/0018-hosted-storefront-custom-domains.md)). No third-party scripts except Stripe.js, and only on the payment step.
- **All booking functionality goes through the SDK** (`lib/client.js`). Never `fetch` the API directly.
- Errors are shown from `VelexisError.code` through `lib/i18n.js`. `PRICE_CHANGED` and `SOLD_OUT` have dedicated UI states.
- **Accessibility:** WCAG 2.2 AA for the booking flow, keyboard-only checkout, focus moved to error summaries.

## 5. SDK (`ota/sdk`)

- One file per contract module (`identity.js`, `flights.js`, `bookings.js`, `console.js`), mirroring `docs/velexis-sdk/sdk/src/*.d.ts` ([ADR-0019](adr/0019-vanilla-js-sdk-jsdoc.md)).
- **One method per OpenAPI operation**, named exactly by `x-sdk-method`, with JSDoc that has:
  - a one-line summary;
  - `@param` with types from `@velexis/api-types`;
  - `@returns`;
  - `@throws` naming the error classes and codes.
- **No dependencies, no Node-only APIs, no top-level side effects.**
- Every new operation in the OpenAPI document gets its SDK method in the same PR, or a task to add it.

## 6. Error model

- **One envelope** for both APIs, as in the OTA document: `{ "error": { "code", "message", "status", "requestId", "details", "fieldErrors", "supplier" } }`.
- **Codes come from the document's `x-error-catalogue`.** `@velexis/errors` is generated from it, so `new AppError("PRICE_CHANGED", { details })` only compiles with a listed code, and the HTTP status comes from the catalogue. A new code is added to the document first.
- `VALIDATION_FAILED` carries `fieldErrors: [{ path, code, message }]` (the document's `FieldError` schema: `path` is a JSON pointer into the request). Messages never echo the rejected value (it may be a card number or a password).
- **Unknown exceptions** become `500 INTERNAL_ERROR` with a generic message and the `requestId`. The stack is logged, never returned.
- **Supplier errors** are mapped inside the Amadeus client to `SUPPLIER_*`, `SOLD_OUT`, `PRICE_CHANGED`, `TRAVELER_DATA_INVALID` and similar codes. The raw `supplier` issue appears only in console scope.
- The platform API reuses the generic codes (`VALIDATION_FAILED`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `RATE_LIMITED`, `INTERNAL_ERROR`) and adds its own in its own catalogue.
- Clients (Next.js apps, the storefront) map codes to user-facing text. They do not parse messages.

## 7. Logging and redaction

- Use the injected pino logger (`PinoLogger` in NestJS, `@velexis/logger` elsewhere). **Never `console.*`** in committed code (ESLint `no-console`).
- **Event-style messages with fields:** `logger.info({ bookingId, status }, "booking.created")`. The `requestId`, `tenantId` and actor come from the context automatically.
- Levels:
  - `error`: needs attention;
  - `warn`: unexpected but handled;
  - `info`: business events and one line per request;
  - `debug`: development only.
- **Never log** request or response bodies, headers carrying credentials, tokens, passwords, card data, document numbers or decrypted secrets. The central redaction list in `@velexis/logger` ([ADR-0016](adr/0016-observability.md)) is a safety net, not a licence.
- **Adding a field that holds a secret** means adding its path to the redaction list and to the redaction unit test in the same PR.
- **Persisted copies** of payloads (`supplier_requests`, `order_snapshot`, `staff_actions`, `idempotency_keys.response_body`, `payment_events.payload`, `notifications.payload`) always pass through the shared redactor ([db README §8](../velexis-sdk/db/README.md)).

## 8. Configuration

- Each app declares its configuration schema in `src/config.ts` with `@velexis/config` (typed, validated at start-up, with unit tests).
- **Secrets come from files or the environment, never from code.** Every new variable is added to the root `.env.example` (dummy value), to the app's env template in `deploy/env/`, and to the [configuration matrix](architecture.md#6-configuration-matrix), in the same PR. The PR lists it as a human step ("add to `/etc/velexis/<app>.env` before the next deploy"), because `velexis-deploy` refuses a release whose templates name a variable the VM lacks.
- Defaults are allowed only when they are safe in production (timeouts, page sizes). URLs, credentials and feature switches that widen access (`AIRLINE_CARD_ENABLED`) have no default except `false`.
- Hosts are always the placeholders of [`decisions.md`](decisions.md) §4 in docs, fixtures and examples. Any other example host uses a reserved name (RFC 2606: `example.net`, `*.example`, `*.test`), never a real registered domain; an OTA's custom domain is `travel.example.net`.

## 9. Database migrations

- **Files:** `NNNN_verb_object.sql` (four digits, next free number in the set), starting with:
  ```sql
  -- velexis:phase expand
  -- <one-line description>
  ```
  Optionally add `-- velexis:no-transaction` for `CREATE INDEX CONCURRENTLY`.
- **A merged migration is never edited.** Checksums make an edit fail the runner. Fix forward with a new file.
- **Tenant migrations** (`ota/backend/migrations/tenant/`) are unqualified, never set `search_path`, never mention another schema except `reference` by value (no cross-schema foreign keys), and must run on an empty and on a populated schema.
- **Platform and reference migrations** are schema-qualified. A new platform table or column that the OTA backend must read includes `GRANT SELECT … TO velexis_ota_app` in the same migration ([ADR-0004](adr/0004-postgresql-schema-per-tenant.md)).
- **Expand / migrate / contract:**
  - *Expand*: add nullable columns, tables and indexes (`CONCURRENTLY` on large tables). Extend CHECK lists by adding the new constraint `NOT VALID`, then `VALIDATE CONSTRAINT`.
  - *Migrate*: code writes both shapes. Backfills of tenant data run as batched jobs per tenant, **not** inside the migration.
  - *Contract*: drop old columns or constraints in a **later release**, once every tenant reports the version.
  - Code must work with schema versions N-1 and N, because tenant fan-out runs while the old code is still serving.
- **Statuses** are `text` + CHECK, never PostgreSQL enums. Every new table and column gets a `COMMENT ON`, matching the dictionary style of the reference DDL.
- **Deploy order:** platform and reference migrations, then tenant fan-out (4 schemas at a time), then restart the apps ([ADR-0007](adr/0007-single-vm-without-docker.md)). The fan-out continues past a failed schema and halts if more than 10 % fail.
- **Every migration PR:**
  - runs `pnpm db:migrate` and `pnpm db:migrate:tenants` from scratch and from the previous version;
  - commits the regenerated types (`pnpm db:codegen`);
  - adds or updates an integration test that uses the change.

## 10. Testing

The strategy and the tools are in [ADR-0015](adr/0015-testing-strategy.md). The rules:

| Level | Location and naming | Must cover |
|---|---|---|
| Unit | `src/**/<name>.test.ts` next to the code | Pure logic, mappers, pricing, redaction, guards' decisions |
| Integration | `test/integration/<context>/<name>.int.test.ts` | Every endpoint: success, validation error, auth failure, tenant isolation, main business errors; response validated against the OpenAPI document |
| Contract | `test/contract/<name>.contract.test.ts` | Route parity, generated types up to date, SDK declarations against the contract |
| UI | `<component>.test.tsx` / `<module>.test.js` | Form states, error rendering |
| End-to-end | `tools/e2e/specs/<journey>.e2e.ts` | One journey per milestone's main flow |

- **Test names** say behaviour: `it("rejects a staff token of another tenant")`. When a test proves a plan acceptance criterion, it ends with the task id and criterion number: `… [OBE-014 AC2]`.
- **Arrange data with builders** (`test/builders/*.ts`), not shared fixtures that tests mutate.
- **Never weaken a test** to make it pass, and never leave `.only` or a new `.skip` ([AGENTS.md](../../AGENTS.md)).
- **Bug fixes** start with a failing test.

## 11. Git workflow

- **Branches:** `task/<TASK-ID>-<short-slug>` for plan tasks (`task/OBE-014-api-key-guard`). For work outside the plans: `fix/<slug>`, `docs/<slug>`, `chore/<slug>`. Branch from the latest `main`. Rebase, never merge `main` into a branch.
- **Commits:** Conventional Commits.
  - `<type>(<scope>): <imperative summary>`, at most 72 characters.
  - Types: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`.
  - Scopes: `platform-backend`, `platform-frontend`, `platform-admin`, `ota-backend`, `ota-frontend`, `ota-admin`, `ota-sdk`, `config`, `logger`, `db`, `crypto`, `errors`, `api-types`, `testing`, `reference-data`, `amadeus-stub`, `e2e`, `deploy`, `ci`, `tools`, `docs`, `plans`.
  - Footer `Task: <TASK-ID>`.
- **One task = one PR.** Title `<type>(<scope>): <title> [<TASK-ID>]`. The PR is squash-merged by the developer after CI is green ([ADR-0020](adr/0020-ai-agent-development-workflow.md)).
- **PR template** (`.github/pull_request_template.md`, created in M0):
  1. **Task:** id and link to the plan entry.
  2. **Summary:** what changed and why, in 3–6 lines.
  3. **Acceptance → tests:** a table mapping each acceptance criterion to the test that proves it.
  4. **Contract changes:** OpenAPI operations or schemas changed, types regenerated (yes or no).
  5. **Migrations:** files, phase, tested from scratch and as an upgrade.
  6. **Docs and ADRs:** files updated, plan status updated.
  7. **Security checklist** (§12): every item ticked or marked n/a.
  8. **Screenshots** for UI changes.
  9. **Questions or follow-ups:** new tasks proposed.

## 12. Security checklist (every PR)

- [ ] No secrets, keys, tokens or real personal data committed. `.env.example` has dummy values only.
- [ ] No card data, passwords, tokens, document numbers or decrypted secrets are logged, queued or persisted outside the allowed ciphertext columns. Persisted payload copies go through the redactor.
- [ ] Tenant data is accessed only through `tenantTx`. No schema-qualified tenant SQL. New tenant repositories have an isolation test. Tenant-bound tokens are checked against the resolved tenant (`tid`).
- [ ] Every new endpoint has the right guard and `x-scope`. Console endpoints check permissions, and customer endpoints check ownership.
- [ ] Input is validated by the OpenAPI schema. SQL uses bound parameters only. The storefront never uses `innerHTML` with data.
- [ ] Cookies are `HttpOnly`, `Secure`, `SameSite`, `__Host-` prefixed. Storefront state changes require the CSRF header. Next.js route handlers that change state check `Origin`.
- [ ] State-changing calls to Amadeus or Stripe are idempotent (`Idempotency-Key`). Webhooks verify signatures on the raw body and de-duplicate by event id.
- [ ] Authentication, search and payment endpoints are rate limited.
- [ ] Errors do not leak stack traces, SQL or raw supplier errors to customers.
- [ ] New dependencies are justified in the PR and `pnpm audit` shows no high or critical issue.
- [ ] Changes touching the airline-card path or the storefront payment page were checked against the PCI controls of [ADR-0011](adr/0011-payments-stripe-and-airline-card.md), including the payment-page script inventory.
