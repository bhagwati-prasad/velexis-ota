# OTA backend (`@velexis/ota-backend`)

This is the NestJS 11 data-plane backend of Velexis: the OTA booking API used by the hosted storefront (through Caddy's same-origin `/api` proxy), by the OTA admin (server side) and by third-party frontends with API keys, the Stripe payment webhook receivers, and a worker process for provisioning, tenant migrations, ticketing, booking sync and reconciliation, notifications, documents and housekeeping. This page is the component specification: folder and module tree, environment variables, processes and workers, commands, the Amadeus stub, the OpenAPI document and tests. Design and decisions are in [`../docs/`](../docs/README.md); start with [`../docs/architecture.md`](../docs/architecture.md).

Related: [`../docs/scope.md`](../docs/scope.md), [`../docs/api-changes.md`](../docs/api-changes.md), [`../docs/data-model.md`](../docs/data-model.md), [`.env.example`](.env.example), [MVP tech stack](../../docs/mvp/tech-stack.md#ota-backend-otabackend-velexisota-backend), [conventions](../../docs/mvp/conventions.md#2-nestjs-backends), [local development](../../docs/mvp/local-development.md).

## 1. At a glance

| Item | Value |
|---|---|
| Runtime | Node.js 22, TypeScript 5.6 strict, CommonJS output |
| Framework | NestJS 11 (Express 5), `nestjs-pino`, `nestjs-cls`, `@nestjs/bullmq`, `@nestjs/throttler`, `helmet`, `cookie-parser` |
| Data | Tenant schemas `tenant_<key>` (DML, role `velexis_ota_app`), `reference` (read), selected `platform` tables (read-only, cached), through `@velexis/db` (Kysely) |

| Health ([ADR-0016](../../docs/mvp/adr/0016-observability.md)) | `GET /health/live` → `200 {"status":"ok"}`; `GET /health/ready` → `200` or `503` with `{"status":"ok"\|"unavailable","checks":{"postgres":…,"redis":…}}` (`ok`, `down` or `timeout` each, at most 2 s); on the API port and on the worker's health port, never cached, never logged |
| Public hosts | `https://api.ota.example.com` and `/api/*` on every storefront host (`<key>.ota.example.com`, verified custom domains); `/internal/*` and `/health/ready` blocked publicly |
| Contract | `openapi/velexis-ota-booking-api.openapi.yaml` (copied in M0 by X-006, extended per [`../docs/api-changes.md`](../docs/api-changes.md)) |
| systemd units | `velexis-ota-api.service`, `velexis-ota-worker.service` ([ADR-0007](../../docs/mvp/adr/0007-single-vm-without-docker.md)); env files `/etc/velexis/ota-backend.env` (both) and `/etc/velexis/ota-worker.env` (worker only, provisioner DSN) |

Each module follows [`conventions.md` §2](../../docs/mvp/conventions.md#layout-one-module-per-bounded-context): thin controllers bound to an `operationId`, services owning transactions, Kysely repositories that take the transaction first, gateways for external calls, processors for jobs. Responsibilities and dependencies are in [`../docs/architecture.md`](../docs/architecture.md) §2.

**The HTTP pipeline** (`src/common/http/`, OBE-010; [architecture §3](../docs/architecture.md#3-request-pipeline), [ADR-0006](../../docs/mvp/adr/0006-contract-first-openapi.md)). `HttpModule.forRoot` in the API's graph, after the request context of `app.module.ts` (pino-http sets and returns `X-Request-Id`, nestjs-cls starts the context with it):

- **Middleware**: helmet (a JSON API's headers, aligned with Caddy's `security_headers`), cookie-parser, then the body parsers of `body-parsers.ts`: the raw bytes (a `Buffer`, 512 KB) on `/webhooks/*`, JSON up to 256 KB elsewhere, and the per-operation limits of `JSON_BODY_LIMITS` in `main.ts` (the 10 KB of the airline-card route, OBE-051), matched case-insensitively and with an optional trailing slash like Express' routes. Nest's own parsers are off. Malformed JSON, a body over its limit or an unsupported encoding answer `400 INVALID_REQUEST` with `details.reason` (`malformed_json`, `body_too_large` with `limitBytes`, `unsupported_encoding`, `body_incomplete`), never with the parser's message, which may quote the body.
- **`@OpenApiOperation("getStorefront")`** binds a handler to its operation. At start-up `loadOpenApiDocument()` parses `openapi/velexis-ota-booking-api.openapi.yaml` (in the release folder too) and compiles, for every operation, one Ajv 2020 validator per parameter location and one for the JSON body (about 1 s, once per process). The global `OpenApiValidationInterceptor` validates each bound request: path, query, header and cookie parameters (strings coerced to the schema's integer, number or boolean; arrays split on commas unless `explode`), then the body. Failures answer `400 VALIDATION_FAILED` with at most 50 `fieldErrors` `{ path, code, message }`: `path` is `/path/<name>`, `/query/<name>`, `/header/<Name>` or `/cookie/<name>` for parameters and a JSON pointer into the body for the body (`/travelers/0/dateOfBirth`; `""` for a missing required body), `code` is the Ajv keyword (`required`, `additionalProperties`, `type`, `pattern`, …), and no message carries a rejected value. A body that is not JSON on a JSON operation is `400 INVALID_REQUEST` (`unsupported_media_type`). Handlers read the input with `@OpenApiInput()` (`ValidatedInput<"listBookings">`), or with `@Param()` and `@Query()`, which see the coerced values. Undocumented query parameters are tolerated; nothing is defaulted. A console operation (`x-scope: console`) puts the request in console scope (`RequestContext`); for `both`, the scope guard of a later task decides.
- **`ErrorFilter`** (global): every error in the envelope of `toErrorEnvelope` (`@velexis/errors`) with the request id of `X-Request-Id`, `Cache-Control: no-store`; `supplier` only in console scope; Nest's HTTP exceptions (the router's 404, an undecodable path) by the catalogue code of their status and never their message; anything else `500 INTERNAL_ERROR`, logged with its stack (`http.unhandled_error`), and an `AppError` of status 500 or more logged with its code and cause (`http.request_failed`).
- **Idempotency** (`src/common/http/idempotency.interceptor.ts`, `idempotency.service.ts`, `idempotency.repository.ts`, OBE-014; [architecture-booking §5](../docs/architecture-booking.md#5-idempotency-end-to-end)). `IdempotencyInterceptor` is global, provided after the validation interceptor, so it runs after the guards and after validation (an invalid request writes no record). It applies to every handler bound to an operation whose `Idempotency-Key` header parameter the document marks required, read from the document at start-up; a request without a tenant (only a test probe on a public route) passes through. The record is `idempotency_keys` of the tenant schema, through `TenantTx`, in short transactions of its own around the handler: scope `<environment>:<principal>:<operationId>` with the actor as principal (`cus_…`, `stf_…`, `key_…`), or `edge-` and the first 16 hex characters of the SHA-256 of `__Host-vx_csrf` for a storefront visitor without a session (no cookie: `403 CSRF_TOKEN_INVALID`); `request_hash` the SHA-256 of the canonical `{operationId, path, query, body}` (or of what the operation's `hashInput` hook makes of it), in which card and identity document data count as the shared redactor keeps them (numbers by their last 4, security codes, birth place and issuance location left out), so no hash of a card or document number is stored; a hashed input that still carries a password is refused before anything is hashed or stored (`UnhashableIdempotentInputError`, a `500`: the operation needs a `hashInput` hook that leaves the password out), while tokens stay in the hash. A seen key with another hash is `409 IDEMPOTENCY_KEY_REUSED`; a stored answer is replayed (status, `Location`, `ETag`, `Cache-Control`, `Retry-After`, cookies, body) without running the handler; a key in flight makes the request wait (polling from 100 ms to 1 s, at most 60 s, then `409 CONFLICT` with `details.reason: idempotency_key_in_use`), and a record whose 2-minute lease ran out (its process died) is taken over; a record past its 24 h is replaced. Outcomes: 2xx (`completed`) and final 4xx (`failed`) are kept 24 h; `429` and the 5xx are transient and delete the record, except a `504` that the operation's `resourceOf` hook links to a resource. `response_body` is always the copy after `redactPayload` of `@velexis/logger`; an answer that the redactor changes or that sets a cookie is also kept verbatim (body and `Set-Cookie`) in `response_ciphertext`, envelope-encrypted with the KEKs of `MASTER_KEY_DIR` (associated data `tenant_<key>.idempotency_keys.response_ciphertext:<idk_…>`), and replayed from there. Per-operation hooks come from providers marked `@IdempotencyHooksFor(["completeCheckout", …])`: `hashInput` (OBE-051 hashes the airline card as `{brand, last4}`), `resourceOf` and `resolveReplay` (OBE-043 rebuilds a stored `504` from its booking). Handlers of these operations return their body (`@Res({ passthrough: true })` at most). Failures to store an outcome are logged (`idempotency.settle_failed`) and the answer is sent; replays are logged as `idempotency.replayed`, never with the key or a body.
- **Caller classification** (`src/common/auth/caller.guard.ts`, `src/tenancy/caller-resolver.ts`, `src/tenancy/api-key.verifier.ts`, OBE-011; [OADR-0009](../docs/adr/0009-caller-and-tenant-resolution.md) point 1, [architecture §3.1](../docs/architecture.md#31-callers)). `CallerGuard` is the first guard of every route (`APP_GUARD` in `app.module.ts`), before validation, so a refused request is never validated. In order: `X-Velexis-Edge` together with `X-Api-Key` is `400 INVALID_REQUEST` (`details.reason: edge_with_api_key`); `X-Velexis-Edge` is compared with `VELEXIS_EDGE_SECRET` in constant time before any lookup (wrong: `401 INVALID_API_KEY`, logged as `caller.edge_refused` without the value; right: the **edge** caller, `X-Velexis-Host` required, else `400 INVALID_REQUEST` `edge_host_missing`); an `X-Api-Key` with a `pk_` or `sk_` prefix goes to the **key** verifier; any other `X-Api-Key` (hosting keys, the OTA admin's service key until OBE-060) is `401 INVALID_API_KEY`. Without a credential a route is refused with `401 INVALID_API_KEY` unless its handler or controller is marked `@PublicRoute()` (`/health/live`, later the asset and file downloads) or `@WebhookRoute()` (the Stripe receivers): those get the **anonymous** caller. `@LocalRoute()` (`/health/ready`) is anonymous only on a direct loopback connection (socket peer on loopback, neither `X-Forwarded-For` nor `X-Forwarded-Host`), the test of rule 1.2; through Caddy it needs a credential like any route. The key verifier takes the format of [PADR-0005](../../platform/docs/adr/0005-api-key-format-and-hashing.md) (`pk_`/`sk_`, `test`/`live`, 40 base62 characters; anything else is refused without a lookup), looks the 14-character prefix up in `platform.api_keys` (`PlatformReadRepository.apiKeyByPrefix`, a short read-only transaction as `velexis_ota_app`), compares `HMAC-SHA-256(pepper, key)` with `key_hash` in constant time (`verifyApiKey` of `@velexis/crypto`; the pepper of `API_KEY_PEPPER_FILE` is read once at start-up), and only then refuses a revoked or expired key, a row whose kind, environment or tenant does not fit the key, or scopes that break PADR-0005 item 6: all `401 INVALID_API_KEY`, the reason logged as `caller.api_key_refused` with the key id, never the key. A `pk_` key sent with an `Origin` it does not list (exact, case-insensitive) is `403 ORIGIN_NOT_ALLOWED`; without `Origin` (a server) it is accepted. A failing platform lookup is `503 SERVICE_UNAVAILABLE`. The caller (`{type: "edge", id, host}`, `{type: "key", id, keyId, kind, tenantId, environment, scopes}` or `{type: "anonymous", id}`) is in the request context (`CallerContext`, nestjs-cls) for the tenant guard. The key rows come through the platform cache below (`apikey:<prefix>`); the usage counter is in the guard bullet below.
- **Tenant resolution** (`src/common/auth/tenant.guard.ts`, `src/tenancy/tenant-resolver.ts`, `platform-cache.ts`, `invalidation.subscriber.ts`, `tenant-context.ts`, `tenant-tx.ts`, OBE-012; [OADR-0009](../docs/adr/0009-caller-and-tenant-resolution.md) points 2–5, [architecture §3.1](../docs/architecture.md#31-callers) and [§7](../docs/architecture.md#7-redis-keys)). `TenantGuard` is the second global guard, after `CallerGuard`. On a handler bound to an operation (`@OpenApiOperation`), an **edge** caller's `X-Velexis-Host` resolves as `<key>.<STOREFRONT_BASE_DOMAIN>` (the tenant of the key, whatever its status: anything but `active` is `403 TENANT_SUSPENDED`, so the storefront can show its maintenance page) or as a `tenant_domains` row with `purpose = storefront` and `verification_status = verified` of an **active** tenant; the environment is `tenants.storefront_environment`. A **key** caller gets the key's tenant (active only, else `403 TENANT_SUSPENDED`) and the key's environment. Unknown hosts, pending, failed or other-purpose domains, custom domains of tenants that are not active, and hosts that cannot be host names are `403 HOST_NOT_ALLOWED` (`details.reason: unknown`, nothing about the tenant). Anonymous callers (public, webhook and local routes), routes outside the document (health) and the 501 routes of pending operations are left alone. The result is the request's `TenantContext` (`{tenantId, key, schemaName, environment, caller: {type, id}, actor: {type, id}, requestId}`; the actor starts as `guest` for the edge and `api_key` for a key, and session guards replace it with `setActor`). `TenantTx.run(fn)` is the only way to tenant data: `tenantTx` of `@velexis/db` with the context's schema and a 15 s statement timeout; without a tenant in the context it throws `NoTenantContextError` before any SQL, and `TenantContext.run(tenant, fn)` opens a context for jobs and tests.
  - **`PlatformCache`** is the Redis read-through in front of `PlatformReadRepository`: `tenant:<id>` (the row), `tenantkey:<key>` and `host:<hostname>` (a tenant id, so a `tenant` invalidation reaches every way to a tenant), `apikey:<prefix>` (the row; the key verifier reads it), and `membership`, `connection` and `amadeusAccount` read-throughs for `member:`, `conn:` and `amadeus:acct:` whose loaders and parsers come with their tasks (OBE-017, OBE-059); values must be JSON-safe, ciphertext as text, never decrypted. Entries are `{"v":1,"value":…}` with the builders' TTLs (60 s; a "not found" of `tenantkey:`, `host:` and `apikey:` for 10 s), checked again when read back (an entry that does not parse is a miss and is replaced, `platform_cache.entry_unreadable`). While the command client is reconnecting, lookups go to PostgreSQL and nothing is cached; a failing platform read is `503 SERVICE_UNAVAILABLE`. A fill that started before an invalidation of this process is not written back (or is deleted again), so a lookup that read PostgreSQL before the platform's commit cannot restore the old row after the subscriber deleted it.
  - **`InvalidationSubscriber`** (in every process that fills the cache: the API, and since OBE-024 the worker, whose jobs resolve their tenant through `tenant:<id>`; each process guards its own fills against the invalidations it receives, and deleting a key twice is harmless) has its own connection (`ota-backend-invalidation`), subscribes to `vx:invalidate` on every `ready` (start-up waits for the first attempt, at most 2.5 s, and never fails because of Redis), validates each message with `validateInvalidation` and applies them in order: `tenant` → `tenant:<id>`; `domain` → `host:<hostname>`; `api_key` → `apikey:<prefix>`; `connection` → the four `conn:{amadeus,payment}:<tenantId>:{test,live}`; `membership` → `member:<accountId>:<tenantId>`; `account` → every `member:<accountId>:*` (SCAN of `redisKeyPatterns.membersOfAccount`); `amadeus_account` → `amadeus:acct:<id>`; `plan` → nothing yet (no cache holds plan data; the feature that caches plan rows adds its key). `tenantkey:` is never invalidated (an immutable key → an immutable id). Invalid messages are refused (`invalidation.refused`, warn, with the failing paths and keywords, never the content); applied ones are logged at debug. Messages published while the connection is down are lost; the 60 s TTL bounds the staleness.
- **Amadeus connections, tokens and the client** (`src/amadeus/`, OBE-017 and OBE-018; [OADR-0001](../docs/adr/0001-amadeus-client-design.md) points 2, 4 and 5, [flow](../docs/flows/amadeus-connection-and-tokens.md) §2 and §3). `AmadeusModule` (API; it imports `TenancyModule.forApi()`) loads the KEKs of `MASTER_KEY_DIR` once at start-up (`LocalFileKeyProvider`; a missing current key or a key file others may read stops it) and provides:
  - **`ConnectionResolver.resolve(tenantId, env)`** → `{tenantId, environment, connectionId, credentialSource, credId, clientId, encryptedSecret: {ciphertext, aad}, baseUrl, offices: {queuing, owner, queue, retrieval}, officeIds}`. It reads `platform.supplier_connections` through `conn:amadeus:<tenantId>:<env>` and the referenced `platform.amadeus_accounts` row through `amadeus:acct:<id>` (`PlatformReadRepository.amadeusConnection` and `amadeusAccountById`, cached 60 s, the client secret as base64 ciphertext, never decrypted to be cached). `credential_source = velexis` uses the shared account of that environment (credId `ama_…`, shared by every OTA on it); `tenant` is part of the types and answers 424 until OBE-079. No row, a row or account that is not `active`, an account of another environment or a connection without a usable office id answer `424 SUPPLIER_NOT_CONFIGURED` (the reason only in the error's `cause`). Offices: queuing and owner from the connection, queue and retrieval from its default office, each falling back to the default or queuing office, and only ever an office of the connection's `office_ids` (on the shared account any other office may be another OTA's). The base URL is `AMADEUS_BASE_URL_<ENV>` when set (an https origin, or http on the loopback interface for the stub), else the account's `base_url`, else the official host.
  - **`TokenProvider.getToken(connection)`** → a bearer token for `credId` and the environment: `MGET amadeus:badcred:<credId> amadeus:token:<credId>:<env>`; a cached token is decrypted (`@velexis/crypto`, associated data `redis.amadeus_token.access_token:<the key>`); otherwise one call takes `amadeus:tokenlock:<credId>:<env>` (`SET NX EX 10`, a random owner, released only by its owner), looks at the cache once more and posts `client_credentials` to `<baseUrl>/v1/security/oauth2/token` (the secret decrypted in memory for that request, 10 s timeout, no redirects), then stores the token encrypted with TTL `expires_in − 60 s`. Calls without the lock look for the token every 50 ms for up to 2 s, take the lock if its holder gave it up without a token, and then request a token themselves. A `401` or `400 invalid_client` sets `amadeus:badcred:<credId>` for 5 minutes and answers `424` (logged as `amadeus.credentials_refused`, error, the trigger of the ops alert that comes with the notifications outbox); while it is set, calls answer `424` without a request. Timeouts and resets answer `504 SUPPLIER_TIMEOUT`, other network errors, `429` and `5xx` `503 SUPPLIER_UNAVAILABLE`, anything else `502 SUPPLIER_ERROR`; one `amadeus.token_request` line per request (`amadeusApi: "Authorization"`, status, outcome, duration, never a body). `dropToken(connection, token)` deletes the cached token when it is still that one (the operation-level `401` retry of OBE-018). Without Redis every call is `503 SERVICE_UNAVAILABLE`. A cached token that does not decrypt is a miss (`amadeus.token_unreadable`).
  - **`AmadeusClient`** (OBE-018; [OADR-0001](../docs/adr/0001-amadeus-client-design.md) points 1, 3 and 6–11, [flow](../docs/flows/amadeus-connection-and-tokens.md) §4–§6): one method per operation (`searchFlightOffers`, `getFlightOffers`, `searchFlightAvailabilities`, `upsellAirOffers`, `quoteAirOffers`, `createFlightOrders`, `issueFlightOrder`, `getFlightOrder`, `patchFlightOrder`, `cancelFlightOrder`, `getFlightOrderByReference`, `listQueue`), each `(context, request, options?)` with the request and answer types of `generated/`, over the built-in `fetch`; it answers `{ body, call: { supplierRequestId, officeId, status, durationMs, correlationId, attempts } }` or throws the mapped `AppError`. The call context (`call-context.ts`) is `{tenantId, environment, operation, requestId, staffId?, bookingId?, searchId?, orderOffice?, stubScenario?}`; its tenant must be the tenant of the request or job context (`TenantContext`). Key callers never get a cookie: `Cache-Control: public, max-age=60, stale-while-revalidate=600`, `Vary: Accept-Language, X-Api-Key`. Express's weak `ETag` answers `304` to a matching `If-None-Match`. `CookieWriter` is the only writer of the `__Host-` cookies (`vx_at`, `vx_rt`, `vx_csrf`, `vx_bt`): edge callers only, `Secure; SameSite=Lax; Path=/`, no `Domain`, `HttpOnly` except the CSRF cookie, values restricted to the tokens' characters.

**Flight search** (`src/shopping/`, OBE-021; [flow](../docs/flows/search-and-price.md) §2–§4, [OADR-0002](../docs/adr/0002-offer-and-priced-offer-caching.md), [OADR-0005](../docs/adr/0005-markup-and-fee-engine.md)). `flights.search` (`POST /v1/flight-searches`), `flights.getSearch` (`GET /v1/flight-searches/{searchId}`) and `flights.listResults` (`GET /v1/flight-searches/{searchId}/offers`), for edge and key callers, every answer `Cache-Control: no-store`. `ShoppingModule` imports `AmadeusModule` and `PricingModule`; it is the first module of the API graph that calls Amadeus, so the API now loads the KEKs of `MASTER_KEY_DIR` at start-up.

- **Search** (synchronous only: `resultOptions.async: true` is `403 FEATURE_DISABLED`, `details.feature = "asyncSearch"`): the currency is the body's, else `X-Currency`, else `storefront_settings.default_currency`, and must be a `reference.currencies` code with at most 2 minor units (the `numeric(12,2)` columns), else `400 VALIDATION_FAILED`. `offers.mapper.ts` builds the Amadeus request: SIMPLE becomes the Flight Offers Search GET query (airline lists comma-separated), ADVANCED the POST body. `search_defaults` is read as `{maxResults, nonStop, cabin, sources}`: `maxResults` (1–250, default 250) caps `max` / `maxFlightOffers`, `nonStop` and `cabin` fill a SIMPLE search that omits them, `sources` is intersected with an ADVANCED search's (`403 FEATURE_DISABLED`, `details.feature = "sources"`, when nothing is left); ADVANCED also defaults the three `additionalInformation` flags to `true`, and refuses corporate codes and negotiated fare types in customer scope (`403 SCOPE_NOT_ALLOWED`; no setting enables them yet). SIMPLE refuses more than 9 adults and children, more infants than adults, included and excluded airlines together and a return before the departure (`400`); ADVANCED refuses more than 9 travellers older than two and more infants than adults (`400`, `/query/travelers`), as Amadeus does and as the search row's traveller counts (0–9) require.
- **Single flight**: `t:<tenantId>:<env>:search:<sha256>` (30 s) of the canonical JSON of the Amadeus request, the channel and the customer. The first request sets it (`SET NX`) and runs the search; identical requests meanwhile poll it every 100 ms for up to 30 s and answer with the search id the first one writes there after its commit (that search, with their own first page). The id replaces the first request's own value only (compare-and-set) and keeps the key's expiry: the key never lives longer than 30 s after the first request, so no result outlives it as a cache. A failed search deletes the key (compare-and-delete), and a waiting request then runs the search itself. Without Redis there is no single flight.
- **Storage**: the search row is inserted `pending` (with `expires_at = now + offer_ttl_minutes`) in a short transaction of its own, so the client's `supplier_requests` row links to it; Amadeus is called outside any transaction; a failed call marks the row `failed` with the public error code (`SUPPLIER_TIMEOUT`, `SUPPLIER_ERROR`, …) and the error is answered. Then one transaction loads the rules, prices every offer with the engine (step `search`: markup only), drops offers that cannot be read or priced and SIMPLE offers whose selling price per traveller exceeds `maxPrice`, keeps at most 250, inserts the `flight_offers` rows with their summary columns and `best_score`, and completes the search with the facets, highlights, dictionaries, warnings and one-way combinations (`expires_at` reset to now + TTL). When that transaction fails, the search is marked `failed` (`INTERNAL_ERROR`) as well: no search stays `pending`. An offer cannot be read (it is left out, never stored or answered) without an id, with an itinerary without segments, a local time that does not exist, a traveller pricing without its traveller id and type or a traveller id twice (customer scope could not rewrite its net price inside `amadeus`), or a net total finer than the currency's minor units or too large for `numeric(12,2)`.
- **Summary columns** (`offerColumns`): `max_stops` (connections of the itinerary with the most), `marketing_carriers`, per-itinerary departure and arrival minutes and durations, `main_cabin` (the cabin of the longest segment for the first adult), `min_checked_bags` (the first adult's fewest included bags, weight-only allowances count 1, `NULL` when a segment's is unknown), `refundable`/`changeable` (fare rules REFUND/EXCHANGE decide, else a branded-fare amenity naming a refund or change says yes and one negating it, such as `NON REFUNDABLE TICKET`, says no, else `NULL`), `branded_fares`, `first_departure_local` and `last_arrival_local` (the last segment's arrival, which the `arrival` sorts use, as the column's definition says). `best_score` = 0.6 × price + 0.3 × total duration + 0.1 × stops, each normalised over the search (`facets.ts`).
- **Reads**: a search is readable in its own environment, and a customer's search (the customer of the request's actor) only by that customer and in console scope; anything else is `404`. `getSearch` answers `status: "expired"` after `expires_at` (its operation documents no `410`), `pending` with `Retry-After: 1`, `failed` with the public `error`. `listResults` answers `409 SEARCH_NOT_COMPLETED` for a pending or failed search and `410 SEARCH_EXPIRED` after `expires_at`, filters, sorts (`best`, `price`, `duration`, `departure`, `arrival`, with descending variants; ties by price, then id) and pages (keyset on the sort keys and the id) in SQL (`searches.repository.ts`), with facets computed over the search's summary columns (`facets.ts`: each group ignores its own filter; the time bands of itinerary *i* ignore only its windows). The cursor carries a fingerprint of the search, filters and sort and the sort keys of the page's last row: another fingerprint, or keys that are not values of the sort's columns (a cursor the client changed), is `400 INVALID_REQUEST`.
- **Scope** (`toFlightOffer`): customer scope (the edge and every key without console scope) gets selling amounts only: the markup is folded into `price.base` and the totals and, inside `amadeus` (`view=full`), into `price.base`, `total`, `grandTotal` and the travellers' `price.base`/`total` (largest-remainder shares by net traveller total), Amadeus `margins` removed, no `netPrice` or `markup`. Console scope (`X-Velexis-Scope: console` with a `console:automation` key) gets the verbatim Amadeus offer, `netPrice`, `markup` (rule id and name) and the search's `diagnostics`. Dictionaries come from `reference.*`, completed by the search's Amadeus dictionaries, with country and currency names in the `Accept-Language` language where ICU has them (`ReferenceNames`, as the reference operations); the verbatim Amadeus dictionaries (`dictionaries.amadeus`) are not returned, because the document's `AmadeusDictionaries` requires a `key` property no Amadeus answer has.

**Offers and upsell** (`src/shopping/offers.*.ts`, `src/shopping/upsell.service.ts`, OBE-022; [flow](../docs/flows/search-and-price.md) §2 step 6, [OADR-0002](../docs/adr/0002-offer-and-priced-offer-caching.md) points 1, 3 and 5). `flights.getOffer` (`GET /v1/flight-offers/{offerId}`) and `flights.upsell` (`POST /v1/flight-offers/{offerId}/upsells`, `200`), for edge and key callers, every answer `Cache-Control: no-store`.

- **getOffer** reads `flight_offers` with its search (PostgreSQL only: OADR-0002 keeps no offer data in Redis, whatever the document's "Redis `offer:{id}`" says) and answers the full view with `dictionaries`, by `toFlightOffer` with the scope rules of the search results. Access follows the owning search: its environment, and a customer-bound search only for that customer or console scope; anything else, another tenant's id included, is `404`. After `expires_at` it is `410 OFFER_EXPIRED`. Upsell offers answer `origin: "upsell"` with `baseOfferId` and `upsellId`.
- **upsell**: customer scope needs the storefront feature `brandedFareUpsell` (on unless `features` turns it off; else `403 FEATURE_DISABLED`, `details.feature`); console scope may always call it. The path offer and `combineWithOfferIds` are read as getOffer reads them (`404`, `410`) and must come from one search (`422 OFFER_COMBINATION_INVALID`, also for two offers with one Amadeus id); a card's `offerIds` must name offers of the request (`400`, `/payments/<i>/offerIds/<j>`). The Branded Fares Upsell request carries the stored Amadeus offers verbatim and the card hints (`bin` as the integer `binNumber`, `offerIds` as Amadeus ids, all offers by default). An identical request (jsonb equality of that request in `offer_upsells.amadeus_request`) of an upsell that has not expired answers the stored upsell again (`cached: true`, same ids) without calling Amadeus. Otherwise Amadeus is called outside any transaction (`409 SOLD_OUT` for error 34651, the other supplier errors as for the search; its `supplier_requests` row links to the search, whose console `diagnostics` still name the search's own Flight Offers Search call), and one transaction prices each readable offer of the answer with the engine (step `search`, in the search's channel) and inserts the `offer_upsells` row (`completed`, or `no_upsell` when nothing could be stored) and the `flight_offers` rows (`origin = 'upsell'`, the base offer's `search_id`, no `best_score`, so `listResults` never lists them). Upsell and upsell offers share the search's `expires_at` (OADR-0002 point 3), so they are purged with it.
- **The answer** is built from the stored rows, fresh or cached: the upsell offers in the summary view plus `travelerPricings`, `oneWayUpselledCombinations` for two or more input offers (rebuilt from the flights: an upsell offer replaces the input offer that flies the same segments), and the `comparison`: columns base offer first, then the upsell offers by ascending selling price with the difference to the base; rows `checked_bags`, `refund` and `change` always, `cabin_bag`, `seat_selection`, `meal`, `lounge`, `priority_boarding` and `miles` when an offer's amenities name them, then other amenities by code. A cell is the lead traveller's amenity (`included`, `chargeable`, `not_offered` when it is negated, such as `NON REFUNDABLE`), the bag allowance or known refundability and changeability when they decide, `not_offered` when the offer publishes amenities without it, else `unknown`.

**Priced offers** (`src/shopping/priced-offers.*.ts`, OBE-023; [flow](../docs/flows/search-and-price.md) §2 steps 7–8 and §3, [OADR-0002](../docs/adr/0002-offer-and-priced-offer-caching.md) point 3, [OADR-0005](../docs/adr/0005-markup-and-fee-engine.md) points 5, 7 and 8). `flights.price` (`POST /v1/priced-offers`, `201` with `Location`), `flights.getPricedOffer` (`GET /v1/priced-offers/{pricedOfferId}`), `flights.getAncillaries` (`…/ancillaries`) and `flights.getFareRules` (`…/fare-rules`), for edge and key callers, every answer `Cache-Control: no-store`.

- **price**: `offerIds` (1–6) are read as getOffer reads them (`404`, `410 OFFER_EXPIRED`) and must come from one search with the same travellers and distinct Amadeus ids (`422 OFFER_COMBINATION_INVALID`, `details.offerIds` and `details.reason`: `different_search`, `travelers_mismatch`, `duplicate`). The Flight Offers Price request carries the stored Amadeus offers verbatim, the card hints (`bin` as the integer `binNumber`, `offerIds` as Amadeus ids, all offers by default; another offer is `400`, `/payments/<i>/offerIds/<j>`), the `travelers` (each `id` one of the offers' traveller ids, once; else `400`, `/travelers/<i>/id`) and `fareRules` (default `true`) in `data.additionalInformation`; the query has `include` and `forceClass`. Without `include`: `bags` and `other-services` when the storefront feature `ancillaries` is on (always in console scope), `detailed-fare-rules`, and `credit-card-fees` with `payments`. Raw `amadeusFlightOffers` are refused in customer scope (`403 SCOPE_NOT_ALLOWED`) and not priced yet in console scope (`422 UNPROCESSABLE`, `details.reason: raw_offers_not_supported`); `additionalServices` are priced by checkout.setAncillaries (OBE-037) and refused here (`422 UNPROCESSABLE`, `additional_services_not_supported`). Amadeus is called outside any transaction (`409 SOLD_OUT` for error 34651, the other supplier errors as for the search; its `supplier_requests` row links to the search). An answer that lacks a requested offer, has one twice or prices it in another currency is `502 SUPPLIER_ERROR` and nothing is stored.
- **Money** (OADR-0005): one transaction loads the rules and prices each confirmed offer's markup at step `search` in the search's channel, as its results price was computed (with the same rules, an unchanged net keeps its markup; a rule changed since the search applies), and the `booking_service` and `ticketing` fees once at step `pricing` for the offers together (net totals summed, the carriers, cabins and segments of all of them, the trip type of all itineraries; one offer is exactly the engine's `pricing` step). `priced_offers` gets `net_total` (Σ confirmed `grandTotal`), `taxes_total`, `markup_amount`, `fee_amount` and `selling_total = net + markup + fees`, `markup_rule_id` (the first offer's base rule), the include flags, `force_class`, `last_ticketing_date` (the earliest), `booking_requirements`, `amadeus_request` through `redactPayload` (documents and loyalty or discount numbers masked) and `expires_at = min(now + offer_ttl_minutes, end of the earliest lastTicketingDate in UTC)`. `response` is the Amadeus answer (through the redactor, which changes nothing in offers) plus `velexis`, the snapshot of OADR-0005 point 8: the owner, the include flags, the results total, per offer its confirmed net, markup and markup lines with the rule's name, the fee lines, the `anc_` ids of the embedded catalogue and the later loads. Every answer is rebuilt from the stored row, so a rule change never changes a priced offer, and flights.price answers what getPricedOffer reads.
- **The answer** (PricedOffer): the confirmed offers as FlightOffer (full view, their selling price without the booking's fees), `price` (`base` with the markup folded in, Amadeus taxes and fees plus the service fees, one `service_fee` line per fee rule with its label, spread over the travellers in proportion to their totals; `total = net + markup + fees`), `priceChange` against the results: results prices carry no fees, so `oldPrice` is the results total plus the priced offer's fees and only a supplier change moves it (`price_changed`). With `expectedTotal`, another confirmed total answers `409 PRICE_CHANGED` (`details.oldPrice` = the expected total, `newPrice`, `pricedOfferId`) after the priced offer is stored; the idempotency interceptor replays that answer for the same key. `bookingRequirements` with `off_` ids for 3-D Secure, `creditCardFees` from `included.credit-card-fees`, the embedded `ancillaryCatalogue` (with `bags` or `other-services`) and `fareRules` (with `detailed-fare-rules` or `fareRules` and rules in the answer), `conditions`, `warnings`, and `amadeus` (query, data, included). Customer scope gets the Amadeus offers with their markup folded in as the results do (an answered offer that is not one of the priced offers is left out: its amounts are net) and no `netPrice`, `markup` or option `netPrice`; console scope gets them verbatim with `netPrice` (Σ net), `markup` (amount, base rule and name, `serviceFee`). `selectedAncillaries` is empty until re-pricing with extras exists.
- **Reads**: a priced offer is readable in its own environment; its owner (the customer who priced it, else the customer of its search) only by that customer and console scope; anything else, another tenant's id included, is `404`. After `expires_at` every read is `410 OFFER_EXPIRED`. PostgreSQL only (OADR-0002 point 1, whatever the document's "Redis `prc:{id}`" says).
- **Ancillaries** (customer scope needs the storefront feature `ancillaries`, else `403 FEATURE_DISABLED`): from the pricing answer when it included `bags` and `other-services`, else from an earlier load, else one more Flight Offers Price call (`include=bags,other-services`, the same Amadeus offers) stored in the snapshot with `anc_` ids (an option the pricing answer embedded already, the same `included` entry under the same key or a seat, keeps its id; the others get new ones); the first stored load wins (`jsonb_set … WHERE … IS NULL`), so ids never change once answered. Options: one per `included.bags` entry (`CHECKED_BAGS`, `CABIN_BAGS` for a cabin bag name; `chargeableCheckedBags`/`chargeableCabinBags` item) and per `included.other-services` entry of a known service (`otherServices` item), for the offer that flies its first segment, its travellers and segments within that offer, priced in the priced offer's currency only (no FX; a trailing letter of the amount is dropped); one `SEATS` option per offer and segment where a fare carries `additionalServices.chargeableSeat` or a chargeable `PRE_RESERVED_SEAT` amenity on GDS or NDC (`requiresSeatNumber`, `price: null`; no seat map). Markup rules have no ancillary scope, so the selling price is the Amadeus price; the `ancillary_service` fees come with checkout.setAncillaries (OADR-0005 point 7).
- **Fare rules**: from the pricing answer when it asked for `detailed-fare-rules` with `fareRules`, else from an earlier load, else one more call (`include=detailed-fare-rules`, `fareRules: true`) stored the same way. `categories` per offer and rule of the document's categories, `fareComponents` per detailed note, `raw` (offers with rules, the detailed map), `summary`: per offer the rules decide (REFUND; EXCHANGE, REISSUE, REBOOK, REVALIDATION for changes), else unambiguous detailed notes (`NON-REFUNDABLE`, `CHANGES NOT PERMITTED`, `CHANGES … CHARGE`), else the branded-fare amenities, else unknown; the most restrictive over the offers, with the highest penalty. A reload that finds the fare gone (`SOLD_OUT`) answers `410 OFFER_EXPIRED`.

**Checkout** (`src/checkout/`, OBE-036; [flow](../docs/flows/checkout-stripe.md) §1 and §2 steps 1–2, [data model §4](../docs/data-model.md#4-encrypted-columns), [OADR-0002](../docs/adr/0002-offer-and-priced-offer-caching.md) point 1). `checkout.create` (`POST /v1/checkouts`, `201` with `Location`, `Idempotency-Key` required), `checkout.get` (`GET /v1/checkouts/{checkoutId}`), `checkout.setTravelers`, `checkout.setContacts`, `checkout.setAncillaries` (OBE-037) and `checkout.setRemarks` (`PUT …/travelers`, `…/contacts`, `…/ancillaries`, `…/remarks`), for edge and key callers with an optional customer (cookie or bearer). Every answer is the whole checkout with `ETag: "<version>"` and `Cache-Control: no-store`. No Amadeus call but the extras' re-pricing: `CheckoutModule` reads the stored priced offer through `PricedOffersService.forCheckout` (exported by `ShoppingModule`; customer scope, so a checkout never shows a net amount, in console scope either), PostgreSQL only.

- **create**: a signed-in customer (gone, disabled or deleted: `401 UNAUTHENTICATED`; `403 EMAIL_NOT_VERIFIED` with `require_email_verification`), else a guest when `guest_checkout_enabled` (`401 UNAUTHENTICATED` otherwise); console scope opens a `channel: console` checkout for the priced offer's owner or as a guest checkout. The priced offer must be of the request's environment and, when a customer priced it, that customer's (`404`), and not past its `expires_at` (`410 OFFER_EXPIRED`). One transaction inserts `checkouts` (`open`, `offer_amount = total_amount` = the priced selling total, `expires_at = now + checkout_ttl_minutes`, locale from the body, `Accept-Language` or the storefront), one empty `checkout_travelers` row per traveller of the priced offer and, for a customer with `prefillContactFromAccount` (default true), the primary contact from the profile; the customer's other `open` checkouts of the same priced offer become `abandoned`.
- **Requirements** (`requirements.ts`): the priced offer's `bookingRequirements` (primary e-mail always), per traveller the flagged fields (name always, the date of birth of every type but ADULT), the date-of-birth range of its type over the trip (minimum at the last arrival, maximum at the first departure) and the accepted identity documents (`PASSPORT`, or `PASSPORT` and `IDENTITY_CARD` when every airport is in one country or in the Schengen area, from the airports' countries). `progress.missing` and each traveller's `missingFields` list what is still missing, with paths into the checkout; `paymentReady` waits for the payment steps (OBE-038).
- **Access**: a checkout is read in its own environment only (`404` otherwise, another tenant's id included); a customer's checkout by that customer, in console scope or with a secret key; a guest checkout by anyone holding its `chk_` id with the OTA's credential. `get` answers expired (computed after `expires_at`), abandoned and completed checkouts too.
- **Steps**: the `PUT`s lock the row, answer `409 CHECKOUT_ALREADY_COMPLETED` (`details.bookingId`), `410 CHECKOUT_EXPIRED` (expired or abandoned) and `412 PRECONDITION_FAILED` for a stale `If-Match` (quoted, weak, bare or `*`), replace their part all or nothing and bump `checkouts.version`. `setTravelers` replaces each listed traveller and keeps the others; it checks what is sent, not what is missing (`422 TRAVELER_DATA_INVALID`, codes of TravelerFieldErrorCode, messages without values): known and distinct traveller ids, Latin names of at most 57 characters, a date of birth not after today and in its type's range, a held infant younger than its adult, identity documents of an accepted type that neither expired nor expire before the last flight, complete resident discounts with well-formed numbers, phones, e-mails and codes, no duplicate traveller; a `savedTravelerId` is `SAVED_TRAVELER_NOT_FOUND` (saved travellers are deferred). `setContacts` replaces the contacts: one STANDARD primary contact with an e-mail (the first by default), then the contact flags (`422 CONTACT_DATA_INVALID`). `setRemarks` replaces the special requests (unknown traveller ids `400 VALIDATION_FAILED`); they are stored as entered.
- **Documents at rest** (`traveler-documents.ts`): a traveller's `documents[]` and `discountEligibility[]` are sealed into `documents_ciphertext` and `discount_eligibility_ciphertext` (envelope encryption with the KEKs of `MASTER_KEY_DIR`, associated data `tenant_<key>.checkout_travelers.<column>:<ctr_…>`, `encryption_key_id` the KEK); no other column holds a number. Answers show the document type, `numberMasked` (last 4 characters), the expiry date, the countries and the holder flag, and discount numbers masked the same way; the issue date, place of issue and birth place stay sealed. A document sent back without `number` keeps the stored number of the same type and issuing country (and the sealed fields it omits); none stored is `422` `REQUIRED` at its `number`, and a masked number fails the document's pattern (`400`).
- **Extras** (`ancillaries.service.ts`, OBE-037; [flow](../docs/flows/checkout-stripe.md) §2 step 2, [OADR-0005](../docs/adr/0005-markup-and-fee-engine.md) point 7): `checkout.setAncillaries` (`PUT …/ancillaries`) replaces the extras. The selections must be options of the base priced offer's catalogue (`PricedOffersService.ancillariesForCheckout`: loaded as `flights.getAncillaries` loads it, `403 FEATURE_DISABLED` in customer scope while the feature `ancillaries` is off), by `optionId` or explicitly by `type` (`serviceName`, `seatNumber`, `quantity`, `weight`), for a traveller and segments of the option: otherwise `422 ANCILLARY_NOT_AVAILABLE` (`details.selectionIndex`, `details.reason`); a selection without a kind, a field of another kind or two selections of one Amadeus slot (traveller, segment and bag kind, seat or service) are `400`. Flight Offers Price runs outside any transaction with the base priced offer's confirmed offers, the extras in `fareDetailsBySegment[].additionalServices`, the travellers entered so far and `include=bags,other-services`; 4926 and 32171 on a selection are `422 ANCILLARY_NOT_AVAILABLE` (`rejected_by_airline`, `seat_unavailable`), `409 SOLD_OUT` and the timeouts stay, any other error is `502 SUPPLIER_ERROR`. `selections: []` reverts to the base priced offer without a call (unless it expired) and loads no catalogue (only the feature is checked). One transaction locks the checkout, stores the answer as a child priced offer (`parent_priced_offer_id`; `PricedOffersService.storeServicesPricing`: the flights' amounts only, the base's markup and booking fees kept while Amadeus confirms the flights' net, else the flights priced again) and prices each extra: its net is Amadeus's `price.additionalServices` of its kind shared by catalogue prices, or the catalogue price where Amadeus states none, plus one `ancillary_service` fee line from the engine (in `checkout_ancillaries.price_amount`, the net in `net_amount`, the lines in `details` and the child's snapshot). The totals follow (`offer` = the child's selling total, `ancillaries` = Σ of the extras, the card fee unchanged, `total = offer + ancillaries + cardFee`); a differing `expectedTotal` is `409 PRICE_CHANGED` (`details.oldPrice`, `newPrice`, `pricedOfferId` of the stored child) with the checkout unchanged. The payment of the checkout is not touched here: `checkout.updatePayment` or a new `checkout.createPayment` starts from the new amounts, and `checkout.complete` compares the authorised amount with the total.

**Payments** (`src/payments/`, OBE-038; [flow](../docs/flows/checkout-stripe.md) §2 steps 3–4, [OADR-0010](../docs/adr/0010-stripe-gateway-and-payment-webhooks.md) points 1–3, 7, 8, [ADR-0011](../../docs/mvp/adr/0011-payments-stripe-and-airline-card.md) (A)). `checkout.createPayment` (`POST /v1/checkouts/{checkoutId}/payments`, `201` with `Location`, `Idempotency-Key` required), `checkout.getPayment` (`GET /v1/payments/{paymentId}`) and `checkout.updatePayment` (`PATCH /v1/payments/{paymentId}`), for edge and key callers, access as the checkout's (`404` otherwise, another tenant's id included), `Cache-Control: no-store`. `card` on Stripe in `velexis` mode and `airline_card` (below) in this release; the flows are described step by step in `payments.service.ts`.

Every Stripe failure is `502 PAYMENT_PROVIDER_ERROR`, logged as `payments.stripe_call_failed` with the operation, error type and code and Stripe's request id only. Stripe's card brand ids map to Amadeus brands in the gateway itself (payments never imports the storefront module, architecture §2.2).
- **Card fee** (`card-fees.ts`): a card hint (`card: {brand, bin?}` on create, the body of update) must be one of the storefront's `accepted_card_brands` (`422 UNPROCESSABLE`, `details.reason: card_brand_not_accepted`). The Amadeus fee comes from the priced offer when it was priced with the same hint, else from one Flight Offers Price call (`include=credit-card-fees`, the confirmed offers verbatim, `binNumber` as an integer); a fare that changed meanwhile is `409 PRICE_CHANGED` (`details.reason: fare_changed`; the checkout is not moved onto a new priced offer yet, see **Not yet**), an unreadable answer `502 SUPPLIER_ERROR`. The `payment_card` fee rules of the pricing engine for the brand are added; the payment amount, the checkout's `fees` and total follow, and the PaymentIntent's amount is updated when it changes. `cardHint` and `cardFee` of a payment name an Amadeus brand only: a card confirmed without a hint keeps the provider's brand in `card` (`JCB`), with neither.
- **Rows first**: the `payments` row (and its `payment_events` row) is committed before the PaymentIntent is created; a row whose Stripe call got no answer is used again by the retry, so the same `pi:create:<pay_id>` goes to Stripe and a PaymentIntent made for a lost answer comes back. Stripe keeps a 5xx as the answer of its idempotency key for 24 hours, so a row whose Stripe call got one is `failed` (`failure.code` `PAYMENT_PROVIDER_ERROR`) and the retry inserts a payment with a key of its own; a failed PaymentIntent update moves the payment's `version` on, so the next `updatePayment` never sends a `pi:update:<pay_id>:<version>` that Stripe may hold for another amount or a 5xx (setting an amount twice is harmless). Not yet confirmed payments of the checkout are cancelled by a new one (`payment.replaced`) and their PaymentIntents cancelled at Stripe, best effort. Events: `payment.created`, `payment.retried`, `payment.session_created`, `payment.provider_error`, `payment.amount_updated`, `payment.<status>` on a change seen by `getPayment`; payloads go through `redactPayload` and never hold card data or the client secret.
- **Webhooks** (`webhooks/`, `stripe-events.processor.ts`, `payment-state.ts`, OBE-039; [OADR-0010](../docs/adr/0010-stripe-gateway-and-payment-webhooks.md) points 4 and 5). `POST /webhooks/stripe/velexis/{test,live}` (`receiveStripeVelexisWebhook`, `x-internal`, `@WebhookRoute()`: no credential, the raw body) verifies `Stripe-Signature` on the raw bytes with `STRIPE_WEBHOOK_SECRET_VELEXIS_<ENV>` (`400 INVALID_REQUEST`, `details.reason: signature_invalid`, before anything in the body is read), checks `livemode` and `metadata.velexis_environment` against the path, takes the tenant from `metadata.velexis_tenant_id` (an object without Velexis metadata that names its PaymentIntent, a dispute, takes the PaymentIntent's, read from Stripe with the endpoint's Velexis key), finds the payment by `metadata.payment_id`, then by the PaymentIntent, inside that tenant only (a Stripe payment of the path's environment whose PaymentIntent, when set, is the event's), and writes one `payment_events` row (`source = webhook`, `type = webhook.<event type>`, `provider_event_id`, a payload of ids, statuses and amounts only) in a tenant transaction; a stored event id is a duplicate. Then it queues `stripe.event {tenantId, paymentEventId}` on `ota-stripe-events` with the Stripe event id as job id (a duplicate queues it again: one job per event id) and answers `200 {received: true}`. An unknown or unusable tenant (not `active` or `suspended`) or payment is logged and acknowledged; every mismatch is a security event (`securityEvent: payments.webhook_mismatch`, ids only) acknowledged without effect. When the job cannot be queued (2 s) or a dispute's PaymentIntent cannot be read, the answer is `503` and Stripe delivers the event again. The worker's consumer (`PaymentsWorkerModule`, concurrency 4) never trusts the body: it reads the PaymentIntent (with its payment method and latest charge), the charge and its refunds, or the dispute again with the Velexis key of the payment's environment and applies that state with the row's lock and `version`, as `payment-state.ts` allows (a state read for an older event never undoes a newer one: `authorized` only moves on to `captured` or `canceled`, `captured`, refunded, `canceled` and `failed` never move back on a PaymentIntent's state): `payment_intent.amount_capturable_updated`, `.succeeded`, `.payment_failed`, `.canceled` (the payment's status, amounts, card and decline code), `charge.refunded` and `charge.refund.updated` (each `refunds` row by its Stripe id, else by the `refund_id` Velexis wrote in it, and the payment's captured and refunded amounts with `captured`, `partially_refunded` or `refunded`; a refund made outside Velexis only moves the amounts and is logged), `charge.dispute.created` (a `payment.dispute_created` event and, once per dispute, an outbox `staff.manual_review` alert to `ops_alert_email`, else `OPS_ALERT_EMAIL`, until OBE-055 adds the owners and the template); other types are stored and ignored. Each change writes a `payment_events` row (`source = webhook`). An object whose metadata names another tenant, environment or payment is a security event (`payments.stripe_event_mismatch`) and changes nothing; a Stripe failure that can pass is retried by BullMQ, a permanent one (`404`, a refused request) ends the job.
- **Airline card** (`airline-card/`, `src/checkout/pricing-mode.ts`, OBE-050; [OADR-0004](../docs/adr/0004-airline-card-data-handling.md) points 1, 2, 4, 5, [flow](../docs/flows/checkout-airline-card.md) §1, §3 steps 1–2). `createPayment {method: "airline_card"}` is `403 FEATURE_DISABLED` (`details.feature: airlineCard`) unless `AIRLINE_CARD_ENABLED` and `storefront_settings.airline_card_enabled_<env>` are on, and `403 SCOPE_NOT_ALLOWED` (`details.reason: edge_only`) for every caller but the storefront edge. It calls no provider (`AirlineCardGateway`, inert): it cancels the checkout's other unconfirmed payments, inserts a `payments` row with `provider = airline`, `method = airline_card`, `capture_method = automatic` and nothing `payments_airline_card_ck` refuses (no provider ids, expiry, 3-D Secure or stored next action; the answer's `nextAction.type = airline_card_form` and `threeDSecure.status = not_required` are derived), and switches the checkout to the airline's price: `pricing_mode = net`, the priced offer's `net_total`, the extras' `net_amount`, and as card fee the Amadeus fee alone (no OTA markup or fee, OADR-0005 point 9). `updatePayment` on it (edge only) quotes the Amadeus fee of the brand and BIN; a card payment created afterwards restores `markup_rules` (selling total, extras' selling prices, the OTA's card surcharge). `SensitiveCard` keeps the card of the completion (OBE-051) in private fields: `toJSON`, `toString`, `Symbol.toPrimitive` and `util.inspect.custom` answer `"[redacted card]"`, `brand()`, `bin()` and `last4()` are the only readers, `toAmadeusCreditCard()` the only full copy (for the Flight Create Orders body), `toRedactedCreditCard()` the persisted copy (last 4, no security code or expiry), `discard()` blanks it.
- **Not yet**: capture, void and refund jobs (OBE-040) and the airline-card completion (OBE-051) use the same gateway; the checkout answer's `payment` is still null and `progress.paymentReady` still reflects `pay_later` only (`checkout.mapper.ts` was outside OBE-038's files); a `409 PRICE_CHANGED` of a card-fee quote leaves the checkout on its priced offer and carries `details.reason` only, where the contract's CheckoutConflict describes the checkout moved to the new priced offer with `details.oldPrice`, `newPrice` and `pricedOfferId` (open question for the re-pricing of OBE-042); `payments.card_brand` is the hint's brand once a hint was sent, so a card confirmed with another brand than its hint shows the hint's brand in `card` and was charged the hint's fee (the provider's brand is only in the `payment.<status>` event): checkout.complete (OBE-042) re-reads the PaymentIntent and logs a card whose brand differs from the hint (`bookings.card_brand_differs_from_hint`); the amount authorised is what it checks.

**Bookings: checkout.complete for Stripe** (`src/bookings/`, OBE-042; [architecture-booking](../docs/architecture-booking.md) §1 and §2, [flow](../docs/flows/checkout-stripe.md) §2 steps 5–7 and §3, [OADR-0003](../docs/adr/0003-booking-orchestration-and-supplier-timeout-recovery.md) points 1–3, [OADR-0008](../docs/adr/0008-ticketing-policy.md) points 1 and 7). `checkout.complete` (`POST /v1/checkouts/{checkoutId}/complete`, `201` with `Location: /v1/bookings/<bkg_…>`, `Idempotency-Key` required, `Cache-Control: no-store`) is CheckoutModule's route over `BookingOrchestrator` (`BookingsModule`, which never imports CheckoutModule or PaymentsModule: it reads checkouts and payments through their repositories). Five steps, and no database transaction is open while Amadeus or Stripe is called (the integration test watches the pool):
- **Read** (T0): the checkout as checkout.get reads it (`404`), a booking of it (`409 CHECKOUT_ALREADY_COMPLETED` with `details.bookingId`, or `504 SUPPLIER_TIMEOUT` while it is `pending`), `410 CHECKOUT_EXPIRED`, travellers and contacts against the requirements (`422 CHECKOUT_INCOMPLETE`), the payment (`paymentId` or the active one; an airline-card payment `422 UNPROCESSABLE`, `use_airline_card_completion`); `payment_timing` must be `authorize_before_booking` (OADR-0008 point 2). The PaymentIntent is read again: `requires_capture` for exactly the total (`409 PAYMENT_AMOUNT_MISMATCH`, as the OTA document says), not confirmed `402 PAYMENT_REQUIRED`, declined `402 PAYMENT_DECLINED`; a total above `expectedTotal` is `409 PRICE_CHANGED`.
- **Claim** (T1): the checkout `FOR UPDATE`; the `bookings` row `pending` with a new reference (`VX` and 6 characters without 0/O/1/I, `booking-reference.ts`), `create_order_started_at`, the amounts of the checkout and the priced offer, the trip; the payment linked; event `booking.create_order_started`. `bookings.checkout_id` is UNIQUE, so a concurrent claim answers as a booking of the checkout does.
- **Call**: a priced offer that expired, is older than 10 minutes or has travellers with discount data is priced again (`PricedOffersService.repriceForCheckout`, a child priced offer): a higher total voids the authorisation, fails the booking, moves the checkout to the new priced offer and total and answers `409 PRICE_CHANGED` (`details.oldPrice`, `newPrice`, `pricedOfferId`); a lower one is booked (warning `PRICE_DECREASED`). Flight Create Orders (`order-request.builder.ts`): the priced offers verbatim, the travellers with their decrypted documents (fields of the specification only), the contacts, the special requests upper-cased (GENERAL_MISCELLANEOUS) and the remark `VELEXIS <reference>` (BACKOFFICE, last), `automatedProcess` IMMEDIATE on `storefront_settings.booking_queue_number`/`_category` in the queuing office, `formOfPayments` `other.method` ACCOUNT, `ticketingAgreement` CONFIRM, `issue=true` for `issue_at_booking` or `instantTicketingRequired`. A refusal (Amadeus answered: `SOLD_OUT`, `PRICE_CHANGED`, data errors, `SUPPLIER_ERROR`) voids the authorisation (`pi:cancel:<pay_id>`; a failed void queues `payment.void {tenantId, id}` on `ota-payments`, job id `payment-void-<pay_id>`), marks the booking `failed` with its `checkout_id` cleared and reopens the checkout (`409 SOLD_OUT`, `422 TRAVELER_DATA_INVALID`, `502 TICKETING_FAILED`, `502 SUPPLIER_ERROR`); a request that never reached the order (token, rate limiter, a gateway's 502/503) fails the booking and keeps the authorisation; a timeout or reset leaves the booking `pending` for the reconciliation of OBE-043 (`504 SUPPLIER_TIMEOUT`, `details.bookingId`).
- **Record** (T2, `order-recorder.ts`): `confirmed`, or `ticketed`/`partially_ticketed` when tickets came back; record locator, associated records, travellers (documents sealed again for `booking_travelers`, associated data `tenant_<key>.booking_travelers.<column>:<btr_…>`), contacts, segments (instants from the airports' time zones), remarks, tickets, `order_snapshot` after the shared redactor, `ticketing_deadline_at` (start of `lastTicketingDate` or an earlier agreement date, in the OTA's time zone), events, the `booking.confirmed` e-mail in the outbox; the checkout `completed`. An order that exists but cannot be recorded (an answer that cannot be read, a T2 that fails) keeps the booking `pending` and answers `504 SUPPLIER_TIMEOUT`, like a lost answer: nothing is voided and Flight Create Orders is never sent again for the checkout.
- **Money and issue**: the capture `pi:capture:<pay_id>:<amount>` (not for `manual_review` without tickets: staff are alerted with `staff.manual_review` and capture from the console). A failed capture answers `201` with the warning `CAPTURE_FAILED`, sets `ticketing_status = manual_review` (a ticketed booking keeps `issued`), queues `payment.capture_retry {tenantId, id}` on `ota-payments` (the payment id, as [architecture](../docs/architecture.md) §6 gives the queue's payload; job id `capture-retry-<pay_id>`, 10 minutes later; OBE-040 consumes it) and alerts staff. `issue_after_payment` then calls Flight Order Issue; a failure leaves the booking `confirmed` with `ticketing_status = failed` and the next attempt 5 minutes later (OBE-044).
- **Answer**: CheckoutCompletion with the booking in customer scope and the warnings; `bookingToken` is null until the guest tokens of OBE-047. Staff alerts go to `ops_alert_email`, else the support address; their console link is `https://admin.<STOREFRONT_BASE_DOMAIN>/bookings/<bkg_…>`.
- **Not yet**: the timeout reconciliation and the idempotency hooks that replay a stored `504` (OBE-043), the guest booking token (OBE-047), the payments jobs that run `payment.capture_retry` and `payment.void` (OBE-040), the ticketing retries (OBE-044), the booking's `amadeus` view and real allowed actions (OBE-046), saved travellers and booking documents.

## 4. Processes, queues and schedules

| Queue | Role of this backend | Processor |
|---|---|---|
| `ota-tenant-ops` | Consumer (`tenant.provision`, `tenant.migrate`, `tenant.suspend`, `tenant.resume`) | `provisioning/tenant-ops.processor.ts` |
| `platform-tenant-events` | Producer | `provisioning/tenant-events.producer.ts` |
| `ota-stripe-events` | Both | `payments/stripe-events.processor.ts` |
| `ota-payments` | Both | `payments/payments.processor.ts` |

The API process only produces jobs; every processor and scheduler runs in the worker. Schedulers are declared at worker start-up with `upsertJobScheduler`.

How the code uses them (OBE-002, `src/common/`):

- **`RedisModule`** (global, built once per process by whichever module imports it) holds two connections on `REDIS_URL`: `REDIS_CLIENT` for caches, locks, counters and hand-offs, which fails fast while Redis is down (one retry per command) so callers can degrade as [architecture §10](../docs/architecture.md#10-failure-behaviour) says, and `REDIS_BULLMQ_CONNECTION`, the BullMQ connection with `maxRetriesPerRequest: null`, which waits for Redis instead. Both connect on first use, log the first error of an outage once (`redis.connection_error`, never the URL), and quit after every queue and worker has closed. A connection with an attempt in flight is closed once that attempt has ended (`closeRedisConnection`): closing it during the attempt would make BullMQ 5 reject the set-ups still waiting on the shared connection after the queues have removed their listeners, unhandled rejections that stop the process. Because the BullMQ connection waits for Redis, a producer on a request path does not await `queue.add` while Redis is down (the outbox and the sweeps catch up).
- **`redis.keys.ts`** is the only place that writes a key: `redisKeys.<builder>(…)` returns `{ key, ttlSeconds, kind }` for every key of [architecture §7](../docs/architecture.md#7-redis-keys), and every write sets that TTL (Redis runs with `noeviction`). `tenant` keys (tenant data) always start with `t:<tenantId>:<env>:`; `shared` keys are those of the cross-cutting tables; `credential` keys belong to an Amadeus credential set. The builders validate every part (ids, environments, host names, SHA-256 hashes) and never echo it in an error. A key reaches the client only as a `RedisKeyName` from a builder, in a form the source scan of `redis.keys.test.ts` can read: no cast to `RedisKeyName`, a literal command name for `call`, literal command arrays for `multi([…])`, and a literal key count for `eval`.
- **`QueuesModule`** (static, imported by every module that produces or consumes jobs; no other module registers BullMQ queues) configures BullMQ once (the BullMQ connection, prefix `vx`, the job defaults of [ADR-0009](../../docs/mvp/adr/0009-background-jobs-bullmq.md): 5 attempts, exponential backoff from 30 s, failed jobs kept 30 days and completed jobs 1 day) and opens every queue of the table above (the eight the worker consumes and `platform-tenant-events`, which it produces), injectable with `@InjectQueue(<queue name>)` (`OTA_QUEUE.<topic>` for the consumed ones). A worker module declares `@Processor(OTA_QUEUE.tenantOps, otaWorkerOptions(OTA_QUEUE.tenantOps))` (the queue's concurrency of architecture §6 and the same retention) and attaches its own `error` listener to its worker. Before shutdown, its `BullmqStartupSettler` waits up to 1 s for queues and workers that are still connecting (`settleBullmqStartup`): BullMQ 5 would otherwise report a set-up interrupted by the close as an unhandled rejection, which stops the process (OBE-005).
- **`job-validation.ts`**: a processor of a cross-backend queue starts with `validateTenantOpsJob(job, logger)` (or `validateQueuedJob(job, names, logger)`). A message that is not one of the queue's names or does not match its `@velexis/api-types/jobs` schema is logged as `queue.job_invalid` (queue, job id, name, failing paths and rules; never the payload) and thrown as BullMQ's `UnrecoverableError`, so it fails at once without the remaining attempts.

The worker's modules (`worker.module.ts`): `RedisModule`, `QueuesModule`, `TenancyModule.forWorker()` (the platform repository and, since OBE-024, the platform caches with their `vx:invalidate` subscriber, `TenantContext` on the worker's request-context module and `TenantTx`, for jobs), `ProvisioningModule`, `JobsModule`, `NotificationsModule.forWorker()` (OBE-030) and `PaymentsWorkerModule` (OBE-039: the `ota-stripe-events` consumer, see Payments in §2), which the API never imports; the API imports `NotificationsModule.forApi()`, which queues e-mails and never sends. The API imports `TenancyModule.forApi()` (since OBE-011): its own `velexis_ota_app` pool (20 connections, opened on the first lookup), the platform repository and the caller classification, which only the API's module provides. Provisioning (OBE-005, OBE-006, `src/provisioning/`, [flow](../docs/flows/tenant-provisioning-worker.md), [OADR-0007](../docs/adr/0007-tenant-migration-runner-and-provisioning-worker.md)):

- **`tenant-ops.processor.ts`** consumes `ota-tenant-ops` (concurrency 2), validates each job and dispatches on its name. `tenant.provision` runs `ProvisioningService.provisionTenant` and `tenant.migrate` runs `migrateTenant(tenantId, targetVersion)`; after the transaction it publishes `tenant.provisioned` / `tenant.migrated` or the failure event. A non-retryable failure is published at once and the job fails as unrecoverable. A retryable one is thrown back to BullMQ while the job has tries left (the platform dispatches with `attempts: 3`; `tenant_ops.retrying`), and only its last try publishes `tenant.provision_failed` / `tenant.migration_failed` with `retryable: true` (the platform then re-dispatches with backoff). `tenant.suspend` and `tenant.resume` are not handled yet (M4–M5) and fail as unrecoverable. Log lines carry the error code, never the error. Worker errors are logged once per outage (`queue.worker_error`).
- **`failure-classifier.ts`** (OBE-006, [OADR-0007](../docs/adr/0007-tenant-migration-runner-and-provisioning-worker.md) item 6, [flow §5](../docs/flows/tenant-provisioning-worker.md#5-failure-handling)) turns what a run threw into the event's `error {code, message}`, `retryable` and the migration at fault (`version`). Retryable: `LOCK_TIMEOUT` (55P03), `SERIALIZATION_FAILURE` (40001), `DEADLOCK` (40P01), `CONNECTION_LOST` (class 08, 57P01–57P03, 53300, `ECONNREFUSED`/`ECONNRESET`/…, `pg`'s connection messages), also inside a failing migration file, and any error it does not know (by its SQLSTATE, or `UNEXPECTED_ERROR`). Not retryable: `CHECKSUM_MISMATCH` (an applied file was edited), `FOREIGN_CONTENT`, `FOREIGN_OWNER`, `SCHEMA_MISSING`, `INVALID_SCHEMA_NAME`, `MIGRATION_FAILED` (a file that fails for another reason fails the same way on every try), `INVALID_MIGRATION_FILES` (an invalid or missing tenant migrations folder) and `UNEXPECTED_PLATFORM_VALUE`, besides the service's own `TENANT_NOT_FOUND`, `TENANT_NOT_PROVISIONING`, `TENANT_NOT_MIGRATABLE` and `UNKNOWN_TARGET_VERSION`. Messages are written there, capped at the 1,000 characters of the event schemas (`jobError`, which the service's own failures use too): never PostgreSQL's text, the SQL, its parameters or a value of the tenant row.
- **`provisioning.service.ts`**: `provisionTenant(tenantId)` re-reads `platform.tenants`. A `provisioning` tenant gets **one transaction** as `velexis_provisioner`: `migrateTenantSchema({ create: true })` of `@velexis/db` (schema under the advisory lock of its name, `lock_timeout` 5 s, grants and default privileges for `velexis_ota_app`, every file of `migrations/tenant` and its ledger row) and, in its `beforeCommit`, the seeds of `provisioning/seeds/` and the ledger read; a crash before `COMMIT` leaves no schema. Another status answers `tenant.provisioned` again when the schema is complete at the latest version (checked read-only through `tenantTx`), otherwise `TENANT_NOT_PROVISIONING`; an unknown tenant is `TENANT_NOT_FOUND`, a schema provisioning did not create `FOREIGN_CONTENT` or `FOREIGN_OWNER` (never dropped). `migrateTenant(tenantId, targetVersion?)` (OBE-006) runs the same transaction without creating the schema or seeding (`migrateTenantSchemaFiles`), for a `provisioning`, `active` or `suspended` tenant (otherwise `TENANT_NOT_MIGRATABLE`), applying the pending files up to `targetVersion` (`0002_add_x` or `0002`; all of them without one, `UNKNOWN_TARGET_VERSION` for a version the release does not have); its `beforeCommit` refuses an edited applied file of the release, also one after the target, and reads the full ledger for `tenant.migrated {schemaVersion, migrations[]}`. Neither method throws: failures come back classified, with the error that caused them for BullMQ. The provisioner database (`DATABASE_PROVISIONER_URL`, a pool of 2 named `ota-worker-provisioner` for the read-only check) can only be built from the worker's configuration: the API's has no provisioner DSN, so it refuses with `ProvisionerDsnMissingError`.
- **`tenant-events.producer.ts`** validates each event with `validateJob` and adds it to `platform-tenant-events` with the BullMQ id of the attempt it answers (`<jobId>-<attempt>`, the platform ignores older attempts), the message's `jobId`, `tenantId` and `requestId`, and `steps[]` (`create_schema`, `run_migrations`, `seed_defaults`: `succeeded`, or `skipped` when there was nothing to do).
- **`report-migrations.command.ts`** (OBE-007, `node dist/cli.js tenants:report-migrations --report <file>`; [flow §4](../docs/flows/tenant-provisioning-worker.md#4-deploy-fan-out), [OADR-0007](../docs/adr/0007-tenant-migration-runner-and-provisioning-worker.md) item 7) turns the JSON report of the deploy fan-out (`migrate.js tenants --report`) into one event per schema it names on `platform-tenant-events`, with `jobId: null`: `tenant.migrated` for every `applied` schema (whether the run applied files or not) with the schema's full ledger, read as velexis_ota_app from its `schema_migrations` in a `tenantTx`, so a repeated run re-sends a correct mirror; `tenant.migration_failed` for every `failed` one, with the file at fault as `version` and an `error {code, message}` written from the report's SQLSTATE, line and exit code (`CHECKSUM_MISMATCH`, the transient codes of `failure-classifier.ts`, `MIGRATION_FAILED`, or the SQLSTATE), never PostgreSQL's text, and without `retryable` (the platform never retries a deploy report). `skipped` schemas (a `provisioning` tenant without a schema) get none. The tenant id is looked up in `platform.tenants` (read-only, `tenant_<key>`); a schema whose tenant is gone is named on stderr and skipped, and so is an `applied` schema that has no `schema_migrations` ledger any more (dropped after the fan-out; checked in the catalog first, since through the `search_path` the name would resolve to the `reference` ledger). Every event is built and validated before the first is added, and `requestId` comes from the report (`deploy-<sha>` for `migrate-<sha>.json`, else a hash of its content), so the events of one report are always the same. It reads `APP_ENV`, `LOG_LEVEL`, `DATABASE_URL` and `REDIS_URL` only (the variables of `ota-backend.env`; never a migrator or provisioner DSN), adds the events through a BullMQ queue whose connection gives up after three connection attempts, and exits 1 on an unreadable or invalid report, a database error or when Redis refuses an event (stderr says how many were published; running it again is harmless), 0 otherwise or when the report names no migrated or failed schema (without connecting).

Schedulers and per-tenant jobs (OBE-024, `src/jobs/`, [OADR-0014](../docs/adr/0014-per-tenant-workers-and-schedulers.md), [architecture §6](../docs/architecture.md#6-workers-queues-and-schedulers)):

- **`schedulers.ts`** declares the schedules of architecture §6 that the release runs (`OTA_SCHEDULES`: id, UTC cron pattern, milestone, the tenant statuses it targets, `active` and possibly `suspended`; never `provisioning`, `failed`, `deprovisioning` or `deleted`). `JobSchedulerRegistry` upserts one BullMQ job scheduler per schedule on `ota-maintenance` at worker start-up and removes the schedulers of schedules that no longer exist (`scheduler.registered`). It waits for the BullMQ connection's first attempt: with Redis up the schedulers are registered before the worker reports itself started; with Redis down the worker starts anyway and registers them once BullMQ is connected. Each iteration adds one `fan-out` job `{task: "<schedule id>"}`. Schedules join the list with the task that adds their work (M3: `checkouts.expire`, `notifications.sweep`, …).
- **`fan-out.ts`**: `MaintenanceProcessor` consumes `ota-maintenance` (concurrency 2). A `fan-out` job runs `FanOutService`: one read-only query of `platform.tenants` for the schedule's statuses (`PlatformReadRepository.tenantIdsByStatus`), then one job per tenant named after the schedule, `{tenantId, bucket, continuation: 0}`, with the deterministic id `<task>:<tenantId>:<minute bucket>`. The bucket is the minute the scheduler iteration was due (BullMQ's `prevMillis` of the iteration's job; the `Clock` minute for a fan-out added by hand), so two runs of one iteration build the same ids and BullMQ adds each tenant's job once. `TenantJobRunner` runs a per-tenant job: it refuses a malformed payload or an unknown name at once (`UnrecoverableError`, `jobs.job_invalid` without values), resolves the tenant through the platform cache (`tenant:<id>`, as the API does), skips it unless its status is still one of the schedule's (`skipped`, `tenant_failed`, …), runs the schedule's handler (an injectable class marked `@TenantJob("<schedule id>")`, provided in the worker) inside `TenantContext.run` (the system actor, the job id as request id), and enqueues the job again as `<…>:<bucket>-<n>` when the handler filled its batch, at most `MAX_CONTINUATIONS` (20) times per run. Failed jobs are logged with their error code only (`jobs.job_failed`); BullMQ retries them with the defaults of ADR-0009.
- **`limits.ts`**: the batch sizes of OADR-0014 point 2 (20 bookings for sync, 50 checkouts for expiry, 500 searches for the purge, 100 outbox rows) and the fan-out's chunk of 100 jobs per `addBulk`.
- **`shopping/offers-purge.processor.ts`** (`offers.purge`, every 15 minutes, `active` and `suspended` tenants; [OADR-0002](../docs/adr/0002-offer-and-priced-offer-caching.md) point 6): one statement per job in `tenantTx` deletes at most 500 expired searches, oldest first, `FOR UPDATE SKIP LOCKED`, cascading to their offers, upsells and priced offers. A search is kept while one of its priced offers backs a checkout (`priced_offer_id` or `base_priced_offer_id`, the RESTRICT foreign keys being the safety net) or has not expired yet (a priced offer may outlive its search by up to `offer_ttl_minutes`, point 3). A full batch continues; `offers.purged` logs the count only.

E-mail notifications (OBE-030, `src/notifications/`, [OADR-0013](../docs/adr/0013-notifications-and-booking-documents.md) items 1–5, [ADR-0017](../../docs/mvp/adr/0017-email-documents-storage.md), [db README §6 and §8](../../docs/velexis-sdk/db/README.md)):

- **`outbox.service.ts`** (both processes, global): a use case calls `OutboxService.enqueue(trx, {templateKey, to, locale, data, secretData?, dedupeKey, customerId?, bookingId?})` inside its `TenantTx` transaction. The call is checked against the key's allow-list (`data` holds exactly the key's caller variables, `secretData` exactly its secrets, the recipient is one plain address; `InvalidNotificationError` rolls the use case back) and inserts a `pending` row: `payload` is `data` after the shared redactor (which must leave it unchanged), the secret values (the verification or reset token) are envelope-encrypted into `secret_payload_ciphertext` with the associated data `tenant_<key>.notifications.secret_payload_ciphertext:<ntf_…>`, and a `dedupeKey` makes the e-mail once only (`queued: false` for the second call). `afterCommit` of `TenantTx` (added for it; work registered in a transaction runs after its commit and is dropped on a rollback) adds `notify {tenantId}` to `ota-notifications`, never failing the caller (2 s at most; the sweep catches a lost enqueue).
- **`template.service.ts`**: the effective template is the tenant's active `notification_templates` row of the key for the e-mail's locale or its language (`en` for `en-GB`), else the English code default `templates/<key>.{subject,html,txt}.hbs` (the build copies them to `dist/`). Templates are a safe subset of Handlebars checked on the parsed template against the key's allow-list (`templates/registry.ts`): variables, `{{#if}}`, `{{#unless}}`, `{{#each}}` over a list (with `../`); no triple braces, helpers, partials, sub-expressions or `@` variables, and no secret link in the subject. A break is `TemplateInvalidError` with every problem (`part`, `line`, `message`, the console's `422 TEMPLATE_INVALID` of OBE-073); the parts compile in an isolated Handlebars environment in strict mode, the HTML part escaped, the subject one line.
- **`renderer.ts`**: the render data holds the allow-listed paths of the payload, `brand.*` from `storefront_settings` (brand name, support e-mail and phone) and the storefront URL `https://<key>.<STOREFRONT_BASE_DOMAIN>`, and the links built from the secrets (`verifyUrl` = `/account/verify.html?token=…`, `resetUrl` = `/account/reset-password.html?token=…`, [OADR-0015](../docs/adr/0015-storefront-build-urls-and-hosting.md) point 5). A tenant template that turns out invalid is logged (`notifications.template_fallback`) and the code default is sent instead.
- **`notifications.processor.ts`** (worker): `notify {tenantId}` resolves the tenant through the platform cache (`active` or `suspended`, OADR-0014 point 4), claims at most 100 due rows with `FOR UPDATE SKIP LOCKED` (a 5-minute lease on `next_attempt_at`, committed before anything is sent; `outbox.repository.ts`), renders and sends each one outside any transaction (`mailer.gateway.ts`: `From: "<brand name>" <MAIL_FROM address>`, `Reply-To: <support e-mail>`, Message-ID `<ntf_…@domain>`) and records it in the update fenced by the lease: `sent` with the secrets erased, or one more attempt and `pending` again after 1, 2, 4 and 8 minutes, `failed` with the secrets erased after the 5th; an e-mail that can never be sent (no template, an invalid code default, a ciphertext that does not decrypt, data outside the allow-list) is `failed` at once, without stopping the other e-mails of the batch. A failure of the SMTP connection ends the batch (the other rows wait a minute without an attempt). `notifications.sweep` (every minute, `active` and `suspended` tenants) enqueues `notify` (`notify:<tenantId>:<minute bucket>`) for a tenant with a due row. Log lines carry ids, the template, the attempt and the SMTP error code, never the recipient, a variable or the message.
- **Defaults**: `auth.verify_email` and `auth.password_reset` (OBE-030); the provisioning seed copies them into each new tenant as system rows. The booking and staff keys get their defaults with OBE-055; until then an e-mail of such a key fails with `TEMPLATE_MISSING`.

## 7. Amadeus stub for development and CI

[`tools/amadeus-stub`](../../tools/) (`@velexis/amadeus-stub`, task X-026, [ADR-0015](../../docs/mvp/adr/0015-testing-strategy.md)) is a Node `http` server on port 4900:

- implements `POST /v1/security/oauth2/token` and the 12 operations from recorded, scrubbed fixtures under `tools/amadeus-stub/fixtures/`;
- validates every request against `docs/amadeus-api/*.json` and answers `400` on a malformed request, so client bugs fail loudly;
- scenarios with `X-Stub-Scenario`: `sold-out`, `price-changed`, `ticketing-failed`, `version-conflict`, `server-error`, `rate-limited`, `timeout`, `timeout-lost`; the client forwards the header only when `APP_ENV` is not `production`. End-to-end runs use magic values (destination `ZZZ` returns no offers);
- remembers created orders in memory so Flight Order Management, by-reference GET and Queue List return them (needed for reconciliation tests);
- is started in-process by integration tests through `@velexis/testing/amadeus` (random port), and as a background process in CI end-to-end jobs.

Point the backend at it with `AMADEUS_BASE_URL_TEST=http://127.0.0.1:4900`. Recording new fixtures (`pnpm --filter @velexis/amadeus-stub record <operation>`) uses the developer's own Amadeus test credentials and is never run in CI.

How the suites run (`vitest.config.ts`, `vitest.int.config.ts`):

- **Contract tests run with the unit tests.** `vitest.config.ts` includes `test/contract/**/*.test.ts` next to `src/**/*.test.ts`, so `pnpm --filter @velexis/ota-backend test` runs both (`test -- contract` narrows it); none of them needs a service.
- **Decorator metadata.** NestJS injects constructor dependencies by their TypeScript types, which esbuild (Vite's default transform) does not emit. Both Vitest configurations compile the package's TypeScript with the TypeScript compiler and the options of `tsconfig.json` instead, so tests run the same decorator output as the `tsc` build.
- **In-process apps.** Tests start the API and the worker with `startApi({ env, logDestination })` and `startWorker({ env, logDestination })` from `src/main.ts` and `src/worker.ts`, or build a test root module around `AppModule.forRoot(config, { logger })` (Supertest). `test/support/create-test-app.ts` does the latter as `main.ts` does (the same pipeline and JSON body limits), with optional probe controllers registered before the application's routes and the log lines in a sink: `createTestApp()` with dummy services for unit and contract tests (a dummy PostgreSQL DSN, and a Redis URL on a loopback port where nothing listens, `unreachableRedisUrl()` of `test/helpers/ports.ts`, so the cache falls back to the repository the same way on every machine; `main.test.ts`, `app.module.test.ts` and the API graph of `platform-read.int.test.ts` use it too, because the API connects its `vx:invalidate` subscriber at start-up and a dummy password does not keep it away from a Redis without one; so does `worker.test.ts`, because the worker registers its job schedulers and connects its subscriber at start-up, OBE-024), `createTestApp({ database, redis })` with the file's `createTestDatabase()` clone and `useRedis()` database for integration tests (`test/integration/common/http-pipeline.int.test.ts`). `test/helpers/log-sink.ts` captures the log lines so tests can assert that a request line carries `requestId` and that no body, token or password is logged. `createApiApp` flushes Nest's start-up log buffer as soon as the pino logger is in place, so Nest's own lines (the exception handler's error lines included) reach the sink after `init()` too, not only after `listen()`.
- **Integration environment.** `test/integration/env.ts` reads `DATABASE_URL`, `REDIS_URL` and `DATABASE_PROVISIONER_URL` through `@velexis/config` (the CI job environment, or the root and app `.env.local` files). The `@velexis/testing` global setup of `vitest.int.config.ts` builds the run's template database as `TEST_DATABASE_ADMIN_URL` (platform and reference migrated, `tenant_alpha` and `tenant_beta` provisioned); a file that needs tenant schemas clones it with `createTestDatabase()` and drops the clone in `afterAll` (`test/integration/provisioning/seeds.int.test.ts`). A file that needs Redis takes an emptied database of its own with `useRedis()` and passes its URL to the module under test (`test/integration/common/queues.int.test.ts` runs a real `ota-tenant-ops` queue and worker there; `test/integration/provisioning/provision.int.test.ts` runs the whole worker graph on both, adds `tenant.provision` messages as the platform does and reads the events back from `platform-tenant-events`; `migrate.int.test.ts` does the same for `tenant.migrate` and the failure classes, a forced lock timeout included, and points the worker at a tenant migrations folder of its own by mocking the default of `provisioning.service.ts`; `test/integration/jobs/offers-purge.int.test.ts` runs the worker graph too, removes the schedulers it registered and plays the scheduler with `fan-out` jobs that carry an iteration's `prevMillis`, with `Clock` pointed at a `FakeClock`). The health suite binds the units' ports `127.0.0.1:4000` and `127.0.0.1:4001`, so integration files run one after the other.
- **Caller credentials in tests.** `test/helpers/api-env.ts` gives every test that builds the API's configuration its API-only variables: a random `VELEXIS_EDGE_SECRET` per test process, an `API_KEY_PEPPER_FILE` and a `master-v1.key` (`MASTER_KEY_DIR`, `MASTER_KEY_CURRENT=local:v1`) written once per checkout as `pnpm dev:keys` writes them (32 random bytes, base64, mode `0600`, in the package's ignored `node_modules/.cache/test-keys/`; `testKeyProvider()` loads the same KEKs), the Ed25519 signing key `ota-jwt-ed25519.pem` (`JWT_PRIVATE_KEY_FILE`, `testApiCredentials().jwtKeyFile`) in the same folder, and the development base domain and public URL. `createTestApp()`, `integrationEnv()` and the unit tests use it; `edgeHeaders(host)` are the headers Caddy adds to a storefront's `/api/*` request, `edgeWriteHeaders(host)` add the CSRF cookie, its header copy and `Origin` that a storefront page's `POST`, `PUT`, `PATCH` and `DELETE` carry, and `testApiCredentials().pepper` computes the `key_hash` of a test key (`hashApiKey`). Probe controllers of tests about the pipeline after the caller guard are marked `@PublicRoute()`; requests to pending operations carry `edgeHeaders()`.
- **One-time work in setup hooks.** Vitest bounds a test at 5 s, and CI runs every package's tests at once on four CPUs. Work a test file does once (parsing and compiling the OTA document, starting module graphs, linting or scanning the whole package) goes into a `beforeAll` with an explicit, commented budget, and the tests only compare its results. A file whose tests start the API runs `beforeAll(preloadOpenApiDocument, OPENAPI_SETUP_TIMEOUT_MS)` (`test/helpers/openapi.ts`): `loadOpenApiDocument` keeps the document for the process, so no test pays for it. Test timeouts are never raised (AGENTS.md §7).
- **Outages.** The shared PostgreSQL and Redis are never stopped by a test. A dependency that is down is a free loopback port where nothing listens (`test/helpers/ports.ts`); a Redis that comes back is `test/helpers/fake-redis.ts`, a minimal RESP server started on that port.
- **nestjs-pino outside requests.** Every `PinoLogger` of a process writes to the first application's logger outside a request. One process runs one application on the VM; a test that starts several and asserts out-of-request lines calls `useNextApplicationLoggerOutsideRequests()` (`test/helpers/nest-pino.ts`) before starting the one it watches.

## 9. Deploy

- Release folder `ota-backend/` with `dist/`, `migrations/tenant/`, `openapi/` and production dependencies (`pnpm deploy --prod`), per [ADR-0023](../../docs/mvp/adr/0023-release-artefact-and-deploy-user.md).
- Deploy order: platform and reference migrations → tenant fan-out (`migrate.js tenants --dir "$REL/migrations/tenant"`, then `velexis-run ota node "$REL/ota-backend/dist/cli.js" tenants:report-migrations --report /var/lib/velexis/migrate-<sha>.json`, both before the switch; the report is made readable, `0644`, for the OTA zone user, and a failed report stops the deploy like a failed migration; the first deploy, without a running release for `velexis-run ota` to start in, skips the report, and every later report re-sends every ledger) → restart `velexis-ota-worker`, then `velexis-ota-api` → `/health/ready` checks ([`../docs/flows/tenant-provisioning-worker.md`](../docs/flows/tenant-provisioning-worker.md) §4, [`deployment-single-vm.md`](../../docs/mvp/deployment-single-vm.md) §8 and §9).
- Both units run with `MemoryMax`, `LimitCORE=0` and no swap on the VM, so card data in memory never reaches disk ([ADR-0011](../../docs/mvp/adr/0011-payments-stripe-and-airline-card.md) §C).
