# OTA backend (`@velexis/ota-backend`)

This is the NestJS 11 data-plane backend of Velexis: the OTA booking API used by the hosted storefront (through Caddy's same-origin `/api` proxy), by the OTA admin (server side) and by third-party frontends with API keys, the Stripe payment webhook receivers, and a worker process for provisioning, tenant migrations, ticketing, booking sync and reconciliation, notifications, documents and housekeeping. This page is the component specification: folder and module tree, environment variables, processes and workers, commands, the Amadeus stub, the OpenAPI document and tests. Design and decisions are in [`../docs/`](../docs/README.md); start with [`../docs/architecture.md`](../docs/architecture.md).

Related: [`../docs/scope.md`](../docs/scope.md), [`../docs/api-changes.md`](../docs/api-changes.md), [`../docs/data-model.md`](../docs/data-model.md), [`.env.example`](.env.example), [MVP tech stack](../../docs/mvp/tech-stack.md#ota-backend-otabackend-velexisota-backend), [conventions](../../docs/mvp/conventions.md#2-nestjs-backends), [local development](../../docs/mvp/local-development.md).

## 1. At a glance

| Item | Value |
|---|---|
| Runtime | Node.js 22, TypeScript 5.6 strict, CommonJS output |
| Framework | NestJS 11 (Express 5), `nestjs-pino`, `nestjs-cls`, `@nestjs/bullmq`, `@nestjs/throttler`, `helmet`, `cookie-parser` |
| Data | Tenant schemas `tenant_<key>` (DML, role `velexis_ota_app`), `reference` (read), selected `platform` tables (read-only, cached), through `@velexis/db` (Kysely) |

| Public hosts | `https://api.ota.example.com` and `/api/*` on every storefront host (`<key>.ota.example.com`, verified custom domains); `/internal/*` and `/health/ready` blocked publicly |

Each module follows [`conventions.md` §2](../../docs/mvp/conventions.md#layout-one-module-per-bounded-context): thin controllers bound to an `operationId`, services owning transactions, Kysely repositories that take the transaction first, gateways for external calls, processors for jobs. Responsibilities and dependencies are in [`../docs/architecture.md`](../docs/architecture.md) §2.

**The HTTP pipeline** (`src/common/http/`, OBE-010; [architecture §3](../docs/architecture.md#3-request-pipeline), [ADR-0006](../../docs/mvp/adr/0006-contract-first-openapi.md)). `HttpModule.forRoot` in the API's graph, after the request context of `app.module.ts` (pino-http sets and returns `X-Request-Id`, nestjs-cls starts the context with it):

- **Middleware**: helmet (a JSON API's headers, aligned with Caddy's `security_headers`), cookie-parser, then the body parsers of `body-parsers.ts`: the raw bytes (a `Buffer`, 512 KB) on `/webhooks/*`, JSON up to 256 KB elsewhere, and the per-operation limits of `JSON_BODY_LIMITS` in `main.ts` (the 10 KB of the airline-card route, OBE-051), matched case-insensitively and with an optional trailing slash like Express' routes. Nest's own parsers are off. Malformed JSON, a body over its limit or an unsupported encoding answer `400 INVALID_REQUEST` with `details.reason` (`malformed_json`, `body_too_large` with `limitBytes`, `unsupported_encoding`, `body_incomplete`), never with the parser's message, which may quote the body.
- **`@OpenApiOperation("getStorefront")`** binds a handler to its operation. At start-up `loadOpenApiDocument()` parses `openapi/velexis-ota-booking-api.openapi.yaml` (in the release folder too) and compiles, for every operation, one Ajv 2020 validator per parameter location and one for the JSON body (about 1 s, once per process). The global `OpenApiValidationInterceptor` validates each bound request: path, query, header and cookie parameters (strings coerced to the schema's integer, number or boolean; arrays split on commas unless `explode`), then the body. Failures answer `400 VALIDATION_FAILED` with at most 50 `fieldErrors` `{ path, code, message }`: `path` is `/path/<name>`, `/query/<name>`, `/header/<Name>` or `/cookie/<name>` for parameters and a JSON pointer into the body for the body (`/travelers/0/dateOfBirth`; `""` for a missing required body), `code` is the Ajv keyword (`required`, `additionalProperties`, `type`, `pattern`, …), and no message carries a rejected value. A body that is not JSON on a JSON operation is `400 INVALID_REQUEST` (`unsupported_media_type`). Handlers read the input with `@OpenApiInput()` (`ValidatedInput<"listBookings">`), or with `@Param()` and `@Query()`, which see the coerced values. Undocumented query parameters are tolerated; nothing is defaulted. A console operation (`x-scope: console`) puts the request in console scope (`RequestContext`); for `both`, the scope guard of a later task decides.
- **`ErrorFilter`** (global): every error in the envelope of `toErrorEnvelope` (`@velexis/errors`) with the request id of `X-Request-Id`, `Cache-Control: no-store`; `supplier` only in console scope; Nest's HTTP exceptions (the router's 404, an undecodable path) by the catalogue code of their status and never their message; anything else `500 INTERNAL_ERROR`, logged with its stack (`http.unhandled_error`), and an `AppError` of status 500 or more logged with its code and cause (`http.request_failed`).
- **Idempotency** (`src/common/http/idempotency.interceptor.ts`, `idempotency.service.ts`, `idempotency.repository.ts`, OBE-014; [architecture-booking §5](../docs/architecture-booking.md#5-idempotency-end-to-end)). `IdempotencyInterceptor` is global, provided after the validation interceptor, so it runs after the guards and after validation (an invalid request writes no record). It applies to every handler bound to an operation whose `Idempotency-Key` header parameter the document marks required, read from the document at start-up; a request without a tenant (only a test probe on a public route) passes through. The record is `idempotency_keys` of the tenant schema, through `TenantTx`, in short transactions of its own around the handler: scope `<environment>:<principal>:<operationId>` with the actor as principal (`cus_…`, `stf_…`, `key_…`), or `edge-` and the first 16 hex characters of the SHA-256 of `__Host-vx_csrf` for a storefront visitor without a session (no cookie: `403 CSRF_TOKEN_INVALID`); `request_hash` the SHA-256 of the canonical `{operationId, path, query, body}` (or of what the operation's `hashInput` hook makes of it), in which card and identity document data count as the shared redactor keeps them (numbers by their last 4, security codes, birth place and issuance location left out), so no hash of a card or document number is stored; a hashed input that still carries a password is refused before anything is hashed or stored (`UnhashableIdempotentInputError`, a `500`: the operation needs a `hashInput` hook that leaves the password out), while tokens stay in the hash. A seen key with another hash is `409 IDEMPOTENCY_KEY_REUSED`; a stored answer is replayed (status, `Location`, `ETag`, `Cache-Control`, `Retry-After`, cookies, body) without running the handler; a key in flight makes the request wait (polling from 100 ms to 1 s, at most 60 s, then `409 CONFLICT` with `details.reason: idempotency_key_in_use`), and a record whose 2-minute lease ran out (its process died) is taken over; a record past its 24 h is replaced. Outcomes: 2xx (`completed`) and final 4xx (`failed`) are kept 24 h; `429` and the 5xx are transient and delete the record, except a `504` that the operation's `resourceOf` hook links to a resource. `response_body` is always the copy after `redactPayload` of `@velexis/logger`; an answer that the redactor changes or that sets a cookie is also kept verbatim (body and `Set-Cookie`) in `response_ciphertext`, envelope-encrypted with the KEKs of `MASTER_KEY_DIR` (associated data `tenant_<key>.idempotency_keys.response_ciphertext:<idk_…>`), and replayed from there. Per-operation hooks come from providers marked `@IdempotencyHooksFor(["completeCheckout", …])`: `hashInput` (OBE-051 hashes the airline card as `{brand, last4}`), `resourceOf` and `resolveReplay` (OBE-043 rebuilds a stored `504` from its booking). Handlers of these operations return their body (`@Res({ passthrough: true })` at most). Failures to store an outcome are logged (`idempotency.settle_failed`) and the answer is sent; replays are logged as `idempotency.replayed`, never with the key or a body.
- **Caller classification** (`src/common/auth/caller.guard.ts`, `src/tenancy/caller-resolver.ts`, `src/tenancy/api-key.verifier.ts`, OBE-011; [OADR-0009](../docs/adr/0009-caller-and-tenant-resolution.md) point 1, [architecture §3.1](../docs/architecture.md#31-callers)). `CallerGuard` is the first guard of every route (`APP_GUARD` in `app.module.ts`), before validation, so a refused request is never validated. In order: `X-Velexis-Edge` together with `X-Api-Key` is `400 INVALID_REQUEST` (`details.reason: edge_with_api_key`); `X-Velexis-Edge` is compared with `VELEXIS_EDGE_SECRET` in constant time before any lookup (wrong: `401 INVALID_API_KEY`, logged as `caller.edge_refused` without the value; right: the **edge** caller, `X-Velexis-Host` required, else `400 INVALID_REQUEST` `edge_host_missing`); an `X-Api-Key` with a `pk_` or `sk_` prefix goes to the **key** verifier; any other `X-Api-Key` (hosting keys, the OTA admin's service key until OBE-060) is `401 INVALID_API_KEY`. Without a credential a route is refused with `401 INVALID_API_KEY` unless its handler or controller is marked `@PublicRoute()` (`/health/live`, later the asset and file downloads) or `@WebhookRoute()` (the Stripe receivers): those get the **anonymous** caller. `@LocalRoute()` (`/health/ready`) is anonymous only on a direct loopback connection (socket peer on loopback, neither `X-Forwarded-For` nor `X-Forwarded-Host`), the test of rule 1.2; through Caddy it needs a credential like any route. The key verifier takes the format of [PADR-0005](../../platform/docs/adr/0005-api-key-format-and-hashing.md) (`pk_`/`sk_`, `test`/`live`, 40 base62 characters; anything else is refused without a lookup), looks the 14-character prefix up in `platform.api_keys` (`PlatformReadRepository.apiKeyByPrefix`, a short read-only transaction as `velexis_ota_app`), compares `HMAC-SHA-256(pepper, key)` with `key_hash` in constant time (`verifyApiKey` of `@velexis/crypto`; the pepper of `API_KEY_PEPPER_FILE` is read once at start-up), and only then refuses a revoked or expired key, a row whose kind, environment or tenant does not fit the key, or scopes that break PADR-0005 item 6: all `401 INVALID_API_KEY`, the reason logged as `caller.api_key_refused` with the key id, never the key. A `pk_` key sent with an `Origin` it does not list (exact, case-insensitive) is `403 ORIGIN_NOT_ALLOWED`; without `Origin` (a server) it is accepted. A failing platform lookup is `503 SERVICE_UNAVAILABLE`. The caller (`{type: "edge", id, host}`, `{type: "key", id, keyId, kind, tenantId, environment, scopes}` or `{type: "anonymous", id}`) is in the request context (`CallerContext`, nestjs-cls) for the tenant guard. The key rows come through the platform cache below (`apikey:<prefix>`); the usage counter is in the guard bullet below.
- **Tenant resolution** (`src/common/auth/tenant.guard.ts`, `src/tenancy/tenant-resolver.ts`, `platform-cache.ts`, `invalidation.subscriber.ts`, `tenant-context.ts`, `tenant-tx.ts`, OBE-012; [OADR-0009](../docs/adr/0009-caller-and-tenant-resolution.md) points 2–5, [architecture §3.1](../docs/architecture.md#31-callers) and [§7](../docs/architecture.md#7-redis-keys)). `TenantGuard` is the second global guard, after `CallerGuard`. On a handler bound to an operation (`@OpenApiOperation`), an **edge** caller's `X-Velexis-Host` resolves as `<key>.<STOREFRONT_BASE_DOMAIN>` (the tenant of the key, whatever its status: anything but `active` is `403 TENANT_SUSPENDED`, so the storefront can show its maintenance page) or as a `tenant_domains` row with `purpose = storefront` and `verification_status = verified` of an **active** tenant; the environment is `tenants.storefront_environment`. A **key** caller gets the key's tenant (active only, else `403 TENANT_SUSPENDED`) and the key's environment. Unknown hosts, pending, failed or other-purpose domains, custom domains of tenants that are not active, and hosts that cannot be host names are `403 HOST_NOT_ALLOWED` (`details.reason: unknown`, nothing about the tenant). Anonymous callers (public, webhook and local routes), routes outside the document (health) and the 501 routes of pending operations are left alone. The result is the request's `TenantContext` (`{tenantId, key, schemaName, environment, caller: {type, id}, actor: {type, id}, requestId}`; the actor starts as `guest` for the edge and `api_key` for a key, and session guards replace it with `setActor`). `TenantTx.run(fn)` is the only way to tenant data: `tenantTx` of `@velexis/db` with the context's schema and a 15 s statement timeout; without a tenant in the context it throws `NoTenantContextError` before any SQL, and `TenantContext.run(tenant, fn)` opens a context for jobs and tests.
  - **`PlatformCache`** is the Redis read-through in front of `PlatformReadRepository`: `tenant:<id>` (the row), `tenantkey:<key>` and `host:<hostname>` (a tenant id, so a `tenant` invalidation reaches every way to a tenant), `apikey:<prefix>` (the row; the key verifier reads it), and `membership`, `connection` and `amadeusAccount` read-throughs for `member:`, `conn:` and `amadeus:acct:` whose loaders and parsers come with their tasks (OBE-017, OBE-059); values must be JSON-safe, ciphertext as text, never decrypted. Entries are `{"v":1,"value":…}` with the builders' TTLs (60 s; a "not found" of `tenantkey:`, `host:` and `apikey:` for 10 s), checked again when read back (an entry that does not parse is a miss and is replaced, `platform_cache.entry_unreadable`). While the command client is reconnecting, lookups go to PostgreSQL and nothing is cached; a failing platform read is `503 SERVICE_UNAVAILABLE`. A fill that started before an invalidation of this process is not written back (or is deleted again), so a lookup that read PostgreSQL before the platform's commit cannot restore the old row after the subscriber deleted it.
  - **`InvalidationSubscriber`** (in every process that fills the cache: the API, and since OBE-024 the worker, whose jobs resolve their tenant through `tenant:<id>`; each process guards its own fills against the invalidations it receives, and deleting a key twice is harmless) has its own connection (`ota-backend-invalidation`), subscribes to `vx:invalidate` on every `ready` (start-up waits for the first attempt, at most 2.5 s, and never fails because of Redis), validates each message with `validateInvalidation` and applies them in order: `tenant` → `tenant:<id>`; `domain` → `host:<hostname>`; `api_key` → `apikey:<prefix>`; `connection` → the four `conn:{amadeus,payment}:<tenantId>:{test,live}`; `membership` → `member:<accountId>:<tenantId>`; `account` → every `member:<accountId>:*` (SCAN of `redisKeyPatterns.membersOfAccount`); `amadeus_account` → `amadeus:acct:<id>`; `plan` → nothing yet (no cache holds plan data; the feature that caches plan rows adds its key). `tenantkey:` is never invalidated (an immutable key → an immutable id). Invalid messages are refused (`invalidation.refused`, warn, with the failing paths and keywords, never the content); applied ones are logged at debug. Messages published while the connection is down are lost; the 60 s TTL bounds the staleness.
- **Amadeus connections, tokens and the client** (`src/amadeus/`, OBE-017 and OBE-018; [OADR-0001](../docs/adr/0001-amadeus-client-design.md) points 2, 4 and 5, [flow](../docs/flows/amadeus-connection-and-tokens.md) §2 and §3). `AmadeusModule` (API; it imports `TenancyModule.forApi()`) loads the KEKs of `MASTER_KEY_DIR` once at start-up (`LocalFileKeyProvider`; a missing current key or a key file others may read stops it) and provides:
  - **`ConnectionResolver.resolve(tenantId, env)`** → `{tenantId, environment, connectionId, credentialSource, credId, clientId, encryptedSecret: {ciphertext, aad}, baseUrl, offices: {queuing, owner, queue, retrieval}, officeIds}`. It reads `platform.supplier_connections` through `conn:amadeus:<tenantId>:<env>` and the referenced `platform.amadeus_accounts` row through `amadeus:acct:<id>` (`PlatformReadRepository.amadeusConnection` and `amadeusAccountById`, cached 60 s, the client secret as base64 ciphertext, never decrypted to be cached). `credential_source = velexis` uses the shared account of that environment (credId `ama_…`, shared by every OTA on it); `tenant` is part of the types and answers 424 until OBE-079. No row, a row or account that is not `active`, an account of another environment or a connection without a usable office id answer `424 SUPPLIER_NOT_CONFIGURED` (the reason only in the error's `cause`). Offices: queuing and owner from the connection, queue and retrieval from its default office, each falling back to the default or queuing office, and only ever an office of the connection's `office_ids` (on the shared account any other office may be another OTA's). The base URL is `AMADEUS_BASE_URL_<ENV>` when set (an https origin, or http on the loopback interface for the stub), else the account's `base_url`, else the official host.
  - **`TokenProvider.getToken(connection)`** → a bearer token for `credId` and the environment: `MGET amadeus:badcred:<credId> amadeus:token:<credId>:<env>`; a cached token is decrypted (`@velexis/crypto`, associated data `redis.amadeus_token.access_token:<the key>`); otherwise one call takes `amadeus:tokenlock:<credId>:<env>` (`SET NX EX 10`, a random owner, released only by its owner), looks at the cache once more and posts `client_credentials` to `<baseUrl>/v1/security/oauth2/token` (the secret decrypted in memory for that request, 10 s timeout, no redirects), then stores the token encrypted with TTL `expires_in − 60 s`. Calls without the lock look for the token every 50 ms for up to 2 s, take the lock if its holder gave it up without a token, and then request a token themselves. A `401` or `400 invalid_client` sets `amadeus:badcred:<credId>` for 5 minutes and answers `424` (logged as `amadeus.credentials_refused`, error, the trigger of the ops alert that comes with the notifications outbox); while it is set, calls answer `424` without a request. Timeouts and resets answer `504 SUPPLIER_TIMEOUT`, other network errors, `429` and `5xx` `503 SUPPLIER_UNAVAILABLE`, anything else `502 SUPPLIER_ERROR`; one `amadeus.token_request` line per request (`amadeusApi: "Authorization"`, status, outcome, duration, never a body). `dropToken(connection, token)` deletes the cached token when it is still that one (the operation-level `401` retry of OBE-018). Without Redis every call is `503 SERVICE_UNAVAILABLE`. A cached token that does not decrypt is a miss (`amadeus.token_unreadable`).

- **List**: in evaluation order (`priority`, then `id`), `active=true|false` filters on `is_active`, keyset cursor (base64url of the last rule's priority and id and the filter; a cursor of another filter or kind, or with a priority outside the `integer` range, is `400`, `/query/cursor`), 20 per page by default. Reads are not audited.
- **Create** (`201`, `Location`, `Idempotency-Key` of the idempotency interceptor): the omitted fields take the documented defaults (markup: `appliesPer` traveler; fee: booking; priority 100, active, no window), `created_by_staff_id` is the staff member (null for a key-only call), `is_default` is never set. **Update** (`If-Match`): one transaction reads the row `FOR NO KEY UPDATE` (a search's foreign-key `KEY SHARE` on the rule never waits for it), `404`, `412`, then the stored rule with the sent fields replacing theirs (`null` clears, `scope` is replaced whole) is checked as a create is, and every column is written at `version + 1`, `scope` only when it is sent (otherwise the stored jsonb stays as it is: the answer leaves out what the document cannot carry, such as a lower-case code the engine reads upper-cased, and writing that back would widen the rule). **Delete** (`If-Match`, `204`): the row is read `FOR UPDATE` and deleted; `ON DELETE SET NULL` clears `markup_rule_id` of `flight_offers`, `priced_offers` and `bookings`, whose amounts and lines stay. The seeded default markup rule cannot be deleted, and a `scope` sent for it must match every offer (`{}`, empty lists, null bounds; stored `{}`): `409 CONFLICT`, `details.reason = "default_rule"`; its percentage, priority and other fields may change.
- **Rules beyond the schema** (`400 VALIDATION_FAILED`, one field error per problem, JSON pointers into the rule): the values the calculation uses (`/percentage`, `/fixed`: `required`), a markup percentage at least -100 and a fee percentage at most 100, amounts with at most two decimals below 10 000 000 000 (`numeric(12,2)`; `decimals`, `maximum`), fee amounts not negative (`minimum`), `fixed`, `min` and `max` in one currency (`currency`; it is `fixed_currency` or `currency`, so a percentage rule with caps keeps the caps' currency), `activeFrom` and `activeUntil` instants `timestamptz` stores as written (not the year 0000 nor a leap second, which the `date-time` format admits; `format`), `activeUntil` after `activeFrom` (`window`). `change` fees are stored though no step applies them in the MVP.
- **Warnings** of the saved rule (create and update): `fixed_currency_not_default` when the money fields are not in `storefront_settings.default_currency` (they apply only to offers in their currency), and for markup rules `sells_below_net` when a value the calculation uses can be negative (percentage, fixed amount or upper cap).
- **Audit**: `staff_actions` `settings.markupRules.create|update|delete` (`settings.feeRules.…`), target `markup_rule` or `fee_rule`, with the rule before and after as the document shows it, in the change's transaction; refusals are the interceptor's `failed` or `denied` rows.

**Flight search** (`src/shopping/`, OBE-021; [flow](../docs/flows/search-and-price.md) §2–§4, [OADR-0002](../docs/adr/0002-offer-and-priced-offer-caching.md), [OADR-0005](../docs/adr/0005-markup-and-fee-engine.md)). `flights.search` (`POST /v1/flight-searches`), `flights.getSearch` (`GET /v1/flight-searches/{searchId}`) and `flights.listResults` (`GET /v1/flight-searches/{searchId}/offers`), for edge and key callers, every answer `Cache-Control: no-store`. `ShoppingModule` imports `AmadeusModule` and `PricingModule`; it is the first module of the API graph that calls Amadeus, so the API now loads the KEKs of `MASTER_KEY_DIR` at start-up.

- **Search** (synchronous only: `resultOptions.async: true` is `403 FEATURE_DISABLED`, `details.feature = "asyncSearch"`): the currency is the body's, else `X-Currency`, else `storefront_settings.default_currency`, and must be a `reference.currencies` code with at most 2 minor units (the `numeric(12,2)` columns), else `400 VALIDATION_FAILED`. `offers.mapper.ts` builds the Amadeus request: SIMPLE becomes the Flight Offers Search GET query (airline lists comma-separated), ADVANCED the POST body. `search_defaults` is read as `{maxResults, nonStop, cabin, sources}`: `maxResults` (1–250, default 250) caps `max` / `maxFlightOffers`, `nonStop` and `cabin` fill a SIMPLE search that omits them, `sources` is intersected with an ADVANCED search's (`403 FEATURE_DISABLED`, `details.feature = "sources"`, when nothing is left); ADVANCED also defaults the three `additionalInformation` flags to `true`, and refuses corporate codes and negotiated fare types in customer scope (`403 SCOPE_NOT_ALLOWED`; no setting enables them yet). SIMPLE refuses more than 9 adults and children, more infants than adults, included and excluded airlines together and a return before the departure (`400`); ADVANCED refuses more than 9 travellers older than two and more infants than adults (`400`, `/query/travelers`), as Amadeus does and as the search row's traveller counts (0–9) require.
- **Single flight**: `t:<tenantId>:<env>:search:<sha256>` (30 s) of the canonical JSON of the Amadeus request, the channel and the customer. The first request sets it (`SET NX`) and runs the search; identical requests meanwhile poll it every 100 ms for up to 30 s and answer with the search id the first one writes there after its commit (that search, with their own first page). The id replaces the first request's own value only (compare-and-set) and keeps the key's expiry: the key never lives longer than 30 s after the first request, so no result outlives it as a cache. A failed search deletes the key (compare-and-delete), and a waiting request then runs the search itself. Without Redis there is no single flight.
- **Storage**: the search row is inserted `pending` (with `expires_at = now + offer_ttl_minutes`) in a short transaction of its own, so the client's `supplier_requests` row links to it; Amadeus is called outside any transaction; a failed call marks the row `failed` with the public error code (`SUPPLIER_TIMEOUT`, `SUPPLIER_ERROR`, …) and the error is answered. Then one transaction loads the rules, prices every offer with the engine (step `search`: markup only), drops offers that cannot be read or priced and SIMPLE offers whose selling price per traveller exceeds `maxPrice`, keeps at most 250, inserts the `flight_offers` rows with their summary columns and `best_score`, and completes the search with the facets, highlights, dictionaries, warnings and one-way combinations (`expires_at` reset to now + TTL). When that transaction fails, the search is marked `failed` (`INTERNAL_ERROR`) as well: no search stays `pending`. An offer cannot be read (it is left out, never stored or answered) without an id, with an itinerary without segments, a local time that does not exist, a traveller pricing without its traveller id and type or a traveller id twice (customer scope could not rewrite its net price inside `amadeus`), or a net total finer than the currency's minor units or too large for `numeric(12,2)`.
- **Summary columns** (`offerColumns`): `max_stops` (connections of the itinerary with the most), `marketing_carriers`, per-itinerary departure and arrival minutes and durations, `main_cabin` (the cabin of the longest segment for the first adult), `min_checked_bags` (the first adult's fewest included bags, weight-only allowances count 1, `NULL` when a segment's is unknown), `refundable`/`changeable` (fare rules REFUND/EXCHANGE decide, else a branded-fare amenity naming a refund or change says yes and one negating it, such as `NON REFUNDABLE TICKET`, says no, else `NULL`), `branded_fares`, `first_departure_local` and `last_arrival_local` (the last segment's arrival, which the `arrival` sorts use, as the column's definition says). `best_score` = 0.6 × price + 0.3 × total duration + 0.1 × stops, each normalised over the search (`facets.ts`).
- **Reads**: a search is readable in its own environment, and a customer's search (the customer of the request's actor) only by that customer and in console scope; anything else is `404`. `getSearch` answers `status: "expired"` after `expires_at` (its operation documents no `410`), `pending` with `Retry-After: 1`, `failed` with the public `error`. `listResults` answers `409 SEARCH_NOT_COMPLETED` for a pending or failed search and `410 SEARCH_EXPIRED` after `expires_at`, filters, sorts (`best`, `price`, `duration`, `departure`, `arrival`, with descending variants; ties by price, then id) and pages (keyset on the sort keys and the id) in SQL (`searches.repository.ts`), with facets computed over the search's summary columns (`facets.ts`: each group ignores its own filter; the time bands of itinerary *i* ignore only its windows). The cursor carries a fingerprint of the search, filters and sort and the sort keys of the page's last row: another fingerprint, or keys that are not values of the sort's columns (a cursor the client changed), is `400 INVALID_REQUEST`.
- **Scope** (`toFlightOffer`): customer scope (the edge and every key without console scope) gets selling amounts only: the markup is folded into `price.base` and the totals and, inside `amadeus` (`view=full`), into `price.base`, `total`, `grandTotal` and the travellers' `price.base`/`total` (largest-remainder shares by net traveller total), Amadeus `margins` removed, no `netPrice` or `markup`. Console scope (`X-Velexis-Scope: console` with a `console:automation` key) gets the verbatim Amadeus offer, `netPrice`, `markup` (rule id and name) and the search's `diagnostics`. Dictionaries come from `reference.*`, completed by the search's Amadeus dictionaries, with country and currency names in the `Accept-Language` language where ICU has them (`ReferenceNames`, as the reference operations); the verbatim Amadeus dictionaries (`dictionaries.amadeus`) are not returned, because the document's `AmadeusDictionaries` requires a `key` property no Amadeus answer has.

**Offers and upsell** (`src/shopping/offers.*.ts`, `src/shopping/upsell.service.ts`, OBE-022; [flow](../docs/flows/search-and-price.md) §2 step 6, [OADR-0002](../docs/adr/0002-offer-and-priced-offer-caching.md) points 1, 3 and 5). `flights.getOffer` (`GET /v1/flight-offers/{offerId}`) and `flights.upsell` (`POST /v1/flight-offers/{offerId}/upsells`, `200`), for edge and key callers, every answer `Cache-Control: no-store`.

- **getOffer** reads `flight_offers` with its search (PostgreSQL only: OADR-0002 keeps no offer data in Redis, whatever the document's "Redis `offer:{id}`" says) and answers the full view with `dictionaries`, by `toFlightOffer` with the scope rules of the search results. Access follows the owning search: its environment, and a customer-bound search only for that customer or console scope; anything else, another tenant's id included, is `404`. After `expires_at` it is `410 OFFER_EXPIRED`. Upsell offers answer `origin: "upsell"` with `baseOfferId` and `upsellId`.
- **upsell**: customer scope needs the storefront feature `brandedFareUpsell` (on unless `features` turns it off; else `403 FEATURE_DISABLED`, `details.feature`); console scope may always call it. The path offer and `combineWithOfferIds` are read as getOffer reads them (`404`, `410`) and must come from one search (`422 OFFER_COMBINATION_INVALID`, also for two offers with one Amadeus id); a card's `offerIds` must name offers of the request (`400`, `/payments/<i>/offerIds/<j>`). The Branded Fares Upsell request carries the stored Amadeus offers verbatim and the card hints (`bin` as the integer `binNumber`, `offerIds` as Amadeus ids, all offers by default). An identical request (jsonb equality of that request in `offer_upsells.amadeus_request`) of an upsell that has not expired answers the stored upsell again (`cached: true`, same ids) without calling Amadeus. Otherwise Amadeus is called outside any transaction (`409 SOLD_OUT` for error 34651, the other supplier errors as for the search; its `supplier_requests` row links to the search, whose console `diagnostics` still name the search's own Flight Offers Search call), and one transaction prices each readable offer of the answer with the engine (step `search`, in the search's channel) and inserts the `offer_upsells` row (`completed`, or `no_upsell` when nothing could be stored) and the `flight_offers` rows (`origin = 'upsell'`, the base offer's `search_id`, no `best_score`, so `listResults` never lists them). Upsell and upsell offers share the search's `expires_at` (OADR-0002 point 3), so they are purged with it.
- **The answer** is built from the stored rows, fresh or cached: the upsell offers in the summary view plus `travelerPricings`, `oneWayUpselledCombinations` for two or more input offers (rebuilt from the flights: an upsell offer replaces the input offer that flies the same segments), and the `comparison`: columns base offer first, then the upsell offers by ascending selling price with the difference to the base; rows `checked_bags`, `refund` and `change` always, `cabin_bag`, `seat_selection`, `meal`, `lounge`, `priority_boarding` and `miles` when an offer's amenities name them, then other amenities by code. A cell is the lead traveller's amenity (`included`, `chargeable`, `not_offered` when it is negated, such as `NON REFUNDABLE`), the bag allowance or known refundability and changeability when they decide, `not_offered` when the offer publishes amenities without it, else `unknown`.

**Priced offers** (`src/shopping/priced-offers.*.ts`, OBE-023; [flow](../docs/flows/search-and-price.md) §2 steps 7–8 and §3, [OADR-0002](../docs/adr/0002-offer-and-priced-offer-caching.md) point 3, [OADR-0005](../docs/adr/0005-markup-and-fee-engine.md) points 5, 7 and 8). `flights.price` (`POST /v1/priced-offers`, `201` with `Location`), `flights.getPricedOffer` (`GET /v1/priced-offers/{pricedOfferId}`), `flights.getAncillaries` (`…/ancillaries`) and `flights.getFareRules` (`…/fare-rules`), for edge and key callers, every answer `Cache-Control: no-store`.

- **price**: `offerIds` (1–6) are read as getOffer reads them (`404`, `410 OFFER_EXPIRED`) and must come from one search with the same travellers and distinct Amadeus ids (`422 OFFER_COMBINATION_INVALID`, `details.offerIds` and `details.reason`: `different_search`, `travelers_mismatch`, `duplicate`). With `expectedTotal`, another confirmed total answers `409 PRICE_CHANGED` (`details.oldPrice` = the expected total, `newPrice`, `pricedOfferId`) after the priced offer is stored; the idempotency interceptor replays that answer for the same key. `bookingRequirements` with `off_` ids for 3-D Secure, `creditCardFees` from `included.credit-card-fees`, the embedded `ancillaryCatalogue` (with `bags` or `other-services`) and `fareRules` (with `detailed-fare-rules` or `fareRules` and rules in the answer), `conditions`, `warnings`, and `amadeus` (query, data, included). - **Reads**: a priced offer is readable in its own environment; its owner (the customer who priced it, else the customer of its search) only by that customer and console scope; anything else, another tenant's id included, is `404`. After `expires_at` every read is `410 OFFER_EXPIRED`. PostgreSQL only (OADR-0002 point 1, whatever the document's "Redis `prc:{id}`" says).
- **Ancillaries** (customer scope needs the storefront feature `ancillaries`, else `403 FEATURE_DISABLED`): from the pricing answer when it included `bags` and `other-services`, else from an earlier load, else one more Flight Offers Price call (`include=bags,other-services`, the same Amadeus offers) stored in the snapshot with `anc_` ids (an option the pricing answer embedded already, the same `included` entry under the same key or a seat, keeps its id; the others get new ones); the first stored load wins (`jsonb_set … WHERE … IS NULL`), so ids never change once answered. Options: one per `included.bags` entry (`CHECKED_BAGS`, `CABIN_BAGS` for a cabin bag name; `chargeableCheckedBags`/`chargeableCabinBags` item) and per `included.other-services` entry of a known service (`otherServices` item), for the offer that flies its first segment, its travellers and segments within that offer, priced in the priced offer's currency only (no FX; a trailing letter of the amount is dropped); one `SEATS` option per offer and segment where a fare carries `additionalServices.chargeableSeat` or a chargeable `PRE_RESERVED_SEAT` amenity on GDS or NDC (`requiresSeatNumber`, `price: null`; no seat map). Markup rules have no ancillary scope, so the selling price is the Amadeus price; the `ancillary_service` fees come with checkout.setAncillaries (OADR-0005 point 7).

A reload that finds the fare gone (`SOLD_OUT`) answers `410 OFFER_EXPIRED`.

Flight Offers Price runs outside any transaction with the base priced offer's confirmed offers, the extras in `fareDetailsBySegment[].additionalServices`, the travellers entered so far and `include=bags,other-services`; 4926 and 32171 on a selection are `422 ANCILLARY_NOT_AVAILABLE` (`rejected_by_airline`, `seat_unavailable`), `409 SOLD_OUT` and the timeouts stay, any other error is `502 SUPPLIER_ERROR`. `selections: []` reverts to the base priced offer without a call (unless it expired) and loads no catalogue (only the feature is checked). One transaction locks the checkout, stores the answer as a child priced offer (`parent_priced_offer_id`; `PricedOffersService.storeServicesPricing`: the flights' amounts only, the base's markup and booking fees kept while Amadeus confirms the flights' net, else the flights priced again) and prices each extra: its net is Amadeus's `price.additionalServices` of its kind shared by catalogue prices, or the catalogue price where Amadeus states none, plus one `ancillary_service` fee line from the engine (in `checkout_ancillaries.price_amount`, the net in `net_amount`, the lines in `details` and the child's snapshot); an extra the answer does not carry in its fare detail is `422 ANCILLARY_NOT_AVAILABLE` (the order is created from those offers verbatim). The totals follow the checkout's pricing mode (`pricing-mode.ts`, as `createPayment` and `updatePayment` compute them): at the selling price `offer` = the child's selling total and `ancillaries` = Σ of the extras' selling prices; at the airline's price (`pricing_mode = net`, an airline-card payment) `offer` = the child's Amadeus total and `ancillaries` = Σ of the extras' Amadeus prices, without markup or `ancillary_service` fee, so the totals stay the airline-card payment's amount. The card fee is unchanged and `total = offer + ancillaries + cardFee`; a differing `expectedTotal` is `409 PRICE_CHANGED` (`details.oldPrice`, `newPrice`, `pricedOfferId` of the stored child) with the checkout unchanged. The payment of the checkout is not touched here: `checkout.updatePayment` or a new `checkout.createPayment` starts from the new amounts, and `checkout.complete` compares the authorised amount with the total.

**Payments** (`src/payments/`, OBE-038; [flow](../docs/flows/checkout-stripe.md) §2 steps 3–4, [OADR-0010](../docs/adr/0010-stripe-gateway-and-payment-webhooks.md) points 1–3, 7, 8, [ADR-0011](../../docs/mvp/adr/0011-payments-stripe-and-airline-card.md) (A)). `checkout.createPayment` (`POST /v1/checkouts/{checkoutId}/payments`, `201` with `Location`, `Idempotency-Key` required), `checkout.getPayment` (`GET /v1/payments/{paymentId}`) and `checkout.updatePayment` (`PATCH /v1/payments/{paymentId}`), for edge and key callers, access as the checkout's (`404` otherwise, another tenant's id included), `Cache-Control: no-store`. `card` on Stripe in `velexis` mode and `airline_card` (below) in this release; the flows are described step by step in `payments.service.ts`.

**Bookings: checkout.complete for Stripe** (`src/bookings/`, OBE-042; [architecture-booking](../docs/architecture-booking.md) §1 and §2, [flow](../docs/flows/checkout-stripe.md) §2 steps 5–7 and §3, [OADR-0003](../docs/adr/0003-booking-orchestration-and-supplier-timeout-recovery.md) points 1–3, [OADR-0008](../docs/adr/0008-ticketing-policy.md) points 1 and 7). `checkout.complete` (`POST /v1/checkouts/{checkoutId}/complete`, `201` with `Location: /v1/bookings/<bkg_…>`, `Idempotency-Key` required, `Cache-Control: no-store`) is CheckoutModule's route over `BookingOrchestrator` (`BookingsModule`, which never imports CheckoutModule or PaymentsModule: it reads checkouts and payments through their repositories). Five steps, and no database transaction is open while Amadeus or Stripe is called (the integration test watches the pool):
- **Read** (T0): the checkout as checkout.get reads it (`404`), a booking of it (`409 CHECKOUT_ALREADY_COMPLETED` with `details.bookingId`, or `504 SUPPLIER_TIMEOUT` while it is `pending`), `410 CHECKOUT_EXPIRED`, travellers and contacts against the requirements (`422 CHECKOUT_INCOMPLETE`), the payment (`paymentId` or the active one; an airline-card payment `422 UNPROCESSABLE`, `use_airline_card_completion`); `payment_timing` must be `authorize_before_booking` (OADR-0008 point 2). The PaymentIntent is read again: `requires_capture` for exactly the total (`409 PAYMENT_AMOUNT_MISMATCH`, as the OTA document says), not confirmed `402 PAYMENT_REQUIRED`, declined `402 PAYMENT_DECLINED`; a total above `expectedTotal` is `409 PRICE_CHANGED`.
- **Claim** (T1): the checkout `FOR UPDATE`; the `bookings` row `pending` with a new reference (`VX` and 6 characters without 0/O/1/I, `booking-reference.ts`), `create_order_started_at`, the amounts of the checkout and the priced offer, the trip; the payment linked; event `booking.create_order_started`. `bookings.checkout_id` is UNIQUE, so a concurrent claim answers as a booking of the checkout does.
- **Call**: a priced offer that expired, is older than 10 minutes or has travellers with discount data is priced again, a child priced offer: without extras `PricedOffersService.repriceForCheckout`; with extras the base priced offer's offers with the same `additionalServices` checkout.setAncillaries sent (`storedExtrasOf`, `buildServicesRequest`), stored with `storeServicesPricing`, each extra priced again with its `ancillary_service` fee, so the new priced offer, the totals and the order keep them. The new total is compared in the checkout's pricing mode: a higher one, or an extra Amadeus no longer confirms (the answer lacks it, or a 4926/32171 on it: the flights are then priced alone), voids the authorisation, fails the booking, moves the checkout to the new priced offer, extras and totals and answers `409 PRICE_CHANGED` (`details.oldPrice`, `newPrice`, `pricedOfferId`, and `reason: extras_unavailable` for an extra): never a booking without an extra that was paid for. A lower one is booked (warning `PRICE_DECREASED`), the booking's `ancillaries_amount` and `net_services_amount` following. Before the send, under the booking's lock (`recordSending`, FIX-W25-BOOKINGS, OADR-0003 point 2), the booking must still be `pending` and undecided (else nothing is sent: a reconciliation that adopted a slow claim decided it) and records what is sent: `issue_requested` and, after an accepted re-price, the priced offer sent with its amounts, so a process that dies after the send leaves a booking the reconciliation captures for the re-priced total; the checkout moves only in T2 or at an unknown outcome, so a request that is not sent leaves it on the total its authorisation holds. Flight Create Orders (`order-request.builder.ts`): the priced offers verbatim, the travellers with their decrypted documents (fields of the specification only), the contacts, the special requests upper-cased (GENERAL_MISCELLANEOUS) and the remark `VELEXIS <reference>` (BACKOFFICE, last), `automatedProcess` IMMEDIATE on `storefront_settings.booking_queue_number`/`_category` in the queuing office, `formOfPayments` `other.method` ACCOUNT, `ticketingAgreement` CONFIRM, `issue=true` for `issue_at_booking` or `instantTicketingRequired`. Its outcome follows [OADR-0003](../docs/adr/0003-booking-orchestration-and-supplier-timeout-recovery.md) (`createFailureKind`): only an Amadeus `4xx` business refusal (`SOLD_OUT`, `PRICE_CHANGED`, data errors, ticketing) voids the authorisation (`pi:cancel:<pay_id>`; a failed void queues `payment.void {tenantId, id}` on `ota-payments`, job id `payment-void-<pay_id>`), marks the booking `failed` with its `checkout_id` cleared and reopens the checkout (`409 SOLD_OUT`, `422 TRAVELER_DATA_INVALID`, `502 TICKETING_FAILED`, `502 SUPPLIER_ERROR`); a request that never reached the order or was refused before it was processed (token, rate limiter, a connection never made, an Amadeus `401`, `403` or `429`) fails the booking and keeps the authorisation; every other answer once the request may have reached Amadeus (a timeout, a reset, an Amadeus `5xx` such as 500, 502, 503 or 504, an answer that cannot be read) is an unknown outcome: the booking stays `pending` with the authorisation and its checkout (which cannot change meanwhile), `reconcile_until = create_order_started_at + 15 minutes` and the event `booking.supplier_timeout` for the reconciliation of OBE-043, and the answer is `504 SUPPLIER_TIMEOUT` (`details.bookingId`); nothing is voided and Flight Create Orders is never sent again for the checkout.
- **Record** (T2, `order-recorder.ts`): `confirmed`, or `ticketed`/`partially_ticketed` when tickets came back; record locator, associated records, travellers (documents sealed again for `booking_travelers`, associated data `tenant_<key>.booking_travelers.<column>:<btr_…>`), contacts, segments (instants from the airports' time zones), remarks, tickets, `order_snapshot` after the shared redactor, `ticketing_deadline_at` (start of `lastTicketingDate` or an earlier agreement date, in the OTA's time zone), events, the `booking.confirmed` e-mail in the outbox; the checkout `completed`. An order that exists but cannot be recorded (an answer that cannot be read, a T2 that fails) is an unknown outcome too: the booking stays `pending` with `reconcile_until` and the answer is `504 SUPPLIER_TIMEOUT`, like a lost answer.
- **Money and issue**: the capture `pi:capture:<pay_id>:<amount>` (not for `manual_review` without tickets: staff are alerted with `staff.manual_review` and capture from the console). A failed capture answers `201` with the warning `CAPTURE_FAILED`, sets `ticketing_status = manual_review` (a ticketed booking keeps `issued`), queues `payment.capture_retry {tenantId, id}` on `ota-payments` (the payment id, as [architecture](../docs/architecture.md) §6 gives the queue's payload; job id `capture-retry-<pay_id>`, 10 minutes later; OBE-040 consumes it) and alerts staff. `issue_after_payment` then calls Flight Order Issue; a failure leaves the booking `confirmed` with `ticketing_status = failed` and the next attempt 5 minutes later (OBE-044).
- **Lock order** (FIX-W24-BOOKINGS and FIX-W25-BOOKINGS, OADR-0003 point 11, [architecture-booking](../docs/architecture-booking.md) §1.1): the checkout, then the booking, then the payment, then the refund, a foreign-key lock (the `FOR KEY SHARE` of an insert that references a row) counting as a lock of the parent. The claim locks the checkout, an existing booking, then the payment; T2, the unknown outcome and the failure (`failBooking`, after a void) lock the checkout before the booking (since FIX-W25-BOOKINGS); the capture and the failed capture lock the booking `FOR UPDATE` before the payment; the reconciliation's found and not-found decisions lock the checkout, then the booking (then the payments), its capture and failed capture the booking, then the payment.
- **Answer**: CheckoutCompletion with the booking in customer scope and the warnings; for a guest booking its guest token (OBE-047, see the guest access below): in `bookingToken`/`bookingTokenExpiresAt` for a key caller, in the `__Host-vx_bt` cookie for the edge (both fields `null`); the `504 SUPPLIER_TIMEOUT` of an unknown outcome carries one the same way (`details.bookingToken`, or the cookie). Staff alerts go to `ops_alert_email`, else the owners, else `OPS_ALERT_EMAIL` (`notifications/staff-recipients.ts`, OBE-055; the API reads it too since FIX-W28-NOTIFY, lead decision (4) of 2026-10-23; skipped and logged only without any); their console link is `https://admin.<STOREFRONT_BASE_DOMAIN>/bookings/<bkg_…>`.
- **Not yet**: the booking's `amadeus` view and the real allowed actions of `allowed-actions.ts` in checkout.complete's answer (bookings.get has them since OBE-046), saved travellers and booking documents. The timeout reconciliation and the replays of a stored `504` are below (OBE-043).

**Bookings: the timeout reconciliation and the replayed `504`** (`src/bookings/reconcile.service.ts`, `reconcile.processor.ts`, the idempotency hooks of `booking-orchestrator.service.ts`, OBE-043; [OADR-0003](../docs/adr/0003-booking-orchestration-and-supplier-timeout-recovery.md) points 4–6, [architecture-booking](../docs/architecture-booking.md) §4 and §5.2):

- **After an unknown outcome** (checkout.complete above): the booking keeps `reconcile_until = create_order_started_at + 15 minutes`, holds what the order sent holds (recorded before the send; an accepted re-price moves the checkout to the new priced offer too, `issue_requested` is the flag sent), and `booking.reconcile {tenantId, bookingId}` goes to `ota-bookings` after the commit, 30 s delayed (job id `booking.reconcile:<bkg_…>:first`; a Redis that does not answer leaves it to the scan).
- **Stale claims** (FIX-W24-BOOKINGS, lead decision of 2026-10-21, OADR-0003 point 4): a booking `pending` without `reconcile_until` (the process died between the claim and Flight Create Orders, or the unknown-outcome write failed: `bookings.reconcile_not_scheduled`) would keep its checkout locked and its authorisation held. Each scan first adopts, at most 100 at a time, the oldest first, the `pending` bookings without `reconcile_until` or `reconcile_outcome` whose `create_order_started_at` is more than 2 minutes old (`ReconcileRepository.adoptStaleClaims`, `FOR NO KEY UPDATE SKIP LOCKED` since lead decision (1) of 2026-10-22, so two scans adopt a claim once and a row's foreign-key `FOR KEY SHARE` never makes a scan skip it): `reconcile_until = now + 15 minutes`, event `booking.reconcile_adopted` (staff only, `data.reason: stale_claim`), log `bookings.reconcile_adopted` (ids only). The adopted booking is then reconciled like any unknown outcome: the search first, a void and a reopened checkout only once the order is proven absent. A younger claim is left alone (its request may still be in flight).
- **Scan**: `bookings.reconcile_scan` (every minute, `active` and `suspended` tenants: a suspended OTA's authorisations are captured or released all the same) adopts the stale claims, then, in the same transaction, lists the bookings to decide and after the commit enqueues `booking.reconcile` (id `booking.reconcile:<bkg_…>:<minute bucket>`) for at most 100 bookings `pending` with `reconcile_until` (the adopted ones included), no `reconcile_outcome` and the order sent at least 30 s ago, the earliest deadline first. Since FIX-W28-CANCEL it also lists, in that transaction, at most 100 live bookings whose newest cancellation event is an undecided flag (`booking.cancellation_timeout`) written a minute ago or more, of the bookings changed in the last day (`cancellation-state.ts` `undecidedFlags`), and adds the first `booking.cancellation_check` of each flag again under the producer's job id `booking.cancellation_check:<bkg_…>:<deadline>-1`, without its delay: a lost enqueue is checked once, a queued one never twice. A flag still undecided 5 minutes after its deadline (`CANCELLATION_SWEEP_FINAL_AFTER_MS`) lost a later check of its chain (every check after the deadline decides), so it gets the chain's last check instead, `…:<deadline>-30` (`CANCELLATION_CHECK_MAX_RUNS`, which never reschedules), just as single by its id. Its counts are `adopted`, `due` and `cancellationChecks`.
- **Attempt** (worker, `ota-bookings`, concurrency 4; `BookingsWorkerModule`): claim with `FOR NO KEY UPDATE SKIP LOCKED` (lead decision (1) of 2026-10-22: a `FOR KEY SHARE` holder never makes it skip; checked again; at most one attempt per 45 s, `reconcile_attempts + 1` as the attempt's fencing token, committed before Amadeus); then Queue List of the booking queue (`storefront_settings.booking_queue_number`/`_category`, `max` RECONCILE_QUEUE_LIST_MAX = 500) in the booking's queuing office, and every PNR created from 1 minute before to 5 minutes after `create_order_started_at` (Queue List's minute, read in UTC unless it names an offset; a PNR whose creation cannot be read counts too, read last) whose travellers include the lead's last name (compared without accents, case or punctuation), the closest in time first, read by record locator (`originSystemCode` GDS), at most RECONCILE_MAX_READS = 50 per attempt (`readSlice`: the next attempt reads the next ones; three before FIX-W25-BOOKINGS, lead decision of 2026-10-21, third batch); an order is accepted only with the general remark `VELEXIS <reference>` of sub-type BACKOFFICE, never for a name alone. A read Amadeus answers `404` is not ours. A search that could not read every candidate is incomplete (`SearchGap`, `listedGap` for what the Queue List answer and the cap leave out: `queue_failed`, `queue_unreadable`, `queue_truncated` when the answer holds 500 PNRs or its `meta.count` says more, `candidate_unreadable` for an entry with the lead's name but no record locator or with no readable names, `read_cap`, `read_failed` for a read that failed or timed out, `order_unreadable`, `lead_unknown`; log `bookings.reconcile_search_partial` with counts), and an incomplete search never proves the order absent: the next attempt looks again until `reconcile_until`. **A booking queue that is nearly full** (FIX-W27-SYNC, lead decision (5) of 2026-10-23): when the Queue List answer holds BOOKING_QUEUE_ALERT_ENTRIES = 400 entries or more (80 % of the 500 one answer carries), or its `meta.count` says the queue does, the attempt raises the staff alert `staff.manual_review` about the OTA (no booking; dedupe key `staff.manual_review:booking_queue_nearly_full:<environment>:<UTC day>`, so at most once a day per OTA and environment, test and live separately since FIX-W28-NOTIFY, lead decision (5) of 2026-10-23; the queue's number, category, office and environment, the count and the 500 limit; log `bookings.booking_queue_nearly_full`) in a short transaction of its own, written by StaffAlerts (`staff-alerts.ts`, the reconciler's alert writer), and goes on with its search as it would without it (an alert that fails is logged, `bookings.booking_queue_alert_failed`). Cleaning the queue stays manual: the runbook "Cleaning the booking queue" in §4 below.
- **Found**: in one transaction under the checkout's lock, then the booking's (still `pending`, no outcome) the order is recorded by `OrderRecorder` as checkout.complete records it, from the checkout's travellers (documents decrypted), contacts and special requests (`confirmed`/`ticketed`, children, events, the `booking.confirmed` e-mail), with `reconcile_outcome = found`, event `booking.reconciled` and the checkout `completed`, which releases its lock. Then the money of step 4 (`pi:capture:<pay_id>:<amount>` for the booking's total, which checkout.complete recorded before the send, the re-priced one included, never more than the authorisation (`captureAmountOf`), through the worker's own `StripeGateway`; not for `manual_review` without tickets, whose staff are alerted; a failed capture sets `manual_review`, queues `payment.capture_retry` 10 minutes later and alerts the staff) and, for `issue_after_payment`, the issuance through `TicketingService.attempt` (a resync, then Flight Order Issue), its next attempt set to now so `ticketing.scan` takes over when needed. A record that fails is logged, alerted once and tried again by the next attempt.
- **Not found** by `reconcile_until` (a complete search after it, or without a booking queue simply once it passed), only while the attempt still holds its claim, the checkout, the booking and its payments locked in that order: the booking `failed` (`failure_code = SUPPLIER_TIMEOUT`, `reconcile_outcome = not_found`, `checkout_id` cleared), events `booking.failed` (staff) and `booking.not_confirmed` (the traveller's timeline), the checkout `open` again (`expired` past its expiry), `payment.void` of its Stripe authorisation on `ota-payments` after the commit (job id `payment-void-<pay_id>`; payments.processor.ts voids it), the e-mail `booking.not_confirmed` to the checkout's primary contact and a staff alert (`staff.manual_review`, "check the office by hand" without a booking queue). An airline-card booking is never failed automatically (OBE-051, OADR-0004 point 7): not found, it goes to the staff's review instead (`reconcile_outcome = manual_review`, `ticketing_status = manual_review`, the staff event `booking.reconcile_manual_review` with `reason: airline_card_not_found`, a staff alert; the booking stays `pending` with its checkout and its `processing` payment, and the scan stops); found, its order is recorded and its payment settled as checkout.completeWithAirlineCard settles it (`settleAirlineCardOrder`: `captured`, `airline.charged`, when every ticket came back; else the ticketing in `manual_review` and a staff alert), with nothing to capture or issue.
- **Undecided** (FIX-W25-BOOKINGS): the search of the attempt at or after `reconcile_until` is still incomplete, only while the attempt holds its claim: never a void (OADR-0003 point 5's manual review). The booking stays `pending` with its checkout (still locked) and its authorisation, `reconcile_outcome = manual_review`, `ticketing_status = manual_review` (the console's `reconcileOutcome=manual_review` filter), the staff event `booking.reconcile_manual_review` (`data.gap`, `code`, `candidates`, `read`, `deadlineRetries`) and a staff alert (dedupe `staff.manual_review:<bkg_…>:reconcile_manual_review`); outcome `manual_review` with the gap, log `bookings.reconcile_manual_review`. The scan no longer picks it up and the same key's replay keeps answering the `504`; the staff decide.
- **Grace after the deadline** (FIX-W26-BOOKINGS, lead decision (3) of 2026-10-22, OADR-0003 point 5): a search at or after `reconcile_until` that is incomplete only because of transient failures (`transientFailure`: `RATE_LIMITED`, `SUPPLIER_TIMEOUT`, `SUPPLIER_UNAVAILABLE`, `SERVICE_UNAVAILABLE`, and an Amadeus `5xx`, `429`, timeout or network error behind any other code, of Queue List or of a by-reference read) is tried again instead of reviewed, up to RECONCILE_DEADLINE_RETRIES = 3 more attempts, one per scan: each writes the staff event `booking.reconcile_deadline_retry` (`data.retry` 1 to 3, `gap`, `code`), whose number is the grace used (counted at the claim; no column), and answers `pending` with `reason: deadline_retry`; the booking keeps no outcome, so the next scan's attempt searches again and decides like any attempt past the deadline (found: recorded; a complete search: not found; failing transiently again after the 3: the review above). A search incomplete for any other reason (`read_cap`, `queue_truncated`, `queue_unreadable`, `candidate_unreadable`, `order_unreadable`, `lead_unknown`, a read Amadeus refuses) goes to the review at the deadline, without grace.
- **Replays**: `CompleteCheckoutIdempotencyHooks` (`@IdempotencyHooksFor(["completeCheckout"])`) links a stored `504 SUPPLIER_TIMEOUT` to its booking (`resourceOf`: `resource_type = booking`), so the record is kept 24 h instead of released, and answers its same-key retries from the booking (`resolveReplay`): the same `504` with `details.replayed: true` while it is `pending`, the final `201` CheckoutCompletion built from the booking (`Location`, `no-store`) once it was found, the final `502 SUPPLIER_ERROR` (`details.bookingId`, `bookingStatus: failed`: nothing was booked, the payment is released) once it failed. checkout.complete refuses a payment whose booking failed that way (`402 PAYMENT_REQUIRED`): its authorisation is being voided.

**Bookings: the customer's bookings** (`src/bookings/customer-bookings.controller.ts`, `customer-bookings.service.ts`, `bookings.mapper.ts`, `allowed-actions.ts`, `src/common/auth/booking-access.guard.ts`, OBE-046; [flow](../docs/flows/my-bookings-and-guest-lookup.md) §3 steps 4–5 and §4, [db README §10](../../docs/velexis-sdk/db/README.md) "My trips"). Five `x-scope: customer` reads, all in customer scope (selling amounts; no net price, markup, office or staff data) and `Cache-Control: private, no-store` (`no-store` for the ticketing status):

- **`bookings.list`** (`GET /v1/bookings`, a signed-in customer required): the customer's bookings of the request's environment only (customers are shared by test and live). `timeframe` `upcoming` (default; `pending`, `confirmed`, `ticketed`, `partially_ticketed` whose `last_arrival_at` is now or later, first departure first), `past` (the same statuses, landed, newest departure first), `cancelled` (newest departure first) and `all` (every status but `failed`, newest booking first); `sort`, `departureFrom`/`departureTo` (local date of the first departure), `createdFrom` (inclusive)/`createdTo` (exclusive). Keyset cursors carry the sort key in UTC with microseconds, the id and a fingerprint of the filters: a cursor of other filters is `400 VALIDATION_FAILED` (`/query/cursor`). A card's lead traveller is the first adult, the destination city comes from the reference schema; a pending booking (no flight rows yet) shows its stored trip.
- **Access** (`BookingAccessGuard` on the four operations under `/v1/bookings/{bookingId}`): without a signed-in customer and without a guest token for the booking, `401 UNAUTHENTICATED` (the page offers the lookup); an unknown id, a booking of the other environment (a test booking from a live storefront or with a live key), another customer's booking and a token of another booking or one expired or revoked all answer the same `404 NOT_FOUND`. Guest tokens are compared by SHA-256 with `booking_access_tokens.token_hash`; their sources (`__Host-vx_bt`, `X-Booking-Token`) are in the guest access below (OBE-047). The decision is kept in the request context (`BookingAccessContext`) and asked again by the service.
- **`bookings.get`** (`ETag: "<version>"`): the booking of order-recorder.ts `toBooking` with its services, refunds, current documents, the cancellation (`bookings.mapper.ts` `cancellationOf`, FIX-W28-CANCEL: of a cancelled booking its typed reason from `cancel_reason`, the customer's comment, request time and estimate from its `booking.cancelled` event and the money of its refund, void or capture; a `pending` block while a cancellation waits for the staff or is undecided; the block bookings.cancel answers), `fareConditions` (fare rules when loaded, else the booked offers' amenities), `fareRules` when asked for and loaded, `allowedActions` (`allowed-actions.ts`: cancel only with the storefront's `features.selfServiceCancellation`, off unless the OTA turns it on, nothing departed and more than 3 h before departure, an Amadeus order and no cancellation undecided or waiting for the staff, `pending`; contacts and remarks until the last flight landed; traveller changes and post-booking extras never in the MVP; refresh throttled for 60 s) and `amadeus`: the stored snapshot through the shared redactor again, the markup folded into the offers' and travellers' prices, forms of payment reduced to type and brand, offices, automated processes, commissions, staff remarks and the net `refundingPreview` removed, form of identification numbers cut to their last 4, and only the `carriers` and `aircraft` dictionaries (the document's location and currency entries require a `key` member Amadeus maps never have). `included` bag options (net prices) are never shown.
- **Refresh** (`refresh=true` of bookings.get and getTicketingStatus, and getFareRules without fresh rules): at most one Flight Order Management GET per booking and minute, shared by the three, run by `BookingSyncService.refresh` (`booking-sync.service.ts`, FIX-W27-SYNC, lead decision (3) of 2026-10-23: the background sync's claim column, diff and events). The claim locks the booking and records `bookings.sync_claimed_at` (the throttle's record, also the background sync's claim, which keeps the sync away for 30 minutes; until FIX-W27-SYNC a staff-only `booking.sync_requested` event, about four a day per upcoming booking, which filled the console's timeline; the events written before stay); a concurrent claim waits for the lock and reads the booking in a statement after it, so it sees the column; a claim within 60 s of the last one or of `last_synced_at` is `syncStatus: throttled`; bookings without an order (pending, failed) and cancelled ones are not refreshed. The call runs without a transaction. The record writes nothing when the booking's `version` moved since the claim (another writer recorded it meanwhile; the stored booking is answered); otherwise it records the order through the background sync's diff of `order-diff.ts` (below) and writes the same events, so a schedule change or a cancellation by the airline is reported whichever path sees it first: the redacted `order_snapshot`, `order_dictionaries`, new tickets and changed ticket statuses, the segments (changed times, airports, terminals, flights and Amadeus statuses rewritten, added and removed ones, `isFlown`; event `booking.schedule_changed`, which asks for a new itinerary), a cancellation by the airline (`cancelled`, `booking.cancelled`, the traveller's e-mail, the staff alert of a paid booking), associated records the booking does not have yet (an airline locator that appeared after booking), a booking that became `ticketed`/`partially_ticketed` (event `booking.ticketed`, also for new tickets alone), the forms of identification (last 4 characters), `order_included` (`bags`, `fareRules` with `loadedAt`), what changed (`sync_changes`), `last_synced_at`, and clears `sync_error`. The `version`, and with it the ETag, moves whenever the record stores new or changed tickets, a new status or changed segments, the changes the documents follow (FIX-W26-BOOKINGS, lead decision (6a) of 2026-10-22: the documents queue deduplicates by the version, so the itinerary is rendered again with a new ticket); a refresh that stores nothing else keeps both. console.bookings.get with `refresh=true` and console.bookings.resync record through the same service, so the same holds there. Amadeus `404` keeps the stored booking with the warning `ORDER NOT FOUND AT THE AIRLINE` (`sync_error = ORDER_NOT_FOUND`, `syncStatus: failed`); other Amadeus errors are recorded in `sync_error` and answered `502/503/504` (an undocumented code becomes `502 SUPPLIER_ERROR`); an answer that cannot be read as an order is `502 SUPPLIER_ERROR`.
- **`bookings.getTicketingStatus`**: the ticketing columns, the tickets and `pollAfterSeconds` (10 while the create-order outcome is unknown, 5 while ticketing is `pending` or `in_progress`, else null); a refresh is skipped once the state is final.
- **`bookings.listEvents`**: `booking_events` with `visible_to_customer` only (staff notes, supplier diagnostics and the refresh claims written before FIX-W27-SYNC are console-only), newest first, with the actor's type but never its id and `data` through the shared redactor; keyset cursor.
- **`bookings.getFareRules`**: from `order_included.fareRules` while loaded less than an hour ago with the requested `types`, else a GET with `fareRules`; per rule the category, applicability, penalty, texts and rebook conditions, `refundEstimate` null (the airline's `refundingPreview` is net: a fully refundable fare's preview is the net price; the cancellation quote of OBE-049 computes refunds in selling amounts), `amadeus` without `refundingPreview`; `available: false` when the airline returned none. A throttled load with nothing stored answers `429 RATE_LIMITED` with `Retry-After`.
- **Not yet**: the booked services' states (a refresh does not read the order's services; post-booking extras are deferred), checkout.complete's booking still carries order-recorder.ts's interim allowed actions and no `amadeus`.

**Bookings: guest tokens and bookings.lookup** (`src/bookings/guest-access.service.ts`, `lookup.controller.ts`, the token sources of `src/common/auth/booking-access.guard.ts`, the `__Host-vx_bt` entries of `src/common/http/cookie-writer.ts`, OBE-047; [flow](../docs/flows/my-bookings-and-guest-lookup.md) §2, §3 step 8 and §4, [OADR-0006](../docs/adr/0006-storefront-cookie-sessions-and-csrf.md) points 1, 4 and 6):

- **Tokens**: `vxbt_<environment>_` and 256 random bits in base64url; only the SHA-256 is stored (`booking_access_tokens.token_hash`, with `issued_via`, `created_ip` and `expires_at`). checkout.complete issues one for every booking without a customer (`booking_created`), with the `201` and with the `504` of an unknown outcome, valid 30 days or until 7 days after the last flight, whichever is later (the contract's `bookingTokenExpiresAt`); a lookup issues one for 24 hours. The edge gets it in `__Host-vx_bt` (HttpOnly, 30 days, up to five `bkg_<id>.<token>` entries separated by `~`, newest first: the new entry is prepended to the entries the request sent, an older entry of the same booking replaced, a sixth booking drops the oldest) and `null` in the body; key callers get it in the body and never a `Set-Cookie`. The same-key replays of a stored answer send the same token (the idempotency ciphertext); the final `201` of a replayed `504` hands on the `504`'s token (its details or its `Set-Cookie`).
- **Access**: the booking access guard reads the `__Host-vx_bt` entry of the requested booking for the edge (an `X-Booking-Token` header is ignored) and `X-Booking-Token` for key callers (cookies are ignored); only a value of the issued shape is looked up, the hash must be a live token row of the requested booking (a token of another booking is `404`), and each request it lets in records `last_used_at` and `use_count + 1` on the token row.
- **`bookings.lookup`** (`POST /v1/bookings/lookup`, `Idempotency-Key`, `Cache-Control: no-store`): `bookingReference` (upper case) against `bookings.reference`, `record_locator` and `booking_associated_records.reference`, among the bookings of the request's environment that are not `failed` (a test booking is never found from a live storefront or with a live key); `lastName` against any traveller's last name (the lead traveller's of a booking without travellers yet), case- and accent-insensitive; the newest match wins. A match issues the 24-hour token, writes the staff-only event `booking.lookup` and answers `200` with the booking's card (`BookingSummary`); every mismatch answers the same `404 NOT_FOUND` (the bodies differ in `requestId` only). **Brute force**: 5 failures per 15 minutes per end-user IP (`rl:ota_lookup_ip:<sha256>`) and per tenant and reference (`rl:ota_lookup_reference:<sha256>`); `LookupAttempts` counts an attempt on both before it is matched (one Lua script, always with the TTL) and takes it back unless it was a mismatch, so with five counted the next lookup answers `429 RATE_LIMITED` with `Retry-After` without being matched, and a burst of parallel guesses never gets more than five matches; a Redis that cannot answer refuses with `503`. Tokens, names and references never reach a log line.
- **Not yet**: e-mail links with a token (`email_link`) and staff-issued tokens; the retention purge of expired tokens (`retention.daily`).

**Bookings: bookings.update** (`src/bookings/booking-changes.service.ts`, the `PATCH /v1/bookings/{bookingId}` handler of `customer-bookings.controller.ts`, OBE-048; [flow](../docs/flows/change-and-cancel.md) §1, §3 steps 1–2 and §4). - **`console.payments.refund`** (`POST …/{paymentId}/refunds`, `payments:refund`, `Idempotency-Key`): an airline-card payment → `422` `refund_via_airline`, anything but a Stripe payment `captured` or `partially_refunded` → `409` `payment_not_refundable`, the amount's currency and format as for a capture; then `RefundsRepository.create` in the request's transaction (the booking `FOR KEY SHARE`, then the payment; `422` `amount_exceeds_captured` with `details.refundable`: captured − refunded − in flight), the booking's customer-visible `refund.requested` event (`PaymentsRepository.insertRefundBookingEvent`, "Refund of 50.00 EUR requested."), `staff_actions` `payment.refund` (reason: `reasonNote`, else the reason code) and, after the commit, `refund.submit` on `ota-payments` (never failing the request: a Redis error or a 2 s timeout is logged and the row stays `pending` until `refunds.sweep` queues it again, 5 to 10 minutes later). `201` with `Location` (the payment) and the payment with its `pending` refund; no Stripe call, so no `502`. The requester is the staff member (`stf_…`), or `staff` without an id for a key-only call, whose `staff_actions` row names the key. Lead decision 6 of 2026-10-22: only Stripe's answer makes a refund refunded, so the webhook's `applyRefunds` writes the booking's `refund.succeeded` event ("Refund of 50.00 EUR completed.") when a refund of a booking becomes `succeeded`, after locking the refunds' bookings `FOR KEY SHARE` before the payment; nothing writes `payment.refunded`.

**Bookings: the ticketing retries** (worker, `ticketing-schedule.ts`, `ticketing.service.ts`, `ticketing.processor.ts`, OBE-044; [OADR-0008](../docs/adr/0008-ticketing-policy.md) points 3–5 and 8, [OADR-0014](../docs/adr/0014-per-tenant-workers-and-schedulers.md) point 6, [flow](../docs/flows/ticketing-and-documents.md) §2–§4). `BookingsWorkerModule` (worker only, on `AmadeusWorkerModule`, the worker's Amadeus client: no `AMADEUS_BASE_URL_*` there, so its calls go to the account's `base_url`, the stub's in development):
- **Schedule** (`ticketing-schedule.ts`): after the failure of attempt 1 (inside checkout.complete), 2 and 3 the next attempt comes 5 minutes, 15 minutes and 1 hour later, then every 2 hours; at most 8 attempts; never later than `ticketing_deadline_at − 2 h`; a failure for payment reasons (`PAYMENT_DECLINED`) is never retried.
- **Scan**: `ticketing.scan` (every 5 minutes, `active` and `suspended` tenants) enqueues `ticketing.issue {tenantId, bookingId}` on `ota-ticketing` (id `ticketing.issue:<bkg_…>:<minute bucket>`) for at most 100 `confirmed` bookings with an order whose `ticketing_status` is `pending` or `failed` with `ticketing_next_attempt_at` reached, or `in_progress` with a claim older than 5 minutes; never an airline-card booking (`payments.method = airline_card`; OBE-051 sends those to manual review) and, for a suspended tenant, only paid ones (`amount_paid > 0`).
- **Attempt** (`ota-ticketing`, concurrency 2): claim with `FOR NO KEY UPDATE SKIP LOCKED` (lead decision (1) of 2026-10-22, OADR-0014 point 6: a transaction that only holds the booking's `FOR KEY SHARE`, such as a document's write or an event's insert, never makes it skip; another claim or a writer that locked the booking does; checked again; `in_progress`, `ticketing_last_attempt_at = now` as the fencing token, `ticketing_attempts + 1`, committed before Amadeus), then Flight Order Management GET first: tickets already there (an earlier call that timed out) are recorded, and no Flight Order Issue is sent; otherwise Flight Order Issue (`other.method` ACCOUNT for the order's offers). A failed GET is a failed attempt (never an issue without a resync); a timed-out issue "may have issued" and the next attempt starts with the resync. An attempt that may not issue any more (deadline, payment, attempts; a worker that was down) only re-reads the order. The result is written under the claim (the booking still `confirmed` and `in_progress` with the claim's time, else nothing is written): tickets (`ticketed`/`issued` or `partially_ticketed`), the redacted `order_snapshot` and event `booking.ticketed`; or `failed` with the error code and the next attempt (event `booking.ticketing_failed`); or, without a next attempt, giving up: `ticketing_next_attempt_at = NULL`, events `booking.ticketing_failed` and `booking.ticketing_delayed` (the traveller's timeline), outbox `staff.ticketing_failed` (to `ops_alert_email`, else the owners, else `OPS_ALERT_EMAIL`: `notifications/staff-recipients.ts`, OBE-055) and `booking.ticketing_delayed` to the primary contact, once per booking (dedupe keys). The worker never cancels. Log lines carry ids, attempts and codes only.

The API process only produces jobs; every processor and scheduler runs in the worker. Schedulers are declared at worker start-up with `upsertJobScheduler`.

How the code uses them (OBE-002, `src/common/`):

- **`RedisModule`** (global, built once per process by whichever module imports it) holds two connections on `REDIS_URL`: `REDIS_CLIENT` for caches, locks, counters and hand-offs, which fails fast while Redis is down (one retry per command) so callers can degrade as [architecture §10](../docs/architecture.md#10-failure-behaviour) says, and `REDIS_BULLMQ_CONNECTION`, the BullMQ connection with `maxRetriesPerRequest: null`, which waits for Redis instead. Both connect on first use, log the first error of an outage once (`redis.connection_error`, never the URL), and quit after every queue and worker has closed. A connection with an attempt in flight is closed once that attempt has ended (`closeRedisConnection`): closing it during the attempt would make BullMQ 5 reject the set-ups still waiting on the shared connection after the queues have removed their listeners, unhandled rejections that stop the process. Because the BullMQ connection waits for Redis, a producer on a request path does not await `queue.add` while Redis is down (the outbox and the sweeps catch up).
- **`redis.keys.ts`** is the only place that writes a key: `redisKeys.<builder>(…)` returns `{ key, ttlSeconds, kind }` for every key of [architecture §7](../docs/architecture.md#7-redis-keys), and every write sets that TTL (Redis runs with `noeviction`). `tenant` keys (tenant data) always start with `t:<tenantId>:<env>:`; `shared` keys are those of the cross-cutting tables; `credential` keys belong to an Amadeus credential set. The builders validate every part (ids, environments, host names, SHA-256 hashes) and never echo it in an error. A key reaches the client only as a `RedisKeyName` from a builder, in a form the source scan of `redis.keys.test.ts` can read: no cast to `RedisKeyName`, a literal command name for `call`, literal command arrays for `multi([…])`, and a literal key count for `eval`.
- **`QueuesModule`** (static, imported by every module that produces or consumes jobs; no other module registers BullMQ queues) configures BullMQ once (the BullMQ connection, prefix `vx`, the job defaults of [ADR-0009](../../docs/mvp/adr/0009-background-jobs-bullmq.md): 5 attempts, exponential backoff from 30 s, failed jobs kept 30 days and completed jobs 1 day) and opens every queue of the table above (the eight the worker consumes and `platform-tenant-events`, which it produces), injectable with `@InjectQueue(<queue name>)` (`OTA_QUEUE.<topic>` for the consumed ones). A worker module declares `@Processor(OTA_QUEUE.tenantOps, otaWorkerOptions(OTA_QUEUE.tenantOps))` (the queue's concurrency of architecture §6 and the same retention) and attaches its own `error` listener to its worker. Before shutdown, its `BullmqStartupSettler` waits up to 1 s for queues and workers that are still connecting (`settleBullmqStartup`): BullMQ 5 would otherwise report a set-up interrupted by the close as an unhandled rejection, which stops the process (OBE-005).
- **`job-validation.ts`**: a processor of a cross-backend queue starts with `validateTenantOpsJob(job, logger)` (or `validateQueuedJob(job, names, logger)`). A message that is not one of the queue's names or does not match its `@velexis/api-types/jobs` schema is logged as `queue.job_invalid` (queue, job id, name, failing paths and rules; never the payload) and thrown as BullMQ's `UnrecoverableError`, so it fails at once without the remaining attempts.

The worker's modules (`worker.module.ts`): `RedisModule`, `QueuesModule`, `TenancyModule.forWorker()` (the platform repository and, since OBE-024, the platform caches with their `vx:invalidate` subscriber, `TenantContext` on the worker's request-context module and `TenantTx`, for jobs), `ProvisioningModule`, `JobsModule`, `NotificationsModule.forWorker()` (OBE-030), `DocumentsModule.forWorker()` (OBE-053: the storage, the renderers and the `ota-documents` consumer, see the booking documents below), `PaymentsWorkerModule` (OBE-039: the `ota-stripe-events` consumer; OBE-040: the `ota-payments` consumer and the authorisation watch; see Payments in §2) and `BookingsWorkerModule` (OBE-044: the `ota-ticketing` consumer and the `ticketing.scan` handler, see the ticketing retries in §2, with `AmadeusWorkerModule`; OBE-043: the `ota-bookings` consumer and the `bookings.reconcile_scan` handler, see the timeout reconciliation in §2; OBE-045: the `bookings.sync_scan` handler and the `booking.sync` jobs, see the background sync in §2), which the API never imports; the API imports `NotificationsModule.forApi()`, which queues e-mails and never sends, and `DocumentsModule.forApi()`, which asks for documents and never renders them. The API imports `TenancyModule.forApi()` (since OBE-011): its own `velexis_ota_app` pool (20 connections, opened on the first lookup), the platform repository and the caller classification, which only the API's module provides. Provisioning (OBE-005, OBE-006, `src/provisioning/`, [flow](../docs/flows/tenant-provisioning-worker.md), [OADR-0007](../docs/adr/0007-tenant-migration-runner-and-provisioning-worker.md)):

- **`tenant-ops.processor.ts`** consumes `ota-tenant-ops` (concurrency 2), validates each job and dispatches on its name. `tenant.provision` runs `ProvisioningService.provisionTenant` and `tenant.migrate` runs `migrateTenant(tenantId, targetVersion)`; after the transaction it publishes `tenant.provisioned` / `tenant.migrated` or the failure event. A non-retryable failure is published at once and the job fails as unrecoverable. A retryable one is thrown back to BullMQ while the job has tries left (the platform dispatches with `attempts: 3`; `tenant_ops.retrying`), and only its last try publishes `tenant.provision_failed` / `tenant.migration_failed` with `retryable: true` (the platform then re-dispatches with backoff). `tenant.suspend` and `tenant.resume` are not handled yet (M4–M5) and fail as unrecoverable. Log lines carry the error code, never the error. Worker errors are logged once per outage (`queue.worker_error`).
- **`failure-classifier.ts`** (OBE-006, [OADR-0007](../docs/adr/0007-tenant-migration-runner-and-provisioning-worker.md) item 6, [flow §5](../docs/flows/tenant-provisioning-worker.md#5-failure-handling)) turns what a run threw into the event's `error {code, message}`, `retryable` and the migration at fault (`version`). Retryable: `LOCK_TIMEOUT` (55P03), `SERIALIZATION_FAILURE` (40001), `DEADLOCK` (40P01), `CONNECTION_LOST` (class 08, 57P01–57P03, 53300, `ECONNREFUSED`/`ECONNRESET`/…, `pg`'s connection messages), also inside a failing migration file, and any error it does not know (by its SQLSTATE, or `UNEXPECTED_ERROR`). Not retryable: `CHECKSUM_MISMATCH` (an applied file was edited), `FOREIGN_CONTENT`, `FOREIGN_OWNER`, `SCHEMA_MISSING`, `INVALID_SCHEMA_NAME`, `MIGRATION_FAILED` (a file that fails for another reason fails the same way on every try), `INVALID_MIGRATION_FILES` (an invalid or missing tenant migrations folder) and `UNEXPECTED_PLATFORM_VALUE`, besides the service's own `TENANT_NOT_FOUND`, `TENANT_NOT_PROVISIONING`, `TENANT_NOT_MIGRATABLE` and `UNKNOWN_TARGET_VERSION`. Messages are written there, capped at the 1,000 characters of the event schemas (`jobError`, which the service's own failures use too): never PostgreSQL's text, the SQL, its parameters or a value of the tenant row.
- **`provisioning.service.ts`**: `provisionTenant(tenantId)` re-reads `platform.tenants`. A `provisioning` tenant gets **one transaction** as `velexis_provisioner`: `migrateTenantSchema({ create: true })` of `@velexis/db` (schema under the advisory lock of its name, `lock_timeout` 5 s, grants and default privileges for `velexis_ota_app`, every file of `migrations/tenant` and its ledger row) and, in its `beforeCommit`, the seeds of `provisioning/seeds/` and the ledger read; a crash before `COMMIT` leaves no schema. Another status answers `tenant.provisioned` again when the schema is complete at the latest version (checked read-only through `tenantTx`), otherwise `TENANT_NOT_PROVISIONING`; an unknown tenant is `TENANT_NOT_FOUND`, a schema provisioning did not create `FOREIGN_CONTENT` or `FOREIGN_OWNER` (never dropped). `migrateTenant(tenantId, targetVersion?)` (OBE-006) runs the same transaction without creating the schema or seeding (`migrateTenantSchemaFiles`), for a `provisioning`, `active` or `suspended` tenant (otherwise `TENANT_NOT_MIGRATABLE`), applying the pending files up to `targetVersion` (`0002_add_x` or `0002`; all of them without one, `UNKNOWN_TARGET_VERSION` for a version the release does not have); its `beforeCommit` refuses an edited applied file of the release, also one after the target, and reads the full ledger for `tenant.migrated {schemaVersion, migrations[]}`. Neither method throws: failures come back classified, with the error that caused them for BullMQ. The provisioner database (`DATABASE_PROVISIONER_URL`, a pool of 2 named `ota-worker-provisioner` for the read-only check) can only be built from the worker's configuration: the API's has no provisioner DSN, so it refuses with `ProvisionerDsnMissingError`.
- **`tenant-events.producer.ts`** validates each event with `validateJob` and adds it to `platform-tenant-events` with the BullMQ id of the attempt it answers (`<jobId>-<attempt>`, the platform ignores older attempts), the message's `jobId`, `tenantId` and `requestId`, and `steps[]` (`create_schema`, `run_migrations`, `seed_defaults`: `succeeded`, or `skipped` when there was nothing to do).
- **`report-migrations.command.ts`** (OBE-007, `node dist/cli.js tenants:report-migrations --report <file>`; [flow §4](../docs/flows/tenant-provisioning-worker.md#4-deploy-fan-out), [OADR-0007](../docs/adr/0007-tenant-migration-runner-and-provisioning-worker.md) item 7) turns the JSON report of the deploy fan-out (`migrate.js tenants --report`) into one event per schema it names on `platform-tenant-events`, with `jobId: null`: `tenant.migrated` for every `applied` schema (whether the run applied files or not) with the schema's full ledger, read as velexis_ota_app from its `schema_migrations` in a `tenantTx`, so a repeated run re-sends a correct mirror; `tenant.migration_failed` for every `failed` one, with the file at fault as `version` and an `error {code, message}` written from the report's SQLSTATE, line and exit code (`CHECKSUM_MISMATCH`, the transient codes of `failure-classifier.ts`, `MIGRATION_FAILED`, or the SQLSTATE), never PostgreSQL's text, and without `retryable` (the platform never retries a deploy report). `skipped` schemas (a `provisioning` tenant without a schema) get none. The tenant id is looked up in `platform.tenants` (read-only, `tenant_<key>`); a schema whose tenant is gone is named on stderr and skipped, and so is an `applied` schema that has no `schema_migrations` ledger any more (dropped after the fan-out; checked in the catalog first, since through the `search_path` the name would resolve to the `reference` ledger). Every event is built and validated before the first is added, and `requestId` comes from the report (`deploy-<sha>` for `migrate-<sha>.json`, else a hash of its content), so the events of one report are always the same. It reads `APP_ENV`, `LOG_LEVEL`, `DATABASE_URL` and `REDIS_URL` only (the variables of `ota-backend.env`; never a migrator or provisioner DSN), adds the events through a BullMQ queue whose connection gives up after three connection attempts, and exits 1 on an unreadable or invalid report, a database error or when Redis refuses an event (stderr says how many were published; running it again is harmless), 0 otherwise or when the report names no migrated or failed schema (without connecting).

Schedulers and per-tenant jobs (OBE-024, `src/jobs/`, [OADR-0014](../docs/adr/0014-per-tenant-workers-and-schedulers.md), [architecture §6](../docs/architecture.md#6-workers-queues-and-schedulers)):

- **`schedulers.ts`** declares the schedules of architecture §6 that the release runs (`OTA_SCHEDULES`: id, UTC cron pattern, milestone, the tenant statuses it targets, `active` and possibly `suspended`; never `provisioning`, `failed`, `deprovisioning` or `deleted`). `JobSchedulerRegistry` upserts one BullMQ job scheduler per schedule on `ota-maintenance` at worker start-up and removes the schedulers of schedules that no longer exist (`scheduler.registered`). It waits for the BullMQ connection's first attempt: with Redis up the schedulers are registered before the worker reports itself started; with Redis down the worker starts anyway and registers them once BullMQ is connected. Each iteration adds one `fan-out` job `{task: "<schedule id>"}`. Schedules join the list with the task that adds their work (M3: `checkouts.expire`, `notifications.sweep`, `payments.authorisation_watch`, `ticketing.scan`, `bookings.reconcile_scan`, `bookings.sync_scan`, `refunds.sweep`, …).
- **`fan-out.ts`**: `MaintenanceProcessor` consumes `ota-maintenance` (concurrency 2). A `fan-out` job runs `FanOutService`: one read-only query of `platform.tenants` for the schedule's statuses (`PlatformReadRepository.tenantIdsByStatus`), then one job per tenant named after the schedule, `{tenantId, bucket, continuation: 0}`, with the deterministic id `<task>:<tenantId>:<minute bucket>`. The bucket is the minute the scheduler iteration was due (BullMQ's `prevMillis` of the iteration's job; the `Clock` minute for a fan-out added by hand), so two runs of one iteration build the same ids and BullMQ adds each tenant's job once. `TenantJobRunner` runs a per-tenant job: it refuses a malformed payload or an unknown name at once (`UnrecoverableError`, `jobs.job_invalid` without values), resolves the tenant through the platform cache (`tenant:<id>`, as the API does), skips it unless its status is still one of the schedule's (`skipped`, `tenant_failed`, …), runs the schedule's handler (an injectable class marked `@TenantJob("<schedule id>")`, provided in the worker) inside `TenantContext.run` (the system actor, the job id as request id), and enqueues the job again as `<…>:<bucket>-<n>` when the handler filled its batch, at most `MAX_CONTINUATIONS` (20) times per run. Failed jobs are logged with their error code only (`jobs.job_failed`); BullMQ retries them with the defaults of ADR-0009.
- **`limits.ts`**: the batch sizes of OADR-0014 point 2 (20 bookings for sync, 50 checkouts for expiry, 500 searches for the purge, 100 outbox rows) and the fan-out's chunk of 100 jobs per `addBulk`.
- **`payments/authorisation-watch.processor.ts`** (`payments.authorisation_watch`, 06:15 UTC daily, `active` and `suspended` tenants, OBE-040; [OADR-0008](../docs/adr/0008-ticketing-policy.md) point 6): one transaction per job alerts the staff about at most 100 authorised, uncaptured Stripe payments whose authorisation is older than 5 days and that were not alerted yet (`payment.authorisation_expiring` event, once per payment), oldest first, `FOR UPDATE SKIP LOCKED`; a full batch continues. See Payments in §2.
- **`payments/refunds-sweep.processor.ts`** (`refunds.sweep`, every 5 minutes, `active` and `suspended` tenants, FIX-W27-FOLLOWUPS): one read without a lock per job finds at most 100 refunds still `pending` and never claimed 5 minutes after their request, oldest first, and `addBulk` queues `refund.submit` for each with its producers' job id (`refund-submit-<rfd_id>`); a full batch continues, and the n-th continuation reads the n-th batch after the first (offset), so refunds whose jobs BullMQ holds and will still run without having claimed them yet (a backlog) never hide a lost enqueue behind them. A refund whose job finished without claiming it (failed for good before its claim, or completed without one) is read again (`RefundsRepository.stillUnclaimed`), its finished job removed (`Queue.remove`, which leaves a job a worker holds) and the job added again under the same id (FIX-W28-FOLLOWUPS, lead decision (7) of 2026-10-23, second batch); the counts are `refunds` and `resent`. See Payments in §2.
- **`shopping/offers-purge.processor.ts`** (`offers.purge`, every 15 minutes, `active` and `suspended` tenants; [OADR-0002](../docs/adr/0002-offer-and-priced-offer-caching.md) point 6): one statement per job in `tenantTx` deletes at most 500 expired searches, oldest first, `FOR UPDATE SKIP LOCKED`, cascading to their offers, upsells and priced offers. A search is kept while one of its priced offers backs a checkout (`priced_offer_id` or `base_priced_offer_id`, the RESTRICT foreign keys being the safety net) or has not expired yet (a priced offer may outlive its search by up to `offer_ttl_minutes`, point 3). A full batch continues; `offers.purged` logs the count only.

E-mail notifications (OBE-030, `src/notifications/`, [OADR-0013](../docs/adr/0013-notifications-and-booking-documents.md) items 1–5, [ADR-0017](../../docs/mvp/adr/0017-email-documents-storage.md), [db README §6 and §8](../../docs/velexis-sdk/db/README.md)):

- **`outbox.service.ts`** (both processes, global): a use case calls `OutboxService.enqueue(trx, {templateKey, to, locale, data, secretData?, dedupeKey, customerId?, bookingId?})` inside its `TenantTx` transaction. The call is checked against the key's allow-list (`data` holds exactly the key's caller variables, `secretData` exactly its secrets, the recipient is one plain address; `InvalidNotificationError` rolls the use case back) and inserts a `pending` row: `payload` is `data` after the shared redactor (which must leave it unchanged), the secret values (the verification or reset token) are envelope-encrypted into `secret_payload_ciphertext` with the associated data `tenant_<key>.notifications.secret_payload_ciphertext:<ntf_…>`, and a `dedupeKey` makes the e-mail once only (`queued: false` for the second call). `afterCommit` of `TenantTx` (added for it; work registered in a transaction runs after its commit and is dropped on a rollback) adds `notify {tenantId}` to `ota-notifications`, never failing the caller (2 s at most; the sweep catches a lost enqueue).
- **`template.service.ts`**: the effective template is the tenant's active `notification_templates` row of the key for the e-mail's locale or its language (`en` for `en-GB`), else the English code default `templates/<key>.{subject,html,txt}.hbs` (the build copies them to `dist/`). Templates are a safe subset of Handlebars checked on the parsed template against the key's allow-list (`templates/registry.ts`): variables, `{{#if}}`, `{{#unless}}`, `{{#each}}` over a list (with `../`); no triple braces, helpers, partials, sub-expressions or `@` variables, and no secret link in the subject. A break is `TemplateInvalidError` with every problem (`part`, `line`, `message`, the console's `422 TEMPLATE_INVALID` of OBE-073); the parts compile in an isolated Handlebars environment in strict mode, the HTML part escaped, the subject one line.
- **`renderer.ts`**: the render data holds the allow-listed paths of the payload, `brand.*` from `storefront_settings` (brand name, support e-mail and phone) and the storefront URL `https://<key>.<STOREFRONT_BASE_DOMAIN>`, and the links built from the secrets (`verifyUrl` = `/account/verify.html?token=…`, `resetUrl` = `/account/reset-password.html?token=…`, [OADR-0015](../docs/adr/0015-storefront-build-urls-and-hosting.md) point 5). A tenant template that turns out invalid is logged (`notifications.template_fallback`) and the code default is sent instead.
- **`notifications.processor.ts`** (worker): `notify {tenantId}` resolves the tenant through the platform cache (`active` or `suspended`, OADR-0014 point 4), claims at most 100 due rows with `FOR UPDATE SKIP LOCKED` (a 5-minute lease on `next_attempt_at`, committed before anything is sent; `outbox.repository.ts`), renders and sends each one outside any transaction (`mailer.gateway.ts`: `From: "<brand name>" <MAIL_FROM address>`, `Reply-To: <support e-mail>`, Message-ID `<ntf_…@domain>`) and records it in the update fenced by the lease: `sent` with the secrets erased, or one more attempt and `pending` again after 1, 2, 4 and 8 minutes, `failed` with the secrets erased after the 5th; an e-mail that can never be sent (no template, an invalid code default, a ciphertext that does not decrypt, data outside the allow-list) is `failed` at once, without stopping the other e-mails of the batch. A failure of the SMTP connection ends the batch (the other rows wait a minute without an attempt). `notifications.sweep` (every minute, `active` and `suspended` tenants) enqueues `notify` (`notify:<tenantId>:<minute bucket>`) for a tenant with a due row. Log lines carry ids, the template, the attempt and the SMTP error code, never the recipient, a variable or the message.
- **Defaults**: every MVP key has one: `auth.verify_email` and `auth.password_reset` (OBE-030), the booking e-mails `booking.confirmed`, `booking.ticketed`, `booking.ticketing_delayed`, `booking.cancelled`, `booking.cancellation_requested`, `booking.not_confirmed`, `booking.updated` (FIX-W28-NOTIFY: a contacts change or a staff patch with `notifyCustomer`; its notice to a previous contact address, `update.contactNotice`, names the booking reference only) and the staff alerts `staff.ticketing_failed`, `staff.manual_review`, `staff.airline_card_alert` (OBE-055); the provisioning seed copies them into each new tenant as system rows. The booking e-mails link to `/booking.html?id=bkg_…` on the tenant's storefront host ([OADR-0015](../docs/adr/0015-storefront-build-urls-and-hosting.md) point 5), the confirmation says that invoices come from the OTA (OADR-0013 item 6), the staff alerts link to the booking in the OTA admin. `templates/templates.test.ts` compiles every default in strict mode against its allow-list and renders it with its sample data.
- **Attachments** (`attachments.ts`, worker, OBE-055; OADR-0013 item 8): `booking.confirmed` and `booking.updated` attach the booking's newest `ready` itinerary (the notice of `booking.updated` to a previous contact address attaches nothing: it has no plan) and `booking.ticketed` the newest `ready` receipt of every e-ticket (all or nothing). The claim plans them in its transaction: ready → the e-mail is sent with the PDFs (read from the storage of STORAGE_DIR, only under the tenant's `tenant_<key>/documents/`, each checked against `content_hash`, at most 10 MB) and `documents.attached` true; not ready and asked for less than 2 minutes ago (the newest booking event of `DOCUMENT_TRIGGERS`, which the record step and the ticketing job write with the e-mail) → the row is released without an attempt for 5 s and a delayed `notify` (`notify:<tenantId>:w<step>`) claims it again; otherwise (the wait is over, or nothing asked for them, as for a contacts change of a booking without an itinerary) → sent without attachments, `documents.attached` false, and the template points to the booking page. `booking.ticketed` is queued by `OrderRecorder.event` whenever tickets are stored (`booking.ticketed` event; dedupe key `booking.ticketed:<bkg_…>:v<version>`), with the e-tickets and their travellers.
- **Staff recipients** (`staff-recipients.ts`, both processes, OBE-055; OADR-0013 item 5): every staff alert (`staff.ticketing_failed`, `staff.manual_review`; the ticketing job, the reconciler, checkout.complete, the payments queue, the authorisation watch and the dispute webhook) is queued with `StaffRecipients.enqueue`: to `storefront_settings.ops_alert_email` when it is one plain address, else to the tenant's owners read from the platform (`PlatformReadRepository.ownerEmails`: active `owner` memberships whose account is active or locked, verified and not erased, the founder first, at most 10; read only), else to `OPS_ALERT_EMAIL` (Velexis ops; in both processes since FIX-W28-NOTIFY, lead decision (4) of 2026-10-23: before, the API had none and skipped the alerts it raised, such as a refresh's; a process without it skips and logs the alert). One row per recipient: the first keeps the caller's dedupe key, every further owner `<key>:<acc_…>`. Log lines carry ids and the rule used, never an address.

Booking documents (OBE-053, OBE-054, `src/documents/`, [OADR-0013](../docs/adr/0013-notifications-and-booking-documents.md) items 6, 7 and 9, [ADR-0017](../../docs/mvp/adr/0017-email-documents-storage.md), [flow §3 step 7 and §4](../docs/flows/ticketing-and-documents.md)):

- **Requests** (`DocumentRequests`, both processes, global): `OrderRecorder.event`, the one way the bookings module writes a booking event, asks for the documents of `booking.created` (the itinerary, and a receipt per e-ticket of an order that came back issued), `booking.ticketed` (a receipt per e-ticket and a new itinerary, whichever path stored the tickets: checkout.complete, the ticketing job, a refresh), `booking.schedule_changed` (a new itinerary with the airline's new times, whichever synchronisation found the change: the background sync, a refresh or console.bookings.resync; FIX-W27-SYNC, lead decision (3) of 2026-10-23) and `booking.cancelled` (the itinerary marked cancelled; the cancellation tasks and a cancellation by the airline write that event) in the event's transaction; after its commit (`afterCommit`, dropped on a rollback) `document.render {tenantId, bookingId, kind, bookingVersion[, ticketId]}` goes to `ota-documents` with the booking's version as the transaction left it. The job key `document.render:<bookingId>:<kind>:<bookingVersion>[:<ticketId>]` is the job's BullMQ deduplication id for a day (BullMQ refuses custom job ids with more than two colons), so a second job of the same key is not added. A document therefore follows a change only when the change moves the booking's `version`, and every writer of a document event moves it: a refresh (and console.bookings.resync, which records through the same sync service) that stores new or changed tickets or changed segments moves the version and the ETag even when the booking's status stays the same (FIX-W26-BOOKINGS, lead decision (6a) of 2026-10-22; before, `updateSynced` kept the version, so the itinerary asked for at that version within the day was not rendered again with the new ticket). The enqueue never fails the caller (2 s at most, logged as `documents.enqueue_failed` / `documents.enqueue_timeout`); a request lost while Redis is down is not swept, so the booking keeps its earlier documents until its next document event.
- **Rendering** (`DocumentRenderService`, `documents.processor.ts`; consumer `DocumentsProcessor`, concurrency 2, for `active` and `suspended` tenants; a payload that is not one fails at once): read the booking in a short transaction (`documents.repository.ts`: the booking, its travellers with only the type and last 4 of their identity document, never `documents_ciphertext`, segments, tickets, the brand, the square logo's `storefront_assets` row, the airport and airline names of `reference`); skip a booking that is gone or has no flights, and a receipt of a ticket that is not an e-ticket (EMD receipts, invoices and credit notes are post-MVP); read the logo from storage (this tenant's prefix only, SHA-256 checked, PNG or JPEG; otherwise, or when it cannot be embedded, the document is rendered without it); render with pdfmake (`renderers/`: English, the fonts of `fonts/`, the creation date from the data, so the same booking data gives the same bytes); when the newest ready version of the document has the same SHA-256 nothing is stored (`unchanged`), otherwise the file goes to `tenant_<key>/documents/<bookingId>/<documentId>.pdf` (mode 0600) and a second transaction takes the booking's documents lock (`DocumentsRepository.lockDocuments`: `pg_advisory_xact_lock` keyed on the booking id, so the document writes of one booking run one at a time; never a `FOR UPDATE` on the booking, lead decision (1) of 2026-10-22, so a ticketing or reconciliation claim made meanwhile is never skipped), reads the booking's version `FOR KEY SHARE` (the lock the row's foreign key takes anyway), checks that it is the one read (a booking changed meanwhile is read and rendered again, at most 3 times), inserts the `ready` row (`content_hash` the file's SHA-256, `size_bytes`, `file_name` `<reference>-itinerary.pdf` or `<reference>-eticket-<number>.pdf`, `locale` `en`) and supersedes the document's other rows (same booking, kind and ticket). Documents show selling amounts only (the booking's total on the itinerary; no fare on a receipt, the ticket's fare is a net amount) and identity documents masked (`Passport •••••1234`); a receipt shows its ticket number in full.
- **Downloads** (API, OBE-054; [OADR-0013](../docs/adr/0013-notifications-and-booking-documents.md) item 9, [flow §3 step 8](../docs/flows/ticketing-and-documents.md)): `bookings.listDocuments` and `bookings.getDocumentDownloadUrl` (`documents.controller.ts`, which BookingsModule registers behind the booking access guard, so the dependency stays bookings → documents) and the file endpoint `GET /v1/files/{storageKey}?exp=…&sig=…` (`files.controller.ts`, downloadFile: `security: []`, `x-sdk-exclude`, a public route with Express 5's `*storageKey` wildcard, 120 per minute per IP) over `document-downloads.service.ts`. The list holds the booking's `ready` documents, newest first, with a keyset cursor bound to the booking and the `kind` filter. A download URL (`ready` or `superseded`; `failed` answers `409 DOCUMENT_NOT_READY`, `details.retryAfterSeconds: 30`, and a failed rendering that a newer version superseded, which has no file, `404`) is the file endpoint's path signed for 5 minutes with `DOCUMENT_URL_KEY_FILE` (`signed-url.ts`, `signUrl` of `@velexis/crypto`: only the path and `exp` are signed) and the injected clock: the edge gets the same-origin `/api/v1/files/…`, a key caller `PUBLIC_OTA_API_URL/v1/files/…`; each call appends the staff-only booking event `document.downloaded`. The file endpoint checks the signature on `req.originalUrl` (`403 FORBIDDEN`, one answer for an expired, tampered or malformed link, before anything is looked up), then the tenant: with the edge or an API key the resolved tenant must be the storage key's and the booking of the request's environment, without a credential the key's tenant must be active; everything else is `404`. It reads the file from the StorageAdapter outside any transaction, checks its SHA-256 against `content_hash` and answers it with `Content-Disposition: attachment; filename="<file name>"`, `Cache-Control: private, no-store` and `X-Content-Type-Options: nosniff`. Signed URLs and signatures are never logged.
- **Failures**: an error of the renderer, the storage or the database writes (or keeps) one `failed` row of the document (nothing stored at its key, `content_hash` the SHA-256 of no bytes, `size_bytes` null), which supersedes nothing, so the last ready version stays downloadable; the job fails and BullMQ retries it (5 attempts, exponential backoff from 30 s); the next ready version supersedes the failed row. `pending` rows are not written: a document without a row is not ready yet. Log lines carry ids, the kind, sizes and error names, never booking data.

### Runbook: cleaning the booking queue

Lead decision (5) of 2026-10-23 ([OADR-0003](../docs/adr/0003-booking-orchestration-and-supplier-timeout-recovery.md) follow-ups): every order Velexis creates is placed on the OTA's booking queue (`storefront_settings.booking_queue_number` and `_category`, queue 50 / category 0 on the Velexis shared offices) of its queuing office, so the reconciliation can find an order whose answer was lost. Queue List has no removal among the 12 Amadeus operations Velexis uses, so nothing removes PNRs from the queue: staff do it by hand in Amadeus. One Queue List answer carries at most 500 PNRs (`RECONCILE_QUEUE_LIST_MAX`); a queue that holds more leaves every search incomplete, and the timed-out bookings then go to the staff's review instead of being decided (OADR-0003 points 4 and 5).

- **Signal**: the staff alert `staff.manual_review` "The booking queue 50 (category 0) of NCE1A0950 (test) holds 412 PNRs …" (to `ops_alert_email`, else the owners, else Velexis ops: `notifications/staff-recipients.ts`), at most once a day per OTA and environment while a reconciliation's Queue List answer holds 400 entries or more; the log line `bookings.booking_queue_nearly_full` (tenant, booking, `entries`, `limit`); later, bookings in the console's needs-attention list with `reconcileOutcome=manual_review` and the gap `queue_truncated`.
- **Who**: an agent of the OTA (own Amadeus credentials) or Velexis ops (the shared offices), signed in to the queuing office in the Amadeus Selling Platform with queue rights.
- **Steps** (Amadeus cryptic entries; confirm them with Amadeus for the shared offices together with the queue convention, OADR-0003 follow-ups):
  1. `QT` shows the queue counts of the office; note the count of the booking queue (queue 50, category 0).
  2. `QS50C0` starts working the queue (its first PNR is displayed). A PNR whose booking is finished for Velexis (its booking is `confirmed`, `ticketed`, `cancelled` or `failed` in the console, or its flights are over; the `VELEXIS <reference>` remark names the booking, which the console's search `q` finds) is removed with `QN` (done, next PNR); a PNR of a booking still `pending` in the console is kept with `QD` (to the end of the queue).
  3. `QI` leaves the queue once the count is well below 400; `QT` again to check.
- **Never** remove the PNR of a `pending` booking whose reconciliation may still need it, nor one of a booking in `manual_review` before the staff settled it: the reconciliation finds orders only on the queue.
- **After**: the alert comes again at the earliest the next UTC day; a queue that fills again within days needs a more frequent cleaning routine (a later job may clean it once Amadeus offers a removal).

## 7. Amadeus stub for development and CI

[`tools/amadeus-stub`](../../tools/) (`@velexis/amadeus-stub`, task X-026, [ADR-0015](../../docs/mvp/adr/0015-testing-strategy.md)) is a Node `http` server on port 4900:

- implements `POST /v1/security/oauth2/token` and the 12 operations from recorded, scrubbed fixtures under `tools/amadeus-stub/fixtures/`;
- validates every request against `docs/amadeus-api/*.json` and answers `400` on a malformed request, so client bugs fail loudly;
- scenarios with `X-Stub-Scenario`: `sold-out`, `price-changed`, `ticketing-failed`, `version-conflict`, `server-error`, `rate-limited`, `timeout`, `timeout-lost`; the client forwards the header only when `APP_ENV` is not `production`. End-to-end runs use magic values (destination `ZZZ` returns no offers);
- remembers created orders in memory so Flight Order Management, by-reference GET and Queue List return them (needed for reconciliation tests);
- is started in-process by integration tests through `@velexis/testing/amadeus` (random port), and as a background process in CI end-to-end jobs.

Point the backend at it with `AMADEUS_BASE_URL_TEST=http://127.0.0.1:4900`. Recording new fixtures (`pnpm --filter @velexis/amadeus-stub record <operation>`) uses the developer's own Amadeus test credentials and is never run in CI.

How the suites run (`vitest.config.ts`, `vitest.int.config.ts`):

- **Contract tests run with the unit tests.** `vitest.config.ts` includes `test/contract/**/*.test.ts` next to `src/**/*.test.ts`, so `pnpm --filter @velexis/ota-backend test` runs both (`test -- contract` narrows it); none of them needs a service.
- **Decorator metadata.** NestJS injects constructor dependencies by their TypeScript types, which esbuild (Vite's default transform) does not emit. Both Vitest configurations compile the package's TypeScript with the TypeScript compiler and the options of `tsconfig.json` instead, so tests run the same decorator output as the `tsc` build.
- **In-process apps.** Tests start the API and the worker with `startApi({ env, logDestination })` and `startWorker({ env, logDestination })` from `src/main.ts` and `src/worker.ts`, or build a test root module around `AppModule.forRoot(config, { logger })` (Supertest). `test/support/create-test-app.ts` does the latter as `main.ts` does (the same pipeline and JSON body limits), with optional probe controllers registered before the application's routes and the log lines in a sink: `createTestApp()` with dummy services for unit and contract tests (a dummy PostgreSQL DSN, and a Redis URL on a loopback port where nothing listens, `unreachableRedisUrl()` of `test/helpers/ports.ts`, so the cache falls back to the repository the same way on every machine; `main.test.ts`, `app.module.test.ts` and the API graph of `platform-read.int.test.ts` use it too, because the API connects its `vx:invalidate` subscriber at start-up and a dummy password does not keep it away from a Redis without one; so does `worker.test.ts`, because the worker registers its job schedulers and connects its subscriber at start-up, OBE-024), `createTestApp({ database, redis })` with the file's `createTestDatabase()` clone and `useRedis()` database for integration tests (`test/integration/common/http-pipeline.int.test.ts`). `test/helpers/log-sink.ts` captures the log lines so tests can assert that a request line carries `requestId` and that no body, token or password is logged. `test/support/pdf-text.ts` reads the text of a booking document back (pdfkit writes it as glyph codes; the reader decodes them through the fonts' ToUnicode maps), so a test can search a PDF for a value (OBE-053). `createApiApp` flushes Nest's start-up log buffer as soon as the pino logger is in place, so Nest's own lines (the exception handler's error lines included) reach the sink after `init()` too, not only after `listen()`.
- **Integration environment.** `test/integration/env.ts` reads `DATABASE_URL`, `REDIS_URL` and `DATABASE_PROVISIONER_URL` through `@velexis/config` (the CI job environment, or the root and app `.env.local` files). The `@velexis/testing` global setup of `vitest.int.config.ts` builds the run's template database as `TEST_DATABASE_ADMIN_URL` (platform and reference migrated, `tenant_alpha` and `tenant_beta` provisioned); a file that needs tenant schemas clones it with `createTestDatabase()` and drops the clone in `afterAll` (`test/integration/provisioning/seeds.int.test.ts`). A file that needs Redis takes an emptied database of its own with `useRedis()` and passes its URL to the module under test (`test/integration/common/queues.int.test.ts` runs a real `ota-tenant-ops` queue and worker there; `test/integration/provisioning/provision.int.test.ts` runs the whole worker graph on both, adds `tenant.provision` messages as the platform does and reads the events back from `platform-tenant-events`; `migrate.int.test.ts` does the same for `tenant.migrate` and the failure classes, a forced lock timeout included, and points the worker at a tenant migrations folder of its own by mocking the default of `provisioning.service.ts`; `test/integration/jobs/offers-purge.int.test.ts` runs the worker graph too, removes the schedulers it registered and plays the scheduler with `fan-out` jobs that carry an iteration's `prevMillis`, with `Clock` pointed at a `FakeClock`). The health suite binds the units' ports `127.0.0.1:4000` and `127.0.0.1:4001`, so integration files run one after the other.
- **Caller credentials in tests.** `test/helpers/api-env.ts` gives every test that builds the API's configuration its API-only variables: a random `VELEXIS_EDGE_SECRET` per test process, an `API_KEY_PEPPER_FILE` and a `master-v1.key` (`MASTER_KEY_DIR`, `MASTER_KEY_CURRENT=local:v1`) written once per checkout as `pnpm dev:keys` writes them (32 random bytes, base64, mode `0600`, in the package's ignored `node_modules/.cache/test-keys/`; `testKeyProvider()` loads the same KEKs), the Ed25519 signing key `ota-jwt-ed25519.pem` (`JWT_PRIVATE_KEY_FILE`, `testApiCredentials().jwtKeyFile`) in the same folder, and the development base domain and public URL. `createTestApp()`, `integrationEnv()` and the unit tests use it; `edgeHeaders(host)` are the headers Caddy adds to a storefront's `/api/*` request, `edgeWriteHeaders(host)` add the CSRF cookie, its header copy and `Origin` that a storefront page's `POST`, `PUT`, `PATCH` and `DELETE` carry, and `testApiCredentials().pepper` computes the `key_hash` of a test key (`hashApiKey`). Probe controllers of tests about the pipeline after the caller guard are marked `@PublicRoute()`; requests to pending operations carry `edgeHeaders()`.
- **One-time work in setup hooks.** Vitest bounds a test at 5 s, and CI runs every package's tests at once on four CPUs. Work a test file does once (parsing and compiling the OTA document, starting module graphs, linting or scanning the whole package) goes into a `beforeAll` with an explicit, commented budget, and the tests only compare its results. A file whose tests start the API runs `beforeAll(preloadOpenApiDocument, OPENAPI_SETUP_TIMEOUT_MS)` (`test/helpers/openapi.ts`): `loadOpenApiDocument` keeps the document for the process, so no test pays for it. An application, a worker or a probe application starts in a hook too (`beforeEach` when the test counts its log lines, else `beforeAll`), and a start-and-stop check runs its requests and its close there and records what they gave: closing an application whose Redis cannot be reached waits up to `BULLMQ_STARTUP_SETTLE_MS` (1 s) for its queues, so a file closes its applications together in `afterAll` (`app.module.test.ts`, `worker.test.ts`, `route-parity.contract.test.ts`; FIX-W28-FOLLOWUPS). Test timeouts are never raised (AGENTS.md §7).
- **Outages.** The shared PostgreSQL and Redis are never stopped by a test. A dependency that is down is a free loopback port where nothing listens (`test/helpers/ports.ts`); a Redis that comes back is `test/helpers/fake-redis.ts`, a minimal RESP server started on that port.
- **nestjs-pino outside requests.** Every `PinoLogger` of a process writes to the first application's logger outside a request. One process runs one application on the VM; a test that starts several and asserts out-of-request lines calls `useNextApplicationLoggerOutsideRequests()` (`test/helpers/nest-pino.ts`) before starting the one it watches.

## 9. Deploy

- Release folder `ota-backend/` with `dist/`, `migrations/tenant/`, `openapi/` and production dependencies (`pnpm deploy --prod`), per [ADR-0023](../../docs/mvp/adr/0023-release-artefact-and-deploy-user.md).
- Deploy order: platform and reference migrations → tenant fan-out (`migrate.js tenants --dir "$REL/migrations/tenant"`, then `velexis-run ota node "$REL/ota-backend/dist/cli.js" tenants:report-migrations --report /var/lib/velexis/migrate-<sha>.json`, both before the switch; the report is made readable, `0644`, for the OTA zone user, and a failed report stops the deploy like a failed migration; the first deploy, without a running release for `velexis-run ota` to start in, skips the report, and every later report re-sends every ledger) → restart `velexis-ota-worker`, then `velexis-ota-api` → `/health/ready` checks ([`../docs/flows/tenant-provisioning-worker.md`](../docs/flows/tenant-provisioning-worker.md) §4, [`deployment-single-vm.md`](../../docs/mvp/deployment-single-vm.md) §8 and §9).
- Both units run with `MemoryMax`, `LimitCORE=0` and no swap on the VM, so card data in memory never reaches disk ([ADR-0011](../../docs/mvp/adr/0011-payments-stripe-and-airline-card.md) §C).
