# OTA backend load tests

Two load tests of the OTA backend. The figures of each recorded run and what was decided from them are in [`ota/docs/performance.md`](../../../docs/performance.md).

- `search-load.mjs` is the M2 search load test of the OTA API (OBE-028). It answers the follow-ups of [OADR-0001](../../../docs/adr/0001-amadeus-client-design.md) ("load-test the buckets") and [OADR-0002](../../../docs/adr/0002-offer-and-priced-offer-caching.md) ("measure search insert time and table sizes").
- `booking-load.mjs` is the M6 mixed-traffic test of the API **and the worker** against the VM's memory budget (OBE-088; [architecture §3](../../../../docs/mvp/architecture.md#3-hosts-ports-and-the-vm), the follow-up of [OADR-0014](../../../docs/adr/0014-per-tenant-workers-and-schedulers.md)). It reuses the helpers of `search-load.mjs` and is described in [its own section](#booking-loadmjs-mixed-traffic-with-the-worker-obe-088). OBE-101 measured Redis's completed jobs with it, and OBE-102 the shoppers' share of the Amadeus buckets while the booking sync runs ([`performance.md`](../../../docs/performance.md) §7 and §8).
- OBE-103 measured both on Node.js 22 and 24 with the units' flags ([ADR-0029](../../../../docs/mvp/adr/0029-nodejs-24-runtime.md) items 3 and 5; [`performance.md`](../../../docs/performance.md) §10), and added the time each process spends in garbage collection and the headroom under its unit's `MemoryMax` to their reports ([below](#nodejs-22-and-24-obe-103)).
- OBE-104 ran `booking-load.mjs` for three hours on Node.js 24 and added the memory over time to its report: every heap figure of `process.memoryUsage()` in the samples, a table per 30 minutes, the least-squares slopes and whether each process's memory settles ([`performance.md`](../../../docs/performance.md) §11; [below](#three-hours-on-nodejs-24-obe-104)). Since lead decision (30b) of 2026-11-19 the verdict judges the JS heap by its floor after the collections, the least heap used of each 5 minutes (FIX-W61-MEMORY).

Both:

- **Plain Node, no dependency of their own.** They use `fetch` and the workspace packages the OTA backend already has (`@velexis/config`, `@velexis/db`, `@velexis/crypto`, `@velexis/testing`, `ioredis`), and the built API, worker and Amadeus stub.
- **Not part of `pnpm test`, `pnpm test:int` or CI.** A load test measures the machine it runs on, so it runs by hand. Every run is recorded in `performance.md` with the machine, its `nproc` and its load. The pure functions of `booking-load.mjs`'s memory report (`floorsOf`, `memorySettles`, `leastSquares`, `memoryOverTime`, `memoryText`) have unit tests beside the other tested tools in [`tools/perf/booking-load-memory.test.mjs`](../../../../tools/perf/booking-load-memory.test.mjs), which CI's build-test job runs with `node --test tools/perf/*.test.mjs` ([`tools/perf/README.md`](../../../../tools/perf/README.md#lint-and-unit-tests)); importing the script starts nothing.
- **Local and test only.** They start their own processes against their own scratch database and the Amadeus stub. They never talk to a deployed API, a real Amadeus, a real Stripe, a real mail server or a database they did not create.

## Run it

You need the local setup of [`docs/mvp/local-development.md`](../../../../docs/mvp/local-development.md) §2: PostgreSQL 16 with the roles of `dev-setup.sh` (`velexis_test_admin` among them) and Redis. `TEST_DATABASE_ADMIN_URL` and `REDIS_URL` come from the environment or from the `.env.local` files, as for `pnpm test:int`. Build the API, the stub and the packages they use, then run the test from the repository root:

```bash
pnpm build --filter=@velexis/ota-backend...                       # the API, @velexis/testing, the stub and the packages
node ota/backend/test/load/search-load.mjs --visitors 10 --searches 200                 # the run of the plan (Verify)
node ota/backend/test/load/search-load.mjs --visitors 10 --searches 1000 --offers 250   # Amadeus-sized answers
node ota/backend/test/load/search-load.mjs --visitors 10 --searches 200 --tenants 8     # the credential set's bucket
node ota/backend/test/load/search-load.mjs --help
```

Before a run you record, write down the machine's load (`uptime`, `nproc`). The test prints `nproc` and the load average at its start and end too. A run on a busy machine measures that machine: if a bound is missed while other work runs, run again later and record both runs.

The runtime is the `node` that runs the test: it starts the API (and `booking-load.mjs` the worker) with its own executable (`process.execPath`) and prints its version. To measure another Node.js, put its `bin` folder first on `PATH` for the run, for example `PATH=/opt/node22/bin:$PATH node ota/backend/test/load/search-load.mjs …` (OBE-103).

| Option | Default | What it does |
|---|---|---|
| `--visitors <n>` | 10 | Concurrent visitors. Visitor i shops at tenant i mod `--tenants`. |
| `--searches <n>` | 200 | Journeys in all. Each journey is one search, its first results page and the price of its first offer. |
| `--tenants <n>` | 2 | Tenants, 2 to 8. They all share the Velexis test Amadeus account, so they share one credential bucket. |
| `--stub-delay-ms <n>` | 300 | How long the stub holds every answer (the token request too). |
| `--offers <n>` | 0 | Offers in each search answer, 1 to 250, but never more than the search asked for (see step 2 below). With 0 the answer keeps the 5 offers of the stub's fixture. Amadeus answers up to 250. The API asks for the storefront's `maxResults`, 150 by default since lead decision (15i) of 2026-11-11 (175 since OBE-096 before it; [`performance.md`](../../../docs/performance.md) §5), so `--offers 250` gives answers of 150 offers at the run's tenants, which set no `maxResults` of their own. |
| `--think-ms <n>` | 0 | A visitor's pause between two calls. 0 means each visitor calls as fast as the API answers. |
| `--max-retries <n>` | 2 | Retries of a `429 RATE_LIMITED`, each after its `Retry-After`, with the same `Idempotency-Key`. This is what the SDK does by default. |
| `--warmup <n>` | 1 | Warm-up journeys per visitor, run at the measured concurrency and not counted. |
| `--p95-budget-ms <n>` | 500 | The budget of the `flights.search` p95 without the stub delay. This is the bound of OBE-028. |
| `--redis-db <n>` | 14 | The Redis database of the run. It is emptied before and after the run. Never 0 (`pnpm dev`) and not 15 (the end-to-end stack). Use another number or a Redis of your own when an integration run could be using 14. |
| `--app-env <env>` | `production` | `APP_ENV` of the API. `production` is how the VM runs it. `test` adds the development checks, such as the `search_path` leak guard's query in every tenant transaction. |
| `--json <file>` | — | Also writes the figures as JSON, with every attempt of the measured phase (operation, tenant, status, code, start, duration). |

Exit codes:

- **0:** every answer was expected and the p95 is within the budget. An expected answer is a 2xx, or a `429` of the Amadeus buckets.
- **1:** an unexpected answer, the budget missed, or a run that could not be set up.
- **2:** a usage error.
- **130:** interrupted by Ctrl-C or SIGTERM. The run stops after the step it is in and cleans up; a second signal cleans up at once.

## What a run does

The header of `search-load.mjs` describes each step. In short:

1. **A database for the run.** It builds `velexis_test_tpl_load_<runId>` like the integration tests' template, with the `@velexis/testing` helper. Then it writes each tenant's rows as the platform and provisioning write them: the tenant on its storefront sub-domain (`alpha.ota.example.com`, …), the shared Velexis test Amadeus account, the tenant's own connection with one office, its storefront settings and default markup rule, and one markup rule of its own.
2. **The Amadeus side.** A child process runs the stub (`@velexis/testing/amadeus`) behind a small proxy. The proxy holds every answer for `--stub-delay-ms`, answers each search with `--offers` offers, moves the last ticketing day 60 days ahead, and counts the calls the buckets let through.
   - **Never more offers than asked for.** As Amadeus does, the proxy answers a search with at most the offers it asked for: `max` of a GET search (SIMPLE mode), `searchCriteria.maxFlightOffers` of a POST search (ADVANCED mode), and 250 when the search names neither. So a run measures what the API stores at its storefront limit, not `--offers` itself: with `--offers 250` and the default limit of 150 (175 until lead decision (15i) of 2026-11-11), each answer has 150 offers. This holds for `--offers 0` too: the stub's 5 offers are cut to a smaller `max`.
   - **The report shows it.** The Amadeus section gives the offers the searches asked for and the offers the proxy answered (p50 and maximum), and the answers with more offers than asked for. Such an answer is an unexpected answer: the run exits 1.
3. **The API.** It starts the built API (`ota/backend/dist/main.js`) as systemd starts it on the VM (`NODE_ENV=production`, `--enable-source-maps`, and the flags of the `NODE_OPTIONS` of [`deploy/systemd/velexis-ota-api.service`](../../../../deploy/systemd/velexis-ota-api.service), which the script reads from the unit file with [`tools/perf/unit-node-options.mjs`](../../../../tools/perf/unit-node-options.mjs) since X-050 instead of copying them: the old generation and the young generation of 32 MiB per semi-space of 2026-11-06, [`performance.md`](../../../docs/performance.md) §4, and [ADR-0029](../../../../docs/mvp/adr/0029-nodejs-24-runtime.md) item 5), on a free port. The unit's `MemoryMax` comes from the same file (`parseUnitMemoryMax`, since OBE-103): a unit that cannot be read, or sets no limit, stops the run before its set-up. The API gets random key files, an edge secret and a service key of its own. A preload, written into the run's temporary folder, times the `INSERT` and `UPDATE` statements of the shopping tables and the waits for a pooled connection. It also samples the RSS and the event-loop delay, reads the API process's CPU time over the measured phase, and sums the time the process spends in garbage collection per minute (since OBE-103: a `PerformanceObserver` on Node's `gc` entries, each the main-thread pause of one collection, counted by kind). It measures and changes nothing.
4. **The visitors.** Each journey is one storefront visitor with an address of their own (`X-Forwarded-For` in `198.18.0.0/15`, the benchmarking range). That is why the per-address shopping limit of [architecture §8](../../../docs/architecture.md#8-rate-limits) never answers. Each visitor goes through the edge as the hosted storefront does (Caddy's headers, the CSRF cookie and header, an `Idempotency-Key` per call) and makes three calls:
   - `flights.search`: SIMPLE, one adult, `resultOptions.limit: 0`.
   - `flights.listResults`: the first page, 20 offers.
   - `flights.price`: the first offer, with the storefront's `include`.

   Each search has its own route and day, so single flight never joins two searches.
5. **The report and the clean-up.** The test prints the report. Then it stops both processes, drops the database, empties the Redis database and removes the temporary folder, also after Ctrl-C or a SIGTERM sent to the test alone (`kill`, `timeout`).

## Reading the report

| Section | What the figures are |
|---|---|
| Latency of the 2xx answers | Client-side duration of every successful answer, per operation (an attempt answered `429` is not in it). **Without the stub delay** subtracts `--stub-delay-ms` once: what the API and the stub spent. **Without the Amadeus call** subtracts the search row's `duration_ms`, the client's measured Amadeus request: the API's own time, rate limiter, token, database, pricing and storage included. |
| Answers per operation | Every attempt with its status. `429 RATE_LIMITED` is the Amadeus buckets ([`src/amadeus/rate-limiter.ts`](../../src/amadeus/rate-limiter.ts)). A refused search still writes a `failed` row in `flight_searches`: the pending row is inserted before the Amadeus call. |
| Phase | Journeys completed, refused (still `429` after the retries) and failed, throughput, and the requests in flight. The mean is the summed request time over the phase's wall time. |
| Amadeus calls | Calls that reached the stub (the buckets let them through), the stub's own time before the delay, and calls per second (mean and busiest second, searches and prices). The offers the searches asked for (`max`, `maxFlightOffers`) and the offers the proxy answered, p50 and maximum, and the answers with more offers than asked for (always 0, or the run exits 1). |
| Statements of the API | Time of each `INSERT` / `UPDATE` at the API's `pg` client, from sending to answer, with the mean rows. `insert into flight_offers` is the search's multi-row offer insert ([OADR-0002](../../../docs/adr/0002-offer-and-priced-offer-caching.md) point 1). |
| API process | CPU time over the measured phase (user and system, `process.cpuUsage()`) and per completed journey (the refused journeys' attempts are in the total too), RSS after start, at its peak and at the end, the peak against the unit's `MemoryMax` (768 MiB, read from the unit file) and the headroom under it, the wait for a pooled connection (`ota-api` pool, 20 connections), and the event-loop delay. Then garbage collection (OBE-103): the main-thread pauses of every collection in the phase, their number by kind (`minor`: scavenges of the young generation; `major`: mark-compact of the whole heap; `incremental`: the steps of incremental marking; `weakcb`: weak callbacks), as a share of the phase's wall time (ADR-0029's measurement allows 5 %), of the worst minute, and of the process's CPU time. The headroom and the share are reported; neither is part of the exit code. |
| Tables after the run | Rows and sizes (table with TOAST, indexes, total) of the shopping tables over all tenants, and the total per completed search. The warm-up's searches are included. |

## booking-load.mjs: mixed traffic with the worker (OBE-088)

### Run it

The same set-up as `search-load.mjs` above. Its Redis figures are those of the whole Redis server, so run it on a Redis of its own, started as the VM's (`maxmemory 512mb`, `noeviction`), and on a database server no integration suite is using at the time. On a shared development machine, take the machine-wide end-to-end lock so no end-to-end run shares the CPUs, and write down `nproc` and the load:

```bash
pnpm build --filter=@velexis/ota-backend...
redis-server --port 6390 --bind 127.0.0.1 --requirepass dev_redis --save '' --appendonly no \
  --maxmemory 512mb --maxmemory-policy noeviction --daemonize yes      # a Redis of the run's own (a free port)
export REDIS_URL=redis://:dev_redis@127.0.0.1:6390/0
nproc; uptime
node ota/backend/test/load/booking-load.mjs --tenants 5 --minutes 30                  # the run of the plan (Verify)
node ota/backend/test/load/booking-load.mjs --tenants 5 --minutes 180                 # three hours: does the memory settle? (OBE-104)
node ota/backend/test/load/booking-load.mjs --tenants 5 --minutes 65 --heap-snapshots api,worker --heap-snapshot-dir /path/to/snapshots   # heap snapshots at minutes 30 and 60 (OBE-104 step 4)
node ota/backend/test/load/booking-load.mjs --minutes 5 --window-minutes 1 --table-minutes 1 --floor-minutes 1   # a short run while developing
redis-cli -p 6390 -a dev_redis shutdown nosave
```

| Option | Default | What it does |
|---|---|---|
| `--tenants <n>` | 5 | Tenants, 2 to 8, served in turn. |
| `--minutes <n>` | 30 | Minutes of measured traffic, after a warm-up of one journey of each kind per tenant. |
| `--shoppers-per-minute <n>` | 120 | Shopper journeys started per minute: `flights.search`, its first results page (20 offers), `flights.price` of the first offer. |
| `--bookings-per-minute <n>` | 4 | Booker journeys started per minute: the shopper's three calls, then the checkout paid by airline card (below). At most one per tenant: the airline card allows 60 completions an hour per tenant (`airlineCardPerTenant`, [architecture §8](../../../docs/architecture.md#8-rate-limits)). |
| `--staff-per-minute <n>` | 30 | Staff journeys started per minute: `console.bookings.list`, `console.bookings.get` of the first, `console.payments.list`, `console.supplierRequests.list`. |
| `--think-ms <n>` | 1000 | A pause between two calls of a journey. |
| `--offers <n>` | 250 | Offers in each search answer, never more than the search asked for, as in `search-load.mjs`. With the default, each answer has the storefront limit's offers (`DEFAULT_OFFERS_PER_SEARCH`). |
| `--stub-delay-ms <n>` | 300 | How long the stub holds every answer. |
| `--deferred-ticketing-every <n>` | 4 | Every n-th booking's Flight Create Orders comes back without tickets (the stub's `ticketing-failed`), and the run makes it a card-paid issuance retry for the worker (below). 0: never. |
| `--timeout-every <n>` | 25 | Every n-th booking's Create Orders answer is lost (the stub's `timeout`: the order is written, the answer is a 504 after 30 s), so the worker reconciles it. 0: never. |
| `--max-retries <n>` | 2 | Retries of a `429 RATE_LIMITED`, as the SDK. |
| `--max-in-flight <n>` | 400 | Journeys at once. A journey due while that many run is skipped, and the run fails: the load was not delivered. |
| `--queue-budget-s <n>` | 60 | The longest wait allowed for an `ota-ticketing` or `ota-bookings` job (OBE-088's acceptance). |
| `--sample-s <n>` | 5 | Seconds between two samples of the processes, PostgreSQL, Redis and the worker's queues. |
| `--window-minutes <n>` | 5 | Minutes per row of the timeline, and between two progress lines. |
| `--table-minutes <n>` | 30 | Minutes per row of the memory table (OBE-104). |
| `--floor-minutes <n>` | 5 | Minutes per window of the JS heap's floor, 1 to 30: the least heap used of each window, whose slope decides whether a process's memory settles (lead decision (30b); [below](#three-hours-on-nodejs-24-obe-104)). The rule's window is 5 minutes; a shorter one is for a short diagnosis run, which a window of 5 minutes leaves with fewer than three floors to fit. |
| `--redis-db <n>` | 13 | The Redis database of the run, emptied before and after. Not 14 (`search-load.mjs`) or 15 (the end-to-end stack). |
| `--app-env <env>` | `production` | `APP_ENV` of the API and the worker. |
| `--json <file>` | — | Also writes the figures, the samples and every attempt of the measured phase as JSON. |
| `--heap-snapshots <processes>` | — | `api`, `worker` or `api,worker`: a diagnosis run (OBE-104 step 4). Each named process starts with `--heapsnapshot-signal=SIGWINCH --diagnostic-dir=<--heap-snapshot-dir>` after its unit's flags, and the run sends it `SIGWINCH` at each of `--heap-snapshot-minutes`; the JSON lists them as `heapSnapshots` (`sent: false` for a process that was no longer running, which the run does not signal). Not `SIGUSR2`: Nest's `enableShutdownHooks()` closes the API and the worker on it. Writing a snapshot stops the process for seconds and holds a second copy of its heap, so the latency and the peaks of such a run are not a measurement. |
| `--heap-snapshot-minutes <list>` | `30,60` | Minutes of the phase for the snapshots, comma-separated, each from 1 to `--minutes`. |
| `--heap-snapshot-dir <dir>` | — | An existing folder for the snapshots (`Heap.<date>.<time>.<pid>.<thread>.<seq>.heapsnapshot`); they outlive the run's temporary folder. Required with `--heap-snapshots`. |

Exit codes: **0** when every answer was expected, no journey was skipped or still running 120 s after the last one started, the API's and the worker's RSS stayed within their `MemoryMax`, and no `ota-ticketing` or `ota-bookings` job waited longer than `--queue-budget-s`, with jobs of both queues measured once a fixture had made their work due long enough before the end (6 minutes for `ota-ticketing`, 11 for `ota-bookings`: a run shorter than about 15 minutes may measure none, and then says so without failing); **1** otherwise, or when the run could not be set up; **2** a usage error; **130** interrupted.

### What a run does

The header of `booking-load.mjs` describes each step. In short:

1. **The tenants** of `search-load.mjs`, and what a booking needs: the shared Amadeus account's `base_url` is the run's proxy (the worker has no `AMADEUS_BASE_URL_*` override), and each tenant has the Velexis Stripe test connection, two staff members (`agent`, MFA on) and, in its storefront settings, the airline card on for the test environment, an alert address and a booking queue (50, category 0).
2. **The Amadeus side.** The stub behind `search-load.mjs`'s proxy. The proxy picks the stub scenario of each Flight Create Orders from the first traveller's last name, which the booking journey chose: `DEFERRED` (`ticketing-failed`), `LATECOMER` (`timeout`), anything else the normal answer, an issued order.
3. **An SMTP sink** in a child process takes the worker's e-mails and keeps only their number and size.
4. **The API and the worker**, built, each started as its systemd unit starts it: `APP_ENV` and `NODE_ENV` `production`, `--enable-source-maps`, and the flags of the `NODE_OPTIONS` of its unit, [`velexis-ota-api.service`](../../../../deploy/systemd/velexis-ota-api.service) and [`velexis-ota-worker.service`](../../../../deploy/systemd/velexis-ota-worker.service), read from the unit files with [`tools/perf/unit-node-options.mjs`](../../../../tools/perf/unit-node-options.mjs) since X-050 (old and young generation, ADR-0029 item 5). Both run with `search-load.mjs`'s preload. The worker's copy also wraps BullMQ's `Worker#emit`: for every job a worker takes, how long it waited from the moment it was due (added, or its delay over) to its first attempt, and how long each attempt ran. A retry is counted but not timed, since its backoff is not in the job.
5. **The traffic.** Each kind of journey starts at its own fixed rate, evenly spread, the tenants in turn (an open model: a slow answer does not slow the arrivals). A booker goes through the edge as the hosted storefront does: the shopper's three calls, `checkout.create`, the traveller and the contact, `checkout.createPayment {method: "airline_card"}`, the card hint (`checkout.updatePayment`, which quotes the card fee), `checkout.get`, `checkout.completeWithAirlineCard` with Visa's documented test card, and `bookings.get` with the guest cookie the completion set. Staff sign in once through the OTA admin's service key with a portal token, as `console-access.int.test.ts` does, and refresh their session every 10 minutes.
6. **Two fixtures, once a minute.** The run cannot reach Stripe, and a fresh booking is not due for the booking sync for 6 hours, so it writes what the API cannot:
   - **The sync.** Every booking with an order is made to look last synchronised 7 hours ago (`last_synced_at`), and its last sync claim, if it has one, as old (`sync_claimed_at`: the scan skips a booking claimed in the last 30 minutes, `BOOKING_SYNC_RETRY_MS`; a claim of the last 2 minutes, a sync that may still run, is left alone). So each `bookings.sync_scan` (every 10 minutes) enqueues its most: every such booking, up to 20 `booking.sync` jobs per tenant.
   - **Ticketing.** An airline-card booking without tickets goes to the staff (`manual_review`) and never to the ticketing job ([`ticketing.service.ts`](../../src/bookings/ticketing.service.ts)). So the run rewrites each such booking as the card path leaves a booking whose Flight Order Issue failed after the capture: the payment `stripe`/`card`, captured, the booking paid, ticketing `failed` and due now. The next `ticketing.scan` (every 5 minutes) enqueues its `ticketing.issue`, which issues the stub's order.

   Both write as `velexis_ota_app`, through `tenantTx`, as the API does. The report counts the rows they changed.
7. **Samples** every `--sample-s` seconds: the API's and the worker's RSS and heap figures (`process.memoryUsage()`: heap used and total, external and array buffers; the last three since OBE-104), the client connections of the run's database by application (`pg_stat_activity`, read as `velexis_ota_app`, so it sees the state of the API's and the worker's sessions; the sampling connection itself and PostgreSQL's own processes, such as autovacuum, are not counted), Redis's memory, clients and keys, the worker's `/health/ready` queues (waiting jobs, the oldest wait, the failures of the last hour: the on-VM check's signal) and the 1-minute load average. With every sample the run also takes the preloads' recordings (the pool waits and the worker's jobs) out of the two processes, with the preload's `take` message (OBE-104), so neither holds more than one interval of them in the heap the run measures; a take that is not answered makes the run fail, since its recordings are missing. Every `--window-minutes` the run prints a progress line with the minute, `nproc`, the load average and the latest sample's RSS and heap used, which the JSON keeps as `progress`.
8. **The report and the clean-up**, as in `search-load.mjs`. The documents the worker rendered are in the run's temporary folder and go with it.

### Reading the report

| Section | What the figures are |
|---|---|

| Amadeus calls | Every call through the proxy by operation and status, with the stub scenarios the proxy sent. |
| E-mails | The SMTP sink's messages, recipients and size. |

The health columns are the most waiting jobs and the oldest wait the worker's `/health/ready` reported. The verdict compares `ota-ticketing` and `ota-bookings` with `--queue-budget-s`. |
| Database | The database's size after the warm-up and at the end, the largest tenant tables (all tenants together: rows, size and growth), the bookings by status, ticketing status and reconciliation outcome, the notifications by status and the documents by kind, and the document storage. |
| Timeline | One row per `--window-minutes`: completed journeys and bookings started in the window, the p95 of `flights.search`, `flights.price`, the completion and `console.bookings.list`, the most RSS of the API and the worker, the share of the window each spent in garbage collection (`API gc%`, `wrk gc%`, from the preload's sums per minute over the window's whole minutes of the phase; none for a last window shorter than a minute, the journeys still in flight after the last full one), connections and Redis memory, the longest wait of the main queues, and the 1-minute load average (mean/max). |

The rows are `--table-minutes` each from the phase's start over `--minutes`; the last one is shorter when `--minutes` is not a multiple of `--table-minutes` and is then named `<from>-end` (`60-end` in a 65-minute run with rows of 30), as is the one row of a run shorter than a row (`0-end`), and it also holds the samples after the last minute (the journeys still in flight and the run's last sample). ### The sync and the shoppers' share of the Amadeus buckets (OBE-102)

Since OBE-102 the booking sync's order read is a background call ([OADR-0001](../../../docs/adr/0001-amadeus-client-design.md) point 6, revision of 2026-11-12). It takes an Amadeus token only while the tenant's bucket and the shared account's keep half their burst for the calls a person waits for. When they refuse it, the sync waits the buckets' own wait inside the job and reads again, up to 10 seconds of waits per job, all its reads together (`BOOKING_SYNC_RATE_LIMIT_BUDGET_MS`). This is where a run shows it:

- **The shoppers' `429` answers** are in *Answers per operation*. With `--json`, each attempt's `at` (milliseconds from the start of the measured phase) places it against the sync bursts. A scan of `bookings.sync_scan` enqueues its jobs at every 10th minute of the clock, so the bursts come every 10 minutes, in minutes of the phase that depend on when the run started (`performance.md` §8 names each run's).
- **The sync's own refusals never reach the proxy**, and they leave no `supplier_requests` row. They show as a longer run time of `ota-bookings booking.sync` in *Queue latency*, and in each job's result: `rateLimitWaits` and `rateLimitWaitMs` when the job waited, and `failed` with code `RATE_LIMITED` when the waits ran out. BullMQ keeps the result with the completed job in the run's Redis database, and the test empties that database at the end. So read the results while the run goes: `ZRANGE vx:ota-bookings:completed 0 -1`, then `HMGET vx:ota-bookings:<job id> timestamp processedOn finishedOn returnvalue`. OBE-102's runs did that every 10 s. The `timestamp` (added) and `finishedOn` of a scan's jobs give how long the scan took.
- **The queue's latency** is the *Queue latency* row of `ota-bookings`, against `--queue-budget-s`, as before.

OBE-102 ran `--tenants 5 --minutes 30` before and after the reserve and the Verify command after it, each under the end-to-end lock with a Redis of its own (`nproc` 4). Before, the largest burst refused one shopper's search and 27 of the sync's 97 reads. After, no shopper got a `429` and no sync read failed: 90 of 198 jobs waited, at most 2.2 s each, and the largest scan's jobs waited at most 15.4 s for a worker. [`performance.md`](../../../docs/performance.md) §8 has the runs, with the load average of each.

## Node.js 22 and 24 (OBE-103)

Since OBE-103 both reports give what [ADR-0029](../../../../docs/mvp/adr/0029-nodejs-24-runtime.md) asks of a measurement of the runtime, with the units' own flags (item 5):

- **The headroom under `MemoryMax`.** The scripts read each unit's `MemoryMax` from its file in `deploy/systemd`, beside its `NODE_OPTIONS`, with X-050's `parseUnitMemoryMax` (lead decision (27g) of 2026-11-17), instead of copying 768 and 512 MiB. A unit that cannot be read, or sets no limit, stops the run before its set-up with a message that names the file. The report gives the headroom at each process's peak RSS; ADR-0029's measurement keeps at least 64 MiB.
- **Garbage collection.** The measuring preload sums each collection's main-thread pause per minute and by kind. The reports give it as a share of the phase's wall time (ADR-0029's measurement allows 5 %), of the worst minute and of the process's CPU time; `booking-load.mjs` also per timeline window, over the window's whole minutes of the phase. In `booking-load.mjs` the run's figures reach to the report's snapshot of the processes, which comes once the fixtures' last pause has ended, up to a minute after the phase.
- **Two runtimes.** Put each one's `bin` folder first on `PATH` for its run (the test starts the API and the worker with its own `node`), and run them in turn on one build, under the end-to-end lock with a Redis of the runs' own, with `nproc` and the load average beside each run.

OBE-103 ran `search-load.mjs --visitors 10 --searches 200 --offers 250` three times and `booking-load.mjs --tenants 5 --minutes 30` once on Node 22.23.4 and on Node 24.22.3, in turn (`nproc` 4). On Node 24 every p95 was within 10 % of Node 22's (all lower but `checkout.get`, +0.5 %), the API and the worker stayed at least 297 MiB under their `MemoryMax`, and garbage collection took at most 2.1 % of the API's time and 0.3 % of the worker's. [`performance.md`](../../../docs/performance.md) §10 has the runs, with the load average of each.

## Three hours on Node.js 24 (OBE-104)

OBE-103's 30-minute run on Node 24 showed the worker's RSS rising in steps after each 5-minute scan while its JS heap stayed flat, and the API's rising slowly; thirty minutes cannot tell memory that settles from a slow leak. Since OBE-104 `booking-load.mjs` reports the memory over time, and a run of 180 minutes answers it:

- **The rule** (OBE-104 step 4, with lead decision (30b) of 2026-11-19, approved by the owner): a process's memory settles when its RSS slope over minutes 90–180 is below 0.02 MiB per minute (about 1 MiB an hour) and the slope of its JS heap's floor over the same window is not above that. The floor is the least heap used of each 5 minutes (`--floor-minutes`), the heap just after the collections, so the rule follows what the collections leave behind instead of the saw-tooth between them; the heap used's own slope stays in the report for information. The report and the JSON (`memory.<process>.settles` with `rssBelowBound` and `heapFloorNotAboveBound`, `verdict.apiMemorySettles`, `verdict.workerMemorySettles`) give it; a run that does not reach minute 180 is not judged. The verdict is reported only and changes no exit code. Until 2026-11-19 the rule judged the heap used's own slope, which on 5-second samples measured the saw-tooth more than a trend (OBE-104's API: +0.025 with r² 0.00).
- **Why the floor is per 5 minutes** (from R180's raw samples, [`performance.md`](../../../docs/performance.md) §11): a floor window must hold at least one collection of the old generation, or its least sample is only the young generation's low point. The worker's drops of heap used between two 5-second samples are mostly its scavenges' (563 of 789 under 1.5 MiB, with its semi-space of 1 MiB) or of 2 MiB and more (213), with 13 between; over minutes 90–180 those above 2 MiB came at most 2.0 minutes apart, as did those above 1.5 MiB. A sample cannot tell the API's scavenges (a semi-space of 32 MiB, and its large objects) from its mark-compacts, of which its garbage-collection observer counted 783 in the 180 minutes (one every 14 s on average); its largest drops, above 32 MiB, came at most 3.8 minutes apart. So every 5-minute window of minutes 90–180 held one of each, while one of the API's 3-minute windows held none. Five is the fewest whole minutes that divide the rule's 90 and do so, and it leaves 18 floors to fit. A longer window gives fewer floors and the same picture (the worker's floor slope over minutes 90–180 is +0.010 to +0.013 for windows of 1 to 15 minutes); the API's floor depends on the requests in flight at its quietest collection, so its slope swings with the window's length (+0.009 to +0.068 for 1 to 15 minutes; r² at most 0.21 for windows of up to 11 minutes, and 0.58 to 0.61 for those of 12 to 14 minutes, which leave 6 or 7 floors and leave out the last 6 to 12 minutes).
- **What the figures tell apart.** Heap used and heap total are V8's JS heap; external and array buffers are memory V8 tracks outside it (`Buffer`s among them). RSS growing while those stay flat is memory of the process outside V8's accounting (the allocator, native modules, code), which a heap snapshot does not show.
- **The measurement's own memory.** The measuring preload records every pool wait and job. Over three hours those recordings alone would grow the API's heap by several MiB, about the bound itself, so the run takes them out of the processes with every sample (step 7 above).
- **Run it** as the 30-minute run, on a Redis of its own started as the VM's, with the units' flags (the script reads them) and the runtime first on `PATH`. It measures memory, not latency, so on the agents' machine it holds the soak lock (`flock /home/user/wt/soak.lock …`) instead of the end-to-end lock, and other work may run beside it; write down `nproc` and the load average, which the progress lines record every 5 minutes. OBE-104's run of 180 minutes ended with a scratch database of 2.8 GB, dropped at the end: 2.2 GB of `flight_offers` (the offers of the last 30 to 45 minutes of searches, and those of every checkout's search, which the purge keeps), `supplier_requests` and `idempotency_keys` ([`performance.md`](../../../docs/performance.md) §11).
- **A process that does not settle** gets a second run of at least 60 minutes with two heap snapshots of it 30 minutes apart (`--heap-snapshots`, above), compared by constructor: the number of objects and their retained size in each snapshot, and what grew between them (the DevTools Memory panel's Comparison view, or a script; OBE-104 kept its script beside the run's outputs, [`performance.md`](../../../docs/performance.md) §11). A heap snapshot shows only V8's heap: growth outside it shows up in `/proc/<pid>/status` (`RssAnon`) and `smaps`, not in the comparison. A unit's flags never change for it: that is a lead decision and a task of its own.
- **What OBE-104 found** ([`performance.md`](../../../docs/performance.md) §11): by the rule of step 4 neither process settled. The API's RSS did (+0.017 MiB a minute over minutes 90–180) but its heap-used slope, +0.025 with r² 0.00, was the collections' saw-tooth; the worker's RSS rose +0.024 MiB a minute, slowing. Heap snapshots 30 minutes apart showed no growing object but V8's compiled code. Read each slope with its r²: a heap that swings with every collection gives a slope near the bound with r² near 0.
- **R180 re-judged by the heap floor** (FIX-W61-MEMORY, from R180's raw samples with this script's functions; [`performance.md`](../../../docs/performance.md) §11): over minutes 90–180 the API's heap floor per 5 minutes rose +0.0351 MiB a minute (r² 0.08, 18 floors from 90.2 to 102.6 MiB) and the worker's +0.0112 (r² 0.61, 66.7 to 68.2 MiB). So by (30b)'s rule neither process settles either: the API on its heap floor (its RSS slope, +0.0166, is below the bound), the worker on its RSS (+0.0241). The lead accepted the memory as measured (decisions (30a) and (30c) of 2026-11-19); the next measurement is a run of 8 to 24 hours of the units on the throwaway VM ([`node-upgrade.md`](../../../../docs/mvp/runbooks/node-upgrade.md) §5 step 9), which reads RSS only: a unit's JS heap cannot be read without changing the unit.

## Extending them

Keep a new measurement in the preload, the proxy or the sink: the API and the worker themselves must run unchanged. Keep everything a run creates removable by the clean-up. Keep the output free of keys, tokens, card data, DSNs and request bodies.
