# OADR-0001: Amadeus client design

**Status:** Accepted
**Date:** 2026-10-12
**Deciders:** OTA backend tech lead. Decided during planning; revisit when a second supplier is added, when the M2 load test shows the bucket sizes are wrong, or when Amadeus publishes a supported Node SDK for Enterprise.
**Revisions:** 2026-10-28 (lead decision (1e), recording FIX-W32-OTA): point 9's row may store what the caller decides of the answer (a response hook), so another office's order never reaches a tenant's row (dated note under point 9). 2026-11-12 (OBE-102, the share it proposes under lead decision (17g) of 2026-11-11): point 6's buckets keep half of each burst for the calls a person waits for; a background call, the booking sync's order read, takes a token only while both buckets keep that reserve, and the sync waits for it instead of failing (dated note under point 6).

## Context

[ADR-0012](../../../docs/mvp/adr/0012-amadeus-account-model.md) fixes the Amadeus account model: the Velexis shared account with an office per OTA by default, OTA-owned credentials later, encrypted tokens in Redis, token buckets per credential set and per tenant, per-operation timeouts, no blind retry of order creation, and a `supplier_requests` row per call. The OTA backend uses 12 operations from the 9 specifications in [`docs/amadeus-api/`](../../../docs/amadeus-api/). The contract exposes those operations through shopping, booking and raw console endpoints. What remained open: how the client is structured in code, how types are produced, how a credential set is chosen per call (including old orders after a switch, [PADR-0012](../../../platform/docs/adr/0012-amadeus-office-pool.md)), and the exact retry and redaction rules.

## Decision

1. **One module, one entry point.** `src/amadeus/` exports `AmadeusClient` with one method per Amadeus operation (`searchFlightOffers`, `getFlightOffers`, `searchFlightAvailabilities`, `upsellAirOffers`, `quoteAirOffers`, `createFlightOrders`, `issueFlightOrder`, `getFlightOrder`, `patchFlightOrder`, `cancelFlightOrder`, `getFlightOrderByReference`, `listQueue`). No other module imports `fetch` for Amadeus (ESLint `no-restricted-imports` outside `amadeus/`).
2. **Types from the specifications.** `openapi-typescript` generates request and response types from the 9 JSON files into `src/amadeus/generated/` (committed, regenerated by `pnpm --filter @velexis/ota-backend amadeus:types`). Business modules work with these types and the OTA contract types, never with untyped JSON.
3. **Call context.** Every call takes `{tenantId, environment, operation (SDK method), requestId, staffId?, bookingId?, searchId?, orderOffice?}`. `orderOffice` is the booking's owner or queuing office, so the resolver can apply the releasing-office rule.
4. **Connection resolver** (`connection-resolver.ts`): cached platform rows → `{credId, clientId, encryptedSecret, baseUrl, offices}`. `credential_source = velexis` uses the referenced `amadeus_accounts` row; `tenant` uses the connection's own credentials. For an existing order whose office is a Velexis office `assigned` or `releasing` for the tenant, the Velexis account is used even after the tenant switched to its own credentials. `AMADEUS_BASE_URL_<ENV>` overrides the base URL (stub in development and CI).
5. **Tokens** (`token-provider.ts`): `client_credentials`, encrypted in Redis under `amadeus:token:<credId>:<env>` with TTL `expires_in − 60 s`, single flight with a 10 s lock, drop and refetch once on an operation `401`. Refused credentials are remembered for 5 minutes (`amadeus:badcred:<credId>`) and answer `424 SUPPLIER_NOT_CONFIGURED`.
6. **Rate limits** (`rate-limiter.ts`): two Redis token buckets per call, per credential set (initially 20/s) and per tenant (5/s, burst 10). Both must have a token; otherwise `429 RATE_LIMITED` with `Retry-After`, without calling Amadeus. Without Redis the client refuses calls (`503`), because unlimited calls could exhaust the shared quota.

   **2026-11-12 (OBE-102, the share it proposes under lead decision (17g) of 2026-11-11): half of each bucket is kept for the calls a person waits for.** OBE-088 found that the booking sync's order reads take their tokens from the buckets the storefront's searches and prices use. A sync scan enqueues up to 20 bookings per tenant at once, and the queue's 4 workers send about 12 reads a second, so a burst empties the tenant's bucket and takes most of the shared account's: all four `429` answers to shoppers in its run came in the minutes of the two largest bursts ([`performance.md`](../performance.md) §6 item 2). With more OTAs on the shared account, one OTA's sync takes the account's tokens from every OTA's shoppers.
   - **The share.** A call is *interactive* or *background*. An interactive call takes one token from each bucket when each holds one, as before. A background call takes one from each only when each bucket holds its reserve and one more, so the reserve stays for interactive calls: **half of each burst**, 10 of the credential set's 20 and 5 of the tenant's 10 (`AMADEUS_BACKGROUND_RESERVE` in `limits.ts`). The rates are unchanged. The script checks both buckets, with the reserve, in the same atomic step as before, and a refused call still takes nothing from either. So a sync burst can no longer take the last 5 tokens of a tenant or the last 10 of the account: a background call only gets the tokens above the reserve, whatever the interactive calls leave of the refill.
   - **Which calls are background.** The call context names it (`priority: "background"`, point 3), set in code, never from a request; a call without it is interactive. The client refuses a background write as a bug of the caller (`500`, before any call): a write is never left waiting. Background since this revision: **the booking sync's order read** (`booking.sync`, BookingSyncService's `attempt`), which can wait seconds without anyone noticing. Every other call keeps today's rule. Shopping, checkout and its payments (the card fee's Flight Offers Price), the bookings' refreshes and the console are what a person waits for. Of the worker's other jobs, ticketing (the order read before Flight Order Issue and the issue), the reconciliation of a lost Create Orders answer (Queue List, the read by reference) and the check after a cancellation without an answer keep it, because a delay there costs a traveller a ticket, a decision about their money or a cancellation they asked for. The queue poller (`queues.poll`, every 15 minutes per OTA) could wait, but it keeps it too: it reads at most two queues at a time (`ota-maintenance`'s two workers), and a refused read stores no snapshot until the next iteration, as it has no wait of its own. Revisit it if a run shows its reads refusing shoppers.
   - **A refused background call** answers as before: `429 RATE_LIMITED` with `retryAfterSeconds`, the wait until both buckets hold the reserve and one more (at least 1 s), and `AmadeusRateLimitedError` with the bucket and the wait in milliseconds as its cause. The sync then waits that wait and reads again, up to 10 seconds of waits per job, all its reads together (`BOOKING_SYNC_RATE_LIMIT_BUDGET_MS`), so a burst is spread over the refill instead of failing, and a job holds one of `ota-bookings`' 4 workers for at most its reads and those 10 seconds. Only a read that the buckets refuse for longer is recorded as before: `sync_error` `RATE_LIMITED`, and the booking is due again 30 minutes after its claim. Nothing else of the booking changes: a wait is never a failed booking. The job's result counts the waits.
   - **Measured** with `booking-load.mjs` (five tenants, the sync fixture, 30 minutes, before and after): the shoppers got no `429` in the sync bursts (one before), none of the sync's reads failed (27 of the largest burst's 97 before), and the jobs of the largest scan, 100 of them, waited at most 15.4 s for a worker, against the 60 s of the queue ([`performance.md`](../performance.md) §8).
7. **Timeouts and retries** through `AbortController`, per operation ([`flows/amadeus-connection-and-tokens.md`](../flows/amadeus-connection-and-tokens.md) §4). Automatic retry (once, 300–800 ms jitter) only for reads and the token request, on network errors, timeouts and `5xx`. Writes (`createFlightOrders`, `issueFlightOrder`, `patchFlightOrder`, `cancelFlightOrder`) are **never** retried by the client; callers reconcile or resync.
8. **Error mapping** (`error-mapper.ts`) turns Amadeus HTTP statuses and canned-message codes into `AppError` codes of the OTA catalogue (`SOLD_OUT`, `PRICE_CHANGED`, `TRAVELER_DATA_INVALID`, `VERSION_CONFLICT`, `TICKETING_FAILED`, `PAYMENT_DECLINED`, `SUPPLIER_*`), keeping the raw issue in `error.supplier` for console scope only. The table is a unit-tested constant, confirmed against the recorded fixtures in M2.
9. **Logging and redaction.** Each call writes one `supplier_requests` row in its own short tenant transaction after the call (never inside the caller's transaction), with bodies through the shared redactor and truncated to 64 KB, and one pino line without bodies. For requests that carry a card, the redacted copy is built **before** the call and the raw object is never handed to the logger or a repository ([OADR-0004](0004-airline-card-data-handling.md)).

   **2026-10-28 (lead decision (1e), FIX-W32-OTA): the answer the row stores.** A call can name what its row stores as the answer: `recordedResponse` (next to `redactedRequest` in `AmadeusCallOptions`), a function the client applies to the parsed answer of every request it sends for the call, before it writes that request's row; its result goes through the same redaction and size rules, and the call itself still answers what Amadeus sent. On the shared Velexis account a read of an order (by reference, Management GET, the orders a Queue List names) can answer another office's order: the caller withholds it in the hook (the PNR lookup and import's `withheldResponseOf`, OBE-064's office rule; the raw reads of OBE-067 take the same hook), so the tenant's row holds the withheld body from its first write, never another OTA's order, even for a moment or for ever when the process stopped between the write and a later replacement (OBE-064 replaced the row's answer after the write until then). A hook that throws leaves the row without an answer. Default: the answer as Amadeus sent it.
10. **Office enforcement.** The client fills `queuingOfficeId`, `ownerOfficeId` and queue offices from the resolved connection; a caller-provided office outside the tenant's list is refused with `403 OFFICE_NOT_ALLOWED` before any call.
11. **Test double.** `tools/amadeus-stub` (X-026) implements the token endpoint and all 12 operations from recorded, scrubbed fixtures, validates requests against the specifications and supports `X-Stub-Scenario`. Unit tests use a fake `fetch`; integration tests start the stub in-process.

## Consequences

### Positive

- One place to change when Amadeus behaviour, quotas or credentials change; business modules stay supplier-agnostic.
- Generated types catch request-shape mistakes at compile time, and the stub catches the rest at test time.
- The shared account's quota and the OTAs' office isolation are enforced in code, not by convention.

### Negative

- Generated types from large specifications are verbose and slow `tsc` slightly; they live in their own folder, excluded from lint.
- Refusing calls when Redis is down turns a cache outage into a search outage. On one VM Redis failures are rare and short; protecting the shared quota matters more.
- The error table is a best guess until fixtures from the real test environment are recorded.

### Follow-ups

- M2: record fixtures for every operation and confirm the error table; load-test the buckets.
- M5: integration tests for the releasing-office rule with the platform's office pool data.

## Alternatives considered

- **The public `amadeus` Node SDK.** It targets the self-service APIs, not Enterprise endpoints and headers, and hides timeouts and retries we must control.
- **Retrying order creation with an idempotency header.** Flight Create Orders has no idempotency key; a retry can create a second PNR.
- **Per-tenant token caches for the shared account.** Multiplies token requests; the shared account's tokens are shared by design ([ADR-0012](../../../docs/mvp/adr/0012-amadeus-account-model.md)).
