# Changelog of `@velexis/ota-sdk`

Every change that a consumer of the SDK can notice is recorded here by hand, newest first ([OADR-0016](../docs/adr/0016-sdk-packaging-and-type-contract.md) point 8). The SDK follows [semantic versioning](https://semver.org/): a change that the contract test would reject is a major version, new methods and options are minor, fixes are patches. Versions `0.x` live only in the workspace (`workspace:*` in the storefront and the OTA admin); `1.0.0` is the first npm release (M6). `VERSION` in `src/version.js` always equals `version` in `package.json` (a unit test fails otherwise), so a release changes both and adds its section here.

A method that will be removed is marked `@deprecated` in its JSDoc for at least one minor release first, and the deprecation is listed here.

## 0.1.0 (unreleased, workspace only)

### Fixed

- In token and server mode, a refresh token the family has rotated leads to the newest tokens of its session only for a client that held it as its own string before the rotation, or within 10 s of the rotation, and an old access token is replaced by a newer one only together with the refresh token of the same session (FIX-W52-SDK, lead decisions (21d) and (21e) of 2026-11-13, before 1.0.0). Before, any client of the family that presented a rotated refresh token, at any time, was given the session's newest tokens instead (a server's per-request client made from the root with a visitor's old refresh-token cookie, or a token function that still gave it), so a rotated refresh token stolen from a cookie jar or a log kept working inside one server process for as long as the family remembered it; and a client whose token functions serve several visitors sent the newer access token it had recorded for an old one whatever refresh token the call gave (none, another session's or an unknown one), so a visitor's expired access token became a valid one. Now the clients that held the token as their own string `refreshToken` before the family recorded the rotation (the string a client was made or derived with, or the refresh token it took from a refresh or session result it took part in) follow it at any later time, along any chain of rotations, as SDK-016 and SDK-017 promised for the clients derived before a refresh; any other client, token functions included, takes the newest tokens for 10 s after the rotation (`ROTATION_WINDOW_MS`, the window of the build-your-own-frontend guide's §8.2) and after that sends the rotated token to the API as it is: the API's reuse detection answers `401 REFRESH_TOKEN_REUSED` and revokes the session, and the SDK reports it as any refused refresh (the starting client's `onSessionExpired`, the `AuthenticationError` to every waiting call). A call that presents a token after the family has recorded its rotation no longer joins the refresh that rotated it while that refresh's hooks still run. A client's own record of replaced access tokens gives the newer access token only when the call's refresh-token source gives that session's newest refresh token, or a value that leads to it under the rules above; an expired access token presented with no refresh token, with another session's refresh token or with an unknown one is sent as it is (`401 TOKEN_EXPIRED`), so a refresh-token function is now also read before a request whose access token the client has replaced, and a client without a refresh token keeps sending the access token it was given after a session result (whose tokens still reach `onSessionRefreshed`). A token function that still gives the tokens a refresh or session result replaced gets the new ones for 10 s, then its own value: store the new tokens through `onSessionRefreshed`. The storefront's cookie mode and the OTA admin (staff clients with an access token only, which refresh through the admin's own de-duplicated `console.auth.refresh`) are unchanged. Internal behaviour only: no option, method or type changed. The ESM bundle is 15.6 KB min+gzip (15 998 B, 328 B more).

- In token and server mode, the clients of one family (the client `createVelexisClient` made and every client derived from it with `withOptions`) share the refresh of each refresh token (SDK-017, lead decision (20f) of 2026-11-13). Before, every client refreshed on its own, so two clients that held one refresh token (a client and one derived from it, before or after a refresh, or two derived with the same `refreshToken` string) each presented it at the next `401 TOKEN_EXPIRED`, at once or one after the other, and the API answered the second `401 REFRESH_TOKEN_REUSED` and revoked the session. Now the calls of the family that present the same refresh token wait for one refresh and are sent again with its new tokens, and a client that still holds a refresh token the family has rotated (also by `auth.refresh`, `console.auth.refresh` or `auth.changePassword` of a client that holds tokens) takes the new tokens instead of presenting it; the family remembers the last 512 rotated refresh tokens. The family is reached through a client's refresh token only, never through an access token, so a client that holds only an old access token of a session is never given its newer tokens. The new tokens are reported once, by the `onSessionRefreshed` (and `onStaffSessionRefreshed`) of the client whose call started the refresh, and a refused refresh calls that client's `onSessionExpired` once and rejects every waiting call with the same `AuthenticationError`. Everything is keyed by the token's value, so clients with different refresh tokens share nothing: a server's per-visitor clients never wait for or take each other's tokens, and one client whose token functions give two visitors' tokens at once now refreshes both (before, the second visitor's call waited for the first's refresh and failed). In cookie mode, the family's shared refresh and CSRF fetch now go out with the transport settings of the family's root, the client `createVelexisClient` made (`baseUrl`, `maxRetries`, `timeoutMs`, `headers`, `fetch`, `onResponse` and the rest), whichever client's call started them: a refresh that the storefront's fare-rules client (`maxRetries: 0`) starts and the API answers `503` is now retried, and every waiting call succeeds; the starting client's `onSessionExpired` is still the one called. Two clients made with `createVelexisClient` still share nothing. Internal behaviour only: no option, method or type changed. The ESM bundle is 15.3 KB min+gzip (15 670 B, 532 B more).

- In cookie mode, the clients derived with `withOptions` from one client share its refresh state (SDK-016, lead decision (17d) of 2026-11-11): the refresh in flight, the count of finished refreshes and the CSRF re-fetch in flight. Before, every derived client had a session of its own, so two of them answered `401 TOKEN_EXPIRED` at the same time (the storefront's currency client and its fare-rules client with `maxRetries: 0`) each sent `POST /v1/auth/refresh` with the same `__Host-vx_rt` cookie, and the API answered the second `401 REFRESH_TOKEN_REUSED` and revoked the session's family (OADR-0006). Now one family of clients sends one refresh for any number of its calls answered `TOKEN_EXPIRED` together and then sends each call once more, a call whose attempt went out before a refresh of any of them has finished is sent again without another one, and their writes share one `GET /v1/storefront` for a missing or refused CSRF cookie. The shared request went out with the options of the client whose call started it (with the root's since SDK-017, above); a refused refresh rejects every waiting call with the same `AuthenticationError` and calls `onSessionExpired` once, the starting client's (a derived client keeps its parent's hook unless it sets its own). Every other option (`maxRetries`, `currency`, `timeoutMs`, headers) stays each client's own. Token and server mode kept a session per client, derived ones included: two clients that held one refresh token (a client and one derived from it, before or after a refresh, or two derived with the same `refreshToken` string) still presented it twice (fixed by SDK-017, above). Internal behaviour only: no option, method or type changed. The ESM bundle is 14.8 KB min+gzip (15 138 B, 111 B more).

- `storefront.resolve()`'s `@throws` JSDoc names `TENANT_SUSPENDED` under `PermissionError`, which its operation lists since FIX-W47-OTA (lead decision (13f) of 2026-11-10: the document lists `TENANT_SUSPENDED` on every operation the tenant guard resolves an OTA for, the same operations as `HOST_NOT_ALLOWED`, and every other method already named it). The class was already named, so no method gained one. JSDoc only: no method, type or behaviour changed; `throws.test.js` checks it on every method.
- The `@throws` JSDoc names `HOST_NOT_ALLOWED` and `STAFF_MEMBERSHIP_INACTIVE` under `PermissionError` wherever the operation lists them since FIX-W46-OTA (lead decision (11k) of 2026-11-06): `HOST_NOT_ALLOWED` on every method (the hosted storefront's host is checked on every operation, the console's included), `STAFF_MEMBERSHIP_INACTIVE` on the console methods but `console.auth.signOut` and on the shopping and checkout methods a `console:automation` key calls in console scope with a staff token (`flights.search` … `checkout.complete`). Both are 403s, so no method gained a class. JSDoc only: no method, type or behaviour changed.
- The `@throws` JSDoc of every method names the generic refusals its operation lists since FIX-W45-OTA (lead decision (9e) of 2026-11-06), each in the tag of the class the SDK throws it as: `ValidationError` `VALIDATION_FAILED` and `INVALID_REQUEST` (the class is new on the 18 methods whose operations OBE-095 gave their `400`, `storefront.get` among them, and on `console.auth.me` and `bookings.getDocumentDownloadUrl`), `AuthenticationError` `UNAUTHENTICATED`, `PermissionError` `ORIGIN_NOT_ALLOWED` and `SCOPE_NOT_ALLOWED`. JSDoc only: no method, type or behaviour changed. A contract test (`test/contract/throws.test.js`) ties every method's `@throws` classes to its operation's `x-error-codes` through `errorClassFor`.
- `account.update()` and `account.preferences.update()` called without params sent `PATCH /v1/account` and `PATCH /v1/account/preferences` without `If-Match` (FIX-W27-FOLLOWUPS); they now reject with a `TypeError` before any request, as SDK-012's methods do. Every method that requires `ifMatch` (`account.*`, `bookings.*` and `console.*`) shares one check (`internal/if-match.js`), so a call without params or without a valid `ifMatch` is the same `TypeError` everywhere, naming whose version it is: the account methods now say "the account version", "the preferences version" and "the saved traveler version" where they said "the version of the last read". The ESM bundle is 14.7 KB min+gzip.

### Added

- The MVP additions of `console` and `storefront` (SDK-012, `docs/extensions.md` §3.1–§3.3): `console.settings` with `markupRules` and `feeRules` (`list`, `create`, `get`, `update`, `delete`), `storefront` (`get`, `update`), `pages` (`list`, `create`, `get`, `update`, `delete`), `assets` (`list`, `upload`, `delete`) and `templates` (`list`, `get`, `put`, `preview`, `reset`); `console.payments` (`list`, `get`, `capture`, `refund`); and `storefront.listPages` and `storefront.getPage`, each named by its `x-sdk-method` and sent through the route table. The console additions send `cache: "no-store"` and the client's `X-Velexis-Environment` like the rest of `console`; the page methods are public and leave the cache mode to the caller, with `locale` as a query parameter. The updates and deletes of markup rules, fee rules, storefront settings and pages and `payments.capture` require `ifMatch` (a version number is sent as `If-Match: "<version>"`, an ETag string as it is; a missing or malformed one is a `TypeError` that names whose version it is, before any request); `templates.put` sends `If-Match` only when `ifMatch` is given. `assets.upload` sends `multipart/form-data` from a `Blob` or `File` with the parts `kind`, `fileName` (when given) and `file` and a generated `Idempotency-Key`, leaves the `Content-Type` and its boundary to `fetch`, and refuses a `file` that is not a `Blob` or a missing `kind` with a `TypeError`. The settings and payments lists resolve with a `Page`. `console.js` exports the parameter, schema and namespace types of the additions (`ConsoleListMarkupRulesParams` … `ConsolePaymentsApi`) after the contract's names. The parity test's pending list is empty: the client has every `x-sdk-method` of the document. The ESM bundle is 14.6 KB min+gzip.
- The `auth` and `account` namespaces (SDK-008): `auth.signUp`, `.verifyEmail`, `.resendVerification`, `.signIn`, `.refresh`, `.signOut`, `.requestPasswordReset`, `.resetPassword`, `.changePassword` and `.getSession`; `account.get`, `.update`, `.delete` and the deferred `account.preferences.*`, `account.savedTravelers.*` and `account.dataExports.*` (nine methods: `ServerError` `NOT_IMPLEMENTED`), each named by its `x-sdk-method` and sent through the route table; `account.savedTravelers.list` resolves with a `Page`; every method sends `cache: "no-store"` unless the call sets `cache` or `next`. `account.update`, `account.preferences.update` and `account.savedTravelers.update` require `ifMatch` (a version number is sent as `If-Match: "<version>"`, an ETag string as it is; a missing or malformed one is a `TypeError` before any request). `auth.signIn`, `auth.refresh` and `auth.changePassword` are typed `AuthSessionResult | AuthSessionInfo`, the approved deviation of OADR-0006. In token and server mode their results feed the client's session: `onSessionRefreshed` gets `result.session`, and the client sends the new tokens wherever its token sources still give the replaced ones, so it never presents a rotated refresh token again; a client without token options only reports them, a call with its own `options.accessToken` or `Authorization` header feeds nothing, and a staff client keeps its staff session. Cookie mode stores nothing: `auth.refresh` sends an empty body, a `refreshToken` in the params of `refresh` or `signOut` is a `TypeError` before any request, the session results resolve without token fields and `signUp` and `resetPassword` with `session: null`, whatever a response says. The public module `identity.js` with the auth and account typedefs of `identity.d.ts` and the factories `createAuthApi` and `createAccountApi`. The ESM bundle is 13.7 KB min+gzip.
