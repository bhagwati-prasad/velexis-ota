# Changelog of `@velexis/ota-sdk`

Every change that a consumer of the SDK can notice is recorded here by hand, newest first ([OADR-0016](../docs/adr/0016-sdk-packaging-and-type-contract.md) point 8). The SDK follows [semantic versioning](https://semver.org/): a change that the contract test would reject is a major version, new methods and options are minor, fixes are patches. Versions `0.x` lived only in the workspace (`workspace:*` in the storefront and the OTA admin, which keep using it); `1.0.0` is the first npm release (M6). `VERSION` in `src/version.js` always equals `version` in `package.json` (a unit test fails otherwise), so a release changes both and adds its section here.

A method that will be removed is marked `@deprecated` in its JSDoc for at least one minor release first, and the deprecation is listed here.

## 1.0.0 (unreleased)

The first npm release (SDK-015, [OADR-0016](../docs/adr/0016-sdk-packaging-and-type-contract.md) point 8), prepared on 2026-11-18. It is published with provenance from the tag `sdk-v1.0.0` once the owner has chosen the licence and approved the publish workflow's lines ([README §9](README.md#9-versioning-publishing-and-what-is-deferred)); this heading then gets the date of the release. 1.0.0 contains every change listed under 0.1.0 below, which never left the workspace:

- 129 methods in 8 namespaces (`storefront`, `reference`, `flights`, `checkout`, `bookings`, `auth`, `account`, `console`), one per `x-sdk-method` of the OTA booking API: the 96 of the contract and 33 MVP additions ([`docs/extensions.md`](docs/extensions.md)), checked against the frozen contract declarations by the contract test.
- Three session modes: cookie mode for the hosted storefront (same-origin cookies and CSRF, one refresh shared by the clients derived from one client), token mode with a publishable key and server mode with a secret key (one refresh per refresh token in a family of clients, and the rotation rules of README §4.2 and §4.3).
- The contract's error classes and `isVelexisError`, `Page<T>` with `for await`, retries with one `Idempotency-Key` per call, timeouts, `Retry-After` and the `onResponse` hook.
- An ESM bundle (15.8 KB min+gzip of its 25 KB budget) and an IIFE (`window.Velexis`), both ES2022 and without dependencies, and declarations that include the OTA API's types; Node.js 22.12 and later and 24, evergreen browsers and edge runtimes.

### Added

- Two optional list parameters, additions to the OTA API's console operations (FIX-W70-CONSOLE, guidebook known issues KI-022 and KI-023): `console.queues.listSnapshots({ latest: true })` lists only the newest stored read of each office, queue and category the other filters match, newest first and paged as before, so a queue read within the 30 days of retention is listed however many later reads of other queues there are; `console.settings.markupRules.list({ isDefault: true, limit: 1 })` reads the seeded default markup rule however many rules come first (an empty page when the OTA has none; `isDefault: false` lists every other rule). `ConsoleListQueueSnapshotsParams.latest` and `ConsoleListMarkupRulesParams.isDefault` are optional booleans and the route table sends them as query parameters; nothing else changed ([`docs/extensions.md`](docs/extensions.md) §4).

### Changed

- The declarations are self-contained (SDK-015, OADR-0016 point 7): the build copies the OTA part of `@velexis/api-types` (the generated `components`, `paths`, `operations`, `webhooks` and `$defs` of the OTA booking API) into `dist/types/api-types.d.ts`, and the declarations import `./api-types.js` instead of `@velexis/api-types`, their declaration maps moved to match. A project that installs the package from npm needs nothing else, not even for its types; `test/unit/pack.test.js` compiles what `npm pack` makes in an empty project with `strict` and without `skipLibCheck`. The types themselves are unchanged, so code that also imports `@velexis/api-types` (inside the monorepo) stays compatible.
- `VERSION` and `package.json`'s `version` are `1.0.0`.

### Fixed

- In cookie mode, the tabs of one storefront no longer revoke the session by refreshing it at the same time (FIX-W67-KI003, guidebook known issue KI-003, lead decision (36f) of 2026-11-21, [OADR-0006](../docs/adr/0006-storefront-cookie-sessions-and-csrf.md) point 5). The refresh was shared only by the clients of one page (SDK-016), but every tab sends the same `__Host-vx_rt` cookie, and the API has no grace window: two tabs whose access cookie had ended sent `POST /v1/auth/refresh` together, the second presented the cookie the first had just rotated, and the API answered `401 REFRESH_TOKEN_REUSED`, revoked the session and cleared its cookies, signing the customer out in every tab. Where the page has Web Locks (`navigator.locks`), each cookie-mode refresh now runs under the origin's lock `velexis-sdk:cookie-refresh`, held from before the request until its answer is in, the root's retries included; the CSRF cookie is fetched outside it. A tab whose refresh finds the lock held waits for it and sends no refresh of its own: it sends its calls once more with the access cookie the other tab's refresh left, and refreshes, under the lock, only when they are refused `TOKEN_EXPIRED` again. The wait is bounded by the refresh's timeout (the root client's `timeoutMs`): a tab stuck holding the lock makes the waiting calls fail with a `ConnectionError` `TIMEOUT`. A refused refresh releases the lock and is reported as before; a tab that waited for it gets the API's answer to its call without the cleared cookies (`401 UNAUTHENTICATED` where a customer is needed, a guest's answer on an optional operation such as a search) and calls no `onSessionExpired` of its own. Without Web Locks (an insecure context, an older browser, a test DOM) or where they refuse the request, the refresh runs as before. Token and server mode are unchanged. Internal behaviour only: no option, method or type changed. The ESM bundle is 16.2 KB min+gzip (16 627 B, 497 B more).
- A custom `fetch` that throws synchronously (a programming error, such as a wrapper that throws before it sends) makes the call rethrow that very error at once (FIX-W70-SDK, guidebook known issue KI-030). It was caught with the network failures, retried up to `maxRetries` times and reported as a `ConnectionError` `NETWORK_ERROR` with the error as its `cause`. A `fetch` that rejects is a network failure as before (`NETWORK_ERROR`, retried), since a standard `fetch` rejects with a `TypeError` for both kinds. `checkout.completeWithAirlineCard` passes such an error on only when it holds nothing of the card, and otherwise throws a plain `Error` with a fixed message instead, as it drops a `cause` that holds the card.
- `request(method, path, init)` refuses a path with a `.` or `..` segment, also percent-encoded in any letter case (`%2e`, `%2E%2e`, `.%2e`), with a `TypeError` before any request (FIX-W70-SDK, KI-031). The URL resolves such a segment, so with `baseUrl: "/api"` a call to `/../v1/storefront` went to `/v1/storefront` on the same origin, outside the base URL (with the cookies, in cookie mode). A dot inside a segment (`/v1/files/a.b`) and dots in the query string are sent as before; the methods' path parameters were already refused as `.` or `..`.
- An `Idempotency-Key` in a call's `headers`, in any letter case, meets the rule of the `idempotencyKey` option (16 to 128 visible ASCII characters), with a `TypeError` that names the entry before any request (FIX-W70-SDK, KI-032). The call sends such a header as its key, so a short one went out and the API refused it with `400`. An `Idempotency-Key` in the client's `headers` is checked the same way by `createVelexisClient` and `withOptions`, although no call sends it; which key a call sends does not change. With this fix and the two above, the ESM bundle is 16.4 KB min+gzip (16 844 B, 217 B more).
- README §4 explains a client made without a key (token mode without `X-Api-Key`, which the MVP API answers `401 INVALID_API_KEY` on every operation) and `hostingKey`, which the MVP API does not serve (FIX-W70-SDK, KI-033, lead decision (39t) of 2026-11-23); neither is refused at construction.

## 0.1.0 (unreleased, workspace only)

Never published on its own: these changes reach npm with 1.0.0 (above).

### Changed

- The supported Node.js versions are stated, declared in `engines` and tested (SDK-019, [ADR-0029](../../docs/mvp/adr/0029-nodejs-24-runtime.md) item 9, before 1.0.0): Node.js 22.12 and later and 24, besides evergreen browsers and edge runtimes, where the docs said "Node.js 22". `package.json` declares `"engines": { "node": ">=22.12" }`, and CI runs the unit and contract tests on 22.12.0 (the non-required job `sdk-node22`, until Node 22's end of life on 2027-04-30) and on the repository's Node.js 24. 22.12.0 is the floor because `require()` of the ES module bundle is on by default from it; on 22.12.x that `require()` prints an `ExperimentalWarning` when the requiring file is outside `node_modules`, which 22.13.0 dropped (`import` never prints it). Docs, package metadata and CI only: no method, type or behaviour changed.

### Fixed

- In token and server mode, `onStaffSessionRefreshed` (the automatic refresh of a `sessionKind: "staff"` client) gets the family's newest tokens of the staff session whenever another client of the family has rotated the refresh token it would report by the time it is called (FIX-W57-SDK, lead decision (26j) of 2026-11-16, before 1.0.0). The staff hook runs once the starting client's `onSessionRefreshed` has finished. When another client that holds the brand-new staff refresh token (one made or derived with the staff member's tokens before the refresh, which follows its rotation) refreshed it while `onSessionRefreshed` still ran, the staff hook reported the result's already-rotated pair, so staff cookies it wrote after the other client's hook had stored the newest pair ended with the rotated refresh token, which the staff member's next request presented after the 10 s window (`401 REFRESH_TOKEN_REUSED`, a revoked session). Now it gets the whole `ConsoleStaffSession` with the newest `accessToken` and `refreshToken` in `session`, and every other field the result's (the session's `accessTokenExpiresAt`, `refreshTokenExpiresAt`, `tokenType` and `subject`, and the `staff`, `tenant`, `permissions` and `environments` of that refresh), as `onSessionRefreshed` does for session results since FIX-W56-SDK: `accessTokenExpiresAt` is early, never late. When nothing has rotated the result's refresh token, it still gets the result itself; `onSessionRefreshed` is unchanged. The OTA admin's staff clients (an access token only, refreshing through the admin's own de-duplicated `console.auth.refresh`) are unaffected. Internal behaviour only: no option, method or type changed. The ESM bundle is 15.8 KB min+gzip (16 130 B, 34 B more).
- In token and server mode, `onSessionRefreshed` gets the family's newest tokens of the session of an `auth.signIn`, `auth.refresh` or `auth.changePassword` result whenever another client of the family has rotated the result's refresh token by the time the hook is called, whatever the client's token sources, and the client keeps those tokens (FIX-W56-SDK, lead decisions (25k) and (25l) of 2026-11-16, before 1.0.0). SDK-018 gave the hook the newer pair only when the client's own read of its token sources had already followed that rotation (a string refresh token it held). A client whose refresh-token function reads the integrator's store, one with a string refresh token it did not hold (it refreshes the store's token explicitly), or one that follows another session's tokens took the result instead and reported its already-rotated pair, so its hook wrote that pair over the newest one another client's hook had stored (the build-your-own-frontend guide's §8.2 cookies), and the visitor's next request after the 10 s window presented the rotated refresh token (`401 REFRESH_TOKEN_REUSED`, a revoked session); and a client whose token functions already gave the newest pair led it back to the result's rotated pair for 10 s after the result, so a refresh of its own in that span, once the rotation's own 10 s had passed, presented the rotated refresh token. Now the hook gets the result's session with the newest `accessToken` and `refreshToken`, and every other field (`accessTokenExpiresAt`, `refreshTokenExpiresAt`, `tokenType`, `subject`) is the result's: `accessTokenExpiresAt` is early by at most the time between the two rotations, never late, and `refreshTokenExpiresAt` is the session's absolute end, the same for every pair. When nothing has rotated the result's refresh token, the hook still gets `result.session` itself, and the call always resolves with the result as the API sent it. The automatic refresh is unchanged: its hook runs as soon as the family has recorded the rotation, before any client can present the new refresh token. Internal behaviour only: no option, method or type changed. The ESM bundle is 15.7 KB min+gzip (16 096 B, 27 B less).
- In token and server mode, two corrections before 1.0.0 (SDK-018, lead decisions (24l) to (24n) of 2026-11-15). When a client keeps newer tokens than its own `auth.signIn`, `auth.refresh` or `auth.changePassword` result (another client of the family rotated the result's refresh token while the client's token sources answered, and the client follows that rotation; FIX-W54-SDK), its `onSessionRefreshed` gets the result's session with those newer tokens: `accessToken` and `refreshToken` are the newer pair, and every other field (`accessTokenExpiresAt`, `refreshTokenExpiresAt`, `tokenType`, `subject`) is the result's; before, it got the result's already-rotated pair, so a store written by every client's hook (the build-your-own-frontend guide's §8.2 cookies) ended with the rotated refresh token, which the visitor's next request presented after the 10 s window (`401 REFRESH_TOKEN_REUSED`, a revoked session). In every other case the hook still gets `result.session` itself, and the call resolves with the result as the API sent it. An empty string as `refreshToken` is no refresh token anywhere, as an empty `accessToken` is no access token since FIX-W54-SDK: a client made with `refreshToken: ""` behaves exactly as one made without `refreshToken` (or with `null`); before, it counted as holding a refresh token, so a call refused with `401 TOKEN_EXPIRED` was sent again when its access-token function had moved on, a client with a string access token and `refreshToken: ""` was not the exempt access-only client of FIX-W53-SDK (`withOptions` started a client derived after its sign-in with the result's refresh token, which then refreshed it), and without an access token it kept its session results and the family learned the rotations of its `auth.refresh`. Cookie mode still refuses every token option that is set, an empty string included. Internal behaviour only: no option, method or type changed. The ESM bundle is 15.7 KB min+gzip (16 123 B, 28 B more).
- In token and server mode, two corrections before 1.0.0 (FIX-W54-SDK, lead decisions (23g) and (23h) of 2026-11-15). A client holds the refresh token of its own `auth.signIn`, `auth.refresh` or `auth.changePassword` result from the moment the result arrived; before, it held it only once its token sources had answered, so when another client of the family that held that token (one that followed the result's rotation) refreshed it while a slow access-token function of the client still answered, a client with a string `refreshToken` followed that rotation for 10 s only and after that presented the rotated token (`401 REFRESH_TOKEN_REUSED`, a revoked session). When reading its token sources has by then already followed the family's rotation of the result's refresh token to newer tokens, the client keeps those newer tokens instead of the result's; before, it went back to the result's tokens and depended on the family still remembering their rotation (the last 512 rotations), so after 512 later refreshes of other sessions it presented the rotated token. `onSessionRefreshed` still gets the result's session. An empty string as `accessToken` is no access token anywhere, as a token function's `""` already was: a client made with `accessToken: ""` behaves exactly as one made without `accessToken`; before, after its own session result `withOptions` started a derived client from the result's access token, and without a refresh token the client counted as holding tokens (it kept the result, and the family learned the rotations of its `auth.refresh`). Internal behaviour only: no option, method or type changed. The ESM bundle is 15.7 KB min+gzip (16 095 B, 47 B more).
- In token and server mode, three corrections of FIX-W52-SDK's rules (FIX-W53-SDK, lead decisions (22g) to (22j) of 2026-11-15, before 1.0.0). A client given a string `accessToken` and no `refreshToken` (neither a string nor a function, such as a server's request client made with the visitor's access token only) sends the access token of its own latest `auth.signIn`, `auth.refresh` or `auth.changePassword` result again from its next call on, and `withOptions` starts from it, as SDK-008 built; since FIX-W52-SDK it kept sending the access token it was given. It still never refreshes, no other client's result reaches it, and every other client keeps FIX-W52-SDK's rule (an access token that a session result replaced is sent anew only together with the new session's refresh token). The 10 s window of a rotation counts a clock set back since by at most 10 s as inside and by more as outside; before, any step back put the rotation outside the window, so a normal clock correction on a server could make a late request present the rotated refresh token and revoke the visitor's session. A call of a client with a string `refreshToken` that starts or joins a shared refresh holds its new refresh token from that moment; before, it held it only once the starting client's `onSessionRefreshed` (and `onStaffSessionRefreshed`) had run, so when another holder rotated the brand-new token in the meantime, the clients of that refresh followed that rotation for 10 s only and after that presented the rotated token (`401 REFRESH_TOKEN_REUSED`, a revoked session). Two behaviours are confirmed as they are: a refresh leaves the family's refreshes in flight as soon as the family has recorded its rotation, and for a token function's value the family's record of a rotation is checked before the client's own record of what a session result replaced. Internal behaviour only: no option, method or type changed. The ESM bundle is 15.7 KB min+gzip (16 048 B, 50 B more).
- In token and server mode, a refresh token the family has rotated leads to the newest tokens of its session only for a client that held it as its own string before the rotation, or within 10 s of the rotation, and an old access token is replaced by a newer one only together with the refresh token of the same session (FIX-W52-SDK, lead decisions (21d) and (21e) of 2026-11-13, before 1.0.0). Before, any client of the family that presented a rotated refresh token, at any time, was given the session's newest tokens instead (a server's per-request client made from the root with a visitor's old refresh-token cookie, or a token function that still gave it), so a rotated refresh token stolen from a cookie jar or a log kept working inside one server process for as long as the family remembered it; and a client whose token functions serve several visitors sent the newer access token it had recorded for an old one whatever refresh token the call gave (none, another session's or an unknown one), so a visitor's expired access token became a valid one. Now the clients that held the token as their own string `refreshToken` before the family recorded the rotation (the string a client was made or derived with, or the refresh token it took from a refresh or session result it took part in) follow it at any later time, along any chain of rotations, as SDK-016 and SDK-017 promised for the clients derived before a refresh; any other client, token functions included, takes the newest tokens for 10 s after the rotation (`ROTATION_WINDOW_MS`, the window of the build-your-own-frontend guide's §8.2) and after that sends the rotated token to the API as it is: the API's reuse detection answers `401 REFRESH_TOKEN_REUSED` and revokes the session, and the SDK reports it as any refused refresh (the starting client's `onSessionExpired`, the `AuthenticationError` to every waiting call). A call that presents a token after the family has recorded its rotation no longer joins the refresh that rotated it while that refresh's hooks still run. A client's own record of replaced access tokens gives the newer access token only when the call's refresh-token source gives that session's newest refresh token, or a value that leads to it under the rules above; an expired access token presented with no refresh token, with another session's refresh token or with an unknown one is sent as it is (`401 TOKEN_EXPIRED`), so a refresh-token function is now also read before a request whose access token the client has replaced, and a client without a refresh token keeps sending the access token it was given after a session result (whose tokens still reach `onSessionRefreshed`). A token function that still gives the tokens a refresh or session result replaced gets the new ones for 10 s, then its own value: store the new tokens through `onSessionRefreshed`. The storefront's cookie mode and the OTA admin (staff clients with an access token only, which refresh through the admin's own de-duplicated `console.auth.refresh`) are unchanged. Internal behaviour only: no option, method or type changed. The ESM bundle is 15.6 KB min+gzip (15 998 B, 328 B more).

- In token and server mode, the clients of one family (the client `createVelexisClient` made and every client derived from it with `withOptions`) share the refresh of each refresh token (SDK-017, lead decision (20f) of 2026-11-13). Before, every client refreshed on its own, so two clients that held one refresh token (a client and one derived from it, before or after a refresh, or two derived with the same `refreshToken` string) each presented it at the next `401 TOKEN_EXPIRED`, at once or one after the other, and the API answered the second `401 REFRESH_TOKEN_REUSED` and revoked the session. Now the calls of the family that present the same refresh token wait for one refresh and are sent again with its new tokens, and a client that still holds a refresh token the family has rotated (also by `auth.refresh`, `console.auth.refresh` or `auth.changePassword` of a client that holds tokens) takes the new tokens instead of presenting it; the family remembers the last 512 rotated refresh tokens. The family is reached through a client's refresh token only, never through an access token, so a client that holds only an old access token of a session is never given its newer tokens. The new tokens are reported once, by the `onSessionRefreshed` (and `onStaffSessionRefreshed`) of the client whose call started the refresh, and a refused refresh calls that client's `onSessionExpired` once and rejects every waiting call with the same `AuthenticationError`. Everything is keyed by the token's value, so clients with different refresh tokens share nothing: a server's per-visitor clients never wait for or take each other's tokens, and one client whose token functions give two visitors' tokens at once now refreshes both (before, the second visitor's call waited for the first's refresh and failed). In cookie mode, the family's shared refresh and CSRF fetch now go out with the transport settings of the family's root, the client `createVelexisClient` made (`baseUrl`, `maxRetries`, `timeoutMs`, `headers`, `fetch`, `onResponse` and the rest), whichever client's call started them: a refresh that the storefront's fare-rules client (`maxRetries: 0`) starts and the API answers `503` is now retried, and every waiting call succeeds; the starting client's `onSessionExpired` is still the one called. Two clients made with `createVelexisClient` still share nothing. Internal behaviour only: no option, method or type changed. The ESM bundle is 15.3 KB min+gzip (15 670 B, 532 B more).

- In cookie mode, the clients derived with `withOptions` from one client share its refresh state (SDK-016, lead decision (17d) of 2026-11-11): the refresh in flight, the count of finished refreshes and the CSRF re-fetch in flight. Before, every derived client had a session of its own, so two of them answered `401 TOKEN_EXPIRED` at the same time (the storefront's currency client and its fare-rules client with `maxRetries: 0`) each sent `POST /v1/auth/refresh` with the same `__Host-vx_rt` cookie, and the API answered the second `401 REFRESH_TOKEN_REUSED` and revoked the session's family (OADR-0006). Now one family of clients sends one refresh for any number of its calls answered `TOKEN_EXPIRED` together and then sends each call once more, a call whose attempt went out before a refresh of any of them has finished is sent again without another one, and their writes share one `GET /v1/storefront` for a missing or refused CSRF cookie. The shared request went out with the options of the client whose call started it (with the root's since SDK-017, above); a refused refresh rejects every waiting call with the same `AuthenticationError` and calls `onSessionExpired` once, the starting client's (a derived client keeps its parent's hook unless it sets its own). Every other option (`maxRetries`, `currency`, `timeoutMs`, headers) stays each client's own. Token and server mode kept a session per client, derived ones included: two clients that held one refresh token (a client and one derived from it, before or after a refresh, or two derived with the same `refreshToken` string) still presented it twice (fixed by SDK-017, above). Internal behaviour only: no option, method or type changed. The ESM bundle is 14.8 KB min+gzip (15 138 B, 111 B more).

### Added

- The MVP additions of `console` and `storefront` (SDK-012, `docs/extensions.md` §3.1–§3.3): `console.settings` with `markupRules` and `feeRules` (`list`, `create`, `get`, `update`, `delete`), `storefront` (`get`, `update`), `pages` (`list`, `create`, `get`, `update`, `delete`), `assets` (`list`, `upload`, `delete`) and `templates` (`list`, `get`, `put`, `preview`, `reset`); `console.payments` (`list`, `get`, `capture`, `refund`); and `storefront.listPages` and `storefront.getPage`, each named by its `x-sdk-method` and sent through the route table.
