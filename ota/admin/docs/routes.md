# OTA admin routes

This page details every route of the OTA admin: what it shows, the SDK `console` calls it makes (server side), the actions it offers with their permissions, and the states and error codes it must handle. It is the checklist for the OTA admin tasks of M4 and for the Playwright journeys. The summary table, sessions, data-fetching pattern and permission rules are in the [OTA admin README](../README.md); the API behaviour behind each call is in the [console operations flow](../../docs/flows/console-operations.md), [SDK guide B4](../../../docs/velexis-sdk/sdk/docs/B4.md) and [API changes part 2](../../docs/api-changes-console-and-internal.md).

Related: [scope §1.3 and §2.3](../../docs/scope.md#13-staff-roles-and-permissions), [OADR-0011](../../docs/adr/0011-console-access-staff-sessions-and-environments.md), [OADR-0018](../../docs/adr/0018-ota-admin-consumes-the-sdk-server-side.md), [OADR-0005](../../docs/adr/0005-markup-and-fee-engine.md), [OADR-0008](../../docs/adr/0008-ticketing-policy.md), [OADR-0012](../../docs/adr/0012-storefront-settings-assets-and-pages.md), [OADR-0013](../../docs/adr/0013-notifications-and-booking-documents.md), reference pages of the [Next.js example](../../../docs/velexis-sdk/examples/next-storefront/app/console/).

## 1. Errors every route handles

| Code | Shown as |
|---|---|
| `401 TOKEN_EXPIRED` | Redirect to `/auth/refresh?next=…` (server components) or an automatic refresh (server actions) |
| `401 UNAUTHENTICATED`, refresh refused | Cookies cleared, redirect to the portal's console page |
| `403 FORBIDDEN` | "You do not have permission (`details.requiredPermission`)" |
| `403 ENVIRONMENT_NOT_ALLOWED` | Environment reset to test, banner "Live is not available for this OTA or role" |
| `403 TENANT_SUSPENDED` | Full page "This OTA is suspended", link to the portal |
| `412 PRECONDITION_FAILED`, `409 VERSION_CONFLICT` | "This record changed; reload to see the latest version" |
| `429 RATE_LIMITED` | "Too many requests, retry in N s" |
| `504 SUPPLIER_TIMEOUT` on an Amadeus action | "Amadeus did not answer. Resync before retrying." with a Resync button ([`architecture-booking.md`](../../docs/architecture-booking.md) §4) |
| Other `VelexisError` | Message from `lib/errors.ts` and the `requestId` |

How (OAD-004):

- **On the server.** In production Next.js replaces an error thrown in a server component with a generic one before it reaches `error.tsx`, so pages handle these codes where they call the SDK: a redirect (`redirectOnSessionError` of `lib/session.ts`) or a state of their own (`ErrorState` of `components/error-state.tsx`). `(console)/error.tsx` is the fallback and shows the error's digest as the reference of the server log.
- **The shell** (`(console)/layout.tsx`) does this for `console.auth.me`: `TENANT_SUSPENDED` renders the full page with the link to the portal, any other API error the message and the request id with "Try again".
- **`ENVIRONMENT_NOT_ALLOWED`.** `getConsoleRequest` (`lib/velexis.ts`) asks `console.auth.me` in the cookie's environment; when the API refuses `live` (or the profile no longer allows it) it asks again in `test`, and the whole request works in `test`. The shell then shows the banner and resets `__Host-vx_env` to `test` with the `resetEnvironment` server action, because a server component cannot write cookies. In server actions `requireStaff` / `requireStaffSession` (`lib/session.ts`) reset the cookie to `test` themselves and throw the refusal, so the action answers the same message without running in another environment; the switch's action (`switchEnvironment`) answers it for a refused `live` and leaves the cookie at `test`.

## 2. Dashboard: `/`

Tiles link to pre-filtered lists. Each tile renders only with its permission.

| Tile | SDK call |
|---|---|
| Ticketing failed or in manual review | `console.bookings.list({ ticketingStatus: ["failed", "manual_review"], limit: 1 })` → `totalCount` |
| Ticketing deadline within 24 h | `console.bookings.list({ status: ["confirmed", "partially_ticketed"], ticketingDeadlineBefore: now + 24 h, limit: 1 })` |
| Outcome unknown (reconciling) | `console.bookings.list({ status: ["pending"], limit: 1 })` |
| Authorised, not captured | `console.payments.list({ status: "authorized", limit: 5 })` (`payments:read`) |
| Last queue snapshot | `console.queues.listSnapshots({ limit: 1 })` (`queues:read`) |
| Latest bookings | `console.bookings.list({ sort: "-created", limit: 10 })` |

How (OAD-005, `(console)/page.tsx` makes the calls, `(console)/dashboard-tiles.tsx` renders them and holds their parameters):

- **Tiles per permission.** The needs-attention counts and the latest bookings need `bookings:read`, the authorised payments `payments:read`, the last queue read `queues:read` (`visibleTiles`, `can()`): a tile the role cannot read is neither requested nor rendered, so a finance user or a viewer sees the payments but no queue and sends no `listSnapshots`. The reads run in parallel; none calls Amadeus or is audited.
- **Counts link their filters.** Each count is a saved view of the bookings list (`bookings/views.ts`): "Ticketing failed or in manual review" (`ticketing-problems`), "Ticketing deadline within 24 h" (`deadline-24h`) and "Outcome unknown (reconciling)" (`reconciling`, `status=pending`). Its request is the view's filters as `/bookings` sends them for the view's link (`listParams`: `deadlineWithin=24h` becomes `ticketingDeadlineBefore` = now + 24 h) with `limit: 1` and no sort, and its card links that view (`viewHref`), so the count and the list it opens ask the API the same question. The card shows `totalCount` ("10,000+" for `null`; without a `totalCount`, the rows read with a `+` when there is a next page) and is highlighted when it is not zero.
- **The other tiles.** "Authorised, not captured" lists up to 5 payments (the payment, its booking or "No booking yet", the authorised amount, the creation time in the OTA's time zone), says when more wait, and links `/payments?status=authorized`. "Last queue read" shows the newest stored snapshot (queue, office, category, time, reader, PNRs) with "Open queue N" (`/queues/N?officeId=…&category=…`, the stored read, no Amadeus call) and "All queues", or says that no queue was read yet. "Latest bookings" lists the newest 10 (reference with "Guest booking", booking and ticketing status, lead traveller, route and departure, total, created) and links `/bookings`.
- **Errors on the server** (§1): `TOKEN_EXPIRED` from any read → `/auth/refresh?next=/`, an ended session → the portal; any other API error is shown in its tile's place (the console's message, the request id and "Try again"; a count reads "Not counted" and still links its list), and the other tiles stay.

## 3. Bookings

### 3.1 List: `/bookings`

- **SDK:** `console.bookings.list(params)` with filters from `searchParams`: `q`, `status[]`, `ticketingStatus[]`, `paymentStatus[]`, `source[]`, `departureFrom/To`, `createdFrom/To`, `ticketingDeadlineBefore`, `recordLocator`, `reference`, `customerEmail`, `travelerLastName`, `validatingCarrier`, `tag`, `customerId`, `createdByStaffId`, the needs-attention filters `reconcileOutcome[]`, `cancellationRequested`, `hasScheduleChange`, `sort`, `cursor`, `limit` (25).
- **URL** (OAD-006, `(console)/bookings/views.ts`): the URL is the state, so every view is a shareable link. A list filter repeats its parameter (`status=confirmed&status=partially_ticketed`; a comma-separated value is read too); `createdFrom` / `createdTo` are days (`YYYY-MM-DD`) in the OTA's time zone (`createdTo` up to the end of its day), `departureFrom` / `departureTo` days local to the airport, as the API takes them; `deadlineWithin=24h|72h|7d` becomes `ticketingDeadlineBefore` = now + the window when the page is rendered (the earlier of the two when a link also carries an instant), so a "deadline within 24 h" link stays right whenever it is opened. The API binds a cursor to the filters of the page that wrote it, so "Next page" of such a list also carries `asOf`, the time the first page's window counted from (read only with a cursor, never later than now); "First page" drops it. `-created` is the default sort and never written. The filter component writes `searchParams` only: a choice (a status, the sort, a yes/no filter) applies at once, text and days on submit; the position (`cursor`, `asOf`) goes, the page size stays. `customerId`, `createdByStaffId` and `ticketingDeadlineBefore` are set by links only and show as removable chips (a value the API would refuse shows its message on its chip). Without JavaScript the filters are a plain GET form to the same page.
- **Saved views** (links with preset filters, the current one marked): the API combines filters with AND, so **needs attention** is one view per reason of the [console operations flow](../../docs/flows/console-operations.md) §3 step 3: Ticketing problems (`ticketingStatus=failed,manual_review`), Reconciliation review (`reconcileOutcome=manual_review`), Deadline within 24 h (`status=confirmed,partially_ticketed`, `deadlineWithin=24h`, deadline order), Cancellation requested, Schedule changed. **Lists:** All bookings, To issue (`status=confirmed,partially_ticketed` in deadline order), Reconciling (`status=pending`), Cancelled, Imported (`source=import`).
- **Columns:** reference (link to the detail page; "Guest booking"), record locator ("None yet" while pending or failed), lead traveller and how many more, route, trip type and first departure (local), status (with "Schedule changed"), ticketing status with its deadline, payment status, total (selling) with its net cost and markup, channel (source), created (OTA time zone). The list row has no margin field; the margin (selling − net, fees included) is on the detail page (`pricing.margin`). Rows are formatted on the server, and only the shown fields reach the browser (not the customer's e-mail address).
- **States:** empty list per view (its own message); `totalCount` "10,000+" when the API returns `null`, nothing when it gives none; "Next page" uses `page.nextCursor`, "First page" drops the cursor. A link with a value the API would refuse is not sent: the page names the parameters ("Not valid: Status, Page size") with "Clear filters". API errors are handled on the server (§1): `TOKEN_EXPIRED` → `/auth/refresh?next=` this list, an ended session → the portal, anything else the console's message and request id under the filters, with "Try again" (and "Clear filters" for `400 VALIDATION_FAILED`).

### 3.2 Detail: `/bookings/[bookingId]`

**Reads:** `console.bookings.get({ bookingId })` (and `refresh: true` from a "Sync from Amadeus" button, throttled by the API to one per 10 s); tabs load their own data:

| Tab | Content | SDK |
|---|---|---|
| Overview | Status, ticketing (policy, deadline, attempts), pricing (net, markup, fees, selling, pricing mode), payment summary, supplier sync state, `consoleActions` | `console.bookings.get` |
| Travellers and contacts | Travellers (documents decrypted for display, never logged), contacts, remarks, ticketing agreement | `console.bookings.get` |
| Amadeus order | The verbatim, redacted Flight Order as Amadeus returns it, with net prices | `console.bookings.retrieve({ bookingId })` (`bookings:read`) |
| Tickets and documents | Ticket numbers per traveller and segment, itinerary and e-ticket receipts | from `get` |
| Payments | Payments with events and refunds | `console.payments.get({ paymentId })` per payment (`payments:read`) |
| Timeline and notes | All booking events (customer-visible and internal), notes | from `get` (`events`, `notes`) |
| Staff actions | The last 20 staff actions on this booking | from `get` (`recentStaffActions`) |

How (OAD-007, `[bookingId]/page.tsx` makes the calls, `[bookingId]/sections.tsx` renders them):

- **Tabs are links.** The open tab is `?tab=` (`travellers`, `amadeus-order`, `tickets`, `payments`, `timeline`, `staff-actions`; none for the overview), so every tab is a shareable link that works without JavaScript and loads only its own data. The tab links never prefetch.
- **Reads per tab.** Every tab reads `console.bookings.get`. Only the Payments tab adds `console.payments.get`, once per payment of the booking and each on its own (one that fails shows its message and request id in its place, the booking's own summary of it stays); without `payments:read` the tab shows the booking's summary and says which permission the events and refunds need. Only the Amadeus order tab calls `console.bookings.retrieve({ bookingId })`, an audited Amadeus call (`order.retrieve`) that also refreshes the stored order: no other tab calls it, and the tab does not either when `consoleActions.canRetrieve` is false (it names the reason). Its answer is shown with the call's facts (method, path, status, duration, office, Amadeus request id, call log entry) and the verbatim order in the JSON view, open, with the `included` options and the dictionaries collapsed; "Read again" reads it anew.
- **Documents.** The travellers tab shows identity document and discount card numbers, and the numbers of the order's forms of identification, with their last 4 characters only, whatever the API sends; the full numbers appear only in the Amadeus order view. The stored `amadeus.order` of `get` is never rendered.
- **Card data.** A form of payment of the order shows its kind and method, or its brand and last 4 digits; never the holder or the expiry date (lead decision (1) of 2026-10-24). An airline-card payment says that the card cannot be charged again and that its refunds go through the airline.
- **Net and markup.** The overview's pricing lists the net base fares, taxes, supplier fees and services, the net cost, the markup with its rule, the service and card fees, the selling total, the margin with its percentage and the pricing mode; beside it the selling totals, what was paid and refunded, and the payments.
- **Cancellation** (FIX-W28-CANCEL). The overview shows the `cancellation` block as the API returns it (status, times, who, typed reason, the staff member's comment, tickets voided, estimate, the refund or release and the amount kept, the money's state) and both `canCancel`s with their reasons: the console's (`consoleActions`) and the customer's self-service (`allowedActions`, `pending` while a cancellation is undecided or waits for the staff); since FIX-W33-OTA both show `pending` while another cancellation's DELETE is in flight, as both cancellations refuse it.
- **What needs staff** is listed above the tabs, the most urgent first (the states table below). ConsoleBooking has no reconciliation fields, so the page reads them from the booking's events: the time the reconciliation decides by is the `data.reconcileUntil` of the newest `booking.supplier_timeout` or `booking.reconcile_adopted` event, and a `booking.reconcile_manual_review` event means the reconciliation was handed to the staff; the reason of a ticketing problem is the summary of the newest `booking.ticketing_failed` or `booking.ticketing_manual_review` event. A cancellation whose `refundStatus` is `manual_review` or that is still `pending`, a schedule change, an order Amadeus no longer has and a failed sync are listed too.
- **Sync from Amadeus** links to `?refresh=1` (the open tab kept), which reads the booking with `refresh: true` and says whether it was synchronised, throttled (the API's 10 s) or not found at Amadeus; a supplier error of that refresh (`424`, `502`, `503`, `504`) reads the booking again without it and says so. It is offered for a booking with an Amadeus order that is not cancelled or pending.
- **Errors on the server** (§1): `TOKEN_EXPIRED` → `/auth/refresh?next=` this booking and tab (never with `refresh=1`), an ended session → the portal; `404 NOT_FOUND` (also the other environment's bookings) and an id that is not a booking id (`bkg_…`, never sent) render "Booking not found" inside the shell, naming the environment, with "All bookings"; any other error the console's message and the request id with "Try again" and "All bookings". The shell's `console.auth.me` failure and a role without `bookings:read` are states too, without a booking request.

**Actions** (each a dialog with a required reason, the environment badge, an idempotency key rendered with the dialog, and `ifMatch` = the displayed `version`):

| Action | SDK | Permission | Notes |
|---|---|---|---|
| Edit travellers, contacts, remarks, ticketing agreement | `console.bookings.patch({ bookingId, ifMatch, travelers?, contacts?, remarks?, ticketingAgreement?, … })` | `bookings:write` | Amadeus Flight Order Management PATCH; `409 VERSION_CONFLICT` on Amadeus 2552 |
| Issue tickets | `console.bookings.issue({ bookingId, ifMatch, reason, capturePayment: true, allowUnpaid?, notifyCustomer })` | `bookings:issue` | Captures an authorised Stripe payment first; `allowUnpaid` only for owner and admin ([OADR-0008](../../docs/adr/0008-ticketing-policy.md)) |
| Issue an airline-card booking left without tickets | `console.bookings.issue({ …, formOfPayments: [{ other: { method: "CASH" \| "ACCOUNT", flightOfferIds } }] })` or Cancel | `bookings:issue` | The card cannot be used again and the admin never takes card numbers ([OADR-0018](../../docs/adr/0018-ota-admin-consumes-the-sdk-server-side.md)) |
| Cancel | `console.bookings.cancel({ bookingId, ifMatch, reasonCode, reason, refund: { mode: "none" \| "full" \| "amount", amount? }, notifyCustomer })` | `bookings:cancel` | The dialog shows release / void / request-only and the refund that will follow |
| Resync | `console.bookings.resync({ bookingId, include?, fareRules? })` | `bookings:write` | Shows the returned `changes` |
| Add note | `console.bookings.addNote({ bookingId, text, visibleToCustomer })` | `bookings:write` | Internal by default |
| Capture payment | `console.payments.capture({ paymentId, ifMatch, amount?, reason })` | `payments:capture` | Stripe, `authorized` only; partial capture releases the rest |
| Refund payment | `console.payments.refund({ paymentId, amount, reason, reasonNote? })` | `payments:refund` | Stripe only; `422 refund_via_airline` for airline-card payments |

| State | Shown as |
|---|---|
| `bookingStatus = pending` | Banner "Outcome unknown, reconciling until <time>"; Issue and Cancel hidden |
| Ticketing `manual_review` / `failed` | Banner with the reason and the deadline; Issue highlighted |
| Airline-card booking without tickets | Banner "The airline card cannot be charged again: issue with another form of payment or cancel" |
| `402 PAYMENT_DECLINED` on capture | "The authorisation has expired; contact the traveller" |
| `409 ALREADY_ISSUED`, `BOOKING_ALREADY_CANCELLED` | Reload with the current state |

How (OAD-008, `[bookingId]/actions.ts` the server actions, `[bookingId]/action-rules.ts` the field names and rules they share with the dialogs, `issue-dialog.tsx`, `cancel-dialog.tsx`, `payment-dialogs.tsx`, `patch-form.tsx` (the order's edits, Resync and the shared form fields) and `note-form.tsx`):

- **Where.** Issue, Cancel and Resync under the header ("Booking actions") on every tab; the order's edits on the Travellers and contacts tab (one dialog per traveller and contact, "Add a remark", "Change the ticketing agreement"); the note form on the Timeline and notes tab; Capture and Refund on each payment of the Payments tab. Each only with its permission (`can()`) and when the booking's `consoleActions` allow it; Issue and Cancel never while the booking is `pending`. The client components get plain values (ids, versions, amounts, the names and contacts they prefill), never the booking.
- **Server actions.** Each starts with `requireStaff(permission)` (a forged POST from a role without it gets "You do not have permission to do this (<permission>)" before any call), then validates the form with Zod (a hidden field that does not parse: "This form is out of date. Reload the page and try again."), then makes one SDK call with the client `requireStaff` hands back. The API's codes become the dialog's state, on the server: the message of `lib/errors.ts` or the action's own words for this page (the table above, `refund_via_airline`, `amount_exceeds_captured`, `ticketing_in_progress`, `cancellation_pending`, `payment_not_capturable`, …), the request id, and the API's field errors on the dialog's fields (`/travelers/0/name/lastName` → `lastName`, `/refund/amount/amount` → `amount`, `/formOfPayments/0` → `settlement`); only redirects (an ended session) and bugs are thrown, never an API error for `error.tsx`. A success revalidates `/bookings/<id>`, whose new render brings new idempotency keys.
- **Keys and versions.** Every dialog posts the key the page rendered with it (`crypto.randomUUID()`, once per render) as `actionKey`, which the action sends as the SDK's `idempotencyKey`: a double submit or a resubmission replays the same issue, cancellation, note, capture or refund. After a final refusal that the API keeps under the key (a stored `4xx` but `412`; `429` and a request still running under the key are not kept), the action's state brings a new key that the dialog sends next, so a corrected form needs no reload; after `412`, `5xx`, a timeout or a network error the key stays (2026-10-27, FIX-W31-OTA, [OADR-0018](../../docs/adr/0018-ota-admin-consumes-the-sdk-server-side.md) point 5 revised; README §7). After `409 IDEMPOTENCY_KEY_REUSED` the key stays too and the dialog asks for a reload: an earlier request under the key may still be running, and a new key could refund or capture twice (2026-10-28, FIX-W32-OTA, point 5 revised again). `ifMatch` is the displayed booking `version` (patch, issue, cancel) or the payment's `version` from `console.payments.get` (capture). A patch has no key in the contract: its `If-Match` makes a replay a `412` ("reload"). Resync is a plain button (the contract keeps no reason for it, and it is idempotent by design) with the `changes` it applied listed under it.
- **Patch.** One element per dialog: a traveller (name, date of birth, gender, e-mail, phone; merged over the stored traveller by the API), a contact (name, company, e-mail, phone, address, all prefilled), a new general remark (added to the order's; `BACKOFFICE` is not offered) and the ticketing agreement (`option`, and `delay` in days for the two delays). The API replaces the order's contact of the same purpose whole, and a traveller's `contact` whole (it merges a traveller field by field), so the traveller and contact dialogs also post the stored contact (`kept`, JSON of `keptContactOf` in `action-rules.ts`, checked by the action's schema) and the action puts the dialog's values over it: what the dialog does not show (the other phones, the first phone's device type, a state, a post box, the address lines after the second, a middle name, the language, a traveller's residence address) is sent back as it was. A phone's country calling code goes as typed: one to three digits with an optional `+` (lead decision (1) of 2026-10-26). Identity documents are not edited here (their numbers are masked on this page).
- **Issue.** `capturePayment: true`. The dialog says what the issuance takes: the authorisation captured first, a paid booking, one without a payment, or an unpaid one, which only an owner or an admin may issue (`allowUnpaid`: the checkbox is theirs, and the action refuses it from another role before any call). An airline-card booking (a payment with method `airline_card`) is issued only with the OTA's own settlement with the airline, `CASH` or `ACCOUNT`, as the one `other` form of payment for the booking's flight offers. When the airline did not charge its card (the payment is not `captured`: so it is for every airline-card booking that waits for its tickets), the API counts the booking as unpaid ([console-operations.md](../../docs/flows/console-operations.md) §2 step 8): the dialog says so and offers `allowUnpaid` to an owner or an admin with the settlement, and tells other roles who can (OAD-016's journey found that it offered neither, so such a booking could not be issued).
- **Cancel.** The dialog says what Amadeus will do (release when nothing is ticketed; void when every ticket was issued today in the OTA's time zone; a request for the airline otherwise) as the API decides it: console.bookings.get's `cancellationMode`, by the API's own clock in the OTA's `storefront_settings.time_zone`, by the rule and in the zone of the API's cancellation quote (since 2026-10-30, lead decision (2a), FIX-W35-OTA; before, the dialog decided it from the platform tenant's zone, which could call void what the API then found to be tickets of yesterday); an answer without a mode names no step. It offers the refund modes of the payment the money step acts on, the default first: a captured Stripe payment `none`, `full` (everything still refundable) or `amount`; an authorisation `full` (released), `amount` (that much released, the rest captured) or `none` (captured whole); an airline card and a booking without payment `none` only. The reason code (the dialog's "Reason category"), the reason and "E-mail the cancellation to the traveller" (on by default). A refund amount above what can still be refunded (`422 amount_exceeds_captured`) says the API's `details.refundable` on the amount, through the refund dialog's helper (`refundableRefusal` of `actions.ts`; FIX-W33-OTA), and the reload message when the refusal carries no figure.
- **Payments.** Capture for an `authorized` Stripe payment (`payments:capture`; an empty amount captures the whole authorisation, a smaller one releases the rest); refund for a captured or partly refunded Stripe payment with something left to refund (`payments:refund`; the amount, the category and the dialog's reason as `reasonNote`). What is left to refund is captured less refunded less the refunds still `pending` or `processing`, as the API counts it, on this page as on the payment's own (`refundableOf` of `action-rules.ts`, FIX-W32-OTA); a refund above it is refused with the API's figure in the message ("at most …", `details.refundable` of `422 amount_exceeds_captured`, FIX-W32-OTA). Airline-card payments get neither: the airline refunds its card (`refund_via_airline`).
- **No card data.** No input of the admin asks for a card (OADR-0018 point 8): `src/app/built-pages.test.ts` builds the admin and searches every built page for a card autofill token, a field named like a card's, and, in the browser's chunks, a card form's label.

## 4. PNR lookup and import: `/pnr`

1. A form with the record locator calls `console.bookings.findByRecordLocator({ reference })` (`bookings:read`): matches with owner office, travellers, segments, and whether it is already a booking (link).
2. "Import" opens a dialog: customer (search via `console.customers.list`) or contact e-mail, pricing mode (`markup_rules`, `net`, `override`), send confirmation, tags, note, reason → `console.bookings.import({ reference, customerId?, contactEmail?, pricing, sendConfirmation, tags, note, reason })` (`bookings:write`), then the new booking's page.

| State | Shown as |
|---|---|
| No match | "No order with this record locator in your offices" |
| `403 OFFICE_NOT_ALLOWED` | "This order belongs to an office outside this OTA" |
| `409 ORDER_ALREADY_IMPORTED` | Link to the existing booking |

An **Advanced** panel (`amadeus:read`) offers the raw `console.amadeus.getFlightOrderByReference` and `getFlightOrder` answers for support (OAD-010).

How (OAD-009, `pnr/page.tsx` the lookup, `pnr/import-dialog.tsx` the dialog, `pnr/actions.ts` its server actions, `pnr/import-rules.ts` their shared field names and the lookup's URL):

- **Lookup.** The URL is the state: `/pnr?recordLocator=L2P9XC` (a plain GET form to the page; `reference` is read too). The value is put in the API's spelling (no spaces, capitals) and checked against `^[A-Z0-9]{5,8}$` before any call; `findByRecordLocator({ reference })` is an Amadeus call and an audited read (`pnr.lookup`), so links to it are never prefetched. Every role may look up (`bookings:read`, OBE-064). Each match shows its record locators, travellers (`LAST/FIRST`), flights, tickets, last ticketing date, queuing office and net total; one that is a booking links to it with its status, an importable one has "Import as a booking" for `bookings:write` (a note names the permission otherwise). For `amadeus:read` the verbatim order of the lookup (already redacted by the API) is in a JSON view.
- **Import.** The dialog is `ConfirmDialog` (reason, environment badge, live warning, the idempotency key the page renders once per match and render, the shared key handling of `useActionKey` and `lib/action-state.ts`). It posts the record locator, the match's `flightOrderId` (the import never picks another order of the locator) and the order's currency, the pricing mode (`markup_rules` by default, `net`, or `override` with a selling total in the order's currency, offered when the page knows it), the customer (a search of active accounts through `searchCustomers`, `console.customers.list`, for `customers:read`; none: a guest booking), the contact e-mail, the confirmation, tags (comma-separated, at most 10) and a note. A success opens the new booking's page, or, when the API answered warnings (a confirmation that could not be queued), stays with them and a link to the booking. The import revalidates no path: an action that revalidates any path makes Next.js render the page it came from again in its answer, here another Amadeus lookup and `pnr.lookup` no one asked for, whose new render would replace the dialog and its warnings (the bookings pages are dynamic and read the API on every visit anyway).
- **Advanced** (OAD-010, `pnr/advanced-panel.tsx`, the server actions `readRawOrders` and `readRawOrder` of `pnr/actions.ts`, OBE-067's raw reads): for `amadeus:read` (owner, admin, agent), under every answer of a valid record locator (also no match, `403 OFFICE_NOT_ALLOWED` and the other refusals, where support may need it most), a panel with "Read the orders of <locator>" (`console.amadeus.getFlightOrderByReference({ reference })`, origin system `GDS`) and "Read order <id>" for each order of the lookup's matches and of that answer (`console.amadeus.getFlightOrder({ flightOrderId })`, which changes no booking). Each is an Amadeus call and an audited read, so it runs only from its button, in a server action that starts with `requireStaff("amadeus:read")` and refuses a record locator or an order id the API would refuse before any call; the page's render never calls them, and nothing is revalidated. An answer shows the call's facts (API, status, duration, office, Amadeus request id, call log entry), each order of the locator with its office and its booking of this OTA (`matches`, a link) or "Not a booking of this OTA", the booking attached to a read order, and the verbatim answer as the API returns it (redacted) in an open JSON view. The panel says that their prices are Amadeus net prices, before the OTA's markup and fees. `404 NOT_FOUND` and `403 OFFICE_NOT_ALLOWED` are answered in the panel's words, every other refusal with the console's message, each with its request id. No customer-scope operation.
- **Refusals** in the dialog: `409 ORDER_ALREADY_IMPORTED` links the existing booking (`details.bookingId`, `details.reference`); `403 OFFICE_NOT_ALLOWED`, "This order belongs to an Amadeus office outside this OTA"; `409 CONFLICT` `customer_deleted` / `customer_disabled` and a customer the OTA does not have (`404` without `error.supplier`) on the customer; `422` `contact_email_required` on the contact e-mail, `currency_mismatch` and `selling_below_net` (with the net price) on the selling total; `504 SUPPLIER_TIMEOUT` asks to send the same form again (the same key imports once). On the page, `404 NOT_FOUND` is "No order with this record locator in your offices" and `403 OFFICE_NOT_ALLOWED` is explained with the OTA's offices: the order's owner office (or its queuing office, without an owner office) is not one of them.

## 5. Queues: `/queues`, `/queues/[queueId]`

- `/queues`: monitored queues of the tenant's office with the last snapshot of each (`console.queues.listSnapshots`).
- `/queues/[queueId]`: "Read now" calls `console.queues.list({ queueId })` (Amadeus Queue List, stores a snapshot); paging the stored snapshot uses `cursor`. Items link to bookings when the record locator is known, otherwise to `/pnr?recordLocator=…`.
- No queue item actions (remove, move) in the MVP ([scope §2.3](../../docs/scope.md#23-ota-admin-otaadmin)).

How (OAD-009, `queues/page.tsx` the list, `queues/[queueId]/page.tsx` one queue, `queues/queue-views.tsx` their shared pieces; `queues:read`: owner, admin, agent):

- **List.** The API lists no monitored queues as such (they are set in the portal, `monitored_queues`), so `/queues` groups the newest 100 snapshots (`listSnapshots({ limit: 100 })`) by office, queue and category: each row is a queue with its last read (time, reader, PNR count) and "Monitored" when the scheduled poller read it (`fetchedBy: null`). "Open a queue" is a GET form to `/queues` (queue number 0 to 99, category 0 to 254, one of the OTA's offices or the queuing office by default) that sends a valid queue on to its page and names what is not valid.
- **One queue.** Without `read` or `cursor` the page shows the last stored read with its PNRs (`listSnapshots({ queueId, officeId, category, limit: 1, include: ["items"] })`, no Amadeus call); the line above the PNRs names the read's time, reader, office and category (a URL without an office or a category shows the newest read of any). "Read now" is a GET form to `?read=1`: `console.queues.list({ queueId, officeId, category, limit: 50 })`, a fresh read stored as a snapshot; "Next page" pages that snapshot with the API's `cursor` and the snapshot's office and category, without calling Amadeus; a cursor the API refuses asks to open the queue again. "Earlier reads" lists the queue's newest 10 snapshots. An expired session comes back to the stored view, never to a second read.
- **PNRs.** Each row: the record locator, creation time, travellers, air segments and the booking: a link to the OTA's booking with its status, or, for an orphan (no booking of the OTA has the record locator), "No booking" and "Import", a link to `/pnr?recordLocator=…` (never prefetched: the lookup reads Amadeus and is audited).
- **Errors on the server** (§1): `TOKEN_EXPIRED` → `/auth/refresh?next=`, an ended session → the portal; `403 OFFICE_NOT_ALLOWED` and the supplier's errors render the console's message with the request id and "Try again"; a queue number, office, category or cursor the API would refuse is never sent.

## 6. Shopping on behalf: `/shopping`

For staff answering a caller: search, compare and quote, with **net** Amadeus prices. All calls are raw, read-only console operations (`amadeus:read`):

| Step | SDK |
|---|---|
| Search offers | `console.amadeus.searchFlightOffers({ amadeus: <Flight Offers Search body> })` (origin, destination, dates, travellers, cabin, non-stop, carriers) |
| Seat availability by class | `console.amadeus.searchFlightAvailabilities({ … })` |
| Branded fares | `console.amadeus.upsellAirOffers({ … })` |
| Confirm price | `console.amadeus.quoteAirOffers({ … })` |

The page shows the net total and, for orientation, the OTA's default markup rule; it says plainly that booking on behalf comes later (`console.bookings.create` is deferred). Staff send the customer to the storefront to book, or import a booking made in the Amadeus terminal through `/pnr`.

How (OAD-010, `shopping/page.tsx` the notices and the markup rule, `shopping/results.tsx` the two searches and an offer's branded fares and price, `shopping/actions.ts` their four server actions):

- **Who.** `amadeus:read` (owner, admin, agent). A role without it gets a state naming the permission, with no request but `console.auth.me`; every server action starts with `requireStaff("amadeus:read")`, so a forged POST from another role is refused before any call.
- **No Amadeus call while the page renders.** The render reads `console.auth.me` and, for `settings:read`, the markup rules; every Amadeus call is a button's server action. Each raw read is an audited read (`amadeus.<operationId>` in `staff_actions`), with the search form's optional reason (an offer's branded fares and price carry the reason of the search they came from). The four reads are idempotent by design and carry no idempotency key; nothing is stored, booked or revalidated. No customer-scope operation is ever called (`flights.*`, `/v1/flight-searches`): the service key is console-only (OADR-0018 point 7).
- **Flight offers** (`searchOffers` → `console.amadeus.searchFlightOffers`, Flight Offers Search POST). The form: from and to (an airport or city code), departure and an optional return day, adults (1 to 9), children, infants on a lap (one per adult at most, nine seated travellers at most), cabin (or any), non-stop, airlines, currency (the OTA's default currency prefilled) and the reason. The action checks them as the API would (field errors by the form's names) and sends the getFlightOffersQuery verbatim: the outbound leg `1` and the return leg `2`, the travellers (adults, children, then each held infant on an adult's lap by position), `sources: ["GDS"]`, `maxFlightOffers` 50 and `maxUpsellOffers` 0, and the flight filters a choice asks for (`cabinRestrictions` with `MOST_SEGMENTS` over every leg, `carrierRestrictions.includedCarrierCodes`, `connectionRestriction.maxNumberOfConnections` 0 for non-stop). Each offer's row: its id, flights in the airports' local times with duration and connections, the fare (cabin, branded fare, booking classes, checked bags of the first traveller), seats, last ticketing day, the **net total**, and "Branded fares" and "Confirm price".
- **Branded fares** (`upsellOffer` → `console.amadeus.upsellAirOffers`) of one offer, posted back as the search answered it: each branded fare with its cabin and class, bags, net total and "Confirm price". **Confirm price** (`quoteOffer` → `console.amadeus.quoteAirOffers`, a read-only quote) of the search's offer or of one of its branded fares, with `include=bags`, and `detailed-fare-rules` too when "Confirm prices with the detailed fare rules" is ticked: the confirmed net price (and, when it differs from the offer's, both), the last ticketing day, what a booking of it needs (`bookingRequirements`, in words), the bag options with their net prices and the fare rules in a collapsed JSON view. The offer staff work on is outlined in the table, its answers stay together under it, and a new search starts afresh.
- **Seat availability** (`searchAvailability` → `console.amadeus.searchFlightAvailabilities`): from, to, day, an optional local time, seats (1 to 9 adults), airlines, one booking class and "Include closed classes, departed and cancelled flights" (`includeClosedContent`). A row per segment of each option: the flight (and the operating airline when another), departure and arrival in local times, aircraft and the seats per booking class (`J2 Y9 BL`: a digit is the seats sold in one booking, 9 or more; `L` waitlist open, `C` waitlist closed, `R` on request; a closed segment's status), with the legend.
- **Net prices.** Every amount on the page is an Amadeus net price and is labelled so (headings, columns, the notice above the tabs). For orientation the page names the OTA's default markup rule (`isDefault`, read with `console.settings.markupRules.list` page by page, at most 5 pages of 100) in words, with its state when it is switched off, and links the markup rules; it computes no selling price, which the first matching rule, the stackable rules and the fees decide ([OADR-0005](../../docs/adr/0005-markup-and-fee-engine.md)). A failure of the markup rules is shown in their tile with its request id; the searches stay usable.
- **Answers.** Each answer shows the call's facts (Amadeus API, HTTP status, duration, office, Amadeus request id, call log entry), Amadeus's warnings and the verbatim answer in a collapsed JSON view (`components/json-view.tsx`). A refusal is the action's state, never `error.tsx`: the form's own field errors, the API's field errors on the form's fields, `422 SUPPLIER_REJECTED` as "Amadeus refused the search" (or the offer) with Amadeus's own issues (`details.errors`: code, title, detail, where), `504 SUPPLIER_TIMEOUT` as "Search again", any other code the console's message, each with its request id. The environment and the OTA's Amadeus offices are named above the tabs, with a warning when the environment has no Amadeus connection.
- **A search is sent once** (2026-10-30, lead decision (2d), FIX-W34-OTA). The two searches (`searchOffers`, `searchAvailability`) call the API with a console client of `maxRetries: 0` (`createConsoleClient`'s client-level `maxRetries`, through `requireStaff("amadeus:read", { maxRetries: 0 })`; no contract change), so a `504 SUPPLIER_TIMEOUT` (or a `503`, a `429`, a network error) is answered at once ("Search again") and reaches Amadeus once: the SDK's default would retry these POSTs (`x-idempotent-by-design`) twice, three Amadeus searches for one click. Since 2026-10-30 (lead decision (2b), second batch, FIX-W35-OTA) the branded fares (`upsellOffer`) and the price confirmation (`quoteOffer`) are sent once the same way: every shopping call of the page has the client of `maxRetries: 0` (`SHOPPING_RETRIES`). `console.auth.me` of the action keeps the SDK's default retries, as every other page does.
- **Errors on the server** (§1): `TOKEN_EXPIRED` → `/auth/refresh?next=/shopping`, an ended session → the portal; a failure of `console.auth.me` renders the console's message.

## 7. Payments: `/payments`, `/payments/[paymentId]`

- List: `console.payments.list({ status, provider, method, bookingId, createdFrom, createdTo, cursor })` (`payments:read`), environment of the switch.
- Detail: `console.payments.get({ paymentId, refresh? })` with events (redacted), refunds, booking link, provider account mode; Capture and Refund dialogs as in §3.2.

How (OAD-011, `payments/page.tsx` the list, `payments/[paymentId]/page.tsx` the detail, `payments/[paymentId]/actions.ts` its server actions):

- **List.** The URL is the state, as on `/bookings` (§3.1): `status`, `provider` and `method` repeat their parameter (a comma-separated value is read too) and take the values of the OTA document's enums (`status` as `Payment.status` spells it, `cancelled`); `bookingId` is one booking id (`bkg_…`); `createdFrom` / `createdTo` are days in the OTA's time zone (`createdTo` up to the end of its day); `limit` is the page size (25); "Next page" sets `cursor` to `page.nextCursor` with the other parameters kept, "First page" drops it. The filters are a plain GET form to the page (it needs no JavaScript), with "Clear filters". The rows, formatted on the server: the payment (a link to its page), its creation time in the OTA's time zone, its booking (reference linking to the booking's Payments tab, with the booking's status) or "No booking yet", the provider and method with the card's brand and last 4 only (never its expiry or holder), the payment's status, and the amount with what was captured and refunded. A link with a value the API would refuse is not sent: the page names the parameters ("Not valid: Status, Page size") with "Clear filters", and the form leaves a refused page size out; an empty list says whether the environment has no payments or none match the filters.
- **Detail.** The payment as the booking's Payments tab shows it (the same `PaymentCard` of `[bookingId]/sections.tsx`: amounts, card brand and last 4, 3-D Secure, failure, account mode, times, version, events, refunds), under a header with the provider and method, the booking (or "No booking yet") and the checkout, the environment, and what is still refundable: captured less refunded less the refunds still on their way to Stripe (`pending`, `processing`), as the API counts it. "Refresh from Stripe" is a GET button to `?refresh=1`, offered for a Stripe payment with a PaymentIntent (the API answers any other as stored, and the page then says nothing of Stripe): it reads the payment with `refresh: true`, and when Stripe fails (`502 PAYMENT_PROVIDER_ERROR`, nothing changed) reads the stored payment again and says so with the request id.
- **Actions.** The booking page's Capture and Refund dialogs (`payment-dialogs.tsx` on `ConfirmDialog`: reason, amount, the environment badge and the live warning, the idempotency key rendered once per render, `ifMatch` = the payment's `version` for a capture) with this page's actions, which run the booking page's `capturePayment` / `refundPayment` (the same permission check, schema, call and messages, and the same key handling) and then revalidate the payment's page, `/payments` and, when the payment has one, the booking's page. Capture for an `authorized` Stripe payment with `payments:capture`; Refund for a Stripe payment with something left to refund with `payments:refund` (owner, admin, finance: an agent sees no refund button, and a forged POST from one is refused before any call); a payment without a booking posts no `bookingId`. An airline-card payment shows "Refunded by the airline" instead, for every role ([OADR-0004](../../docs/adr/0004-airline-card-data-handling.md): the airline reverses its own charge). The API's codes are the dialog's state, on the server: a refund above what is still refundable (`422 UNPROCESSABLE`, `amount_exceeds_captured`) shows its message on the amount, with the API's `details.refundable` ("at most …", FIX-W32-OTA), and the request id; `refund_via_airline`, `402 PAYMENT_DECLINED`, `409 CONFLICT` (`payment_not_capturable`, `payment_not_refundable`), `412` and `502 PAYMENT_PROVIDER_ERROR` in the words of §3.2.
- **Errors on the server** (§1): `TOKEN_EXPIRED` → `/auth/refresh?next=` the list with its filters or the payment (never with `refresh=1`), an ended session → the portal; `404 NOT_FOUND` (also the other environment's payments) and an id that is not a payment id (`pay_…`, never sent) render "Payment not found" inside the shell, naming the environment, with "All payments"; any other error the console's message and the request id with "Try again" (and "Clear filters" for the list's `400 VALIDATION_FAILED`). A role without `payments:read` gets a state without a request.

- **List.** The URL is the state, as on `/payments` (§7): `q` (the start of an e-mail address, first or last name, 2 to 100 characters, the API's prefix search), `status` (repeated or comma-separated: `active`, `disabled`, `deleted`; none is the API's default, active and disabled, so deleted accounts are listed only when asked for), `emailVerified` and `hasBookings` (`true` or `false`), `sort` (the document's values; the default `-created` is never written), `cursor` ("Next page" sets `page.nextCursor` with the other parameters kept, "First page" drops it) and `limit` (25). Nothing is looked up elsewhere to fill the gaps.
- **Errors on the server** (§1): `TOKEN_EXPIRED` → `/auth/refresh?next=` the list with its filters or the customer with its page of bookings, an ended session → the portal; `404 NOT_FOUND` and an id that is not a customer id (`cus_…`, never sent) render "Customer not found" inside the shell with "All customers"; any other error the console's message and the request id with "Try again" (and "Clear filters" for the list's `400 VALIDATION_FAILED`). A role without `customers:read` (or, for the bookings section, `bookings:read`) gets a state without a request.

How (OAD-013, `settings/markups/` and `settings/fees/`: `page.tsx` the list, `new/page.tsx` a new rule, `[id]/page.tsx` one rule; `settings/pricing-rule-form.tsx` the shared form, the delete dialog and the pieces the pages share; `settings/pricing-actions.ts` the server actions; `settings/pricing-rules.ts` the field names, the Zod mirrors of `MarkupRuleInput` and `FeeRuleInput`, the request bodies and a rule's texts, which the client form and the `"use server"` actions share):

- **Lists.** `console.settings.markupRules.list` / `.feeRules.list` (`settings:read`, every role) in the order the engine evaluates the rules (priority, then id), 50 a page. The URL is the state: `active=true|false` (the links "All rules", "Active", "Inactive"; none: every rule) and `cursor` ("Next page" sets `page.nextCursor`, "First page" drops it, the filter kept); a value the API would refuse is never sent. Each row: the priority, the name (a link to the rule; a fee rule's type and label), the scope in words ("Every offer" for `{}`), the amount (percentage of the net price or the base amount, fixed amount, per unit, caps) and the state (default, active or inactive, stackable or refundable, the validity window in the OTA's time zone). "How rules apply" explains, collapsed above the list: markups by first match (the first matching rule that is not stackable is the base, matching stackable rules with a lower priority number add to it, the default rule at 1000 always matches) and fees by step and type (no stacking: per fee type the first matching rule applies; `change` fees not charged in the MVP), as [OADR-0005](../../docs/adr/0005-markup-and-fee-engine.md) points 3, 4 and 7 decide.
- **Who writes.** Owners and admins (`settings:write`) get "New … rule", the rule's form and "Delete rule"; agents, finance and viewers see the lists and each rule read only (the button disabled, naming the permission; a rule's page shows its fields as text, without a form), and `/new` names the permission without a form. Every action starts with `requireStaff("settings:write")`, so a forged POST is refused before any call.
- **The form.** One form for both kinds: name (a markup rule's notes; a fee rule's label shown to travellers and its type, each with the step that charges it), the scope (origins, destinations, origin and destination countries, airlines as codes separated by commas, upper-cased; cabins, traveller types, trip types, sources, channels and a fee rule's card brands as checkboxes; the inclusive net range), the calculation, the percentage and the fixed amount (shown as the calculation uses them; the action sends only those), one currency for the fixed amount and both caps (the API requires one; the OTA's default currency for a new rule), the unit, the caps, the priority, stackable (markup) or refundable (fee), the active flag and the validity window typed in the OTA's time zone (`datetime-local`, sent as instants). The fields are named after the request body's JSON pointers (`fixed.amount`, `scope.origins`), so the API's field errors land on the field that caused them. The action validates the form with the Zod mirror of the schema and the API's own rules (a percentage for a percentage calculation, a fixed amount for a fixed one, -100 to 999.9999 for a markup, 0 to 100 for a fee, two decimals, a fee never negative, the one currency, the window's end after its start) and names every problem at once.
- **Create** sends the form's values without empty optional fields, under the idempotency key the page renders once (a double submit creates one rule; a final refusal the API stored under the key brings a new one, lib/action-state.ts). A new rule without warnings is opened at once; with the API's `warnings[]` the page stays and shows them with a link to the rule. **Update** sends only the fields the form changed (the form posts the rule as the page rendered it; `scope` as a whole, `null` for a cleared value; the window compared as the form shows it in the OTA's time zone, so a time of the hour the clocks go back is unchanged when it is sent as shown; a value the API stored that the calculation ignores is neither sent nor cleared) with `ifMatch` = the displayed version, and shows the API's warnings under the form (`fixed_currency_not_default`, `sells_below_net`, as the API words them); a form sent unchanged makes no call. The default rule's form has no scope fields and no "Delete rule", and since 2026-10-30 (lead decision (2e), FIX-W34-OTA; [OADR-0005](../../docs/adr/0005-markup-and-fee-engine.md) point 3 revised) no priority, active or window inputs either: it shows its priority (1000), its state and its validity read-only under "The default rule always matches, so every offer gets a base markup: it stays active, has no validity window and keeps priority 1000 (rules with a lower number are checked before it)", posts the hidden marker `defaultRule`, and the action takes those values from the rendered rule and never sends them (`withDefaultRuleValues`, `withoutDefaultRuleFields` of `pricing-rules.ts`), so a forged POST cannot send them either; its name, notes, calculation, amounts, unit, caps and stacking stay editable. **Delete** is `ConfirmDialog` without a reason (`askReason={false}`: the contract's `DELETE` takes none, so a reason would be stored nowhere) with `ifMatch` = the displayed version, then the list. The markup and fee rule deletes ask no reason (2026-10-30, lead decision (1i), FIX-W34-OTA): the contract has no field for one (the operations take no body), and `staff_actions` records who deleted which rule (`settings.markupRules.delete` / `settings.feeRules.delete` with the staff member and the rule before the delete). `412` asks for a reload, `409 CONFLICT` `default_rule` says the default rule cannot be deleted (or, for a save, that its scope, active flag, window and priority stay as they are), `404` that the rule no longer exists. Rules are shared by the test and live environments, which every page and the dialog say.
- **Errors on the server** (§1): `TOKEN_EXPIRED` → `/auth/refresh?next=` the list with its filter and page, the rule or the new rule's page, an ended session → the portal; an id that is not a rule id of the kind (never sent) and `404 NOT_FOUND` render "… rule not found" with the list; any other error the console's message and the request id with "Try again" (and "First page" for a cursor the API refused).

How (OAD-014, `settings/storefront/`: `page.tsx` the settings, `sections.tsx` one form per section in tabs, `theme-editor.tsx` the branding, `actions.ts` one server action per section, `settings-rules.ts` the choices, the Zod mirrors of the thirteen sections of `StorefrontSettingsUpdate` and the texts of the API's refusals; `settings/assets/`: `page.tsx` the images, `upload-form.tsx` the upload and delete dialogs, `actions.ts` their actions, `asset-rules.ts` the kinds, limits, file check and list URL):

- **Storefront settings.** `console.settings.storefront.get` once per render, and `console.settings.assets.list({ kind, limit: 100 })` for each picker's kind (`logo`, `logo_dark`, `logo_square`, `favicon`, `og_image`); a failure of the images leaves the pickers with the current choices and says so. Tabs (`?tab=` opens one; every tab stays mounted, so switching keeps what was typed): **Brand and theme** (brand name, legal name, time zone from the server's IANA list; the theme editor: logo, dark logo, square logo and favicon pickers, five colours with a live preview and the WCAG contrast check of `lib/contrast.ts`, fonts from `StorefrontFontFamily`, corner radius), **Locales and markets** (default and supported locales and currencies typed as lists, markets as rows with add and remove, the default market), **Features**, **Policies** (ticketing policy with what each does, payment timing fixed to `authorize_before_booking`, 3-D Secure, accepted card brands, e-mail verification, offer and checkout lifetimes), **Payments** (the airline card per environment with the warning that airline-card bookings are sold at the airline's price; the live box only while the API's read-only `airlineCard.liveAvailable`, its `AIRLINE_CARD_ENABLED` switch, is true, and otherwise the reason, the platform's security review; a live card that is on while the switch is off stays as saved, as the API keeps a stored `true`: 2026-10-30, lead decisions (2d) and (2e), FIX-W35-OTA), **Legal and support** (terms and privacy versions, legal links to an https page or a content page's slug; the support contact), **SEO and consent** (title template, default title and description, the social sharing image picker, robots; the regime, the banner, the policy version and the four cookie categories, only `necessary` required), **Operations** (staff alert e-mail, booking queue number and category). The header shows the version and the last change in the OTA's time zone and says the storefront shows a change within 5 minutes.
- **Saving.** Each section is its own form and its own `console.settings.storefront.update` of that one section, complete (the API replaces a section as a whole), with `ifMatch` = the version the page displayed; the `PATCH` has no idempotency key. The action validates the section first with its Zod mirror (every problem on its field at once; codes normalised as the API spells them: `fr_ca` → `fr-CA`, currencies and countries in capitals; the supported lists include their default; each market country once; the default market among them). A success shows "Saved" with the API's `warnings[]` as it sent them (`airline_card_net_price`) and revalidates the page: every form gets the new version, a form whose section changed starts again from the saved values, the others keep what was typed. `412` asks for a reload ("this section was not saved"); `422 UNPROCESSABLE` shows its `details.reason` in the admin's words on the field of `details.path` (a row's position mapped to the row the form posted, a consent category's position to its id; a saved market that the locales or currencies sent no longer support, which the API points at in the markets, on the list staff changed, naming the market); the API's field errors land on their fields (a code list's item on its list). Owners and admins save; agents, finance and viewers see every section read only (disabled, no "Save"; the actions refuse them before any call).
- **Airline card in live.** The live box is offered only while the API's read-only `airlineCard.liveAvailable` (its `AIRLINE_CARD_ENABLED` switch; an answer without the field counts as off) is true, with "On in live: untick to stop offering it." or "The platform has turned the airline card on: tick to offer it in live too."; otherwise it is disabled with "Live stays off until the platform turns the airline card on after its security review". A live card that is on while the switch is off (the switch went off after it was turned on) is shown ticked and disabled, with the reason, and a hidden field sends the saved `true` with the section, so a save keeps it as the API does (2026-10-30, lead decisions (2d) and (2e) of the second batch, FIX-W35-OTA; before, the switch could not be read and the box was offered only when the API already had it on, to turn it off). A `403 FEATURE_DISABLED` (`details.feature = "airlineCard"`) is shown on the box.
- **Images** (`/settings/assets`). `console.settings.assets.list` newest first, 50 a page; the URL is the state (`kind`, `cursor`; a value the API would refuse is never sent). Each row: the file name with "Open" (the public URL on the API host in a new tab, `http(s)` only: the admin's CSP shows images of its own origin only, so the list names them), the kind, the type read from the bytes, the size, the dimensions, the upload time in the OTA's time zone and the id. Owners and admins get "Upload an image" and "Delete"; the other roles see the list read only. The page says that images are stored as uploaded, metadata included.
- **Upload.** `ConfirmDialog` without a reason: the kind (with what each is for; the list's filter by default), the file (`accept` PNG, JPEG, WebP, ICO), an optional name, and the metadata notice. An SVG (by its type, its extension or its first bytes) or a file above 1 MB is refused in the browser and again in the server action before any call, with the words of the API's `ASSET_INVALID` (`type`, `size`); the server action's 2 MB body limit (`next.config.ts`) is never reached by a refused file. `console.settings.assets.upload` sends `multipart/form-data` with the dialog's key as `Idempotency-Key` (the same on a double submit). `422 ASSET_INVALID` is shown by `details.reason` (`type`, `size`, `dimensions`) on the file, `409 CONFLICT` `asset_exists` as "This file is already your <kind> (<id>)"; after a final refusal the API stored under the key the dialog sends a new key. A success revalidates the images and the storefront settings, whose pickers list them.
- **Delete.** `ConfirmDialog` without a reason (the contract's `DELETE` takes none and has no `If-Match`); `409 CONFLICT` `asset_in_use` says where the image is used (the storefront settings' fields of `details.settingsPaths`, the number of content pages of `details.pageIds`) and to choose another image there first; `404` that it is gone.
- **Errors on the server** (§1): `TOKEN_EXPIRED` → `/auth/refresh?next=` the page with its tab or the list with its filter and page, an ended session → the portal; any other error the console's message and the request id with "Try again" (and "First page" for a cursor the API refused).

How (OAD-015, `settings/pages/`: `page.tsx` the list, `[pageId]/page.tsx` one page and, at `/settings/pages/new`, a new one, `page-form.tsx` the form, its Markdown help and the delete dialog, `actions.ts` their server actions; `settings/templates/`: `page.tsx` the list, `[key]/[channel]/[locale]/page.tsx` one template, `template-form.tsx` the editor and the reset dialog, `preview-frame.tsx` the preview, `actions.ts` their server actions; `settings/content-rules.ts` the field names, the Zod mirrors of `StorefrontPageInput` and `NotificationTemplateInput`, the refusals' texts and the lines of a body, which the forms and the actions share):

- **Pages list.** `console.settings.pages.list` (`settings:read`, every role), drafts included, in the API's order (footer order, then address, then language), 50 a page. The URL is the state: `locale` (one language, typed in a GET form and put in the API's spelling: `fr_ca` → `fr-CA`), `published` (the links "All pages", "Published", "Drafts") and `cursor` ("Next page" sets `page.nextCursor`, "First page" drops it, the filters kept); a value the API would refuse is never sent. Each row: the title (a link to the page), the address on the storefront (`/p/<slug>`), the language, the kind, published since when or draft, listed in the footer, the footer order and the last change in the OTA's time zone. Owners and admins get "New page"; the other roles see the list read only.
- **A page.** `console.settings.pages.get` once per render. Owners and admins get the form: the kind (with the legal kinds the storefront settings' legal links point to), the title (trimmed, one line, at most 120 characters), the body in a monospaced text area with a collapsed help of the Markdown subset (headings 2 to 4, paragraphs, bold, italic, lists, `https:` / `mailto:` / `tel:` and `/p/<slug>` links, page images by their `ast_…` id, and what is refused), published, listed in the footer and the footer order (0 to 10 000). "Save" sends the writable fields (`StorefrontPageUpdate`; the address and the language are fixed) with `ifMatch` = the displayed version, no idempotency key (the contract's `PATCH` has none), and revalidates the list and the page: a saved page starts again from the saved values. The other roles see the page read only, its body as written. **A new page** (`/settings/pages/new`, `settings:write` only: the other roles get a state naming the permission) adds the address (`^[a-z0-9]+(-[a-z0-9]+)*$`, at most 64 characters) and the language, chosen from the storefront settings' languages (`console.settings.storefront.get`, the default first; when they cannot be read the form takes a typed code and says so), both fixed from then on; "Create page" sends every field under the idempotency key the page renders once (a double submit creates one page; a final refusal the API stored under the key brings a new one, `withNextActionKey`) and opens the new page. A body is sent with its line breaks as `\n` (a browser posts a text area's with `\r\n`).
- **A refused body** (`422 UNPROCESSABLE`, `markdown_not_allowed`, `asset_not_found` or `asset_kind`, with `details.line`) is shown next to the line it names: the lines around it as they were sent, numbered, the reported line marked (`aria-current`) with the message in its row, which also describes the body's text area (`aria-describedby`), and "Go to line N", which selects that line in the body. The message is the admin's own for the reason (the API's message is never shown); `locale_not_supported` is shown on the language, `409 CONFLICT` `page_exists` on the address (with a new key), the API's field errors on their fields (`/title` → the title), `412` asks for a reload and `404` says the page is gone.
- **Delete.** `ConfirmDialog` without a reason (the contract's `DELETE` takes none, as for the rule deletes) with `ifMatch` = the displayed version, then the list. `409 CONFLICT` `page_linked` says that a legal link of the storefront settings points to the page's address and to change the link first or unpublish the page.
- **View on storefront.** The admin knows no storefront host (neither its configuration nor any answer of the contract carries one), so a page names its address on the storefront (`/p/<slug>`, "on your storefront's domain") instead of linking it.
- **Visibility.** The API deletes the page caches of both environments on every change (`t:<tenantId>:<env>:pages:<locale>`, [OADR-0012](../../docs/adr/0012-storefront-settings-assets-and-pages.md) point 7 as confirmed on 2026-10-30), so the next `storefront.getPage` reads it; the storefront's own copy lasts 5 minutes, which the page and the messages say. Pages are shared by the test and live environments.
- **Templates list.** `console.settings.templates.list` (`settings:read`, every role): the effective template of every key for every language of the storefront, grouped by who receives it (customer accounts, bookings, staff alerts), each with its words and key (a link to its editor), the language, where it comes from (`Customised`; `Default (own copy)` for the row provisioning seeded from the code default, which is not customised but has a version; `Inherited from <language>`; `Default`), whether it is sent and the last change (an inherited template has no row, so no change, of its own: "See the <language> template"; the code default "Never changed").
- **A template.** `console.settings.templates.get` once per render: where the template comes from in words, its version and last change, whether it is sent, the key's variables (`{{name}}` with their descriptions) and a collapsed help of the template language (variables, `{{#if}}` / `{{#unless}}` with `{{else}}`, `{{#each}}` with `{{../…}}`, comments; no triple braces, helpers or partials). The editor: the subject, the HTML body and the text body, and "Send this template" (`isActive`). "Save" (`console.settings.templates.put`, owners and admins) sends the three parts and `isActive` with `ifMatch` whenever the page showed a `version` (the seeded row included; none for an inherited template or the code default, whose save creates the locale's row) and no idempotency key (the contract's `PUT` has none); the other roles see the parts read only. "Preview" (`console.settings.templates.preview`, `settings:read`, every role) sends the draft as the form holds it and shows the rendered subject, the HTML body in an `<iframe sandbox="" srcdoc>` (no `allow-scripts`, no `allow-same-origin`, no other permission; the HTML never enters the admin's document) and the text body; the frame inherits the admin's CSP, so images on other hosts are not shown, which it says. `422 TEMPLATE_INVALID` is listed per part and line ("HTML body, line 3: …", the API's messages, which name parts, lines and variables, never render data) with "Go to line N" for the bodies, and each part shows its first problem on its field; `422 UNPROCESSABLE` `locale_not_supported` and `412` are answered in this page's words. "Reset to default" (`console.settings.templates.reset`, owners and admins) is `ConfirmDialog` without a reason (the reset takes no body), enabled when the locale has its own row; after it the page shows what serves the locale (its language's row or the code default) and the dialog says so.
- **Errors on the server** (§1): `TOKEN_EXPIRED` → `/auth/refresh?next=` the list with its filters and page, the page, the new page or the template, an ended session → the portal; an id that is not a page id (`stp_…`) and `404 NOT_FOUND` render "Page not found" inside the shell, an address the API would refuse (a key not shaped like one, a channel other than `email`, a locale not like `en` or `fr-CA`; never sent) and its `400 VALIDATION_FAILED` "Template not found"; any other error the console's message and the request id with "Try again" (and "First page" for a cursor the API refused).

## 10. Supplier log: `/supplier-log`

`console.supplierRequests.list({ bookingId?, amadeusApi?, outcome?, httpStatus?, createdFrom?, createdTo?, includeBodies?, cursor })` (`supplier_requests:read`): time, API and operation, HTTP status, duration, booking link, Amadeus error codes; bodies (redacted, card numbers masked) only on demand.

How (OAD-012, `supplier-log/page.tsx`):

- **Filters.** The URL is the state, as on `/payments` (§7): `amadeusApi` and `outcome` repeat their parameter (a comma-separated value is read too) and take the document's values; `httpStatus` (100 to 599), `errorCode` (an Amadeus code), `bookingId` (`bkg_…`), `requestId` (the Velexis `X-Request-Id` an error message quotes: the way from a failed console action to the Amadeus call behind it), `createdFrom` / `createdTo` (days in the OTA's time zone, `createdTo` up to the end of its day), `cursor` and `limit`. A plain GET form with "Clear filters"; a link with a value the API would refuse is not sent.
- **Rows**, formatted on the server: the time in the OTA's time zone; the Amadeus API by its documented name with the Amadeus operationId and the Velexis operation; the method and path with the office; the outcome, the HTTP status ("No response" without one) and the Amadeus error codes; the duration; the booking (a link to its page), the Velexis request id and the Amadeus request id (`correlationId`, the one Amadeus support asks for).
- **Bodies on demand.** `includeBodies=true` ("Show the redacted bodies": a link that keeps the filters and the position, or the form's checkbox) asks the API for the request and response bodies, at most 20 calls a page then (the page size is 20 with bodies, and a larger one in the URL is refused before any call). Each call gets a row under it with its two collapsed JSON views (`components/json-view.tsx`) showing the stored, redacted bodies exactly as the API returns them (lead note of 2026-10-28), whether they were redacted and whether they were truncated (a body above 64 KB is stored as `{ truncated, bytes, preview }`, [OADR-0001](../../docs/adr/0001-amadeus-client-design.md) point 9); the page adds and removes nothing. Not an audited read.
- **Errors on the server** (§1): `TOKEN_EXPIRED` → `/auth/refresh?next=` the log with its filters, an ended session → the portal, any other error the console's message and the request id with "Try again" (and "Clear filters" for `400 VALIDATION_FAILED`); a role without `supplier_requests:read` (a viewer) gets a state without a request.

## 11. Portal links: `/portal`

Links to `${PUBLIC_PORTAL_URL}/otas/<tenantId>/…`: `api-keys`, `domains`, `amadeus`, `payments`, `team`, `billing`, `go-live`, `settings`. These areas are owned by the platform; the admin only links to them.

How (OAD-012, `portal/page.tsx`, `lib/portal-links.ts`): every role sees the page; the portal checks its own roles when a page opens. The links are the OTA's overview (`/otas/<tenantId>`) and the areas above, built by `portalLinks` from the configured `PUBLIC_PORTAL_URL` (its scheme, host, port and path; credentials, query and fragment dropped) and the session's tenant id (`console.auth.me`, `tenant.id`, a `ten_` ULID or no link at all) only: no cookie, header, query parameter or other answer goes into a link. The page makes no call besides the request's `console.auth.me`.
