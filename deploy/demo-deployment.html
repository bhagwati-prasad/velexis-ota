Velexis demo deployment

Step-by-step instructions to run every Velexis app (portal, platform admin, OTA admin, storefront and their back ends) as a demo: in GitHub Codespaces, or on your own Ubuntu computer. Every command is in its own box with a Copy button. You do not need to be an engineer: copy, paste, and compare with What you should see.

Written for the branch claude/intelligent-bardeen-90hhu7 (commit 6dd1aa5), checked on 7 November 2026. This page works offline: it loads nothing from the internet and sends nothing you type anywhere.

What you get

At the end you have the whole Velexis product running as a demo, with fake data and no real money:

App What it is Who uses it
Platform admin The back office of Velexis itself: OTAs, accounts, Amadeus accounts, audit. Velexis staff
Portal Where a travel agency signs up, creates its OTA (online travel agency) and opens its console. OTA owners
OTA admin The console of one OTA: bookings, customers, settings of its storefront. OTA staff
Storefront The public flight shop of one OTA: search, choose, pay, get tickets. Travellers
Mailpit A fake mailbox that catches every e-mail the demo sends, so nothing reaches a real person. You, to read the e-mails

Behind them run two APIs, two background workers, a database (PostgreSQL), a fast store for queues (Redis) and the Amadeus stub, a fake airline booking system: flights are made up and nothing is booked for real. Payments use the test card 4111 1111 1111 1111.

Time: about one hour the first time, most of it waiting. Cost: nothing within GitHub's free monthly Codespaces quota (Part A says how much that is).

Choose where to run it

GitHub Codespaces recommended

A computer in the cloud that GitHub runs for you, with an editor in your browser. Free within a monthly quota. Follow Parts A to G.

Your own Ubuntu 24.04 computer or VM

Any Ubuntu 24.04 machine with at least 8 GB of memory. The same steps with small changes: read this section.

Render or Vercel free tiers not possible today

The free tiers are too small and too separated for this product as it is built today. Why, and what it would take.

Words used on this page

  • Terminal: the window where you type commands. In a codespace it is the panel at the bottom of the editor. Paste with Ctrl+V (on a Mac Cmd+V), then press Enter.
  • Port: a numbered door of a computer. Each app listens on its own port, for example the portal on 3000.
  • Forwarding a port: connecting a port of the codespace to your browser, so you can open the app.
  • Seed: filling the database with demo data (a demo admin account, a demo OTA).
  • Authenticator code (TOTP): the 6-digit code that changes every 30 seconds, which the admin sign-in asks for. Part F shows how to get it without a phone.
  • Config files (.env.local): small text files with the settings of each app. Part C makes them for you.

Part A. Create the codespace about 5 minutes

Optional, before you start: a codespace stops by itself after 30 minutes without activity. To make that longer (up to 240 minutes), change the idle timeout at github.com/settings/codespaces now: the setting applies only to codespaces created afterwards.

  1. Sign in to GitHub and open github.com/bhagwati-prasad/velexis-ota.
  2. Click the green <> Code button, then the Codespaces tab.
  3. Click the … (three dots) next to the +, then New with options….
  4. Choose:
    • Branch: claude/intelligent-bardeen-90hhu7 (the current code is on this branch, not on main).
    • Dev container configuration: leave the default.
    • Region: the one closest to you.
    • Machine type: 4-core (see below why).
  5. Click Create codespace.

What you should see: after 1 to 3 minutes, an editor (VS Code) opens in your browser. On the left is the list of files (the Explorer); at the bottom is a terminal ending with something like /workspaces/velexis-ota (claude/intelligent-bardeen-90hhu7) $.

If it fails: no terminal at the bottom? Open the menu (☰, top left) and choose Terminal > New Terminal. No Codespaces tab? Codespaces may be turned off for your account or organisation; try with your personal account.

Why 4-core, and what it costs

  • Building all the apps once (Part D) needs memory and processor time. The demo itself runs on about 1.25 GB of memory when idle, but the build is slow on 2 cores. A 2-core machine should also work (not tested): Part D shows the slower build command for it.
  • Free quota for a personal account on GitHub Free: 120 core-hours and 15 GB of storage a month (GitHub Pro: 180 core-hours and 20 GB). A 4-core machine uses 4 core-hours per hour, so it runs about 30 hours a month for free (a 2-core machine about 60 hours). Storage counts even while the codespace is stopped.
  • A codespace stops by itself after 30 minutes without activity (you can set up to 240 minutes at github.com/settings/codespaces; change it before you create the codespace: the setting applies only to codespaces created afterwards). Stopped codespaces are deleted automatically after 30 days by default.
  • Stop or delete the codespace when you are done (Part G). See your usage at github.com/settings/billing.

Quota figures: GitHub's Codespaces billing rules as known on 6 November 2026 (medium confidence: check the billing page above for your own numbers).

Part B. Install the tools 5 to 10 minutes, once per codespace

Run each box in the codespace terminal, one after the other. Wait for each to finish.

B1. Node.js 22 and pnpm

Node.js runs the apps; pnpm installs their building blocks.

cd /workspaces/velexis-ota
nvm install 22
nvm alias default 22
nvm use 22
export COREPACK_ENABLE_DOWNLOAD_PROMPT=0
echo 'export COREPACK_ENABLE_DOWNLOAD_PROMPT=0' >> ~/.bashrc
corepack enable
hash -r
node -v
pnpm -v

What you should see: the last two lines print v22. followed by numbers (for example v22.23.4) and 9.15.9.

If it fails: nvm: command not found: open a new terminal (☰ > Terminal > New Terminal) and run the box again. pnpm -v shows another number: run this box, which should then print 9.15.9: 

corepack prepare pnpm@9.15.9 --activate
pnpm -v

B2. PostgreSQL 16 and Redis 7.4

The database and the queue store, from their makers' package sources. These are the same commands the project's own checks run on a clean Ubuntu 24.04 machine (.github/workflows/ci.yml, job dev-setup). 

. /etc/os-release
{ sudo grep -rlE 'apt\.postgresql\.org|packages\.redis\.io' /etc/apt/sources.list.d/ || true; } | xargs -r sudo rm -f
sudo install -d -m 0755 /etc/apt/keyrings
curl -fsSL https://www.postgresql.org/media/keys/ACCC4CF8.asc | sudo gpg --dearmor --yes -o /etc/apt/keyrings/pgdg.gpg
echo "deb [signed-by=/etc/apt/keyrings/pgdg.gpg] https://apt.postgresql.org/pub/repos/apt ${VERSION_CODENAME}-pgdg main" \
  | sudo tee /etc/apt/sources.list.d/pgdg.list
curl -fsSL https://packages.redis.io/gpg | sudo gpg --dearmor --yes -o /etc/apt/keyrings/redis.gpg
echo "deb [signed-by=/etc/apt/keyrings/redis.gpg] https://packages.redis.io/deb ${VERSION_CODENAME} main" \
  | sudo tee /etc/apt/sources.list.d/redis.list
printf 'Package: redis redis-server redis-tools\nPin: version %s\nPin-Priority: 1001\n' '6:7.4*' \
  | sudo tee /etc/apt/preferences.d/velexis-redis
sudo apt-get update -y
sudo DEBIAN_FRONTEND=noninteractive apt-get install -y --no-install-recommends \
  postgresql-16 postgresql-client-16 redis-server redis-tools

Then check:

psql --version
redis-server --version
pg_lsclusters

What you should see: psql (PostgreSQL) 16.…, Redis server v=7.4.…, and a line starting with 16 main 5432. It may say down: that is fine, Part D starts it.

If it fails: apt-get update complains about a key or a list that is not PostgreSQL or Redis (for example NO_PUBKEY for Yarn): see Part H, then run the box again.

B3. Mailpit (the fake mailbox)

Optional but recommended: without it the demo works, but you cannot read its e-mails (for example a password reset). The second line checks that the download is exactly the expected file. 

curl -fsSL -o /tmp/mailpit.tar.gz https://github.com/axllent/mailpit/releases/download/v1.29.7/mailpit-linux-amd64.tar.gz
echo "2ca8202f34b0ce35cf2144671ea6a0e43470c4a3621873e107dad440fd39f2b2  /tmp/mailpit.tar.gz" | sha256sum -c -
sudo tar -xzf /tmp/mailpit.tar.gz -C /usr/local/bin mailpit
mailpit version

What you should see: /tmp/mailpit.tar.gz: OK and mailpit v1.29.7. A line about checking for the latest release can be ignored.

If it fails: FAILED after sha256sum means the download is not the expected file: do not install it, run the box again later. You can skip Mailpit: the start script then says it is not installed and carries on.

    Part D. One-time setup 10 to 20 minutes

    Run these in the codespace terminal, one box at a time, in this order.

    D1. Install the building blocks

    cd /workspaces/velexis-ota
pnpm install --frozen-lockfile

    What you should see: after 1 to 3 minutes, Done in and a time. A box Update available! may appear: ignore it and do not update pnpm (the project needs 9.15.9).

    If it fails: pnpm: command not found or a Node version warning: go back to B1.

    D2. Set up the database and Redis

    bash deploy/scripts/dev-setup.sh

    What you should see: a summary box in which every line says ok (five database roles and password required ok REDIS_URL), then Next steps.

    If it fails: psql not found: go back to B2. Redis did not start: see Part H.

    D3. Make the keys

    The encryption and signing keys of the demo, made inside the codespace (they never leave it).

    pnpm dev:keys

    What you should see: five lines starting with created (for example created .local/keys/master-v1.key) and one with ready.

    D4. Build every app

    pnpm build

    On a 2-core machine use this instead, so the build does not run out of memory:

    pnpm build --concurrency=2

    What you should see: after 3 to 10 minutes, Tasks: with a number of successful and the same number in total.

    If it fails: Killed or heap out of memory: see Part H.

    D5. Create the tables and load the reference data

    Airports, airlines, countries, currencies and time zones.

    pnpm db:migrate
pnpm db:seed:reference

    What you should see: both finish within a minute, without ERROR.

    D6. Start the fake airline system, then fill in the demo data

    The seeds need PostgreSQL, Redis and the Amadeus stub. The second line starts just those. The seeds print the demo admin's password and keys only once, so their output is also added to the end of two files in .local/ (a folder git ignores), readable only by you. 

    cd /workspaces/velexis-ota
bash .local/demo/start.sh stub
( umask 077; (cd platform/backend && node --enable-source-maps dist/cli.js dev:seed) 2>&1 | tee -a .local/platform-seed.txt )
( umask 077; (cd ota/backend && node --enable-source-maps dist/cli.js dev:seed) 2>&1 | tee -a .local/ota-seed.txt )

    What you should see, and what to keep:

    • From the platform seed: Platform admin admin@example.com (…): created, with MFA. Shown once, never again:, then Password: (24 characters) and TOTP set-up URI: (starts with otpauth://totp/; the part after secret= up to the next & is the secret for the 6-digit codes). Keep both: you sign in with them in Part F.
    • From the OTA seed: the demo OTA demo, and three lines Publishable test key, Secret test key and Console automation test key. You do not need them for this guide; they are for trying the developer SDK.
    • Both are saved in .local/platform-seed.txt and .local/ota-seed.txt (the box below shows the admin's lines again). Do not share these files, and delete them when you delete the demo.

    If it fails: exists already; nothing changed means the seed ran before: the password of that first run is further up in .local/platform-seed.txt. This box shows the saved lines; the last Password: and TOTP set-up URI: lines are the current ones: 

    cd /workspaces/velexis-ota
grep -E "Password:|TOTP set-up URI:" .local/platform-seed.txt

    Nothing there? See Part H. A ConfigError: see Part H.

    Your choice: on my computer, through localhost

    Use one of these two:

    With VS Code Desktop

    1. Install VS Code from code.visualstudio.com and open it once.
    2. Back in the codespace in your browser, press Ctrl+Shift+P (Mac: Cmd+Shift+P), type Open in VS Code Desktop and choose Codespaces: Open in VS Code Desktop. Allow the browser to open VS Code, and install the GitHub Codespaces extension if VS Code asks.

    Your choice: in the browser, through the codespace links

    1. In the codespace, open the PORTS tab (next to TERMINAL at the bottom).
    2. For each of 3000, 3001, 3002 and 4173: right-click the row > Port Visibility > Public.

    If this command answers with a permission error, use the clicks above.

    What you should see: the Visibility column says Public for 3000, 3001, 3002 and 4173, and Private for 8025. Open the platform admin at https://<codespace>-3001.app.github.dev.

    Part F. Use the demo about 15 minutes

    A complete tour: an admin creates an OTA, switches on a payment method, and a traveller books a flight.

    F1. Get a 6-digit sign-in code

    The demo admin needs a code that changes every 30 seconds. This command reads the secret from the saved seed output (the last one, if the seed ran more than once) and prints the current code: 

    cd /workspaces/velexis-ota
(cd platform/backend && node -e "const m = [...require('fs').readFileSync('../../.local/platform-seed.txt', 'utf8').matchAll(/secret=([A-Z2-7]+)/gi)]; if (m.length === 0) { console.error('No secret in .local/platform-seed.txt: see Part H'); process.exit(1); } console.log(require('otplib').authenticator.generate(m[m.length - 1][1]))")

    What you should see: six digits, for example 492817. Type it within 30 seconds. Each code works only once: for the next sign-in, wait until the next 30-second window and run the command again.

    Or use an authenticator app on your phone (Google Authenticator, Microsoft Authenticator, 1Password, …): add an account with Enter a setup key, name it Velexis demo, and type the secret: the letters and digits after secret= in the last TOTP set-up URI: line, up to the next &. This box shows that line again: 

    cd /workspaces/velexis-ota
grep "TOTP set-up URI:" .local/platform-seed.txt | tail -n 1

    F2. Sign in to the platform admin

    1. Open the platform admin: http://localhost:3001.
    2. E-mail admin@example.com, the Password from the seed output, then Continue.
    3. Type the 6-digit code (F1) into Authentication code and click Verify and sign in.

    What you should see: the platform admin's Dashboard. Its menu has Tenants (the OTAs; the seed's Demo Travel is there), Accounts, the Amadeus pages and the Audit log.

    F3. Sign in to the portal and create an OTA

    1. Open the portal: http://localhost:3000. Click Sign in at the top right (not Get started, which makes a new account). Sign in with the same e-mail and password, click Sign in, then type a new code into Authentication code (wait for the next 30 seconds, then run F1 again) and click Verify and sign in.
    2. Click Create an OTA.
    3. Fill in: OTA name My OTA; OTA key myota (3 to 30 lower-case letters or digits, starting with a letter, no hyphen; it cannot be changed later); Country any; Default currency Euro (EUR); Time zone any. Click Continue.
    4. Keep the early access plan, Continue, check the summary and click Create OTA.

    What you should see: the page OTA set-up ticks its steps off, usually within a minute, then says Your OTA is ready. Click Go to the OTA dashboard: it has an Open console button.

    Links to addresses ending in .ota.example.com (such as Open your storefront) lead nowhere in the demo: that domain is a placeholder. Open the storefront at its address of E3 instead.

    If it fails: the set-up does not move: the workers may not run; run the box of E1 again (it starts what is missing) and reload the page. A key that is taken or reserved: choose another one, and use it instead of myota below.

    F4. Open the OTA admin

    Click Open console.

    What you should see: the OTA admin opens on its Bookings page (empty for now), at http://localhost:3002.

    If it fails: This sign-in did not come from the portal: see Part H.

    F5. Switch on the airline card

    1. In the OTA admin's menu, under Settings, click Storefront.
    2. In the row of tabs at the top of Storefront settings, click Payments (not the Payments item of the menu).
    3. In the section Airline card, tick Offer the airline card in the test environment and click Save airline card.

    What you should see: Saved. The storefront shows the change within 5 minutes.

    F6. Point the storefront at your OTA

    One storefront process shows one OTA. Type your OTA's key here (if it is not myota) and copy the box into the codespace terminal: it changes one line of ota/frontend/.env.local and restarts only the storefront.

    Also type the same key into field 3 of Part C, so that files you make there later keep showing your OTA. Otherwise putting the files in place again sends the storefront back to the demo OTA, which has no airline card. 

    cd /workspaces/velexis-ota
sed -i 's/^STOREFRONT_DEV_HOST=.*/STOREFRONT_DEV_HOST=myota.ota.example.com/' ota/frontend/.env.local
bash .local/demo/stop.sh storefront
bash .local/demo/start.sh

    What you should see: storefront: stopped, then storefront: ready and the table, where the storefront line ends with (shows the OTA of myota.ota.example.com).

    F7. Book a flight on the storefront

    1. Open the storefront in a new tab: http://localhost:4173. A banner says it is in test mode. (A tab that already showed the storefront keeps its old settings for up to 5 minutes.)
    2. Choose One way. From: type Madrid and pick it from the list. To: Paris. Departure: any date a few weeks ahead. Click Search flights. (The fake airline answers any route with the same made-up flights.)
    3. Click Select (the button under the price) on a result, then Continue with this fare, then Continue to checkout.
    4. Traveller: any first and last name, a date of birth (for example 12 April 1985; type it in the order the field shows, or pick it from the calendar), a gender; Continue. Contact: your e-mail address (it goes to Mailpit, nowhere else), country calling code 34, mobile 600000000; Continue. Extras: Continue.
    5. Payment: choose Card, charged by the airline, tick I accept the terms and conditions, click Continue to payment.
    6. On Pay with your card: name on the card any, card number 4111 1111 1111 1111, month 11, a year in the future, security code 853. Click the Pay €… button.

    What you should see: the confirmation with a booking and its e-tickets (numbers starting with 000-).

    If it fails: no Card, charged by the airline at the payment step: see Part H. The card 4000 0000 0000 0002 is the fake airline's declined card, for trying a refusal.

    F8. See the booking and the e-mails

    • In the OTA admin (http://localhost:3002), open Bookings: the new booking is there.
    • Open Mailpit (http://localhost:8025): the e-mails of the demo, for example the booking confirmation.

    Optional: Stripe card payments

    Only if you filled in Stripe test keys in Part C. Stripe tells the OTA backend about payments through "webhooks", which need the Stripe command-line tool running in a second terminal of the codespace: 

    cd /workspaces/velexis-ota
curl -fsSL -o /tmp/stripe.tgz https://github.com/stripe/stripe-cli/releases/download/v1.53.1/stripe_1.53.1_linux_x86_64.tar.gz
echo "032fe0b849a9d6a222488bc846445bafeae993af1026b78a8121d02321ca1fd1  /tmp/stripe.tgz" | sha256sum -c -
sudo tar -xzf /tmp/stripe.tgz -C /usr/local/bin stripe
read -rsp "Stripe secret test key: " STRIPE_API_KEY && export STRIPE_API_KEY && echo
bash tools/dev/stripe-listen.sh --only ota

    Paste your sk_test_… key when asked (it is not shown). The tool prints a line STRIPE_WEBHOOK_SECRET_VELEXIS_TEST=whsec_…: put that whsec_… value into the form (Part C, field 4), check that field 3 holds your OTA's key (F6), put the files in place again and restart (Part G), with the Stripe tool still running. Then the storefront also offers Stripe's card form; use Stripe's test card 4242 4242 4242 4242.

    Part G. Next day, restart, delete

    After a stop, or the next day

    When a codespace stops, every app stops. Open it again from github.com/codespaces and run: 

    cd /workspaces/velexis-ota
bash .local/demo/start.sh

    It starts PostgreSQL and Redis again (through deploy/scripts/dev-setup.sh), then every app. Your data (accounts, OTAs, bookings) is still there. Check in the PORTS tab that 3000, 3001, 3002 and 4173 are still Public.Connect your browser again as in E2.

    After you change the form

    Before you make the files again, check field 3 of the form: once you did F6, it must hold your own OTA's key (for example myota), or the storefront goes back to the demo OTA. Put all the files in place again (Part C), then restart everything: 

    cd /workspaces/velexis-ota
bash .local/demo/stop.sh
bash .local/demo/start.sh

    What a rebuild loses

    Everything in /workspaces stays when the codespace stops or is rebuilt: the code, your config files, the keys, the build and the saved seed output. A rebuild (the command Codespaces: Rebuild Container, or a change of machine image) also wipes what is outside it: Node.js 22, PostgreSQL, Redis, Mailpit and the database with all its data. After a rebuild: do Part B again, then Part D from D2 (skip D1, D3 and D4), and Part E. The seed then makes a new admin password and sign-in secret, added at the end of .local/platform-seed.txt, and the command of F1 uses the new secret. Your own OTA is gone too: do Part F again.

    Stop or delete the codespace

    • Stop (keeps everything, stops using core-hours): at github.com/codespaces, click … next to the codespace > Stop codespace. Or in the codespace: Ctrl+Shift+P > Codespaces: Stop Current Codespace.
    • Delete (removes everything, frees the storage): same menu > Delete.
    • To stop only the apps and keep the codespace running: 
      cd /workspaces/velexis-ota
bash .local/demo/stop.sh

    Find the message you see. The logs of every app are in .local/demo/logs/ (how to read them).

    cd /workspaces/velexis-ota

    sudo apt-get update fails with NO_PUBKEY, EXPKEYSIG or is not signed for a source that is not PostgreSQL or Redis (for example Yarn) A package source of the codespace image has an expired key. It has nothing to do with Velexis. List the sources:

    Then run the box of B2 again.
    Redis did not become ready from dev-setup.sh Redis is installed but could not be started as a service. Start it by hand, then run the script again:

bash deploy/scripts/dev-setup.sh
    You lost the admin password or the sign-in secret The seed prints them only once. First look in the saved seed output (the last lines are the current ones): 
    cd /workspaces/velexis-ota

    cd /workspaces/velexis-ota

    After this, the command of F1 no longer works (it reads the old secret): type the new key into an authenticator app instead. Lost the password: on the portal's sign-in page click Forgot your password?, enter admin@example.com, and open the e-mail in Mailpit (port 8025) to choose a new one.
    The 6-digit code is refused Each code works once and only for 30 seconds. Wait for the next 30-second window and make a new code (F1).
    No Card, charged by the airline at the storefront's payment step The storefront shows an OTA where the airline card is off, or the tab still holds the settings it loaded earlier. Do F5 in the OTA admin of the OTA the storefront shows, and check that F6 used that OTA's key.     502 or a GitHub error page for a codespace link Nothing answers on that port. Run the box of E1 again: it starts what is missing. Then look at the app's log (Logs). Still a 502 while start.sh says every app is ready? Use the way On my computer, through localhost instead (Part C, field 1).

    A VM in the cloud, reached over SSH

    Keep the apps private on the VM and connect your own computer's ports to it through SSH. On your computer, with your VM's user and address: 

    ssh -N -L 3000:127.0.0.1:3000 -L 3001:127.0.0.1:3001 -L 3002:127.0.0.1:3002 -L 4173:127.0.0.1:4173 -L 8025:127.0.0.1:8025 you@your-vm-address

    Keep it running (Ctrl+C disconnects) and open http://localhost:3001 on your computer. Never open these ports in the VM's firewall.

    Render and Vercel (free tiers)

    Short answer: the full Velexis stack cannot run on the free tiers of Render or Vercel today. This is not a missing step in this guide: the free tiers are too small, and Velexis is built for one machine where its parts talk to each other privately. Here is why, in plain words.

    What Velexis needs Render free tier Vercel Hobby (free)
    Memory: about 1.25 GB when idle (measured on this code on 6 November 2026), an estimated 1.6 to 2 GB in use 512 MB per free web service No long-running servers, only short functions
    Two background workers, always on (set-up of new OTAs, e-mails, tickets) No free background workers None
    Always awake Free services sleep after 15 minutes without visitors and lose their files Functions start and stop on demand
    Parts that talk privately on one machine: by design every app listens only on its own machine (127.0.0.1; docs/mvp/adr/0007-single-vm-without-docker.md) Each service is a separate machine and must listen publicly on its own port Same problem
    The OTA admin and the fake airline system right next to the OTA backend (they accept each other only on the same machine) Would all have to share one container The OTA admin cannot run there
    A PostgreSQL database with four separate roles, created by an administrator account (deploy/postgres/bootstrap.sql) Free database expires after 30 days, and the set-up script needs changes without an administrator account No database of its own; partner databases (such as Neon) need the same set-up changes as Render's
    Sending e-mail Free services block the e-mail ports 25, 465 and 587 (since 26 September 2025) Not applicable
    Use Not applicable The Hobby plan is for non-commercial, personal use only

    Vercel could host at most two of the apps (the portal and the platform admin), and only if the platform API were reachable on a public HTTPS address somewhere else, which it is not by design. The OTA admin cannot run there, and the storefront would need extra request rules that nobody has tested.

    What it would take

    • Code and file changes in the repository: a configurable listening address for the APIs and workers (or a proxy inside the container), a Dockerfile, a Caddyfile for the demo, a variant of deploy/postgres/bootstrap.sql for a managed database without an administrator account, and the Next.js setting serverActions.allowedOrigins for hosts that rewrite addresses. Some of these touch the "single VM without Docker" decision (ADR-0007), so the owner decides first.
    • A paid instance with at least 2 GB of memory to run everything in one container (on Render: Standard, 2 GB, about $25 a month; Pro, 4 GB, about $85 a month is safer).

    If you want this, ask for these changes as tasks: each is a normal change to the repository, with its own review. Until then, use GitHub Codespaces or an Ubuntu machine: any Ubuntu 24.04 VM with 8 GB of memory works with the section above.

    Sources and confidence: the idle memory figure, the private-listening design and the database set-up come from this repository and a full run of the stack on 6 November 2026 (high confidence; the figure in use is an estimate from the project's own load measurements). The Render and Vercel limits and prices come from their public pages as summarised by web search on 6 November 2026, because their sites could not be opened directly (medium confidence: plans change, check render.com/pricing and vercel.com/pricing).

    Logs

    Every app writes to .local/demo/logs/<name>.log (the names of the table above).

tail -n 50 .local/demo/logs/ota-api.log
tail -f .local/demo/logs/portal.log
